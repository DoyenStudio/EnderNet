# 04 交付说明（能源增量：创造能量源 + 最小能源服务）

日期：2026-09-25。范围：**任务 04-04 的固定部分**，加上 `blocks.md` 里那块
**创造能量源**（`endernet:creative_energy_source`）。

**这是一次部分交付，而且不是「已验收」交付。**

- 交付的是「这台网络有没有电」这件事：按定义表结算固定耗能、按供能设备判定
  `power_ok`（三态），`ServiceId.ENERGY` 从替身换成正式实现。
- **04-05 / 04-06 / 04-08 一行都没写**：RF 计量与 EN 缓冲、断电暂停与逐步恢复、
  设备级能源状态查询与变化通知。
- **耗能结算只算得出「固定」那一半**：工作态、装置数量（硬盘/内存条个数）、
  负载跟随的折算都还没有来源。**它们没有被当成 0**，而是让判定停在「待确认」，
  或由 DEV 档显式选择的替身口径忽略，并把被忽略的设备逐个报出来。
- 未定规则一律保留成具名配置点（全局约束 7），
  `EnergyPolicy.assert_settled()` **没有被调用**（只有一条把调用包在
  `assertRaises` 里的用例，用来证明守卫确实会拦）。

## 一、为什么做这个

`blocks.md` 早就写好了创造能量源（2147483647 EN/t、不占带宽），代码里一个字都没有；
而任务 04 的能源半边没开始时，`ServiceId.ENERGY` 是替身，`power_ok()` 一律返回
`None`，于是**每一台设备**的理由都是「能源服务尚未实现」，任何网络都跑不起来，
连「供电 → 耗能」这一段都无从验证。

创造能量源**不是替身**：它是 `blocks.md` 里已经定案的正式方块。因此它同时关掉了
04 文档里记着的那项待决事项（「能源落地时在 DEV 档加一个调试 RF 电源」）——
不需要那个替身方块了。

**结果是这条链路真的通了**：真机上放上创造能量源，那台网络的判定从「没电」变成
「有电」，`run_state` 变成 `runnable`，设备状态栏转成在线，**一条存储命令真的执行
成功**（见第六节第 4—7 条）——这是本项目第一次在游戏内把业务命令做成。
而「断电暂停与恢复」那半条仍然缺（创造能量源关不掉，04-06 也没写），
这一点如实记在第五节与第六节末尾。

## 四、接口输入输出

### `EnergyPolicy`

三个字段，取值与默认值：

| 字段 | 取值 | 库默认 | DEV 档 | 含义 |
| --- | --- | --- | --- | --- |
| `no_source` | `PENDING` / `BROWNOUT` | `PENDING` | `BROWNOUT` | 一台供能设备都没有时，报「待确认」还是「确认没电」 |
| `missing_spec` | `PENDING` / `IGNORE` | `PENDING` | `IGNORE` | 定义表给不出耗能数值（基带、总线接口、连接器、创造能量源自身） |
| `unwired_inputs` | `PENDING` / `IGNORE` | `PENDING` | `IGNORE` | 数值要由装置数量/工作态/负载推导，而这些输入尚未接线 |

`no_source` 对应的是 04 文档 §「待定与交接」里那句「网络里没有任何能源接入口时
报没电还是待确认」——**规则仍未定案**，所以库默认在保守那一侧，替身口径由
`EnergyPolicy.dev_stand_in()` 具名提供，并在 `start_server()` 里显式选用。

### 判定的四条次序（**顺序是契约，不是实现细节**）

1. 没有供能设备 → `no_source` 决定。
2. **有供能设备的速率算不出** → `None`。必须排在 3 之前：这时供能总量只是**下界**，
   拿它比大小会得出一个不成立的「没电」。
3. **已知供能 < 已知需求** → `False`。到这里供能是**精确的**（2 已经排除未知供能），
   而需求至多是下界，因此「精确 < 下界 ≤ 真需求」成立，哪怕还有需求算不出。
4. 有需求算不出 → 策略决定；都没有 → `True`。

### `EnergyService`

- `power_ok(node_key)`：**网络级判定**（一个分量共用一份供需账），`True`/`False`/`None`。
  **非成员返回 `None`**：设备刚放下、还没被同步进来的那一帧就是这样。
- `add_node` 幂等：判据是整行的签名（含**代次**），同一台设备一行都不动。
  这一条不是优化而是必需的——`sync_members` 每次拓扑重建都会对**每个**成员调一遍
  `add_node`，每次重算就是 O(n²)。
- `is_ready()`：绑定了运行时为真；`EnergyService(None)` 为假。**裸构造合法**是既有
  契约（`default_stand_ins()` 会用 `None` 构造每个槽位，`debug_query("assembly")`
  也走这条），与 `StorageService(None)` 同形。
- `tick()` 恒返回 0：判定是成员与输入的纯函数，已在它们变化时算好，因此本服务
  不占帧预算，也不参与 `context["tick"]` 的时间推导。
- 不覆盖 `handle()`：命令路由表里没有能源这一格，真调到这里是编程错误。
- `note_domain_change()` 返回 `False`：`follows_bandwidth` 的折算属 R08、至今未定，
  域变化**不改变判定**，因此不声称「处理了」。
- `save_node_data()` 返回 `None`：供需两边的权威都在定义表与设备自身，
  本服务在该节点上没有持久数据；不返回一份看起来像存档的空字典。
- `set_device_state(ref, state=None, unit_count=None)`：`unwired_inputs` 那类缺口的
  **接线入口**，只接受当前这一代。**本次没有消费者**（05 的槽位、08/09 的加工状态
  都还没接过来），因此现在传与不传只影响诊断明细，不影响判定。

### 三态与原因码

`power_blocker` 的映射未改，因此**没有新增 `Reason` 码、也没有动
`_BLOCKER_STATES` / `PENDING_CODES` 两张表**：

| `power_ok` | 原因码 | 网络状态 |
| --- | --- | --- |
| `True` | 无 | 视其余条件 |
| `False` | `brownout`（确认没电） | `no_power` |
| `None` | `energy_unavailable`（算不准） | `no_power` |

`Reason.ENERGY_UNCONFIGURED` 至今**全仓库未使用**，它属于 04-08 的「详情区分原因」。
本次的理由**只到服务级诊断**（`debug_query("energy")`），不到设备级载荷。

### 「为什么不加 `CAP_ENERGY_SOURCE`」

能力 `energy_port` 的协议是 `accept_rf`（**拉**式：向外部机器要 RF 再折算），
创造能量源是**推**式静态电源，两者不是同一个能力。而 `supply is not None` 已经足以
认定「谁是供能设备」，再挂一个能力名就是把同一件事存两处——本仓库为这类分叉付过
代价（[04-交付说明](./04-交付说明.md) 第七节第 3 条）。因此能源服务像
`AdmissionService` 读带宽那样**直接读定义表**。13-02 接入真实 RF 时要做的是给能源
接入口一个能算出数的方法，而不是在能源服务里加一条 `if device_id == ...`。

## 五、未验证项与已知限制（重要）

1. **耗能只算得出固定那一半。** 工作态（`work != idle` 的设备）、装置数量
   （`per_unit` 的驱动器与内存槽）、负载跟随（`follows_bandwidth` 的控制器）
   三类需求**都算不出来**，因此：
   - 库默认口径下**任何真实网络**（基带跑不掉）的判定都是 `energy_unavailable`；
   - DEV 档把它们忽略掉，于是实际语义是「**只要网络里有供能设备就算有电**」。
     这是本次增量的核心限制，被具名标注、可在 `debug_query("energy")` 的
     `ignored_demand` 里逐个查到、正式档会拒绝，但它**不是可以交付的口径**。
2. **断电链路只走通了一半。** 「供电 → 耗能」现在能在真机上走通；「断电 → 恢复」
   不能——创造能量源关不掉，而 04-06（断电暂停与逐步恢复）没写。
3. **没有设备级能源状态通知（04-08）。** `power_ok` 是一个三态；「为什么是待确认」
   只在服务级诊断里，不在设备状态载荷里。11/13 要区分能源与带宽原因，得等 04-08。
4. **`assembly_view()` 与 `assert_assembly_ok()` 报的未定规则不同。**
   `ApplicationService.policy` 默认就是 `admission.policy`（03 用一条用例
   ——`test_application_shares_the_admission_policy`——把这条钉成了有意的行为），
   而 `assert_assembly_ok()` 读的是四份策略的合成视图。因此
   `debug_query("assembly")["unresolved"]` 里**看不到能源的未定项**。
   本增量**没有偷改那个签名**（`test_application` 会拦），交给 14：这与 04
   交接里「调度策略也不在守卫覆盖范围内」是同一件事，两处一起收。
5. **`SchedulerPolicy` 仍然不在 `policy_bundle()` 里**，理由同上；本增量只加了
   能源一份，没有顺手把调度那份混进来冒充「已经检查过」。
6. **规模未测。** `energy_view()` 每次诊断遍历全部运行时并读各服务的
   `diagnostics()`；`_settle()` 是 O(成员数)，每次成员变化各一次。当前规模
   （个位数网络、几十台设备）没有实测到问题，大网络上的开销没有测量。
7. **`stats["added"]` 与 `stats["settles"]` 的口径**：前者在「一行真的变了」时自增
   （含「同位置换设备」），后者在每次重算时自增。两者都不是「成员数」。

## 七、给下游任务的交接

- **11（终端与状态栏）**：`power_ok` 现在是**真结论**（`True`/`False`/`None`），
  不再是「服务没写」。因此状态栏可以显示真正的「没电」与「待确认」两种情况，
  但**仍不要把 `None` 显示成「没电」**——它是「算不准」，文案要分开。
  设备级的原因明细要等 04-08。
- **13-02（RF 接入）**：能源接入口的 `supply` 已经是
  `Value(UNCONFIGURED, unresolved="R08", is_test_value=True)`——**它是「供能但速率
  未定」，不是「不供能」**。能源服务对速率未知的电源一律不下结论（`None`），
  这个行为不要改成「按 0 计」。接进真实 RF 时给那台设备一个能算出数的途径即可。
- **05 / 08 / 09（装置数量与工作态）**：耗能要算准，需要有人调
  `EnergyService.set_device_state(ref, state=..., unit_count=...)`。**2026-09-29：驱动器数量、处理器与装配仓工作态已接入；内存条数量仍未接，见 [增量交付](04-交付说明-权威能源输入.md)。2026-10-03：内存条数量已接入**（来源是内存槽容器里插着的内存条，见 [内存物品交付](09-交付说明-内存物品与容量接线.md)）。驱动器槽位的
  权威在 `StorageDriverStore`，加工状态在 08/09 手里。接上之后库默认口径会自己
  开始给出 `True`，**不需要改能源服务的代码**。
- **12（持久化）**：能源状态**刻意不落盘**。供需两边都是派生量（定义表 + 成员表），
  重启后由拓扑重建自然恢复；`save_node_data()` 返回 `None`。
- **14（发布验收）**：`EnergyPolicy` 的三个字段进 `policy_bundle()`，会随
  `assert_assembly_ok()` 一起报出来；但注意第五节第 4 条的偏差。
