### 拓扑：`TopologyService`

| 接口 | 输入 | 输出 / 错误 |
| --- | --- | --- |
| `mark_dirty(node_key)` | 变化的位置 | 无返回。立即把相关分量置为「重建中」（撤销旧资格） |
| `advance(step_budget)` | 本帧允许展开的节点数 | `RebuildReport`。**没有脏点时一步都不走**；预算用尽则保存游标，下帧继续 |
| `snapshot()` | — | `TopologySnapshot`，发布后不再变化 |
| `validate(ref, expected_version=None)` | 设备实例 + 期望图版本 | `TopologyVerdict`，`status` 取 `ok / blocked / stale` |
| `link_state(node_key)` | 位置 | `LinkState`：连通了谁、谁被拒、原因码 |
| `explain_link(a, b)` | 两个相邻位置 | `{connected, reason, detail}`；不相邻时 `reason="not_adjacent"` |

`validate()` 的判定顺序与理由：

| 情形 | status | 原因码 |
| --- | --- | --- |
| `expected_version` 与当前图版本不符 | `stale` | `stale_version` |
| 实例已不存在或代次过期 | `stale` | `device_gone` |
| 分量正在重建 / 该位置尚未归属 | `blocked` | `rebuilding` |
| 分量内控制器不是恰好一个 | `blocked` | `no_controller` / `controller_conflict` / `topology_unknown` |
| 设备所在区块未加载 | `blocked` | `unloaded_member` |
| 以上都通过 | `ok` | — |

## 四、适用存档版本

**本层不持久化。** 图、分量编号、负载域与判定结果全部是**可重建数据**，
与架构规划 6.5「临时网络编号及汇总索引可以重建」一致：

- 分量编号在进程内分配，重启后重新分配。**主控身份不得绑定分量编号**，
  必须绑定控制器实例（`DeviceRef` 的位置 + 代次）。
- 负载域编号与处理器群编号由成员位置直接推导（`domain:dim:x,y,z`），
  确定且可复现，但不保证跨版本稳定。
- 重启后 `ServerBootstrap.start()` 会 `mark_all_dirty()` 全量重建，
  因此不会沿用上一轮的内存状态。

`CURRENT_SCHEMA_VERSION` 保持 1，本批次**没有**触碰存档结构。

## 七、开发与复审中撞到并修好的六处问题

前三条是**自己写测试时逼出来的**（离线全绿之后才暴露），
后三条来自一轮**独立复审**（随机操作序列 + 逐条构造反例）。
每条都补了会失败的回归用例，记在这里是为了以后不再犯：

1. **域编号由位置推导 → 换基带没有归属变化 → 准入从不重算。**
   把 8u 基带换成 16u 基带时分量与域的成员都没变，`MigrationNotice`
   一条都不产生，容量却必须重算。修法：发布时凡是被重建过的分量所属的域
   一律重算，不再只看迁移通知。
2. **撤销资格后没有任何种子能扫到那个分量 → 永远停在「重建中」。**
   在相邻位置放一台连不上的设备（处理器贴着基带），会把邻居分量的旧资格
   撤销掉，而那颗种子永远走不到那个分量，于是它永久显示待确认。
   修法：撤销邻居资格的同时把邻居本身也标脏。
3. **设备判定按「域」存 → 同时属于两个域的设备被覆盖。**
   多接入设备在两个域里各算一次，后算的覆盖先算的，结果只看到一个域。
   修法：域只存容量与获准集合，设备判定按「设备的全部域」单独计算。
4. **`status_of()` 会返回**别的实例**的判定。**
   缓存按位置存，位置被顶替后（终端换成内存槽）代次已经变了，
   但缓存要等到下一次重建才刷新——而调用方正好是在 `tick()` 里
   消费设备变化的那些服务，拿到的是一台**已经不存在**的设备的绿色判定，
   连需求量都是旧的。修法：缓存必须比对实例代次，对不上就重算。
5. **多接入设备在每个域都被扣了额度，而它自己的判定是「待确认」。**
   一台设备夹在两段互不相连的基带之间时，两个域各按它的需求扣一次，
   于是 `used != 已获准设备的分配量之和`（破坏界面契约），
   两个域上都因此挤掉了本来能工作的设备，而且这等于**替 R02 定了案**。
   修法：归属未定的设备不占任何域的额度，单独记进 `DomainAdmission.unresolved`；
   配好多接入策略后只算到被选中的那个域。
6. **负载域改名会清空「先到先得」的顺序。**
   域编号由基带位置推导，往更低坐标加一段基带就会让整个域改名；
   原实现跟着把顺序表一起删了，于是同一批里新到的设备可能挤掉老设备。
   修法：顺序表按**位置**保存、不随域编号变化，并在扫描时清理已消失的位置。

第 1、2 条现在由夹具里那条稳定态不变量守着（任何分量不得停在重建中）；
第 4、5、6 条各有独立回归用例，且都验证过「回退修复即失败」。

| 2 | 区块加载即发现 | 6 设备由 `ChunkLoadedServerEvent` 自动发现，`duplicate_events: 0` |
| 3 | 链式分量与控制器计数 | 控制器 + 3 段基带 + 驱动器 + 终端 → 1 分量、`controller_state: single`、`partial: false`、`runnable: true` |
| 4 | 端口规则与方向 | 逐对 `explain_link` 正确；驱动器↔终端被拒，`categories_not_connectable`；朝向：基带 `None`（无方向），控制器/驱动器/终端均为 `south` |
| 5 | 负载域与容量 | 3 段 8u 基带 → 1 域，容量 96q（24u）；`role` 分别为 `core`/`carrier`/`consumer` |
| 6 | 准入数值 | 控制器与基带需求 0（不参与准入），终端需求 4q（1u），域占用 4q、空闲 92q |
| 7 | 多网络唯一主控 | 两个互不相连的网络各成一分量，**各恰好一个主控**，互不影响 |
| 8 | 区块卸载 | `ChunkAcquireDiscardedServerEvent` 确实触发；5 个设备标记 `unloaded` 且**记录保留**（未计掉落、未删除）；分量标 `partial: true` |
| 9 | 区块重载 | 设备**恢复为同一实例**（`generation` 不变，未分配新代次）；`partial` 归 `false`，图版本推进、`LOADED` 通知到达拓扑 |

三处与先前文档预期不符、以实测为准的记录：

- **分量 `partial` 不会使 `controller_state` 降级为 `unknown`**。恰好一个已确认的
  控制器仍报 `single`（卸载的正是主控自身时，由 03 的运行时给出
  `master_unloaded`）。这条正是 §6 末条列为「需要确认的取舍」的那一点，
  实测确认行为如此，**取舍本身仍待规划确认**。
- **出生点附近区块永不卸载**。01 曾记录「远距离传送后区块并未按预期卸载」——
  实测原因是当时设备位于世界原点附近（常驻区块），传送到 3000 格外后
  设备所在区块仍保持加载。把设备放到远端即可正常复现卸载路径。
- **`registry.reloads` 在真机路径上恒为 0**。重载走的是 `restore_chunk` 的
  「先已知、后补查」分支：`mark_loaded` 先兑现了 LOADED，引擎随后给出的
  `blockEntities` 到 `register()` 时记录已是 loaded，于是只计入
  `duplicate_events`。这是 §7 里「两个各自充分的修复」中生效的那一个，
  两条都保留，不是缺陷；只是 `reloads` 这个指标在真机上不会被用到。

| 10 | **`unknown` 三态（R10）** | 并行处理器连接器报 `state: unknown`、`bandwidth_ok: None`、`demand_quarters: None`，原因码 `r10_unconfigured`；域的 `unconfigured` 单列、`used_quarters` **不含它**——「未知不等于 0」在真机成立 |
| 11 | **`denied`（容量不足）** | 8u 域（32q）接一台 `disk_count=40` 的驱动器（40q）→ `state: denied`、`bandwidth_ok: False`、`allocated_quarters: 0`，域把它列入 `denied` 而 `used_quarters` 仍为 0（**被拒的设备不占额度**） |
| 12 | 插拔介质触发重算 | 写入 `config["disk_count"]` 后 `note_device_load_changed` 返回 1，域占用与判定随之重算 |

三条准入状态（`granted` / `denied` / `unknown`）至此都有真机记录。

### 一点五、实测撞到的缺陷：被拒原因把空域说成「已满载」

做第 11 项（`denied`）时撞出来的。域是 8u（32q）、占用 0，一台需求 40q 的
驱动器被拒——它拿到的解释是：

```
bandwidth_denied     域 domain:0:3035,73,3020 已占用 0/32 个四分之一 u
bandwidth_overloaded 负载域已满载
```

**域是空的，却告诉玩家「已满载」。** 根因是
`DomainAdmission.is_overloaded()` 的语义是「本域存在未获额度的设备」，
而生成文案时直接把它当成了「域已经满了」：

```python
if admission.is_overloaded():
    reasons.append(BlockReason(Reason.BANDWIDTH_OVERLOADED, "负载域已满载"))
```

两者在「域真的满了、新设备挤不进来」时重合，所以既有测试一直是通过的；
但在「单台设备的需求就超过整个域容量」时分开，文案就说反了。
02-07 要求的正是「不把业务错误仅显示为『离线』」——给一条**指错方向**的
原因比不给更糟：玩家会去查一个根本不存在的占用。

**修法：把三种拒绝情形分开说**（都不改变行为，只改变解释）。

| 情形 | 原因码 | 说明 |
| --- | --- | --- |
| 域已满，挤不进来 | `bandwidth_overloaded` | 保留原样，此时 `used >= capacity` |
| 单台设备需求 > 域总容量 | `bandwidth_demand_exceeds_domain`（**新增**） | 域还空着也放不下，是这台设备自己的问题 |
| 域没满、单机也没超容，只是剩余额度不够 | 不加第二条 | 第一条已给出「需求 N，域已占用 A/B」，结论玩家自己算得出 |

同时第一条原因改为**带上本设备的需求**（原先只报域占用）：
`"本设备需求 40，域 X 已占用 0/32 个四分之一 u"`。
`is_overloaded()` 保留（11 做详情弹窗时「域里有没有未获额度的设备」是有效查询），
但文档字符串写明它**不等于「域已满」**，并点明这次误用。

**验证**：759 项全绿；新增两条用例分别钉住「单机超容」与「剩余不够」，
两条都验证过「回退修复即失败」——回退后分别重现
`('bandwidth_denied', 'bandwidth_overloaded')` 这个错误组合。
游戏内复验：同一台驱动器现在拿到
`bandwidth_demand_exceeds_domain`「单台设备需求 40 个四分之一 u 已超过本域总容量 32」，
「已满载」不再出现。

### 二、R02 禁止异容量基带混联：落实

规则见 `blocks.md` 网络传输介质一节（2026-09-24 定）。

**修改文件**

| 文件 | 改动 |
| --- | --- |
| `common/protocol.py` | 新增原因码 `Reason.BASEBAND_CAPACITY_MISMATCH` |
| `server/devices/catalog.py` | `can_connect` 改为两层判定：先分类白名单，再基带容量一致；新增 `_baseband_capacity_mismatch` / `_baseband_capacity` / `_format_quarters` |

**实现位置与计划不符，理由在此**：原计划写的是 `node.py` 的连接规则，
但 `node.py` 的 `PortRuleSet` 只持有**分类**与端口/面，看不见 8/16/32；
容量校验需要**设备标识**。`catalog.can_connect` 是「连接判定的唯一入口」
（该模块自己的文档就是这么写的），且建图与诊断两条路径都已经过它，
放在这里一处即覆盖全局。

**两个设计决定**

- **在建边处拦，而不是合网后再拆。** 后者会让「已经合并过一次」的中间状态
  被下游看见。
- **容量未知时不拦。** 未知不等于 0、也不等于「与对方不同」；把缺项判成
  「异容量」等于用一个没定过的数值定了案。缺项由 `unconfigured_report()`
  负责报出，而准入层遇见未知容量会把整个域报成待确认（`bandwidth_ok=None`，
  主控不放行），因此放行不会造成「悄悄按一个错的容量合并」。

**控制器桥接的例外不需要额外代码。** `_build_domains` 只沿**基带**邻接扩展，
因此「同一控制器分别接两条不同容量的独立分支」天然是两个独立的负载域。

**改动带来的测试调整**：3 条旧用例编码的是旧行为（`test_baseband_connects_to_baseband`、
`test_different_baseband_widths_still_connect`、`test_mixed_capacity_depends_on_the_configured_mode`），
已按新规则改写；另新增 5 条（含 1 条防「过度拦截」的守卫）。多数新用例
验证过「回退修复即失败」。
