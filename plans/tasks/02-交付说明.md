## 三、接口输入输出与错误结果

### 拓扑：`TopologyService`

| 接口 | 输入 | 输出 / 错误 |
| --- | --- | --- |
| `mark_dirty(node_key)` | 变化的位置 | 无返回。立即把相关分量置为「重建中」（撤销旧资格） |
| `advance(step_budget)` | 本帧允许展开的节点数 | `RebuildReport`。**没有脏点时一步都不走**；预算用尽则保存游标，下帧继续 |
| `snapshot()` | — | `TopologySnapshot`，发布后不再变化 |
| `validate(ref, expected_version=None)` | 设备实例 + 期望图版本 | `TopologyVerdict`，`status` 取 `ok / blocked / stale` |
| `link_state(node_key)` | 位置 | `LinkState`：连通了谁、谁被拒、原因码 |
| `explain_link(a, b)` | 两个相邻位置 | `{connected, reason, detail}`；不相邻时 `reason="not_adjacent"` |

`validate()` 的判定顺序与理由：

| 情形 | status | 原因码 |
| --- | --- | --- |
| `expected_version` 与当前图版本不符 | `stale` | `stale_version` |
| 实例已不存在或代次过期 | `stale` | `device_gone` |
| 分量正在重建 / 该位置尚未归属 | `blocked` | `rebuilding` |
| 分量内控制器不是恰好一个 | `blocked` | `no_controller` / `controller_conflict` / `topology_unknown` |
| 设备所在区块未加载 | `blocked` | `unloaded_member` |
| 以上都通过 | `ok` | — |

### 准入：`AdmissionService`

| 接口 | 输入 | 输出 |
| --- | --- | --- |
| `status_of(ref)` | 设备实例 | `AdmissionResult`。**只读**，不预留、不消耗、不改动任何判定 |
| `refresh(affected_domains=None)` | 要重算的域（None = 全部） | 判定发生变化的设备数 |
| `note_device_load_changed(node_key)` | 插拔介质后的设备 | 只重算该设备所属的域 |
| `domain(domain_id)` / `domains()` | — | `DomainAdmission`（容量、占用、获准/未获准名单） |
| `demand_of(node_key)` | 位置 | 四分之一 u 整数，或 `UNCONFIGURED` |

`AdmissionResult` 的对外字段（交给 11 的状态聚合与详情诊断，保留 `bandwidth_ok` 内部含义）：
`device_id`、`generation`、`role`、`state`、`bandwidth_ok`、`bandwidth_domain_id`、
`domain_ids`、`demand_quarters`、`allocated_quarters`、
`domain_capacity_quarters`、`domain_used_quarters`、`version`、`reasons`、`notes`。

`state` 三态与 `bandwidth_ok` 的对应：

| state | 含义 | `bandwidth_ok` |
| --- | --- | --- |
| `granted` | 已获额度（恰好满载时仍是它） | `True` |
| `denied` | 未获额度：容量不够，或根本没接在任何基带上 | `False` |
| `unknown` | 结果待确认：重建中 / 定义缺项（R10）/ 多接入归属未定 | `None` |

**未知不等于 0。** blocks.md 没有给出并行处理器连接器的带宽占用（R10），
它因此报 `unknown` 并**不计入**域占用；域占用是「已知部分」的下界，
该设备的结果里带 `notes` 说明这一点。基带与控制器不参与准入
（blocks.md 未给它们列 `带宽负载占用`），返回 `granted` 且需求为 0。

## 四、适用存档版本

**本层不持久化。** 图、分量编号、负载域与判定结果全部是**可重建数据**，
与架构规划 6.5「临时网络编号及汇总索引可以重建」一致：

- 分量编号在进程内分配，重启后重新分配。**主控身份不得绑定分量编号**，
  必须绑定控制器实例（`DeviceRef` 的位置 + 代次）。
- 负载域编号与处理器群编号由成员位置直接推导（`domain:dim:x,y,z`），
  确定且可复现，但不保证跨版本稳定。
- 重启后 `ServerBootstrap.start()` 会 `mark_all_dirty()` 全量重建，
  因此不会沿用上一轮的内存状态。

`CURRENT_SCHEMA_VERSION` 保持 1，本批次**没有**触碰存档结构。

## 五、未验证项（重要）

1. **游戏内一次都没跑过。** 本次全部是离线断言。01 的经验是
   「离线全绿、进游戏连撞四个错」，而 02 依赖的正是**区块卸载**
   （01 交付说明里明确写着「区块卸载路径整体未验证，
   `ChunkAcquireDiscardedServerEvent` 一次都没触发」）——
   卸载会走 `mark_unloaded` → 拓扑标注 `partial` → 控制器计数降级为
   `unknown`。这条路**只在离线用假 world 走过**。
2. **玩家真实放置/破坏事件**对拓扑的驱动未验证（01 已实测脚本 `SetBlock`
   与脚本破坏两条路径；玩家手动放置可能同时触发两条事件，队列合并 +
   注册表幂等各挡一道，但拓扑这一层还没有实测记录）。
3. **规模与帧预算未实测。** 跨帧重建的步数预算是按「一次节点展开」
   记账的，真实网络上单步的耗时（6 次注册表查询 + 规则判定）没有测量；
   `rebuild_steps_per_tick=64` 只是默认值。
   另有一处**已知的预算外开销**：一个分量的 BFS 走完之后，推导它的负载域与
   处理器群（`_compute_structure`）是在**同一帧**里完成的，规模是 O(分量大小)，
   不受 `step_budget` 约束。已把它计进 `RebuildReport.structure_nodes` 与
   诊断的 `structure_nodes`，供 04 评估；要真正限住需要把结构推导也改成
   跨帧增量。当前规模下（数百节点）没有实测到问题。
4. **`AdmissionService.refresh` 的代价是 O(受影响设备 + 已缓存设备)**，
   已缓存的是全部消费者设备。大网络上每次发布都要扫一遍缓存，
   实际开销没有测量，接入 04 的预算时需要重新评估。
5. 多接入、环路、混合容量、优先级这四类**只在注入的测试策略下验证过机制**，
   真实规则未定，见下节。

## 七、开发与复审中撞到并修好的六处问题

前三条是**自己写测试时逼出来的**（离线全绿之后才暴露），
后三条来自一轮**独立复审**（随机操作序列 + 逐条构造反例）。
每条都补了会失败的回归用例，记在这里是为了以后不再犯：

1. **域编号由位置推导 → 换基带没有归属变化 → 准入从不重算。**
   把 8u 基带换成 16u 基带时分量与域的成员都没变，`MigrationNotice`
   一条都不产生，容量却必须重算。修法：发布时凡是被重建过的分量所属的域
   一律重算，不再只看迁移通知。
2. **撤销资格后没有任何种子能扫到那个分量 → 永远停在「重建中」。**
   在相邻位置放一台连不上的设备（处理器贴着基带），会把邻居分量的旧资格
   撤销掉，而那颗种子永远走不到那个分量，于是它永久显示待确认。
   修法：撤销邻居资格的同时把邻居本身也标脏。
3. **设备判定按「域」存 → 同时属于两个域的设备被覆盖。**
   多接入设备在两个域里各算一次，后算的覆盖先算的，结果只看到一个域。
   修法：域只存容量与获准集合，设备判定按「设备的全部域」单独计算。
4. **`status_of()` 会返回**别的实例**的判定。**
   缓存按位置存，位置被顶替后（终端换成内存槽）代次已经变了，
   但缓存要等到下一次重建才刷新——而调用方正好是在 `tick()` 里
   消费设备变化的那些服务，拿到的是一台**已经不存在**的设备的绿色判定，
   连需求量都是旧的。修法：缓存必须比对实例代次，对不上就重算。
5. **多接入设备在每个域都被扣了额度，而它自己的判定是「待确认」。**
   一台设备夹在两段互不相连的基带之间时，两个域各按它的需求扣一次，
   于是 `used != 已获准设备的分配量之和`（破坏界面契约），
   两个域上都因此挤掉了本来能工作的设备，而且这等于**替 R02 定了案**。
   修法：归属未定的设备不占任何域的额度，单独记进 `DomainAdmission.unresolved`；
   配好多接入策略后只算到被选中的那个域。
6. **负载域改名会清空「先到先得」的顺序。**
   域编号由基带位置推导，往更低坐标加一段基带就会让整个域改名；
   原实现跟着把顺序表一起删了，于是同一批里新到的设备可能挤掉老设备。
   修法：顺序表按**位置**保存、不随域编号变化，并在扫描时清理已消失的位置。

第 1、2 条现在由夹具里那条稳定态不变量守着（任何分量不得停在重建中）；
第 4、5、6 条各有独立回归用例，且都验证过「回退修复即失败」。

## 八、给下游任务的交接

- **03（主控制器）**：用 `validate(ref, expected_version)` 做准入；
  分量编号不可绑定身份；分量 `pending` 期间禁止新转移。
  迁移清单在 `TopologyPublication.migrations`，槽位清单一在 `.slot_changes`。
- **09（订单）**：槽位来源看 `ProcessorGroup.slot_count()`（已处理去重与
  未接入/跨网两种情况），不要自己数处理器方块。
- **11（终端）**：`status_of(ref).to_dict()` 已含界面需要的全部字段；
  三项状态显示口径见第三节。读取无副作用，可以随时打开诊断面板。
- **05（存储）**：插拔介质后写 `DeviceRecord.config["disk_count"]`
  并调用 `note_device_load_changed(node_key)`，域占用会自动重算。
- **04（能源）**：带宽判定与能源完全独立（`diagnostics()["energy_independent"]`）；
  两者不得互相推导失败。
