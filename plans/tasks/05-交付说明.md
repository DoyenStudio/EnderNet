### 离线验证能证明什么、不能证明什么

能证明：槽位校验的顺序与结论（范围 → 同盘重复 → 旧版本 → 占用）；额度是整数
记账且余数跨帧累积（`fps=3` 时每帧 66 微单位而不是 0，三帧凑成一件）；时钟回退
不发放额度；模拟与拒绝不改任何状态（含 `revision` 与桶余额）；`op_id` 重发返回
**原回执**；卸载保留介质内容；未知 schema / 缺型号 / 损坏**原样保留载荷**并禁交易；
索引与介质之间的守恒可以用独立求和核对。

不能证明：真实 Python 2.7 行为；引擎事件回调；**`netease:block_container` 在游戏里
的实际行为**（首轮已覆盖一部分，见第八节）；以及**玩家真实的物品装卸路径**——
那条路要等 06。

## 三、接口输入输出

### `Medium` —— 单介质的权威状态

`plan(key, count, direction, now_tick) -> MediumPlan` 是**纯函数**；只有
`commit(plan, now_tick)` 落账。判定顺序固定为 **类型配额 → 容量 → 额度**。
这条是「模拟、失败、重复请求不消耗实际库存或预算」的结构性保证，不是靠调用方自觉。

`to_dict()` / `from_dict(data, definitions, policy, now_tick)`：

- 读不懂的载荷**照样返回一个介质对象**，带 `recovery`（`UNKNOWN_SCHEMA` /
  `MISSING_MODEL` / `CORRUPT`）、`raw_payload` 原样保留、`is_tradeable()` 为假，
  一切转移给 `MEDIUM_UNRECOVERED`。**绝不当空盘覆盖**。
- 缺 `schema_version` 字段**也**判为 `UNKNOWN_SCHEMA`——「认不出来」与「就是 v1」
  是两回事。
- 桶的容量与速率由**规格**决定，只从存档恢复余额与余数；连速率一起恢复的话，
  改一次定义表就会让老存档带着旧速率继续跑。

### `TokenBucket` —— 共享额度

`peek()` 纯函数、`refill()` 推进、`take()` 取用。整数记账，余数以分子跨帧累积：

```
credit = (numerator + elapsed * rate) // fps;  numerator -= credit * fps
```

`now_tick <= last_tick` 时**不发放任何额度**（只回退游标）。桶容量 = 速率 ×
`bucket_seconds`，因此空转再久也只攒一个桶，不构成刷额度路径。

### `StorageService` —— 每网络一份

派生索引逐字沿用 `terminal_item_index.md` §2 的契约：
`item_totals[key] = [stored, reserved]`、`item_sources[key] = set(medium_id)`、
`mounted[medium_id]`（含挂载代次）、`dirty_items`。

- `mount_medium(...)` / `unmount_medium(...)` / `refresh_mounts()`。
  卸载顺序定死：摘掉挂载 → 撤销受影响预留 → 扣贡献，反过来的话会短暂出现
  `reserved > stored`。
- `add_node(node, saved_data)` **两侧都做**：先卸掉权威槽位里已经没有的
  （「对最终挂载集合求差」），再挂上新出现的。没有前半步的话，任何一处直接调
  `provider.unmount()` 而不经过本服务的路径都会让索引与设备悄悄不一致。
- 返回值是**是否真的变了**（比挂载指纹），不是「有没有调用成功」——
  `sync_members` 每帧对每个成员调它，把幂等重挂报成变化会让运行时每帧发一次
  成员变更通知。
- 转移走**提供者**（`provider.read/write`），不直接操作介质对象：设备的能力契约
  应该是唯一那道门。`op_id` 去重复用主控的 `RequestLedger`，**不新建第二套
  交易去重表**。
- `save_node_data(node)` 返回 **`None`**：本服务在该节点上确实没有独立于驱动器
  状态的持久数据（预留是网络级的，而本入口是按节点的）。**不返回一份看起来像
  存档的空字典**——那会让恢复流程以为有东西要读。

### `StorageDriverStore` —— 驱动器状态集合 + 介质权威表

由启动层持有并注入网络服务（架构 §3）。`observe(change)` 是生命周期唯一入口，
从既有的 `ChangeKind` 驱动：

| 变化 | 动作 |
| --- | --- |
| `ADDED` | 建状态 + 投影 + 通知负载重算 |
| `REMOVED` | 清槽位、把介质标 `orphaned` 并保留；**不删除介质** |
| `LOADED` / `UNLOADED` | 只改 `loaded`；**槽位与介质 ID 一字不改** |
| `NEIGHBORS_AFFECTED` / `PLACEMENT_REVIEW` | 忽略 |

`project(state)` 是**唯一**能写 `DeviceRecord.config["disk_count"]` 的地方。
`provider.mount()/unmount()` 成功后立刻调它并通知负载——放在这里而不是交给调用方，
是因为「先改计数、后交易」是准入的前提，漏一条路径就会让后续交易按旧准入放行。

`id_source` 可注入，默认实现**只保证进程内单调**：
`diagnostics()["durable_medium_ids"]` 显式报 `False`。它不是持久身份，
任务 12 必须换成从存档推导的来源（架构 §4 已点名 `runtime@component_id` 同样不合格）。

**槽数写在定义表里是刻意的**：它同时是方块 `container_size` 的取值来源
（`scripts/gen_blocks.py` 从同一条读出）。两处各写一个 10 迟早会分叉成

`disk_count_scope` 取「已占用槽位数」意味着**软盘与磁带也算一块硬盘**，
带宽与能耗会被高估。这是 R10 未定案下的显式选择，不是疏漏。

### 考虑过、但没有采用的方案（一并记下来，免得下一个人重新想一遍）

- **不把介质内容存进驱动器状态里**：那样驱动器就成了第二份权威库存，
  同位置换方块、跨网迁移时会各说一套。现在介质对象独立存在、
  驱动器只持有稳定 ID，网络侧只有派生索引。
- **不让 `StorageService` 自己持有介质**：架构 §3 要求「驱动器与介质的权威状态
  不能只存在于每网络的 StorageService，网络断开、主控移除、运行时重建不等于
  设备和库存消失」。因此权威表在启动层持有的 store 里。
- **不让 `add_node` 用 `saved_data` 决定装了什么**：那会让「存档说什么」盖过
  「设备上真的有什么」。挂载集合的唯一依据是驱动器自己的权威槽位。
- **不把 `disk_count` 做成命令参数**：客户端能提交计数就等于能绕过权威槽位改负载。

## 七、开发过程中撞到并修好的问题

1. **挂载之后 `disk_count` 不投影。** `observe(ADDED)` 会投影一次，但
   `provider.mount()` 之后没人再调 `project()`，于是设备记录里恒为 0，带宽按
   零需求放行。修法是把投影放进 `provider.mount()/unmount()` 内部，
   而不是要求每个调用方自己记得调。
2. **幂等重挂被报成「有变化」。** `mount_medium` 对「本来就挂着」返回 `ok=True`，
   `add_node` 据此报 `changed=True`；而 `sync_members` 每帧对每个成员调一次，
   结果是**每帧发一次成员变更通知**。修法是比挂载指纹，不是比调用成败。
3. **绕过服务直接改槽位会让索引永远不收敛。** 测试里直接调
   `provider.unmount()` 之后，`item_totals` 还留着那份库存。修法是让 `add_node`
   先按权威槽位做一次求差卸载——这同时也就是 `terminal_item_index.md` §4
   要求的「对最终挂载集合求差」。
4. **我自己的两条错误假设被测试当场抓住**（写在测试注释里）：
   (a) 以为界面文件名等于 UI 命名空间——`storage_driver.json` 的命名空间是
   `storage_driver_ui`，原版同样如此；
   (b) 以为屏幕在 JSON 里的键就是 `main`——它写的是
   `main@common.inventory_screen_common`，带继承后缀，外部引用才写 `namespace.main`。
5. **`.gitignore` 的 `dev*` 会静默吞掉 `dev` 开头的文件名。** 本轮的
   `storage_driver.py`、`storage/*.py` 都不受影响，但架构 §2 点名的
   `sync/devices.py`、`devices/device_status.py` **会被吞掉**。本次交付前用
   `git status --untracked-files=all` 逐个核过，确认没有文件只存在于本机。
6. **`service.py` 长到 1400 行。** 实现完成后才发现，已经超出「1000 行就该警惕」
   的线。**没有拆**，因为拆分是纯结构调整、会打散这次的评审边界；建议下一轮
   把汇总索引与预留台账抽成一个 `StorageIndex` 协作者（它们有独立的守恒不变式，
   抽出去正好以那个不变式作为单元）。这条列为已知实现缺陷。

## 八、游戏内实测记录（2026-09-25）

方式：MCDK 启动游戏 → `reload_game(reload_addons=True)` → MCP 的 `execute_code`
在服务端与客户端两侧读实际状态。**约 4000 帧、`tick_errors` 为 0。**

### 已实测确认

1. **两个介质物品注册成功**：`GetItemBasicInfo` 返回 `小型单面磁带` / `1K软盘`，
   `maxStackSize: 1`，`customTips` 里的容量/类型数/读写速度**与定义表逐字一致**
   （文案由 `gen_items.py` 从 `MediumSpec` 生成，不是手抄）。
2. **`netease:block_container` 真的生效**：放下方块后，方块实体数据里出现
   `Items`（列表）与 `Size` 两个字段——**没有声明该组件时它们不存在**，
   这是组件生效的直接证据。`GetContainerItem(pos, slot, dim)` 在这个自定义容器上
   可用（空槽返回 `None`，不报错）。
3. **`container_size` 落到 10**：`Size` 读出来是 `{'__type__': 3, '__value__': 10}`，
   与 `STORAGE_DRIVER_SLOT_COUNT` 一致。
4. **物品在容器里能往返**：直接改 `Items` + `SetBlockEntityData` 写入一件
   `endernet:singleside_tape`，`GetContainerItem` 在槽 2 读回同一件（数量 3）。
   这同时确认了架构期望的读写通道——`adapters/world.py` 的
   `get_block_entity_data` / `set_block_entity_data` 包的正是这两个调用。
5. **存储不再是替身**：`assembly.stand_ins` 只剩 `energy` 与 `factory`；
   `assembly.slots` 为 `["energy", "factory", "scheduler", "storage"]`。
6. **领域层在真机上跑通**：方块放下后模组建出 10 槽 `DriverState`、`disk_count: 0`
   投影进设备记录；`create_medium('endernet:singleside_tape')` 得到 `medium:1`
   （容量 86400 微单位 = 1728 单位物）→ 装入槽 0 → `disk_count` 变成 1。
7. **拆除路径与纪律一致**：用 `SetBlockNew` 换成空气（走真实的
   `BlockRemoveServerEvent`）后，设备记录与驱动器状态销毁、`disk_count` 归零，
   而**介质仍然存在、被标 `orphaned`、`is_tradeable()` 为假**，并出现在
   `orphans()` 里。
8. **实例代次在真机上递进**：同位置重新放置后拿到 `generation: 1`。
9. **诊断可读**：`diagnostics()["storage"]` 返回 8 条未定规则（字段名与规则编号
   齐全）与 `durable_medium_ids: False`。

### 本次仍然没覆盖的

- 界面标题与网格的渲染（只确认了 `stat_bar` 可见，即屏幕确实打开了）。
- 玩家站在方块前右键之后的一切交互。
- 保存退出重进后的槽位恢复。
- 多人、距离限制、会话。

### 一条由本次实测确定下来的结论

**`netease:block_container` 的屏幕不需要 ScreenProxy 就能打开。**
参照的成品 mod 为容器界面注册了 `RegisterScreenProxy`，一度让我怀疑不注册就打不开；
实测表明那是为了它自己的燃烧进度逻辑，不是打开界面的前提。

## 九、给下游任务的交接

- **06（资源转移）**：介质的**真实物品**是方块的方块实体 NBT `Items` 里的条目
  （`{'Count': {'__type__':1,...}, 'Slot': {...}, 'Name': {'__type__':8,...}, ...}`），
  不是本模组自己的结构；读写用 `adapters/world.py` 的
  `get_block_entity_data` / `set_block_entity_data`（第八节第 4 条已实测）。
  领域层这边，装入 = `StorageDriverStore.create_medium(model_id)` +
  `provider.mount(slot, medium_id, expected_slot_version)`，取出 = `provider.unmount()`；
  **装卸成功后 `disk_count` 会自己投影并通知负载，不要在外面再改一次**。
  注意 `engine_block_events.md` 那条约束：拆除时若要读走介质内容，必须在
  **事件处理函数内同步取**，现有 `NormalizedEvent.remove` 不带方块实体数据。
- **11（终端与状态栏）**：本轮**没有**接任何 `sync/` 或 `client/` 代码。
  查询面已经备好：`StorageService.snapshot()` / `query(key)` / `keys()` /
  `take_dirty_keys()` / `publish_version`、`StorageDriverProvider.slot_views()`。
  `index_version`（交易验证）与 `publish_version`（UI 发布）是**两个版本**，
  不能互相替代（`terminal_item_index.md` §6）。
  `stat_bar` 与 `interact_btn` 的接线步骤与两个必须先做的探针，见 **第十节**。
- **12（持久化）**：可序列化结构已就位——`Medium.to_dict/from_dict`、
  `DriverState.to_dict/from_dict`、`StorageDriverStore.save_all()/restore()`，
  并有往返测试。**两点必须知道**：(a) 介质 ID 的默认分配器只保证进程内单调，
  `durable_medium_ids` 报 `False`，必须换成从存档推导的来源（`id_source` 可注入）；
  (b) 本轮**不落盘**，也没有接 `WriteCoordinator`。
- **14（发布验收）**：显式调用 `bootstrap.assert_assembly_ok()`——它会把
  `BandwidthPolicy` / `DriverPolicy` / `MediumPolicy` **三份**未定规则一起交给
  `ServiceRegistry.assert_profile_ok`。只报带宽那一份会让 R07/R08/R10 漏网。
  `DriverPolicy.assert_settled()` 与 `MediumPolicy.assert_settled()` **不会自动运行**。
