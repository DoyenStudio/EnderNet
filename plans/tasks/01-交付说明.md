### 离线验证的定位

本机只有 **Python 3.11**（无 2.7、无 pytest）。做法是：

- 业务源码写成 **Python 2.7 / 3.x 公共子集**（禁用 f-string、注解语法、
  `nonlocal`、`yield from`、关键字-only 参数、`await`、海象运算符、
  无参 `super()` 等），由 `endernet_tests/py2check.py` 用 AST 逐文件强制。
- 每个源文件**不得**包含 `from __future__ import ...`
  （2026-09-24 已全部移除，见 §五点九）：整除陷阱用 `//` 与显式浮点回避，
  导入一律写成相对导入。
- 测试用标准库 `unittest` 在 3.11 下运行。

**这条门禁只能拦语法，不能证明行为等价。** dict 视图对象、`str`/`unicode` 语义、
异常链、排序稳定性等差异不在检查范围内。
（「在真实 Python 2.7 上运行」当时是未验证项，**已由本文件第五节的游戏内实测覆盖**——
游戏内跑的就是真实 py2.7.13。）

### 分层守卫

`endernet_tests/test_import_boundaries.py` 强制：`common/` 与 `server/{devices,runtime,persistence}`
**不得导入 `tooldelta` 或 `mod.*`**。引擎导入只能出现在 `server/adapters/`、
`server/bootstrap.py` 与 `client/`。

适配器把引擎调用放在**方法体内部**而非模块顶层，因此适配器模块本身仍可被离线导入，
`server/bootstrap.py` 也就能在没有 `mod.server.*` 的环境下构造——这是离线测试能存在的前提。

实测发现：本机 site-packages 里确实装有网易 ModSDK 桩包（`mod/`），
但 `tooldelta.events` 导入时会撞上桩包自身的循环导入，因此离线**不能**绑定引擎监听器。
`ServerBootstrap.start(bind_engine=False)` 因此在注册任何监听器之前就分流，
不走「先 import 再决定」的路径。

### 查询类返回的「空」有明确语义

| 返回 | 含义 |
| --- | --- |
| `DeviceRegistry.get(key)` → `None` | 该位置没有设备 |
| `DeviceRegistry.unregister_matching(...)` → `None` | 事件与当前方块不符，**未做删除** |
| `DeviceCatalog.connected_neighbors(...)` → `[]` | 无按规则相连的邻居 |
| `DefinitionSet` 中 `UNCONFIGURED` | `plans/` 未给出该数值，**不等于 0**；`bool(UNCONFIGURED)` 会抛 `TypeError` 以防被当作免费 |
| `ContainerAdapter.count_of(...)` → `None` | 容器不可读，数量**未知**，不是 0 |
| `ContainerAdapter.can_accept(...)` → `None` | 容器无模拟能力，可接收量**未知**，不是 0 |
| `Repository.load(...)` 返回 `read_only=True` 的记录 | 存档版本过新，读不懂；原样保留，写入会被拒绝 |
| `EventQueue.drain()` 返回不足 limit 条 | 队列已空 |

### 转移回执

`TransferReceipt.moved` 是**核对后的实际数量**，是记账的唯一依据；
`requested` 只是意图。状态取 `complete / partial / refused / uncertain / unsupported`。
`uncertain` 明确表示「已动作但无法确认」，**不得据此重发整批**。
构造时若 `moved > requested` 直接 `ValueError`。

## 五点五、游戏内修复（离线测不出来的四处）

离线测试全绿的情况下，进游戏后连撞四个问题。共同点是**都在离线测试的覆盖边界之外**：
适配器从不被离线导入，引擎回调从不被离线触发。

| # | 问题 | 症状 | 修复 |
| --- | --- | --- | --- |
| A | 适配器用绝对 `from tooldelta...` | `ImportError: No module named tooldelta.api.server.block`，`OnServerInited` 抛异常，**模组静默不启动** | 改为相对导入；新增守卫 `test_no_absolute_tooldelta_imports` |
| B | `bootstrap.py` 用了 4 级相对导入 | `ValueError: Attempted relative import beyond toplevel package` | 该文件在 3 层深度，应为 3 级。守卫升级为**按文件深度计算应有层级**，多一个点也拦 |
| C | 没有任何东西驱动 `tick()` | 事件一直入队、`ticks` 恒为 0，**设备永远注册不上** | 新增 `_bind_tick_driver()` 把 `OnScriptTickServer` 接到 `tick()`；异常只记录不抛出，避免一帧出错让后续全废 |
| D | 补查路径不解析朝向 | 重启后方向性设备 `facing=None`，端口方向丢失 | 朝向解析统一收进 `DeviceLifecycle._resolve_facing()`，放置与补查共用 |

A、B 两处值得强调：**离线时 100% 不会被发现**——适配器从不被离线导入，

## 五点六、集成评审修复（2026-09-24）

一轮集成评审在 01 与 02 的接缝处找出 4 个 P1 正确性问题，全部在 01 的文件内，
已修复并补了**能真正失败**的链路回归（每条都验证过：回退修复即测试失败）。

| # | 问题 | 根因 | 修复 |
| --- | --- | --- | --- |

## 五点八、tooldelta 事件库迁移到 EventBus（2026-09-24）

上游 tooldelta 更新后，`events` 改用 `EventBus` 实例管理事件。适配层已跟进。

**API 变化**

| 旧 | 新 |
| --- | --- |
| `tooldelta.events.serverapi`（模块别名） | 已删除，`ListenEvent` / `RemoveEventListener` 不再是模块属性 |
| `serverapi.ListenEvent(event, priority, static)` | `GetMCServerEventBus().ListenEvent(event, priority, static)`，**`priority` 改为必填位置参数** |
| 模块级函数 `RemoveEventListener(...)` | `EventBus.RemoveEventListener(event, listener, priority)` |
| — | 新增 `GetMCServerEventBus` / `GetModServerEventBus` 等工厂 |

**总线选择：本项目统一走 `GetMCServerEventBus()`，原版事件与自定义事件都用它。**

`EventBus` 注册时用的是 `event.GetNamespace() or self.namespace` 与
`event.GetSystemName() or self.system_name`——**事件类自带的命名空间优先**，
总线自身的只是回退值。自定义事件（`CustomC2SEvent` 之类）的
`GetNamespace()` / `GetSystemName()` 返回本模组名字，因此挂在 MC 总线上
同样注册到正确位置。`GetModServerEventBus()` 那一支对本项目是多余的：
单一总线少一个「这个事件该挂哪条」的判断，也就少一处会挂错的地方。

该约定由 `test_project_uses_only_the_mc_event_bus` 固定（AST 扫描，文档里提到名字不算），
后续加自定义事件（如任务 11 的客户端同步）时若另起一条总线会立刻失败。

**`bind()` 直接引用事件类。** 槽位别名（`api.chunk_loaded`）已去掉——
它和 `api.ChunkLoadedServerEvent` 本来就是同一个对象，多一个短名只是多一层要对齐的东西。
现在 `@self.register(api.ChunkLoadedServerEvent)` 里的就是 tooldelta 的事件类本身。

但 `api.` 前缀**不能**去掉：`bind()` 若直接 `from ....tooldelta.events import ...`，
它就无法在离线环境执行，而「stop 之后回调还在不在」正是最需要离线验证的地方。
`api` 对象是让 `bind()` 保持引擎无关、同时又能拿到真事件类的那个接缝。
离线测试用 `testsupport.declared_event_class_names()` **从适配器的注册代码里
读**类名（`event_class_assignments()` 解析 `__init__` 里的赋值），
两边不可能对不上。

**随之而来的两处调整**

1. **槽位清单改成从代码里读。** 早期版本另立过一张「槽位名 → 事件类名」的
   映射表（`EVENT_SLOTS`）；现在不单列了，`testsupport` 直接从
   `adapters/events.py` 的赋值里解析，少一份要对齐的东西。
   同一套守卫仍覆盖三种漂移：上游改名、`bind()` 用了未声明的类、
   以及「声明了却没注册」——后者当场发现 `block_entity_tick` 是**声明了但
   从未接上**的死槽位，已移除（设备级 tick 是任务 04 休眠/唤醒要用的信号，
   届时再加）。
2. **补上销毁钩子。** `modMain.py` 新增 `@ServerUninitCallback` /
   `@ClientUninitCallback`，在 `Destroy()` 时调用 `stop_server()` / `stop_client()`。

   没有这个钩子，`unbind()` 永远不会被调用，监听器会一直留在总线表里。
   **新版 `_dyn_listen` 不再按函数对象去重**（旧版有 `if listener not in listeners`），
   热重载产生的新闭包会被直接追加，同一次事件触发多次回调。

## 五点九、移除 `__future__` 导入（2026-09-24）

项目约定改为**不使用 `__future__`**。48 个文件里的
`from __future__ import absolute_import, division, print_function` 已全部移除，
`py2check.py` 也由「要求必须有」改成「出现即报 PY2019」。

**这不是纯风格改动——那三项保护必须有人接住。** 先核查了现状，三项都可以安全去掉：

| 原本靠 | 现状核查结果 | 现在的替代检查 |
| --- | --- | --- |
| `absolute_import` | 包内**零**绝对 `endernet.*` 导入；全部是显式相对导入。绝对导入只有 `fractions`、`traceback`，都是 stdlib，无同名兄弟模块 | 相对导入的分层守卫（已有） |
| `division` | 全仓库**零** `/` 除法——一律用 `//` 或 `Fraction` | **PY2022** 新增 |
| `print_function` | 全仓库**零**多参数 `print` | **PY2021** 新增 |

后两项是**静默出错**的：没有 `division` 时 py2 的 `4 / 3` 得 1 而不是 1.333，
不报错、只是数值悄悄变小；没有 `print_function` 时 `print(a, b)` 在 py2 打印元组。
所以不能只是删掉导入，必须把这两条变成检查：

- **PY2022**：`/` 的任一边必须明显不是整数（浮点字面量、`float(...)`、
  `Fraction(...)`、或含浮点的乘积如 `1.0 * n`），否则报错；要用整除就写 `//`。
- **PY2021**：`print` 只能有一个位置参数且不能带关键字参数。

两条都验证过**确实会失败**：往 `runtime/events.py` 注入
`self.pushed / 2` → PY2022；注入 `print('a', 'b')` → PY2021；
注入 `from __future__ import division` → PY2019。

反向用例也补了：`//`、`float(a) / b`、`a / float(b)`、`1.0 * a / b`、
`Fraction(a, b)`、`-1.0 / b` 都必须放行（`1.0 * a / b` 一开始被误报，
已让检查认得「含浮点的乘积也是浮点」）。

## 五点七、交给 03 的两项契约（接手前必须明确）

### 1. 拓扑的「单控」不等于「主控可运行」

`topology.validate(终端)` 在**控制器区块已卸载、终端区块仍加载**时仍返回允许。
这是有意的：图保留已知拓扑，不把「暂时访问不到」当作「已拆除」。
但 **03 不能把这个接口当作最终业务准入**，必须另外校验主控实例确实已加载、已恢复。

建议 03 的准入串联至少包含：主控实例存在且 `loaded` → 拓扑版本未失效 →
本设备已获带宽 → 供能满足。**接口名称与调用点应在 03 里显式体现这一点**，
避免后来者直接拿 `validate()` 当准入结果用。

### 2. 测试策略必须与正式装配区分

`ServerBootstrap` 默认构造准入服务，用的是容量求和等**测试默认策略**
（已标 `unresolved='R02'`, `is_test_value=True`）。`assert_no_silent_unresolved()`
只会在被调用时检查，**并不自动构成运行门禁**。

风险：后续存储服务可能直接使用这些替身数值，而没人注意到它们还没定案。
建议 03/04 接入时引入显式的装配档位（开发 / 正式），正式档对未定规则
返回「待确认」而不是替身值。这属于实现决策，本次未替 03 决定。

那套「只与紧邻前一条合并 + 合并键带 `device_id`」逻辑，对
「同一次放置的两条不同事件」也正确合并——两次事件是**不同事件类**，
只有合并键选对了才压得成一条。手动放置与脚本放置走的是同一条入队路径。

顺带在真机上确认了「物理连接」与「功能范围」的分层：
DOS 控制器与总线**连得上**（端口判定通过、分量成型），
但 `controller_serves` 给出 `controller_does_not_accept_device`——
与 blocks.md「DOS 仅能控制存储控制器、通用终端模版和合成终端面板」一致。
（**注**：该原因码在开发档下**看不到**——准入链第 8 条会先以
`service_absent` 拦下业务命令，第 9 条走不到。本结论来自直接调用
`controller_serves`，不是来自一条被拒的命令。）

### 退出世界再重进：无陈旧监听器残留

真人先退出世界（引擎日志 23:25:32 `Destroying the Level...` → `start_screen`），
后再加载同一存档。**进程没有重启**（PID 不变），但 Level 与脚本环境重建了
——这正是 `Destroy()` 钩子该被调用的那条路径。

重进后实测：

| 探针 | 值 | 含义 |
| --- | --- | --- |
| `ticks` 速率 | **30.0 / 秒**（26.7 秒内 801 tick） | 恰为 `OnScriptTickServer` 的 30Hz。**若陈旧监听器残留，这里会是 ~60/s** |
| `script_tick` / `ticks` | 增量都是 801，1:1 | 一个驱动对一次事件 |
| 注销注册表条目 | `_on_server_uninit` **恰好 1 条**（无累积） | 注册表没有被重复填充 |
| 设备重新发现 | 25 台，与世界里实际存在的 25 个方块**逐一对应** | 重进后状态正确 |

**即：钩子要防的那个后果（监听器累积、每帧推进两次）没有发生。**

### 退出世界：钩子被调用的直接证据

上面那些是**结果**层面的证据，还不足以确证「引擎真的调用了钩子」——
环境拆除本身也会让监听器消失。因此加了一处**临时埋点**：
在 `_on_server_uninit` / `_on_client_uninit` 里向三个候选路径
（`%APPDATA%\MinecraftPE_Netease\`、`%TEMP%`、`%USERPROFILE%`）
各追加一行日志。模组的 Python 输出**不落进 `Debug_Log`**（实测打印，
日志里 `[Python]` 行数为 0），所以只能写文件。

**对照设计**（用来区分「钩子没被调用」与「写不进去」）：

1. `CONTROL` 行——由游戏进程预先写入，证明路径可写；
2. `SELFTEST` 行——从模组侧调用一次探针函数，证明函数本身可用；
3. 之后才是钩子行。

**结果：退出世界后三个文件都出现了钩子行**，各**恰好一条**：

```
2026-09-24 23:39:27 PROBE server_uninit: 钩子被调用（引擎销毁路径）
2026-09-24 23:39:27 PROBE client_uninit: 钩子被调用
```

`ToolDeltaModServer` 是通过 `serverApi.RegisterSystem` 注册进引擎的正规
ServerSystem（`tooldelta/mod_main.py`），引擎销毁服务端系统时调用它的
`Destroy()` → `general.UninitServer` → 本钩子。**链路的最后一环至此闭合。**
「恰好一条」也说明没有重复注册。

**埋点已在验证后整块删除**，`modMain.py` 恢复原状（与加埋点前逐字一致），
三个日志文件一并删除。

- 「尝试破坏」→ **中途放弃**（没有真正破坏）时是否留下状态。

### 本轮新发现的一处限制：进程内 stop → start 丢失已加载区块

显式 `stop_server()` 后原地 `start_server()`，新实例**发现不了任何已有设备**
（实测：`devices: 0`、`topo_version: 0`、`chunks_with_block_entities: 0`）。

原因是结构性的，不是缺陷：`ServerBootstrap.__init__` 里
`self.world = world if world is not None else ToolDeltaWorldAdapter()`，
而 `start_server()` 不传 `world`——**每次重启都拿到一份空的区块缓存**；
缓存只由 `ChunkLoadedServerEvent` 填充，而已加载的区块不会重新发加载事件。
补查也救不了：它枚举的正是这份缓存（`world.list_loaded_chunks()`）。

**引擎级热重载不受影响**：实测 `reload_game` 之后设备全部重新发现
（22 台、12 个分量），说明引擎重载会重新派发区块加载事件。

这条与设计文档不冲突——「冷启动不会漏」的论证明确只针对**进程冷启动**
（脚本初始化时世界尚未加载）。但进程内 stop→start 这条路径会丢状态，
文档此前没有写明，记在这里。
