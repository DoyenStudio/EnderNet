## 三、接口输入输出

### 命令：`CommandKind.ORDER` → `ServiceId.FACTORY`

`order` 是**写命令**（`COMMAND_ROUTES` 早就这么定的），因此它一条都走
主控准入与去重账本。`payload["action"]`：

| action | 载荷 | 返回 |
| --- | --- | --- |
| `submit` | `{target: <ResourceKey.to_dict()>, amount: int>}` | `ok` + 订单视图；计划不可执行时 `rejected` 并原样透出 08 的 `plan_*` 码 |
| `cancel` | `{order_id}` | `ok` + 订单视图（含 `residue`）；未知 → `order_unknown`，已终态 → `order_terminal` |
| `pause` / `resume` | `{order_id}` | 同上 |
| `list` / `detail` | `{order_id?}` | 与 `debug_query("order")` 同一份纯数据 |

**入口设备可以是网络内任意一台设备**：订单归属该设备所在网络的主控实例，
不绑在入口设备上。这是 09 与 11 的接口定调（用户 2026-09-26 确认）。

### 只读查询：`debug_query("order", component_id=..., order_id=..., status=...)`

与 `port` / `pattern` / `plan` 同形：**一条命令都不发、一张订单都不推进**，
没有主控、网络不能工作时照样能答（全局约束 9）。给的正是最该看的那部分：
每张订单的状态、进度、预留、步骤明细、阻塞原因，以及
`returns`（回流入口接上了没有）。

### 进度（用户 2026-09-26 要求）

> **2026-09-28 已改**：**口径那句没变**（「已完成的配方数 / 总配方数」），
> 变的是分母真的按配方数算了——下面这个快照里的 `steps_*` 当时数的是
> **步骤数**，`ratio` 因此是「做完了几个步骤」而不是「跑了几次配方」。
> 现在 `Order.progress()` 另给一组 `tasks_*`（完成数按执行实例计），
> 网络级只汇总 `tasks_*`；`steps_*` 保留，改答「这张订单分几种配方」。
> 新形状见第十节。

**进度 = 已完成的配方数 / 计划里配方树的总配方数。**

```
"progress": {
    "steps_total": 3, "steps_completed": 1,
    "steps_blocked": 1, "steps_cancelled": 0,
    "outstanding_step": 1, "by_status": {...}, "ratio": 0.333...
}
```

三个刻意的口径，逐条都写进了 `Order.progress()` 的 docstring：

- **不额外记账**：步骤状态就是进度的唯一依据，再维护一个计数器只会多一个
  会走偏的数。
- **零步骤的计划没有分母**：`HOLD` 口径下「库里已经够了」的订单
  `total = 0`，此时按订单是不是已完成给 `0.0` / `1.0`。返回 `0/0`
  或者一个凭空的 `1` 都会让界面画出一条不存在的进度条。
- **`cancelled` / `blocked` 不从完成数里扣**：「8/10 完成、1 个取消」与
  「7/10 完成」在界面上是两件不同的事。
- **`ratio` 不参与任何判定**：结单看的是「每一步都 `COMPLETED`」。
  （2026-09-28 起是「**每一步的每一次执行**都完成」——见第十节。）

网络级合计在 `RuntimeManager.order_view()` 与 `FactoryService.progress()`，
两处给的是 `tasks_completed` / `tasks_total` **两个数**而不是一个平均比例——
平均会让「10/10 完成」与「0/5 完成」拼成 50%，而那份一张都没做。
（**2026-09-28 起汇总的键是 `tasks_*`**，不是上面快照里的 `steps_*`；
`steps_*` 保留下来改答「这张订单分几种配方」，见第十节。）

## 四、适用存档版本与持久化

**09 不存档，也不迁移。** 订单台账是每张网络的工厂服务持有的内存状态，
`save_node_data()` 保持基类默认（返回 `None`）。

这对 12 有两处**必须处理**的后果，写在明处：

1. **重启之后订单全没**，而**预留记在 05 那侧、批次记在 06 那侧**——
   如果 05/06 将来接了持久化而 09 没接，会出现「料还被锁着，而没有任何
   订单知道它在等谁」。12 恢复时必须**先撤掉所有没有对应订单的预留**
   （或者让 09 一起持久化），否则那是一份永远放不掉的预留。
2. 订单 ID 里带着主控实例（`order@<分量>/<主控实例>/<序号>`），而
   **分量编号在进程重启后会重新分配**（02 的口径）。因此现在的订单 ID
   只是进程内身份，不是持久身份——12 要把身份绑到位置集合或控制器实例上。

`WaitingLedger` 的 `op_id` 去重表有上界（`OrderPolicy.op_ledger_limit`，
默认 4096，按插入顺序淘汰最旧的），因此它不会随长跑无限增长。

## 五、未定规则与剩余限制

### R04：槽位与内存是**替身口径**

`blocks.md` 只说了「单个处理器提供 1 个配方处理槽位」，没说一个订单吃几个；
定义表里也没有「一个内存槽提供多少内存单位」。本增量按替身取最小的一侧，
并**把它们全部挂进 `unresolved_report()`**。R04 定案之前
`assert_settled()` 会拒绝盖章，`PRODUCTION` 档的准入链会拦。

### R09 的执行侧：返还物算不算完成

替身取**「算」**（见 §三），因为 09 验收原文写的就是这一侧。
另一侧是 `returns_block_completion=False`，一个字段就能翻过去。

### 已知实现限制

1. **回流入口是替身**（任务 10）。默认装配下订单**永远到不了 `completed`**，
   这是有意的：与其假装收货，不如停在等待产物并报出为什么。
2. **装配仓执行未实现**（07-06）。2026-09-27 已确认其 19 槽网易容器与直接执行样板配方的规则，见 [07 交付说明补记](./07-交付说明.md)；09-05 仍需补齐向 0～8 槽实际投料、从 9 槽回收的订单衔接，不能据此视为已交付。计划里若引用了装配仓提供者，那一步会
   `BLOCKED` 并给出 `service_absent` + 「07-06」，**不静默停滞**。
3. **不做中途重规划**。复核失败（库存被拿走、样板被编辑、拓扑变了）时
   订单转 `BLOCKED` 并报出原因，**不重新规划**——重规划会换掉 `seal`，
   而订单已经按旧 `seal` 预留过料了。玩家要做的是取消后重新下单。
   08 的另一侧（用新快照重规划）是具名可选的，本增量没接。
4. **取消后的在途资源按 R05 待定处置**：替身口径是「留在原地不动、
   逐条报出来」（`residue`）。已经进了外部机器的那部分不可能拿回来
   （09 文档：不伪造回滚外部机器）；中转位里的余量归谁、该退回哪里，
   是一条还没定案的规则。
5. **一次只搬一种料**。`PortState.batch` 只有一个格子，因此同一个步骤要备
   两种料时是串行的（这一种投完再备下一种）。备料期间别的订单要让位
   （`order_port_busy`），不会把别人的批次冲掉。
6. **多订单只做了基础轮转**（游标前移 + 每帧订单数上限 + 预算钳位）。
   R06 的公平性（回流分配顺序）归 10，09 不另写一套分配算法。
7. **规模未测**：夹具是 8 台设备、1~2 个步骤、1~2 张订单。大计划、
   多订单并发的帧预算属任务 14。
8. **`tick` 里不做重活**：每帧每个订单最多发一条命令（一条 `port_stage`
   或一条 `port_dispatch`），规划分帧推进。真机上单张订单时 `tick_errors`
   一直是 0，但**多订单并发时的帧占用没有测过**。
9. **`HOLD` 口径会把「库里已有」的那一份也预留掉。** 真机上观察到：
   请求 2 个铁块、库里已有 1 个时，计划声明 `claims` 里**同时**有
   「已有的 1 个铁块」与「要生产的 1 个所需的 2 个铁锭」。
   这是**对的行为**（否则两个订单会各自把同一份已有成品算进去），
   但它意味着「下一张订单看到的可用铁块是 0」——11 的界面要把这条讲清楚，
   否则玩家会以为库存凭空少了一个。

## 七、开发过程中撞到并修好的问题

（全部是**自查与设计评审**撞出来的，没有一条来自游戏内——因为这个增量
一行都没上过真机。列在这里是因为它们都是「离线用例照不到就会漏掉」的形状。）

### 1. 备料时「先预留再取」会取到 0

05 的 `_do_extract` 里可用量是 `stored - reserved`，而 `reserved` **含本订单
自己的预留**，且 05 **没有**任何 consume/commit-reservation 入口。
照直觉写的「先 `reserve(N)`、再 `port_stage` 取 N」会取到 0，而症状看起来
与「网络里根本没料」一模一样。正确顺序是**释放 → 备料 → 补回没搬走的**，
三段在同一次同步调用里完成（中间没有让出点）。`_stage_next_input()` 的
docstring 把这条写在最前面，用例 `test_staging_takes_material_out_of_the_network`
钉住它。

### 2. 同一帧里被访问两次 → 同一个 `op_id` 被发两条命令

04 的 `RuntimeManager` 有余量轮，**同一帧会把同一个运行时访问两次**。
`stage_batch` 每次都用新批次覆盖 `state.batch`，而协调器账本按 `op_id` 去重
——第二条命令会拿到**第一次的回执**，于是 `moved` 被加第二次，中转位里
凭空多出一份料。修法不是「一帧只做一次」（帧号可能缺失），而是**结构性**的：
`_owns_live_batch()` 判「格子里的批次还是不是我的」，是就不再开新的。

### 3. 重复用同一个 `op_id` 开第二批 → `delivered` 一帧涨一截

紧接着上一条的另一面：批次推不动之后要**按差额再备一批**，而第二批若复用
`op_id`，协调器会返回第一批的旧回执，`state.batch` 却已经被新批次覆盖——
两个读数从此对不上，`delivered` 每帧涨一截而料根本没动。
修法：**每一批一个新的 `op_id`**（带批次序号），`delivered_base` 在换批前
把旧批次的终值折进去。`test_the_order_finishes_without_sending_the_whole_batch_twice`
用「原料缓冲一次只装一件」的夹具把这条路径走出来，并断言机器最后收到的
**恰好**是配方要的量。

### 4. 批次推不动时执行器会一直等它

备料只备了一部分时，批次记的 `requested` 是**想要的量**而中转位里只有实际
搬来的那些；投完之后批次仍然不满足 `is_complete()`，接口那边也报「中转位里
已经没有这批资源」——**而它自己不会放弃**。没有 `_batch_is_dead()` 这条判据，
执行器既不重试也不报错，界面上看起来「还在投」。
用例见第 3 条那条。

### 5. 被阻塞的步骤读的是**过期**的原因列表

`step.blockers` 是「被挡住那一刻」的快照，而挡住它的东西大多会自己消失
（机器腾出空间、别人的批次投完）。第一版 `_unblock` 直接把这份快照当结论，
表现是「接口早就恢复了而订单永远醒不过来」，**而它自己报的原因还是对的**。
修法：`_step_obstacle()` **重新算一遍**，且调用的是执行路径上那几个判据函数
本身（`_port_for` / `_foreign_batch` / `_stock_blocker_for_staging`），
两处不会各说各话。

### 6. 运行中的订单不复查主控实例、也不重验拓扑

订单级的闸门原先只在「排队 → 运行」那一次过。于是「订单已经在 RUNNING、
这时主控被换掉了」永远发现不了——它不会自己变成 `BLOCKED`。
修法：`_advance()` 对 `QUEUED` **与** `RUNNING` 都过一遍
`_order_obstacles()` 与 `_recheck_if_stale()`。
这条尤其要紧，因为 `NetworkRuntime.tick` 在网络不开放时**根本不调服务的
`tick`**——「重开之后」是唯一能发现它的时刻。

### 7. 「阻塞解除」不等于「可以开工」

容量不足被挡下的订单**还没有材料与租约**（落地只做了一半）。第一版
`_unblock` 直接把它推到 `QUEUED`，于是下一帧的 `revalidate` 打在
`order.plan`（`None`）上直接抛 `AttributeError`。
修法：把「落地」拆成一个**可重入**的步骤 `_finish_adoption()`，
加一个显式的 `adopted` 标志，并让 `_resume_adoption()` 处理半成品。

### 8. 预留的**本地镜像**会在两处与事实脱节

介质被拔出时 05 会 `revoke_reservations_of_medium` 把预留收走，
并明确把「通知订单重验」留给 09；取消之后订单对象还会存在到被清理为止。
照着镜像去释放，会去释放一个已经不存在的预留——而 `release` 对未知 id
**返回 0 且不报错**，症状是「备料越备越少料」，完全看不出原因。
修法：释放与判据**一律以 05 的活预约为准**（`reservations_of()`），
镜像只在每一轮同步之后供界面读。用例
`test_a_released_reservation_is_not_trusted_from_the_local_mirror`
先制造「料还被锁着」的假象再断言订单会挡下来。

### 9. 假回流只「通知」不「入库」→ 多级配方第二步卡住

`FakeReturns` 第一版只调 `receive_output`，于是订单的账是对的，
而网络里什么都没有——下游步骤去取中间产物时发现不在，报出来的是
**「缺料」**，与真相（假回流没入库）完全不同。
修法：假回流**先 `commit_insert` 真入库、再按 `receipt.moved` 分配**，
这正是任务 10 的形状（10-02「从真实接受数量进行分配」）。

### 10. 用例自己的缺陷：`request_id` 复用被主控账本当成重放

`query` 走的是 `CommandKind.STORAGE`（写路由），因此它进主控的去重账本。
夹具里连续两次 `stock(key)` 用同一个 `request_id`，第二次拿到的是
**第一次的缓存结果**——于是「取消之后库存看起来没变」看起来像实现缺陷。
**这条不是实现缺陷，但它值得记**：它说明主控账本在正常工作，
也说明「只读查询」在 `order` 这个形状下走的其实是写路由。

### 11. 订单视图里塞了非纯数据

`Order.to_dict()` 原先把一个活的 `ResourceKey` 放进了 `reservations`，
而这份视图是要 `json.dumps` 出去给 11 与诊断用的。它会在**序列化那一刻**
才炸，而那时离出错的地方已经很远了。修法：只给 `canonical`。

### 12. `RevalidationReport.reasons` 是**属性**不是方法

`report.reasons()` 会抛 `TypeError: 'list' object is not callable`。
它只在复核**失败**时才走到，因此夹具全绿也照不到——
而复核失败恰恰是「提交前最后一道闸」的位置。

### 13. 用户可见的文案里贴的是身份文本

`ResourceKey.canonical()` 是给排序与对齐用的全序文本
（`item|minecraft:iron_ingot|0|(30:(12:enchant_data10:...`），
第一版把它直接写进了「料被别人锁着」那句提示里。修法：**给人看的一律用
`key.name`**，`canonical` 只留在数据字段里。

### 14. 租约台账里同一拥有者领两次会漏账

`_by_owner` 原先存单个 id，第二次领会把第一条覆盖掉——那条租约还躺在表里、
`active` 仍是真，于是**永远放不掉**：可用量平白少掉几个槽位，而账面上
查不出少在哪。改成存列表，`release` 一次放光该拥有者的全部租约。
（这条是设计评审提出的，不是我自己撞到的。）

### 15. `MemoryLedger.claim_for_order(oid, 0)` 返回 `None`

零步骤的 `HOLD` 计划根本不该走到领租约这一步，而返回 `None` 会让
「不该调」与「内存不够」在调用方看来一模一样——后者是可恢复的业务结论，
前者是代码写错了。改成直接抛 `ValueError`。

> **2026-09-28 已按 R04 重做（第十节）**：这条修法的方向反了。`required_bytes`
> **可以合法地为 0**（`ByteRounding.FLOOR` 下不足一个单位物，`test_planner.py`
> 已有断言），而「每一个通过准入的订单都有一条内存租约」是诊断与恢复要用的
> 不变式。因此现在 `_Ledger.claim` **只对负数抛 `ValueError`**，`0` 是合法的、
> 会留下一条 0 单位的租约；入口也从 `claim_for_order` 改名 `claim_order_bytes`。

### 16. 等待台账的去重表没有上界

它是唯一一张只增不减的表，一张长跑的存档会让它一直长下去。
加上界（按插入顺序淘汰最旧的）并计数。顺带修掉一处 py2 陷阱：
回执的资源键原先是 `str(key)` 兜底，而 py2 上对非 ASCII 的 `unicode`
调 `str()` 会抛 `UnicodeEncodeError`——把一个「读不懂的键」的异常
换成静默记成 `unknown`，表现就是订单永远等差而日志里一条线索都没有。
现在只认 `ResourceKey` 与**规范文本**两种形状，其余一律计数拒绝。

### 17. `order_returns_absent` 盖住了别的阻塞原因（**真机**）

**真机上撞出来的第一条。** 被容量挡下的订单，在槽位释放之后本该自己恢复，
却一直卡在 `order_returns_absent` 上——因为那条提示原先按**订单级**报，
而它答的其实是「为什么这一步等不到产物」。一个还在 `waiting_inputs`、
甚至还没落地的订单根本谈不上等产物。修法是把它的适用范围收窄到
**真的有步骤在 `waiting_outputs`**；`_ready_to_finish()` 那条判断同时
提到它前面（先让能收尾的步骤收尾）。

**离线为什么没照到**：假回流报 `available: True`，那条提示根本不出现。
回归用例补在 `TestReturnsNotWired` 里（那个夹具用的正是替身回流）。

### 18. 步骤的产物到齐了却不结单（**真机**）

同一个根的**另一面**：订单因为 `order_returns_absent` 转成 `BLOCKED` 之后，
就再也回不到 `_track_outputs` 去看产物到了没有。真机上的表现是
**步骤的 `received` 已经是 1/1，订单却停在阻塞上、进度停在 0**。
修法是在 `_blockers_for` 里先问「这一步能不能自己收尾」
（`_ready_to_finish`：台账满足 **或** 步骤自己的产物账满足）。

第二条尤其要紧：**「10 还没接上」与「10 接上了并且把产物分配过来了」
必须能分开**——只认等待台账会让手工（或将来真接上的 10）分配过来的产物
被无视。

### 19. 零步骤的 `HOLD` 订单永远停在「规划中」（**真机**）

**真机上撞出来的第三条，也是最好的一条**：库里已经够了时，08 给出的是一份
**零步骤但 `COMPLETE`** 的计划（08 交付说明第五节），而订单状态机的迁移表里
**没有 `PLANNING -> COMPLETED` 这条边**——`move_to` 静默返回 `False`，
订单从此停在「规划中」空转：`plan_job` 已经是 `None`，
`_step_plan` 变成了一个什么都不做的空操作，**而它自己的账看起来全都对**。

修法两处：

- 迁移表补上 `PLANNING -> COMPLETED`（它是唯一一条从规划直接结单的边）；
- `submit_order` 原先把**任何终态**都当成同步失败丢掉，
  于是这份零步骤的**成功**订单会被返回成 `internal_error`。
  改成只排除 `FAILED` / `CANCELLED`。

**离线为什么没照到**：零步骤的完工路径只单测了 `Order.progress()` 的
零分母口径，**没有一条端到端用例真的提交过零步骤订单**。补上了。

**这一条的经验**：`move_to` 返回 `False` 时的静默是这次三个缺陷共同的
放大器——不止一处「状态没转成，但代码继续往下走」。`_step_plan` 里那句
「停在规划中却没有计划任务」现在会**主动判失败**，把这类静默变成一条
看得见的错误。

### 真机顺带确认的两条事实

- **分量编号在重进世界/热重载后会重新分配**（02 文档里写过，这次亲眼看到
  订单 ID 从 `order@2/...` 变成 `order@3/...`）。交付说明第四节里
  「订单 ID 目前只是进程内身份」因此不是纸面推论。
- **样板跨热重载存活**（它存在方块容器里），而**介质与端口配置不存活**
  （内存态，12 未落地）。重载之后要重新播介质并重配端口。

### 改了什么

| 原来的口径 | 现在的口径 | 落点 |
| --- | --- | --- |
| 一个步骤 = 一个派发单位，一个订单同时只推「最靠前的那个未完成步骤」 | **一次配方执行 = 一个执行实例**，同单可同时派发多个就绪实例，直到槽位用尽 | `jobs.py` 的 `ExecutionInstance`；`executor.py` 的 `_dispatch_round` |
| 执行实例 ID = `订单ID/步骤下标` | `订单ID/步骤下标/执行序号` | `jobs.py::ExecutionInstance.__init__`（`:616`）；由 `executor.py:1383` 的 `step.open_execution(order.order_id)` 创建 |
| 准入时整单领 `slots_per_order` 个槽 | **每次配方执行各领 1 槽**，`WAITING_OUTPUTS` 期间仍占着，完成时释放 | `capacity.py::SlotLedger.claim_slot` / `release_slot`；调用点在 `executor.py` 的 `_claim_slot` 与 `_complete_execution` |
| 内存按 `int(steps) * memory_units_per_step` 估 | 按 `CraftPlan.required_bytes` 计**字节**（08 已经算好的那个数） | `capacity.py::MemoryLedger.claim_order_bytes`；`executor.py::_finish_adoption` |
| 内存不足 → 订单进 `BLOCKED` 等 | 内存不足 → **拒绝下达**（`order_no_memory`），订单不进订单表 | `executor.py::_finish_adoption` → `_reject_request` |
| 进度总数 = `len(steps)` | 进度总数 = 各步骤 `batches` 之和（**配方任务数**），完成数按执行实例计 | `jobs.py::Order.progress`（**新增** `tasks_*` 一组键；`steps_*` 保留但改答「这张订单分几种配方」，网络级汇总只读 `tasks_*`） |

同一个订单里另一个已经在等产物的实例会被无谓冻住。

容量 8 B，下单 44 金（库存 42 + 铁 2 = 44 B）：

### 未验证

- **回流不是真实机器产出**：夹具里的处理器不做合成，产物是先 `commit_insert`
  进网络存储、再调 `ReturnsPort.accept_assembled()`（07-06 的入口，**至今仍没有
  生产调用方**，台账 D-05）注进回流索引的。顺带一条实测：**只 `commit_insert`
  不会自己触发回流分配**（放进去后 `waiting_by_key` 与 `stats` 都没动），分配是
  `accept_assembled` 做的。因此本轮验的是 **09 侧的完成记账与资源释放**，
  **没有验** 10 侧「机器产出 → `receive_output` → 索引」那条回路。
- **只有单步骤、单端口**：夹具 1 个样板提供者，所以「同 `rank` 的多个步骤跨步骤
  并行」在真机上没验（离线有，见 `TestParallelSteps`）；处理器群归属（02 的 R03
  边界）会不会让「4 个槽」实际凑不满，也没测过。
- **`order_no_memory` 只在改动替身数值的条件下验过**（见上节 C），不是自然条件；
  「内存容量」这个玩法数值本身仍未定案。
- 每订单的**规模**没测：离线夹具最多 10 次执行、1 个端口；真机本轮跑到 6 次执行、
  1 个端口。10 次执行意味着同一台机器上先做 1 个、再排队若干在等产物——那条路径
  在真机上的行为（端口让位、批次不被打断）本轮**没有重新实测**，仍按 06 的既有
  结论。
- **2026-09-28 早些时候那次真机尝试的教训，保留在这里**：当时游戏进程在跑，但
  **服务实例从头到尾没有重建过**——`ServerBootstrap.get_server().tick_count` 已累计
  93 万+。`reload_game` 两种调用（`reload_addons` 真/假）都返回成功，**但那两轮都
  没让 mod 重新初始化**。**那一轮要换 Python 只能重启游戏进程。**
  **坑在这里**：在调试环境里 `import` 一遍模块，读到的会是**磁盘上的新代码**，
  于是判别位全过——但那个模块对象与 mod 实际在用的不是同一份。判别位必须读
  **运行实例上的对象**（`get_server()` 的属性、`type(x)` 上的函数/方法），不能靠一次
  新 import 自证。
- **上面那条原先还引了「`order_policy.__slots__` 仍是旧的」当旁证，2026-09-28 已判
  为无效证据**：热重载只换函数方法体，**不重载常量与变量定义**（类变量也在内，
  实现在 ModSDK 自带的 `mod/common/utils/xupdate.py`），所以 `__slots__` **本来就
  不会变**，没变证明不了重载失败。该条结论**唯一的证据是 `tick_count`**。
  同一天稍晚 `reload_game(reload_addons=False)` 确实重建了实例（`tick_count` 归零到
  5001），口径因此是「**它时灵时不灵，必须现场判定**」，而不是「一定无效」。

### 已知实现限制

- **同一端口只能有一个实例在备料**（`PortState.batch` 只有一格）。因此「4 次
  同时在途」并不要求 4 台机器：实例备完料、进了 `WAITING_OUTPUTS` 就让开端口。
  但**备料那一段仍是串行的**，`batches` 很大时派发速率受端口轮次限制。
- 订单处于 `BLOCKED` 时 **`_advance` 不派发**，因此一个还有实例可以推进的
  兄弟实例，会等到那个**不可重试**的障碍清掉才继续。这是「订单级状态」与
  「实例级状态」两层的取舍，不计入本轮范围。
- `_release_everything` 的内存仍按 `order.order_id` 一次释放（一条订单一条租约），
  槽位改为逐实例释放。

### 未定案（**不得当成已定案**）

- **内存不足是否也该留一条拒绝记录**：09-02 明写「拒绝记录保留方式和其他失败
  终态另行确认」。本轮内存不足与缺料**共用 `OrderExecutor._reject_request`
  这一个入口**，因此它同样会落一条记录——这只是沿用既有形状。两者是否该有
  区别，要等 09-02 那句「另行确认」有结论。方法注释里也写明了这一点。
- `bytes_per_memory_slot = 1024` 仍是**替身数值**：定义表里没有「一根内存条多大」，
  R04 只定了计费口径没定这个数。它照旧进 `unresolved_report()`。
