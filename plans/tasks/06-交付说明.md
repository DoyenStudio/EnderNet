## 三、接口输入输出

### `TransferEndpoint`（鸭子类型，不用 ABC）

| 方法 | 语义 |
| --- | --- |
| `endpoint_id()` / `holder_id()` | 身份 / **余量当前归谁** |
| `is_valid()` / `invalidate()` | 邻接容器失效（13-05） |
| `can_read()` / `can_write()` | 能不能读写 |
| `probe_supply(key, n)` / `probe_space(key, n)` | 还能进出多少；`None` = 不知道 |
| `commit_extract(op_id, key, n, owner)` | 取出，返回核对过的回执 |
| `commit_insert(op_id, key, n, owner, origin)` | 放入 |
| `last_extract_origins()` | 上次取出实际动了哪些来源（只有缓冲实现） |

四个实现：`NetworkEndpoint`（包 `StorageService`，探针直接转发 `simulate_*`）、
`ContainerEndpoint`（包 13-01 的 `ContainerAdapter`）、`InventoryEndpoint`
（背包，加槽版本与槽锚）、`BufferEndpoint`（中转位，按 op 固定）。

### `TransferCoordinator`

```python
preflight(request, source, target) -> TransferPlan      # 零副作用
commit(request, source, target, plan=None, return_to=None, tick=None) -> TransferReceipt
pending_reconcile() / clear_pending(op_id) / tick(tick)
```

预检顺序是写死的：请求合法性 → 两端存在且有效 → 源可读、目标可写 →
来源可动 → 目标可容纳。**主控、能源、带宽、节点代次不在这里判**——
那四条归主控准入链（第 5/8/9/11 条），重复一遍迟早分叉。

`commit` 的顺序也是写死的：**去重 → 预检 → 取出 → 放入 → 余量回退**。
去重排在预检之前（与准入链第 2 条同序）：「这条请求做过没有」与
「此刻还做不做得成」是两个问题；反过来的话，一条已经搬空了来源的请求重发
会报「库存不足」，听起来像没搬过。

### 新增的 STORAGE 动作

| 动作 | 用途 | 调用方 |
| --- | --- | --- |
| `port_status` | 一台接口的完整状态（只读面，但仍需主控准入） | 界面 |
| `port_configure` | 写过滤/方向/单次上限 | 界面 |
| `port_dispatch` | 接口自报的一次搬运尝试 | 接口自己的轮询 |
| `port_stage` | 成批备料（网络 → 中转位） | **任务 09 的工厂** |
| `port_clear` | 人工解除待核对标记 | 界面/管理 |
| `inv_take` / `inv_put` / `inv_split` / `inv_merge` / `inv_quick_move` | 自定义背包槽的取放、拆分、合并、快捷转移 | 任务 11-12 |

`CommandResult` 的四分法（`ok`/`partial`、`stale`、`rejected`、`blocked`）由
`transfer.receipt_result()` 统一给出，接口与存储服务**共用同一份**——
各写一份的代价是同一个失败在两处给出不同的下一步提示。

### 对外端口：实际的能力对象

`PortState.capabilities`（`CapabilityRegistry`）里挂的是**真的对象**，不是标签
（架构 §4 的硬要求，与 `DriverState.provider` 同一分工）：

| 对象 | 契约 | 对外那一侧 |
| --- | --- | --- |
| `PortItemPort` | `ItemPort.insert/extract(op_id, key, count)` | 被动总线/样板口 → **它自己的缓冲**；存货口/取货口 → **朝向的容器** |
| `PortFluidPort` | `FluidPort`（同签名） | 一律拒绝，`no_adapter`，`pending_task = "13-03"` |

`PortItemPort` 是**外部物流的脚本层入口**：别的模组（或测试）通过它把东西
放进总线接口的缓冲、或从中取走。它**不经过主控**，也**不动网络库存**——
那件事本来就发生在网络之外，网络只是事后按配置把缓冲收进来（06-04）。

### 只读诊断

`debug_query("port")`（`node_key=` 或 `ref=`，都不给就列全部）**不经过主控**，
因此在网络没有主控、不能工作时照样能答。这是全局约束 9「设备离线时仍可查看诊断」
在接口上的落点——`port_status` 是 `CommandKind.STORAGE`，没有主控时根本到不了服务。

| 规则 | 字段 | 替身取值 | 位置 |

| R04 | `transfer.max_ops_per_poll` | 4 | `TransferPolicy` |
| R05 | `transfer.reconcile_limit` | 256 | `TransferPolicy` |
| R12 | `transfer.cursor_disposition` | 拒绝接管 | `TransferPolicy` |
| R05 | `port.buffer_capacity` | 9 × 64 = 576 件 | `PortPolicy` |
| R05 | `port.max_batch` | 64 | `PortPolicy` |
| R05 | `port.probe_unit` | 1 | `PortPolicy` |
| R05 | `BUS_BUFFER_SLOT_COUNT` | 9 格 | `definitions.py`（同时是方块容器格数） |

两份策略都进了 `bootstrap.policy_bundle()`，因此 `assert_assembly_ok()` 与
PRODUCTION 档会一起检查它们——少放一份的代价是 R05/R12 在正式验收时漏网。
`assert_settled()` **只在正式验收时调用**，开发与离线测试都不调用
（`test_storage.py` 有一条静态检查钉着这一点，本轮的策略一并被它覆盖）。

### 已知实现限制

1. **每个接口每轮只搬一种资源。** 过滤里有多项时，靠多轮轮询逐个搬。
   这让「先搬什么」按配置顺序走（可解释），代价是种类多时收敛慢。
2. **中转缓冲的容量是件数上限，不是槽数。** 真实上界在方块容器的
   `container_size`（9 格）与 `maxStackSize` 上；576 只是一个保守估计，
   两个数不一致时以容器为准（`deposit` 与 backing 各会让一步）。
3. **待核对标记只能人工解除**（`port_clear`）。这是有意的：自动重试正是
   06-02 要防的东西。没有这个入口，一条 `UNCERTAIN` 会永久停用该接口。
4. **`port_stage` 没有调用方**：工厂（09）未实现。它在这里的意义是把契约
   定下来，而不是假装已经联调过。
5. **`inv_merge` 是「取出来再放进去」**，不是引擎的原子合并。中间那一步
   失败时会退回原槽；退不回就报 `blocked` 并说明还有几个没退回去。
6. **`EngineItemPrimitives` 用原始字典，不用 `tooldelta.define.item.Item`。**
   后者把 `durability` 的 `None` 归一成 `0`，而 `item_codec` 按「空值与缺省
   是不同身份」处理——包装一次会让同一件物品在两条路径上得到不同的 `ResourceKey`。
7. **介质装卸没有改走转移层**（任务 06 的「接口与交付」里点名要求的那一条）。
   `mount` / `unmount` 仍是 05 的路径：`drivers.create_medium(model_id)` +
   `provider.mount(slot, medium_id)`。**原因不是漏了，而是那一步需要先定案**：
   「介质物品如何携带自己的身份与内容」（物品 NBT 还是世界记录 + ID）
   是 **12-02** 尚未做出的选择，05 交付说明第九节也把这件事交接了出去。
   在没有那个决定之前把装卸接到转移层，就得替它选一种身份携带方式——
   那正是全局约束 7 说的「用临时实现悄悄定案」。
   接口侧已经完全走转移层（这也是本轮的实质内容），接上装卸只需要在
   12-02 定了之后把 `_cmd_mount` 的 `model_id` 分支换成"从玩家背包搬一件
   介质物品过来"。**在那之前 `mount` 的 `model_id` 是开发用的造盘口子**，
   它不是可玩形态。

### 考虑过、但没有采用的方案

- **新开 `ServiceId.TRANSFER` 槽位**：更贴合「服务各有归属」，但要改
  `ServiceId.ALL`、默认装配表、替身清单与一批现有测试，而转移本来就没有
  独立的跨网状态（协调器是每网络一份、账本是进程内的）。见第二节。
- **把缓冲直接做成方块容器而不另记归属台账**：不行。批次上的 `origin` 是
  「这份算不算外部输入」的唯一依据，而方块 NBT 里放不下它，也不该放
  （物品与元数据分属两个后端时，只能有一个是权威——这里是物品在 NBT、
  归属在 `PortStore`）。
- **给流体总线也挂物品容器**：会得到一个「看起来能用、实际存错东西」的方块。
  流体路径随 13-03 一起做。
- **`PortState.buffer` 用 `None` 表示「没有缓冲」而不是空缓冲**：采用。
  「没有缓冲」与「缓冲是空的」必须分得开，前者不该被当成后者放行。

两批都发生在「已经全绿」的版本上：

- 评审那批说明**全绿不等于对**——10 个里有 4 个会破坏守恒；
- 真机那批说明**离线全绿也测不到引擎的真实字段形状**——
  第 11 条在任何离线夹具里都不可能复现，因为夹具的形状是照我们自己的
  期望写的。

这一节逐条记下来，因为每一类的形态都可能再犯。

### 会破坏守恒的四条（最严重）

1. **锚定路径是一条旁路：它只动背包，不动网络。**
   `inv_take` 带 `slot` 时调 `inventory.anchored_extract` 就完事了——
   网络那一侧**一次都没被调用**。于是「把 5 个石头从背包存进网络」
   实际执行成了「把 5 个石头从背包删掉」，而 `inv_put` 反过来凭空造出
   5 个。总量守恒让离线断言也看不出问题（我只断言了背包侧）。
   修法不是补一段回滚，而是把锚做成**端点视图**（`AnchoredInventoryView`），
   让锚定路径与普通路径**走同一段代码**——预检、去重、取出、放入、
   余量回退全都共用。这样「少写一条路」这类错误在结构上就不成立了。

2. **`anchored_insert` / `anchored_extract` 名不副实。**
   它们核对完锚就委托给按**资源键**工作的 `ContainerAdapter.insert/extract`，
   而后者从 0 号槽起整表扫描。于是「放进第 7 槽」变成了「放进第一个同种
   或空着的槽」；`_recheck_after` 只复核被锚定的那个槽，恰好**复核不出**
   东西是从别的槽进出的。总量守恒，界面上却是另一个槽变了。
   修法：给 `SlotBackedContainer` 加**按槽原语**（`insert_slot` /
   `extract_slot`，逐槽读回核对），锚定路径只走它；适配器不支持时
   明确回 `unsupported` 而不是退化成按资源键。

3. **同角色的两台接口会生成同一个 `op_id`。**
   `next_request_id()` 原来是 `port:<角色>:<序号>`。主控的账本键含设备实例
   所以没事，但**存储服务自己的账本键是 `(op_id, 方向)`，不含设备**——
   第二台接口的写入会命中第一台的去重记录，回执说成功、东西没进网络，
   而它自己那份已经扣掉了。修法：request_id 里带上方块位置。

4. **回退余量时来源标识被抹掉。**
   从混合来源的缓冲里搬东西、目标只收一部分时，退回的那部分一律记成
   `internal`，于是那批**外部**送进来的东西以后再进网络就再也不会被算成
   回流。修法：`_return_leftover` 按取出的来源构成**拆成几笔退回**，
   余数归第一个来源，保证各段之和恰好等于余量。

### 会让「不确定不重放」失效的两条

5. **轮询读不到 `UNCERTAIN`。** `receipt_result` 对 `UNCERTAIN` 返回
   `CommandResult.blocked()`，而那个快捷方式会把 payload 压成 `None`——
   轮询于是读不到回执里的 `status`，`hold` 闸门**在生产路径上从未被设上**，
   每一轮都换个新 op_id 再搬一次。修法：`UNCERTAIN` 显式构造带 payload 的
   `blocked`。
   （这个缺陷之所以没被测出来，是因为我的测试**手工设了** `state.hold`
   再断言「被拦下」——它测的是闸门的下游，不是闸门本身。）

6. **存放处说不清时被降级成「缓冲满了 / 库存不足」。**
   `_backing_extract/insert` 在 `UNCERTAIN` 时返回 0，调用方据此报
   `INSUFFICIENT_STOCK`/`BUFFER_FULL`。那会让调用方换个 op_id 再试一次，
   而东西可能已经进去了。修法：把不确定**原样上报**，不再降级。

### 其余四条

7. **缓冲会永远报着不存在的余量。** 有人绕过缓冲直接动了方块容器时，
   原来只记一笔 `desync` 而不修账，于是 `total_of`/`free`/`probe_supply`
   永远虚高，那台接口再也收不进东西，而且**每次轮询都再记一笔偏差**
   （`desync` 无界增长）。修法：`forget()` 把账压到现实上。
8. **回执在「说不清」时谎报位置。** 回滚也没成功时仍旧返回
   `back.holder_id()`，于是 `receipt_result` 会告诉玩家「余量仍在某处」，
   而真相是没人知道。修法：返回空串（「说不清」）。
9. **拆除时余料的处置记录跟着 `PortState` 一起被丢掉。**
   `drop()` 把 `BufferDisposition` 的报告写在那个**紧接着就被 pop 掉**的
   对象上，于是 R05「拆除后余料处置」等于没实现。修法：记进
   `PortStore._disposed`（比设备状态活得久），诊断里能读。
10. **`PortConfig.from_dict` 的 `enabled` 默认值与构造器相反**（`False` vs
    `True`），而 `port_configure` 又是整体替换——界面只发一个 `filter`
    就会把接口**悄悄关掉并重置方向**，玩家看到的原因是「尚未配置过滤」。
    修法：默认值与构造器一致，并改成**合并**语义。

### 11. 真机撞出来的第 11 条：引擎返回的物品字典与 `item_codec` 不同形

**离线测不到、只有真机才会暴露的一条**，也是本轮最值得记的一条。

第一次把取货口跑通时，**箱子里已经收到了 12 个石头，命令却返回
`rejected internal_error`**——东西进去了、回执说失败。原因是逐槽读回那一步：
`GetContainerItem` 对一个**原版箱子**返回 **16 个字段**，比
`item_codec` 认识的 10 个多出 `itemId` / `itemName` / `auxValue` /
`isDiggerItem` / `modId` / `modItemId`；而且身份字段的「空值」是
`[]` / `""` / `0` 而**不是 `None`**。于是：

- `_check_fields` 对多出来的字段直接抛 `ValueError`（它是**对的**：
  未知字段可能携带身份，不能静默丢）；
- 就算放行，`[]` 与 `None` 也会让同一件物品**写出一个键、读回另一个键**
  （`item_codec` 按「空值与缺省是不同身份」处理），守恒核对立刻失效。

修法在**引擎边界**：`normalize_engine_item()` 丢掉那 6 个**已知派生**字段、
把空值归一成 `None`，但**认不出的字段仍然抛错**——
不能因为「引擎字段多」就把 `item_codec` 的守卫整体放开。
回归用例里的期望值是**逐字段照抄真机读数**的。

`item_codec` 的模块 docstring 早就写着「引擎默认值归一化必须经实测后在
转换边界统一处理」。这一条就是那个实测，也说明**为什么它必须实测**：
从 05 的驱动器容器读数推不出原版箱子的字段形状，两者不一样。

### 同类但没改的（有意留着，记下来免得下次重复评估）

- **`assert_settled()` 在全仓库有 6 份逐字重复的实现**（本轮又添了两份）。
  收成一份共享基类是更好的形态，但那要同时改 4 个已交付的模块
  （`medium.py` / `admission.py` / `energy.py` / `scheduler.py`），
  超出本轮范围，且那 4 份是既有的。留给一次专门的收敛。
- **`add_node` 里的 `_mount_signature()` 是 O(介质数) 且每帧每个成员各算两次**
  （05 带过来的）。它是驱动器路径，不属于本轮新增；改成读
  `index_version` 是 O(1) 的等价写法，同样留给一次专门的收敛。
- **`_intake_candidates` 与协调器的预检会各扫一遍容器**（一次轮询里同一个
  箱子被扫好几趟）。假容器上这是列表下标，真机上是引擎调用。修法是让
  `PortDispatcher` 把已经算出的数量通过 `plan=` 传给 `commit`——
  但那样两条路径的「谁能动多少」又会有两个来源，与本轮刚统一的
  「判定只有一处」相冲突。**先不动，记为已知代价**，等 13/14 的真实
  容器测量出来再决定。

## 八、开发过程中撞到并修好的问题

这一节是第一轮实现过程中**自己撞出来**的（跑测试、对日志时发现的）；
第七节是之后那一轮对抗式评审找出来的。**第七节的条目更严重，而且其中两条
把这一节的第 5、6 条覆盖掉了**（锚定路径的问题比「调错了端点」更深一层），
两节都留着是为了保留「当时是怎么发现的」这条线索。

1. **`item_key_from_dict(None)` 抛 `TypeError`。** 逐槽读回时，写失败的槽
   读出来是 `None`，而身份提取拒绝非字典输入。原先无条件取身份，
   于是「写失败」这条路径直接炸成异常而不是回一份拒绝回执。
   修法是先判空再取身份（`_do_insert` 与 `_do_extract` 两处）。
2. **缓冲的「部分接受」原因码写反了。** `accepted < room` 表示**存放处不肯收**，
   `accepted == room < count` 才是**缓冲满了**。写反的后果是界面把
   「换个位置就行」说成「放不下了」。
3. **`stranded` 记的是次数而不是件数。** 诊断要回答的是「有多少件东西说不清
   在哪」，而不是「发生过几次回滚失败」。
4. **`_backing_insert` 在 `UNCERTAIN` 时 `note_desync(receipt.moved)`。**
   `UNCERTAIN` 的 `moved` 恒为 0，于是这条留痕等于没留——记的应该是**请求量**。
5. **锚定路径调错了端点。** `inv_take` 里背包是**来源**，而锚定分支原先
   对 `target`（网络）调 `anchored_extract`，异常被 `ApplicationService`
   兜成 `rejected internal_error`——看起来像「参数不合法」，实际是缺陷。
   修法是把背包端点单独传进来，不靠方向参数去推断。
6. **`port_status` 的注释说它「无论网络能不能工作都要能答」，而这是假的。**
   它是 `CommandKind.STORAGE`，必须过主控准入。改成如实描述，并另开
   `debug_query("port")` 作为真正不受限的只读入口——**注释撒谎比没有注释更糟**。
7. **`test_assets` 的 `test_only_the_storage_driver_is_a_container` 挡下了本轮改动。**
   它是对的：我确实新增了两个容器方块。改法是让它从 `gen_blocks.CONTAINERS`
   派生期望集合（两个方向都查），而不是放宽或删掉它。
8. **能力对象一开始根本没建**（自查时发现，不是测试撞出来的）。
   定义表给四类接口声明了 `item_port` / `fluid_port`，`NetworkNode.has_capability()`
   也据此返回真，但 `CapabilityRegistry` 里**一个实现都没有**——
   正是 `script_architecture.md` §1.5 点名的「已有能力标签不等于已实例化能力对象」。
   现在每台 `PortState` 构造时建 `PortItemPort` 与 `PortFluidPort` 并注册进去。

## 十、接口规格变更后的增量（2026-09-25 晚）

`plans/` 做了一轮接口规格同步之后，06 已交付的几处实现被判成与新规则不符。
这一节记的是**按新规格改了什么、还差什么**。

### 已按新规格改掉

| 改动 | 之前 | 现在 |
| --- | --- | --- |
| **被动接口不再来回搬** | 导入与导出共用一份过滤与一份缓冲，导出刚补进去的供货物，下一轮就被导入看见并搬回网络 | **供货位由玩家逐槽指定**（`PortConfig.supply_slots`），导入只扫存货位（补集）、导出只写供货位——两个集合不相交，「自己的货不被自己搬回去」是**结构性**的 |
| **样板槽与原料缓冲分离** | 把方块自身的 9 格容器当作原料中转位 | 只有被动接口把方块容器挂成实际存放处；样板接口改用**独立的内存缓冲**，那 9 格从此只归任务 07 |
| **定义表按用途拆分** | 一条 `BUS_BUFFER_SLOT_COUNT` 同时服务两类设备，容量一律按 9 × 64 估 | `PASSIVE_PORT_SLOT_COUNT` / `TEMPLATE_PATTERN_SLOT_COUNT` / `PICKUP_FILTER_LIMIT` **三条定案值**（不带 unresolved 标签）；容量改由**每格物品的 `maxStackSize`** 决定，`9 × 64 = 576` 那个估计对被动接口彻底消失 |
| **存货口黑白名单** | 只有白名单；空过滤表示「接收全部」 | `PortConfig.filter_mode`；**取货类只接受白名单**（`blocks.md`：「设定 N 种」是显式集合），只有存货口两种都支持；空名单行为走未定案口径 |
| **取货配置上限** | 无校验 | 服务端按角色校验，**第 10 种被拒**（`filter_limit_reached`）——11-07 的验收明确要求服务端拦 |
| **配置变化即触发** | 只有轮询 | `port_configure` 成功后 `SchedulerService.wake(ref)`，本帧就试一次 |
| **存档可区分两种语义** | 两种接口的容器都当缓冲 | `PortState.buffer_kind`（`container` / `memory` / `None`）+ `PORT_STATE_SCHEMA_VERSION = 2`，v1 的样板口记录**不按新语义解释**，留给 12 写迁移 |

**8 个源文件、4 个测试文件**；离线 **1268 项全绿**（本轮之前 1251），
py2 门禁 0 违规，`gen_blocks.py --check` 通过——**生成物一字未变**，
因为拆出来的三条常量值都是 9，这正是拆分没写错的旁证。

### 仍未定案、留在具名策略里的三条

`PortPolicy` 现在报 6 条（原来 3 条），新增的三条都是**这轮新暴露**的：

| 字段 | 规则 | 替身口径 | 依据 |
| --- | --- | --- | --- |
| `port.template_buffer_capacity` | R05 | 9 格 × 64 件 | 规格明写「不能用 9 个样板槽推算」 |
| `port.intake_filter_limit` | 待确认 | **16**（刻意不等于 9） | 文档明写**不得从取货的 9 种推导**存货上限 |
| `port.default_filter_mode` | 待确认 | 白名单 | 与旧存档语义一致，不改变既有设备的读法 |
| `port.empty_filter_means` | 待确认 | 什么都不搬 | 唯一不会让一台刚放下的接口立刻动手的解释 |

**取货的 9 种上限不进策略**：它已在 `blocks.md` 定案，进定义表
（`PICKUP_FILTER_LIMIT`）且不带 unresolved 标签。把已定案的数值继续挂在
替身规则上，等于让正式验收为一条不存在的规则盖章。

### 「立即尝试」验到什么程度

规格明写「原有轮询搬运验证不能替代立即尝试的触发验证」。本轮做到的：

- **配置变化**：`port_configure` 成功后 `wake(ref)`，本帧就试一次
  （离线有断言，真机未测）；
- **槽位变化**：容器 API 不提供变化通知，靠方块实体 tick 打回退避。
  **这不是零延迟**——04 明确警告过「拿方块实体 tick 当变化信号去立刻轮询
  会让开 tick 的设备退化成每帧扫描」。因此「立即尝试」在实现上的含义是
  **不等满退避**，交付说明不把它说成瞬时完成。

### 游戏内实测（2026-09-25 晚，第三轮）

MCDK 启动 → `reload_game(reload_addons=True)` → `execute_code` 读实际状态。
**2055 帧、`tick_errors` 为 0。**

**已实测确认：**

1. **两种缓冲的形态在真机上分开了**：被动接口 `buffer_kind: "container"`
   （挂自己的 9 格容器），样板接口 `buffer_kind: "memory"`（独立内存缓冲）。
   这条是「投料不得占用样板槽」的结构性根据。
2. **供货位由配置生效**：给被动接口配 `supply_slots: [0]` 之后，
   **外部往存货位（槽 3）放的 7 个被搬进网络、槽 3 清空，
   而网络按「保持满」把 7 个补进了槽 0**（供货位）。
3. **不来回搬在真机上成立**：后续把网络抽干之后，
   **槽 0 里的 7 个一直没动**（网络存量为 0 而供货位仍有 7），
   也就是说「补进供货位的货」没有被导入路径搬回网络。
   旧实现下这一条会表现为无休止的来回搬。
4. **样板槽没被投料占用**：往样板接口的容器槽 0 放 1 张纸当「样板」，
   然后备料 5 个 + 投料，**槽 0 前后都是 `["minecraft:paper", 1]`**，
   原料进了朝向的箱子。
5. **第 10 种取货配置被服务端拒绝**（`filter_limit_reached`）——
   11-07 的验收项。
6. **取货口拒绝黑名单**（`filter_mode_mismatch`）；
   **样板口拒绝供货位**（`supply_slots_invalid`，它没有共享槽）。
7. **网络没有容量时接口不丢东西**：中途介质未挂载时，
   端口报 `no_capacity` 并**把外部的 7 个留在存货位里**——
   「网络拒收部分留在可追踪位置」在真机上成立。
8. 新的策略替身值可读：`intake_filter_limit: 16`（**不等于 9**）、
   `template_buffer_capacity: 576`、`empty_filter_means: nothing`。
9. **旧存档迁移路径生效**：上一轮留下的 v1 配置读进来之后
   `filter_mode` / `supply_slots` 落在旧语义上（白名单、无供货位），
   既有设备行为不变。

**仍然没验的：**

- **主动存货口的黑名单在真机上没跑过**（离线有断言）：只验了
  「取货口拒绝黑名单」这条服务端校验，没验「存货口开黑名单之后真的
  只搬名单外的东西」。
- **`empty_filter_means` 换成 `everything` 之后的行为**只有离线证据。
- **配置变化唤醒（`wake`）**的「本帧就试」只有离线断言；
  真机上观察到的是「配置后很快生效」，没有逐帧确认。
- **拆除/区块重载后缓冲与归属台账的保留**仍未测。
- 上文「上一轮真机验的是旧语义」这一条要收窄：**第九节那四个方向
  （取货口/存货口/被动接口的搬运、守恒）在新代码下没有重跑**，
  本轮验的是新增的供货位与样板槽语义。第九节的守恒结论仍未在新规格下复核。
- **主动存取口的「无内部槽」只有离线证据**：`buffer is None` 与
  `buffer_kind is None` 现在是显式的，但仍需界面侧确认（属 11-07）。
- **介质装卸仍没走转移层**（第七节第 7 条），原因不变：那要先有 12-02 的
  身份携带决定。
- **流体接口**整条未接入（13-03），9 槽的表示与容量归 R07。
