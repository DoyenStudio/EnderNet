## 目标与边界

统一搬运网络与外部容器间的资源，实现总线接口、存货口和取货口。样板接口的投料也复用同一转移机制，避免另写一套扣库存逻辑。

代码归属：`ROOT/server/storage/transfer.py`、`server/devices/io.py`、`server/adapters/containers.py`（纯契约与测试替身）及 `server/adapters/containers_engine.py`（真实引擎实现）。存储驱动器的介质装卸也复用转移机制，归属与接线见 [设备脚本架构](../technical_notes/script_architecture.md)。参考 AE2 的统一网络存取入口；网易容器操作的提交细节按实际 API 验证。

## 接口与交付

### 2026-09-25 接口规格补充（待实现与验收）

以下以最新 `blocks.md` 为准；既有勾选和交付记录仅代表原搬运路径，不代表本节新增规则已完成。

| 接口 | 实物存储与配置 | 资源流向与行为 |
| --- | --- | --- |
| 被动总线物品/流体接口 | 存取共用 9 个槽位，取货最多配置 9 种资源 | 存货为外界→网络，有货立即尝试存入；取货为网络→外界，供货槽空出立即尝试按配置补货 |
| 主动取货口 | 无内部库存槽，最多配置 9 种待取资源 | 从网络取出并送入朝向容器 |
| 主动存货口 | 无内部库存槽，提供黑名单/白名单配置 | 从朝向容器提取符合过滤规则的资源并存入网络 |
| 样板接口 | 9 个工厂样板专用实物槽；原料缓冲独立 | 按订单向邻接容器投料，无法投入的原料由独立缓冲保管 |

“保持满/空”及“立刻”指立即尝试，不保证瞬时完成，不绕过库存、空间、读写额度、供能或调度预算。共享槽的存入资源与待供货资源必须有可区分的归属，不能把刚补入的供货资源再次自动存回网络；具体槽位分工和冲突处理仍待确认。

- [ ] 06-05/06 增量：落实主动接口无库存槽、取货配置上限及存货黑白名单。部分成功/拒收/不确定时记录实际持有者；转移台账不等于设备可用库存，不得用隐藏库存绕过无槽位规格。
- [ ] 06-07 增量：隔离样板实物槽与原料缓冲，投料不得占用样板槽；原料缓冲容量仍归 R05。

存货口过滤条目上限、空黑白名单语义及默认模式仍待定，不能套用取货的 9 种上限；流体槽的表示、容量与单位粒度由 R07 和 13-03 补齐。

`TransferRequest` 包含来源、目标、资源、数量、操作 ID、主控/拓扑版本和可选预留凭据；`TransferReceipt` 返回实际量、余量、当前持有者和状态。缓冲有明确容量、拥有者和保存结构；外部容器适配契约由 13 定义。

玩家背包作为实际转移端点，使用玩家、槽号、槽版本和物品指纹定位，不能以客户端显示索引代替。网络虚拟槽数量可以很大；写入真实背包时按物品 maxStackSize、可合并性、可用槽和介质预算拆分或部分接受，保留所有元数据。

## 验收

- [ ] 满容器、缺物品、写入失败、目标卸载、方向改变和部分写入时，资源守恒且不会无限忙轮询。
- [ ] 主控无效或断电不继续抽取源容器；外部物流已送入缓冲的资源仍保留。
- [ ] 取货口与存货口同时操作同一容器不会重复扣取；同一个转移重试不会完成两次。
- [ ] 普通库存搬迁、补偿和恢复不新增订单产物计数；真实新输入只发一份回执。
- [ ] 当前 ToolDelta 高层插入方法的失败路径单独验证，不能仅凭“无余量”推断引擎写入成功。
- [ ] 大于 maxStackSize 的网络提取不会生成超堆叠背包物品；背包容量不足只转移实际数量；背包槽在点击后变更时不会误取替换后的物品。

## 待定与交接

介质 Lore 写回按 [刷新与交接契约](../technical_notes/medium_lore.md#5-写回与交接顺序)：普通展示刷新合并、限预算、失败退避；真实交接捕获并核对介质 ID、槽位/设备代次与内容版本，将最新两行合入交接载荷。不得先交出旧物品再按旧槽号补写，也不得把仅展示更新当作资源转移或回流。实际失败/不确定结果沿用现有回执与核对机制。

介质物品交接新增要求（配合 05-04/07，待实现）：从驱动器取出、跨容器移动或按既定规则生成掉落物时，保留稳定介质身份及其他元数据，携带由最新已提交内容生成的容量 Lore。元数据写回须校验当前真实槽位、物品身份与版本，避免覆盖并发替换的物品；Lore 刷新不是新资源转移，不新增产物回流回执。

R05 决定样板原料/订单缓冲容量、写盘阻塞及余料处置；被动接口共用 9 格、样板接口 9 个专用样板槽已经确定，不再属于待定槽数。外部 API 不保证事务时，只对已确认操作给出守恒承诺；无法确认的崩溃窗口由 12 记录和恢复，不承诺任意外部模组的精确一次提交。

原搬运交付的落点（不代表已符合上述新增规格）：**R05 与 R12 都留在具名策略里**（`TransferPolicy` / `PortPolicy` /
`BUS_BUFFER_SLOT_COUNT`），逐条进 `unresolved_report()`，并由
`bootstrap.policy_bundle()` 交给正式验收一起检查。**没有一处用临时实现把玩法
定下来**：

- 旧实现共用 `BUS_BUFFER_SLOT_COUNT`，以 9 格 × 64 件作为测试容量；后续须区分被动库存槽、样板专用槽和原料缓冲。9 格不能一律换算为 576 件，实际物品遵守各自 `maxStackSize`；流体容量另定；
- 取消/拆除时缓冲里剩下的东西交给注入的 `BufferDisposition`，默认实现**只保留
  并留痕，不掉落、不复制、不丢弃**；
- 光标持有物一律拒绝接管（`r12_cursor_held`）。

外部 API 不保证事务这一点在代码里的形态是：**不确定就停在待核对台账里**，
既不算成功也不重放，并把余量当前的位置写进回执的 `holder`。
