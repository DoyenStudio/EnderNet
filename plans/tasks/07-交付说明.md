## 三、接口输入输出

### `patterns.py` —— 纯数据与纯函数

```
PatternStack(key, count, slot=None, unlimited=False)
    key        ResourceKey（物品或流体）
    count      正整数（0 与负数被拒）
    slot       0..8 的有序槽位；None = 无序。仅合成样板可用，流体不可用
    unlimited  标记「不限量」；**含义由 PatternPolicy 解释**，标记本身不决定行为

PatternDefinition(mode, inputs, outputs, returns=())
    mode       "crafting" | "factory"
    校验顺序：模式 → 条目 → 非空 → 有序一致性 → 返还物
    .digest()        内容指纹（**就是「样板版本」**，由内容派生）
    .output_keys()   全部产物、去重、保持首次出现顺序（索引按它建）
    .summary()       给界面与诊断的概要（不含完整内容）
    .is_ordered() / .has_fluid() / .fluid_group()

encode_pattern(definition) -> dict        加上格式版本，供写入
decode_pattern(payload)    -> DecodedPattern   **不信任外部载荷**
read_pattern(user_data)    -> DecodedPattern   从物品的 userData 读
write_pattern(user_data, definition) -> dict   返回**新**字典，别人的键原样保留
has_pattern(user_data)     -> bool            不解码，不抛错
describe_tip(definition)   -> str             一行摘要，写进物品的 customTips

DecodedPattern.definition / .format / .is_dispatchable() / .needs_upgrade()
```

错误一律是 `PatternValidationError`（`ValueError` 的子类，带 `.code` 与
`.detail`）。`code` 取自 `PatternError`，界面按它指到具体哪一行。

### `PatternPolicy` —— R09 的三个字段

| 字段 | 替身取值（保守侧） | 另一侧 |
| --- | --- | --- |
| `unlimited_fuel` | `EXTERNAL_SUPPLY`（不自动供给未授权燃料） | `MODELING_ONLY` |
| `return_rule` | `DECLARED_ONLY`（只认样板显式声明的返还物） | `DERIVE_CONTAINERS`（**选它会直接报错**，见第五节） |
| `kind_scope` | `STRICT`（按 items.md 严格区分两类样板） | `ANY` |

`unresolved_report()` 三条全报，`assert_settled()` 只在正式验收调用，
并已挂进 `bootstrap.policy_bundle()`——正式档跑不掉。

### `PatternStore` —— 状态与索引

读：`ensure` / `get` / `get_by_ref` / `states` / `candidates(output_key, include_unavailable=False)` /
`output_keys()` / `check_dispatch(ref, slot, digest, expected_mode=None)` /
`provider_blocker(state)` / `editable(ref)` / `view(node_key, ref)` / `diagnostics()`

写（**领域 API，本轮只有领域层调用方**）：`install(ref, slot, definition)` /
`uninstall(ref, slot)` / `template_item(definition)`

事件：`mark_dirty(node_key)` / `mark_all_dirty()` / `advance(tick)` /
`refresh(ref, force=False)` / `refresh_all()` / `observe(change)` / `accepts_put(device_id, item_name)`

**`check_dispatch` 是 07-04 的核心**：09 拿着计划里记的
`(提供者, 槽位, digest)` 回来问，答案只有「还能用」或「为什么不能」。
它**只回答能不能，不做事后处置**——已派发的批次属 09 的台账，本模块
既不删也不重发。

### 新增原因码（`common/protocol.py`）

| 码 | 什么时候 |
| --- | --- |
| `pattern_invalid` | 样板结构不合法（数量、无产物、无效资源） |
| `pattern_format_unsupported` | 编码格式读不出来，或已不再允许派发 |
| `pattern_stale` | 计划引用的样板版本变了（被编辑、换成另一块、被拔出） |
| `pattern_kind_mismatch` | 样板模式与这台设备不符 |
| `pattern_not_a_template` | 槽里的物品根本不是本模组的样板 |

**刻意不复用 `slots_changed` / `r12_cursor_held`**：前者说的是「槽里的东西
换了」，这里说的是「同一块样板的内容变了」，两者对旧规划的影响相同但处置
不同（一个要重新找样板，一个只要重新核对）；后者是 R12 的替身口径，
与样板无关。

### 只读查询

`debug_query("pattern")` 三种入参：

- `ref=<DeviceRef>` / `node_key=<NodeKey>` → 该提供者的状态 + `editable` 视图
- `output=<ResourceKey>` → 该产物的候选提供者（**含离线的**，带 `blocker`）
- 都不给 → 全部提供者 + 诊断

与 `port` 同形：**没有主控、网络不能工作时照样能答**（全局约束 9）。
样板索引根本不经过网络，因此它在这一刻反而是最准的信息。

### 容器事件接线（`adapters/events.py`）

| 事件 | 用途 | 有无维度 |
| --- | --- | --- |
| 事件 | 用途 | 有无维度 |
| --- | --- | --- |
| `ContainerItemChangedServerEvent` | 脏标记 | 有（`dimensionId` + `pos`） |
| `PlayerTryPutCustomContainerItemServerEvent` | **插槽拒收** + 脏标记 | 无 → 用交互玩家的维度 |
| `PlayerTryRemoveCustomContainerItemServerEvent` | 脏标记 | 无 → 同上 |
| `ItemPushInCustomContainerServerEvent` | **插槽拒收** + 脏标记（漏斗漏入） | 有 |
| `ItemPullOutCustomContainerServerEvent` | 脏标记（漏斗漏出） | 有 |

**全部只当脏标记，一条都不拿来推断状态**（理由见第四节）。
**取出永不被拦**（两个 Remove/PullOut 路径）——连拿都拿不出来会让玩家
对着一块卡住的方块无计可施；拒收只针对「不该进来的东西」。

**拒收规则只有一份实现**（`ServerEventBinder._veto_or_mark`），玩家拖入与
漏斗漏入共用它。分开写的代价是加新规则时只改了其中一处，症状是
「手动放不进去、用漏斗能放进去」——而它不是错觉，确实是漏洞。

`player_dimension` **可注入**——不注入的话「插槽拒收」这条业务规则在离线
测试里根本走不到，只能进游戏试（与 `event_api` 同一考虑）。

## 四、适用存档版本与持久化

### 样板编码格式：`format: 1`

写在物品的 `userData["endernet:pattern"]` 下。**每份权威数据带自己的版本**
（与 `ResourceKey` 的 `schema_version` 同一条纪律）。

- `format > 本版本` → **拒绝读取、原样保留**（`format_too_new`）。
  不当作空样板覆盖，与任务 12 的「未知的更新版本原样保留」一致。
- `format < PATTERN_MIN_DISPATCHABLE_FORMAT`（当前 = 1）→ **读得出来但不可派发**。
  界面照样显示内容（人要看得见才知道该重做），订单不能用它。
  当前只有 v1，因此这条路径由测试用合成版本号覆盖。

### 9 格**不存档**，也没有迁移

任务 12 的原文是「**派生样板索引在恢复后重建**」。本模块据此把 9 格的权威
放在**方块容器本身**：索引每次从容器重读重建，`PatternStore` 里没有任何
需要持久化的权威数据（`save_all()` / `restore()` 因此根本不存在）。

这条对 12 的直接结论：**07 侧不需要迁移**。12 只需保证旧的
`PORT_STATE_SCHEMA_VERSION = 1` 的 `buffer` 载荷**不被重解释成样板槽**
（06 已经用 `buffer_kind` 把它标记出来了）。这条回答了 12 文档里
「处置方案需与 06/07 确认」那句。

## 五、未定规则与剩余限制

### R09：三个字段就位，替身取保守侧

见第三节的表。三条都进 `unresolved_report()`，也进了 `policy_bundle()`。

**`return_rule` 的推导那一侧选不了**：它需要一张「容器物品 → 空容器」
映射表（属 13 的兼容层）。`PatternPolicy(return_rule=DERIVE_CONTAINERS)`
**在装配期直接抛错**，而不是返回一个空表——空表会让 10 的完成判定
永远满足，而「空桶未到就完成了」正是 09 文档点名要防的那件事。

### 已知实现限制

1. **执行侧整条未实现。** `push_inputs` / `accept_returns` 一律返回
   `UNSUPPORTED` + `service_absent`，`moved=0`（因此 `is_applied()` 为假，
   去重账本不会把它记成「已完成」而挡掉真正的重试）。
2. **预设配方未适配（07-03）。** `execution.NoPresetRecipeSource` 的
   `recipes_for` 与 `to_pattern` **都明确拒绝**（`NotImplementedError`），
   不返回空表——空表会让「这个功能没做」被读成「这个配方不存在」，
   而让人去到处找配方。想报告原因用 `blocker()`（`no_adapter`）。
3. **编辑界面未做（11）。** 领域层的写入口已备好，但**本轮不开命令路径**：
   绕开主控的写入口（哪怕是给调试用的）就是全局约束 2 说的那种旁路。
4. **装配仓一条都没接。** 它声明了 `pattern_provider` 能力，也在
   `PATTERN_DEVICES` 的映射里，但没有方块容器，因此 9 格读不到东西、
   索引恒为空。它的样板来源（合成样板放哪里）属 07-06。
5. **样板物品没有堆叠之外的分辨手段**，只有 `customTips` 那一行摘要。
   真正的分辨属 11 的样板终端。
6. **`customTips` 参与资源身份**（`item_codec` 把 `custom_tips` 算作身份）。
   因此写样板物品时**必须同时给 `userData` 与 `customTips`**，否则
   「刚装上去就被判成换了另一块」。这一点在 `PatternStore.template_item`
   里已经这样处理，但值得记下来。
7. **`PlayerTryAddCustomContainerItemServerEvent` 没有挂**（见第七节第 13 条）：
   vendored tooldelta 没封装它，而当前的两条放入路径都已经拦住了触发它的前提。
   要补它需要在本仓库里定义引擎事件类，是一套新机制，本轮没有引入。
8. **`debug_query("pattern")` 的参数类型有守卫，`port` / `device` 没有。**
   本轮的样板查询会对 `node_key`/`ref`/`output` 的类型先判、给出一条
   能读的错误载荷；而既有的 `port`/`device` 传错类型时仍会抛
   `AttributeError`。这是**有意只改新代码**，不是没看见——统一它们属于
   门面层的一次小重构，改动面比本任务大，记在这里交接。

### py2 的字符串语义：一条写给下一个人的规则

`ResourceKey.name` 在 py2 上**永远是 `unicode`**（`resource_key.py` 里
`name.decode("utf-8")`），而 `tree_text()` 返回的指纹也是 unicode。
非 ASCII 的**字节串**格式模板一旦插值到 unicode 值，py2 会按默认（ASCII）
编码去解码模板——模板里的中文于是炸 `UnicodeDecodeError`。

`py2check.py` 明确不覆盖 `str`/`unicode` 语义，因此**离线测试对这类问题
完全瞎**（它在 py3 上跑）。本轮的处置：把插值 `key.name` / 指纹的模板
一律写成 `u"..."`（与 `resource_key.py` 既有的 `u"%s|%s|%d|%s"` 同一写法）。
判据是「模板非 ASCII **且** 插值了可能是 unicode 的值」——纯 ASCII 模板
即使被提升也没有解码问题。

**校验这一条只能靠真机**：`PatternStore.install` 会走 `describe_tip`，
而那是本轮最容易踩到的一处。

### 考虑过、但没有采用的方案

- **不用 `tooldelta` 的 `Delay(0)`**（参考实现在容器事件上用的那个）：
  本模块把重读推到 `PatternStore.advance()`，既过了静默期又带去抖，
  比 `Delay(0)` 更保守，也不必给领域层引入一个引擎依赖。
- **不把 9 格内容缓存在内存里当权威**：那样会出现两份真相（容器一份、
  索引一份），而任务 12 明写索引是派生的。
- **不按设备名判定谁是样板提供者**，按定义表里的 `pattern_provider` 能力。
  否则新增提供者（比如将来某种工厂方块）要同时改两处。
- **不在 `store.py` 里读 `userData` 判插槽**：插槽拒收只看物品标识
  （物品类型就是配方模式），因此绕开了「事件里的 `itemDict` 带不带
  `userData`」这个不确定项。

## 六、与下游任务的接口定调

`plans/` 里三处跨任务的口径不一致，本轮把它们定下来并写在代码注释里：

### 1. `push_inputs` 与 `port_stage` 是两个投料入口（与 06/09 的接缝）

`capabilities.py` 声明了 `PatternProvider.push_inputs(execution_id, entries)`，
而 06 已经把成批备料做成了 STORAGE 命令 `port_stage`（`storage/service.py`
的 `_cmd_port_stage` → `devices/io.py` 的 `stage_batch`），并交接给 09。

**定为**：`push_inputs` **必须**是 `port_stage` 的薄封装（经主控准入），
不得自己碰容器、不得自己写中转位。理由写在 `io.py` 里：`stage_batch` 靠
「主控账本 + 协调器账本」双重去重，**另开一条不经过账本的投料路径会让
同一批原料备两遍，而两侧的账本都显示正常**。

### 2. 08 要的「配方候选优先级」（`08:35`）

08 文档要求「默认配方优先级……须在接口中明确」，而 `PatternDefinition`
里没有优先级字段。

**定为**：07 只提供**确定性稳定顺序**（排序键取「设备标识、位置、槽位」），
**不是优先级**。它保证同样的输入永远给同样的输出（08-04 要在其之上定义
优先级，因此必须能复现），而「哪个更优」是 08 的规则——混为一谈会让
08 的一个策略决定被 07 悄悄定案。

### 3. 12 的旧样板口迁移（`12:38`）

## 七、开发过程中撞到并修好的问题

（第 1–6 条是开发时自己撞出来的，第 7–14 条是**交付前一轮三路代码评审**
找出来的——它们都只在「外部数据是伪造的」「容器行为与契约不符」「py2 的
字符串语义」这类事情上才发作，离线断言原本照不到。）

### 1. 同一帧「先刷新、后收到变更」会把标记吃掉

去抖的判据原来是 `refresh_tick >= dirty_tick` 就认为「这次变更已被覆盖」。
但 `observe(ADDED)` 会先读一次，而同一帧稍后容器事件才标脏——两者帧号
相同，于是那次标记被永久判成「已覆盖」。

症状会非常难查：**拖进去的第一块样板不生效，第二块才生效**。
改成严格大于（同一帧算「不确定读到没有」，因此再读一次），并补了
一条专门的回归用例 `test_the_same_frame_refresh_does_not_swallow_a_later_mark`。

### 2. 空槽判定原来有两份实现（07 需要第三份时暴露出来）

`adapters/containers_engine.py` 的 `_is_empty` 是引擎边界的私有函数。
07 读样板槽也要判空，而领域层**不该 import 适配器**。

把它提成 `common/item_codec.is_empty_item()`（公共、带说明），
适配器改为委托。不这么做的代价是两份实现分叉——而分叉的表现是
「某一处忘了判空气」，于是空槽被当成一件 `minecraft:air` 物品喂给
严格转换器，在一个毫不相干的地方炸掉。

### 3. 资产检查原来只覆盖介质物品

`test_assets.py` 的 `TestItemResources` / `TestItemLocalisation` 全部从
`item_mediums` 派生。新增两类样板之后，`test_no_orphan_item_json` 会
**先失败**（多出两个 JSON 没人认领），而**其余检查会静默地不覆盖它们**。

改为从 `definitions.item_specs()` / `item_keys()` 派生（介质 + 样板一份清单），
并补了「物品必须有提示文本」一条。分成两份清单的代价是新增一类物品时
总有一处漏掉，而漏掉的表现是「游戏里有这件物品、但没人检查它的贴图」。

### 4. 未加载的提供者会占满每帧的重读预算

`advance()` 原来是「先取到期的，再截断到预算」。未加载的提供者永远
「到期」（`refresh` 会拒掉它们，但它们在候选列表里排前面），于是会
**把已加载设备的重读饿死**——一台卸载的区块能让另一台的索引永远不同步。

改成在取候选时就把 `loaded` 为假的排除掉，并补了回归用例。

### 5. `PatternDefinition.from_dict` 会把 `format` 当成未知字段

`decode_pattern` 原来把整个 payload（含 `format`）交给内容解析，
而内容解析拒绝未知字段（那是对外部载荷的守卫）——结果是**每一份合法样板
都被判成 `malformed`**。解码时先摘掉 `format` 再交给内容解析。

### 6. 一处被测试而不是被静态检查抓到的死代码

在 `bootstrap.py` 里插入 `pattern_diagnostics()` 时误把
`def energy_diagnostics(self):` 那一行替换掉了，能源诊断的方法体于是
挂到了上一个方法尾部，成了不可达的死代码。`py2check` 过（它只看语法），
**11 项测试直接报 `AttributeError`**。

记下来是因为它说明了一件事：**这类错误只有「真的调用一遍每个诊断方法」
的测试才拦得住**。`test_every_whitelisted_op_is_implemented` 正是这么写的。

### 7. 伪造的样板载荷能崩掉整帧，并把索引冻住（评审）

`PatternDefinition.from_dict` 先做列表推导再交给构造器校验，于是
`{"inputs": 5}` 这种载荷抛的是 `TypeError: 'int' object is not iterable`
——而 `store._read_one` 只捕 `PatternValidationError`。后果是链式的：

1. 异常冒到 `bootstrap.tick()` 被记成 tick_error，**本帧剩余的事件批次作废**；
2. 那台设备的 `refresh_tick` 没被推进，于是 `_is_due` 判它「从没读过」，
   **每帧都会再崩一次**；
3. `advance` 的循环在第一台就断了，**排在它后面的提供者永远刷不到**。

一块手改过的 NBT 就能把整张样板索引冻住。已修：三个组一律先判类型再逐条
转换（`_stacks_from_payload`），构造器校验 `mode` 的类型先于取值
（不可哈希的值会让 `mode not in MODES` 抛 `TypeError`）。

### 8. 指纹用了线上载荷，同一份配方有两个「版本」（评审）

`PatternStack.to_dict()` 照抄 `key.raw_identity`，而 `ResourceKey` 的相等与
哈希按**身份**算（附魔表是集合语义、排序后比较）。于是
`enchant_data=[(1,2),(0,1)]` 与 `[(0,1),(1,2)]` 是同一个键，却给出不同的
digest——**样板根本没被编辑，09 却去重做了一遍计划**。

已修：比较与指纹走 `fingerprint()`（`key.canonical()`，身份派生），
**线上格式仍走 `to_dict()`**（那必须无损）。顺带补了 `__hash__`：
定义了 `__eq__` 却不定义它，py2 上对象仍按 `id` 哈希，`{a: 1}[b]` 在
`a == b` 为真时会 `KeyError`。

### 9. 产物能带槽位 / 能带「不限量」标记（评审）

`_check_layout` 只查输入、`_check_returns` 只查返还物，于是
`PatternStack(key, 1, slot=5)` 放进 `outputs` 会被接受。那个槽位对
`output_keys()` / 索引 / `is_ordered()` 全都不可见，**却进指纹**——
同一份配方两个版本，肉眼看不出差别；而 `execution.editable_view` 交给 11
的表单契约又明写「产物：槽位必须为空」，模型与校验对不上。
`unlimited` 同理。已修，并补了 `PatternError.FLAG_NOT_ALLOWED`。

### 10. 写入口凭 `write_slot` 的布尔值报成功（评审）

架构规划 §6.3 点名的真实缺陷就是「说写进去了、其实没有」，而本模块的写入口
原来正踩在同一个坑上：`install` 拿到 `write_slot` 的 `True` 就报成功，
**紧接着那次重读本来就能回答，却没看**。真实引擎上的对应物是
`SpawnItemToContainer` 对满容器/被锁容器静静地什么都不做。

已修：写完立刻核对（读回来的是不是刚写进去的那块 / 那一格是不是真的空了），
核对不过就报失败且**不计数**。另补了「未加载时拒绝写入」。

### 11. 「派发前复核」可能拿一份过时的答案作答（评审）

去抖会把重读推到若干帧之后。玩家在第 N 帧把样板拖走、09 在第 N+1 帧来问，
`check_dispatch` 读的仍是第 N-1 帧那份记录 → 答「还能派发」，
而槽已经空了。**那条正是 07 验收里「样板编辑后旧版本计划不能直接派发」。**

已修：变更不比上次重读更旧时先补读一次。这里的判据用 `>=`，与 `_is_due`
的 `>` **刻意相反**——`_is_due` 是节流判断，同一帧算「已覆盖」可以省一次读；
`check_dispatch` 是正确性判断，同一帧时读没读到说不准，宁可多读一次。
读不到的设备不在这里重试（那由 `advance` 按固定节拍兜底），代价因此有界。

### 12. 「槽里的东西坏了」被报成「样板没了」（评审）

`check_dispatch` 只看 `entries[slot]`，于是槽里放着石头、放着合成样板、
放着一份格式过新的样板，一律回 `PATTERN_STALE` +「槽位 N 里已经没有样板了」。
而 `common/protocol.py` 为这几种情形各自留了码（`PATTERN_NOT_A_TEMPLATE`、
`PATTERN_KIND_MISMATCH`、`PATTERN_FORMAT_UNSUPPORTED`），`editable_view`
也分开报——只有复核那条路把它们糊成了一个。已修（`reason_for_pattern_error`）。

### 13. 漏斗能绕过插槽拒收（评审）

玩家拖入走 `PlayerTryPut…`（已拦），但**漏斗漏入是第二条放入路径**，
原来只标脏、不判。一台对着样板接口的漏斗因此能把任意物品塞进那 9 格，
而 `blocks.md` 明写它们「专用于存放工厂样板」。

已修：两条路径共用 `_veto_or_mark`。被动接口不受影响——`accepts_put`
对非提供者一律放行，那正是 06「外部物流往本地缓冲里塞东西」的通道。
**残留**：ModAPI 还有一个 `PlayerTryAddCustomContainerItemServerEvent`
（同种物品合堆时触发），**vendored tooldelta 没有封装它**。要触发它得先让
一个非样板物品躺在样板槽里，而那条路（玩家路径 + 漏斗路径）现在都堵上了；
样板物品本身 `max_stack_size` 为 1，合堆不成立。因此**没有为它引入
「自定义引擎事件类」这套新机制**，但记在这里。

### 14. 守卫本身有三个洞（评审 + 自查）

- **`test_import_boundaries` 看不见相对导入的 `tooldelta`。** `tooldelta` 就在
  行为包里，所以领域层写 `from ....tooldelta.api.server.player import …`
  是**真能跑通**的——层级正确、也不触发「绝对导入」那条，但效果与绝对导入
  一样：领域层从此依赖引擎，而「离线测试能存在」这个前提正是靠这条不变量。
  已修（按层级解析相对导入），并补了守卫自己的正例。
- **`gen_items.py --check` 不看贴图在不在**：删掉一张贴图照旧返回 0。
  而交付说明里那条命令就是这个工程的门禁。
- **诊断会重建索引**：`diagnostics()` 原来调 `_ensure_index()`，把
  `index_rebuilds` 加一——于是「谁在反复重建索引」这个问题的答案，
  被诊断调用自己污染。已改为只读已建好的那份，并配 `index_current`
  说明它过没过时。

### 15. `NoPresetRecipeSource.recipes_for()` 返回空表（评审）

它自己的文档说「不能返回空表，因为空表与『确实没有』无法区分」，
而查询入口恰恰返回了空表——调用方从 `recipes_for` 拿到的 `[]` 仍然分不清，
只有 `to_pattern` 那条走不到的路才拒绝。已改为查询入口同样拒绝，
想知道为什么用 `blocker()`。

### 真机才暴露的三件事（都改写进了代码）

**1. 引擎的 `userData` 对 py2 `unicode` 是破坏性的。** 隔离实验：

| 写进去的 | 读回来 |
| --- | --- |
| `{"k": "v"}`（字节串） | 原样往返 |
| `{u"k": u"v"}` / `{u"k": "v"}`（unicode **键**） | **整个条目消失** |
| `{"k": u"v"}`（unicode **值**） | 条目在，但被**清空成 `{}`** |
| 非 ASCII 的 UTF-8 字节串 | 留得下，但被再编码一次（`中文` → `ä¸æ`） |

**与内容是不是 ASCII 无关**——引擎就是不接受 `unicode`。
第一版转义层用 `u"".join(...)` 构造，于是一份**完全正确**的样板写进去之后
整个不见了，且不报任何错；`install` 的读回核对把它拦下了，报的是
「写入没有生效」。第二版改为构造 py2 **字节串**，通过。

**2. 引擎给 `userData` 里的每个标量加了类型标签。** 写普通值、读回来是
`{"__type__": T, "__value__": V}`：`1`=Byte（**兼表布尔与 None**：0/1/2）、
`3`=Int、`5`=Float、`8`=String；空列表与空字典不加标签。
不解包的话 `decode_pattern` 会报「格式版本必须是整数」。

**3. `SpawnItemToContainer` 的布尔值在某些替换状态下会说谎。**
实测到一次「返回 `False`、东西其实写进去了」。因此写入口**不看返回值**，
一律读回核对——与 06 的 `SlotBackedContainer._do_insert` 同一套做法
（架构 §6.3 点名的缺陷正是「不看返回值」，而反过来「看了但返回值不可信」
同样会误报）。

### 仍未验证

  它只标脏、从不拦截，因此没有独立的正确性风险，但确实没测过。
  要覆盖它需要一台从样板接口**往外漏**的漏斗。
- **`PlayerTryAddCustomContainerItemServerEvent` 没有挂**（第七节第 13 条）：
  vendored tooldelta 未封装它。触发前提（样板槽里躺着非样板物品）已被

- **`unlimited` 标记、流体样板、有序合成样板**在真机上没走过——它们只在
