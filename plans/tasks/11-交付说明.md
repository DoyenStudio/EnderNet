### 离线验证能证明什么、不能证明什么

**能证明**：协议编解码与字段边界、会话校验的每一条判据（身份/维度/距离/
实例代次/epoch/主控）、快照冻结与版本推进的顺序、增量批的基准与分片、
断档重取的全部触发条件、订阅与历史的回收、长列表模型的排序/锚点/代次/
分页规则、以及接线把两侧真的接上了。

**不能证明**（这些全部要等 11-14）：

- **真实引擎的时序**：一帧内提交与发布的先后在真负载下是否仍然成立、
  `take_dirty_keys()` 那个「原子点」的假设是否被引擎的派发顺序打破；
- **包的实际大小与节流**：分片按 UTF-8 JSON 字节**确定性计量**，但那只作
  分片依据，**不承诺等于引擎实际包大小**（docstring 里写明了）；
- **消息能不能真的送达**：`CustomC2SEvent` / `CustomS2CEvent` 挂在 MC 总线上
  是否真的收发（这是「挂错了就安静地什么都不发生」的那一类）；
- **慢客户端、乱序、重包、丢包**：离线用例是确定性驱动的，没有真丢包；
- **滚动与渲染**：模型给了锚点与分页，但没有任何一次真实滚动。

## 三、接口输入输出

### 协议：11 种消息（`common/protocol.py`，`SYNC_SCHEMA_VERSION = 1`）

方向 | 种类 | 用途
--- | --- | ---
C2S | `session_open` / `session_close` | 开会话 / 关会话
C2S | `snapshot_request` | 带 `from_version` 重取快照
C2S | `ack` | 推进发送窗口（`transfer_id` + 连续序号）
S2C | `session_ready` | **两个版本都在这里，且名字不同**
S2C | `snapshot_begin` / `snapshot_chunk` / `snapshot_end` | 快照冻结 + 分片
S2C | `item_delta` | 一个窗口 = 一次版本推进 = 1..N 个包
S2C | `resync_required` | 客户端必须丢弃缓存重取
S2C | `error` | **唯一**允许空会话字段的 S2C 消息

信封 `SyncEnvelope` 带 `session_id` / `network_id` / `epoch` / `view_kind`，
**路由字段不放消息体**：「每个 S2C 包都带会话与 epoch」因此是结构保证。
`VIEW_ORDER` 保留常量但**整块拒绝**：`SessionRegistry.check()` 按
`VIEW_KINDS_WITH_PRODUCER` 判、给 `Reason.UNSUPPORTED`（「还没做」），
与「发来一个不认识的种类」（协议错误）**理由不同**——两处测试钉着这条分界。

**两个版本绝不合流**：`index_version`（存储提交 / 交易期望）与
`item_view_version`（物品视图 / 界面发布）。线格式上**没有裸 `version` 字段**，
四个相关字段各自具名（`expected_index_version` / `item_view_version` /
`base_version` / `new_version`），有测试扫这一条。

### 服务端：`TerminalSyncHub`（`server/sync/terminal.py`）

```python
attach(port)                       # 组合根注入引擎边界
accepts(source)                    # 交给 MasterController 的 session_check 闭包
context_of(player_id, device_ref)  # 由 bootstrap 实现（查位置/维度/网络/epoch）
receive(player_id, data)           # 入口：原始字典 → 解析 → handle
tick(context=None, budget=None)    # 每帧推进：发布窗口在前、传输在后
close_session / close_for_player / close_for_device / close_for_network / close_for_epoch
on_runtime_change(change)          # 设备替换、网络实例变化
shutdown(reason="shutdown")
resync_network(network_id, code, detail)
diagnostics()                      # stats + frame + networks{} + rotation
```

`SessionRegistry`：`open` / `check` / `revalidate` / `get` / `close*` /
`evict_expired(frame)` / `accepts(source)` / `diagnostics()`。

**`accepts()` 在 `source.session_id` 为空时必须返回 `True`**——这是 05/08
既有命令的非回归要求，有专门用例钉着。

### 客户端：`NetworkClient`（`client/network_client.py`）

```python
open_session(device_ref, dimension)   # device_ref 必须是 DeviceRef
close_session()                       # 无会话时返回 None 且不发包
request_snapshot(from_version)        # **没有缺省值**
ack(transfer_id, sequence)
on_message(handler) / clear_handlers()
take_events(limit=None) / pending_count()
receive(value)                        # 坏包只计数、不抛出
diagnostics()
```

**没有 `send_command`**（见第五节第 1 条）。客户端**自己定义一份**事件类
（`client/` 不允许 import `server/`），防漂移靠协议常量 + 跨边界离线测试。

两处方向上的不对称，都写进了 docstring 与用例：

- **`__id__` 只在 C2S 方向存在**（引擎附的发送者身份）。服务端必须在解析前
  摘掉它（`ENGINE_ADDED_FIELDS`）；S2C 方向引擎没有发送者身份可附，客户端
  **不摘任何字段**。真机上若这一侧也带了附加字段，症状是**每一条都判成坏包**
  （`stats["bad_packets"]`），测试钉的是「拒收并计数」而不是悄悄容忍。
- **收件人**：服务端 `send(player_id, payload)` 要判有没有收件人；客户端
  `send(payload)` **没有收件人参数**（对端恒为服务端）。两侧都只收**已经
  编码好的**字典——编码要逐会话的资源描述表，只有 hub 拿得到。

### 05 的两个窄读口（本轮的 05 修复）

```python
_mark_dirty(key)          # 唯一脏标记入口：if key.is_item()
has_dirty_items()         # 不推进版本、不清空集合
iter_item_records()       # canonical 序、只含物品，与 keys() 同序
```

`take_dirty_keys()` 语义不变。修好之后，纯流体提交不会让 `publish_version`
前进，因此 **sync 层一行都不需要为流体写特例**。

### 诊断（实机排障的入口）

- `ServerBootstrap.diagnostics()["sync"]`：hub 的 `stats` / `frame` /
  `networks{会话数、发布版本、历史条数、快照数}` / `rotation`；
- `NetworkClient.diagnostics()`：会话身份、**两个版本各自具名**、待处理包数、
  `stats`（`requests / received / bad_packets / dropped / handler_errors /
  sessions_opened / sessions_closed`）；
- `ClientEventPort.diagnostics()`：`stats` + 两个频道名 + **是否在监听**；
  `AdapterSyncPort.diagnostics()`：只有 `stats` + 两个频道名——**没有
  「是否在监听」这一项**。服务端把监听器记在 `ServerEventBinder` 上
  （`listen` 走 `binder.register`），要看有没有挂上/摘干净，那里有
  `unregistered` 与 `unregister_failures` 两个计数器。

**计数器与键名是契约的一部分**：实机上排障要按名字去查，少一个键不会报错，
只会让人以为「没有这件事发生」。两侧各有用例钉住键的集合。

## 四、适用存档版本与持久化

**11 不写任何权威存档数据。** 会话、订阅、订阅者快照缓存、增量历史全在
**内存**里，进程重启后为空——与 05/09/10 的处境一致（09 的等待台账、
10 的索引同样只在内存里）。

对 12 的交接点：要恢复的是「谁在看什么」这一份**易失**状态，而**没有任何
一方需要它**——会话本来就是瞬时的（玩家关了界面、走远了、离线了就没了），
重连之后重新开会话即可，代价只是一次快照重发。因此**不建议**把会话或
订阅写进存档：那会引入「存档里的会话 id 在新进程里指向谁」这种没有答案的
问题。真正要进存档的是库存与版本（05），而本轮的 `index_version` /
`item_view_version` 都是**从 05 的 `publish_version` 推出来的**，不额外记账。

## 五、未定规则与剩余限制

### 1. `send_command` 没写：R12 未定稿，且协议里没有命令通道

`common/protocol.py` 的 `CLIENT_TO_SERVER_KINDS` 只有四条会话/快照消息；
任务文档要求命令「含请求 ID、动作和期望版本」，而那个信封的动作词表属于
**R12（手势映射，未定稿）**与 11-11（数量命令）的范围。在这里编一个动作
词表，等于把未定玩法悄悄定案——正是 11 文档禁止的「用占位绕过前置条件」。
因此**整条命令通道留给 11-11**，本轮记为未写，不记为「已实现待接线」。

已经就位、11-11 可以直接用的那一半：`index_version` 与 `item_view_version`
在客户端是两个不同名属性，`session_check` 闭包已经在主控准入链上，
`Reason.STALE_VERSION` 与 `CommandResult` 的拒绝口径都已存在。

### 2. 两套 policy 的每一个字段都是**首轮配置**，不是验收指标

`SyncPolicy.unresolved_report()` 报 16 项、`SessionPolicy.unresolved_report()`
报 4 项，来源一律指 11.md 页尾「请求大小、会话过期和分页上限由目标环境测量
后确定」与 §5「100～200ms 仅作为首轮合并窗口测试配置」。

- **`SyncPolicy` 里没有任何时间字段**，这是有意的：窗口由调用方每帧推一次，
  本模块不持有周期，因此「100～200ms」那个测试配置不会被固化进另一个模块。
- `SessionPolicy.require_position = True`（查不到坐标即拒绝，fail closed）
  **不进** `unresolved_report()`：那是有取向的安全默认，不是待测量的数值；
  混进去会让真正待定的四项变得不起眼。
- `SyncPolicy.require_admission = False`：R13 只读物品视图不重复判定准入，
  恰好满载不影响查看。注释写明了这条取向。

`assert_settled()` **本轮没有被调用过**（开发与离线测试都不应调用它）。

### 3. 队列与历史的上限：丢包的后果是**可发现**的

客户端收件队列有界（`DEFAULT_QUEUE_LIMIT = 256`，**待定**），溢出丢**最旧**
的一条并计入 `stats["dropped"]`；服务端的历史与暂存同样有界，溢出**不扩容**
而是终止传输、重取快照。丢包之所以可以接受，是因为版本链会把它变成
`ListResyncRequired` / `resync_required`——**只影响要重取多少，不影响正确性**。

### 4. 已知实现限制

1. **`SnapshotChunk` 的条目在客户端没有「边收边建」**：`client/network_client.py`
   只把包解出来交给界面，快照的组装（`snapshot_begin` → chunks → `snapshot_end`
   → `model.replace_snapshot`）是 11-03 界面层的活，**目前没有实现**。
   模型侧 `replace_snapshot` 是现成的，缺的是那个组装循环。
2. **服务端不做服务端筛选分页**：`query_page` 是渲染切片，`snapshot_chunk`
   是传输分批，两者分开。将来加服务端筛选是**新增消息种类**，不是返工。
3. **`item_list_model` 的默认名称解析用 `key.name` 而不是计划里写的
   `key.canonical()`**：`canonical()` 是给身份用的指纹，直接当显示名会把
   附加字段的编码露在界面上。测试里两种都给 `name_resolver` 验过。
4. **`transfer.py` 是从 `terminal.py` 拆出来的**（计划里预留的口子）：
   纯计算部分与引擎无关，拆开后两边都不到 1500 行。

## 七、开发过程中撞到并修好的问题

### 1. 纯流体提交会推进物品视图版本（**05 的行为缺陷**）

`_apply_contribution` / `_set_reserved` / `_reindex_keys` 三处都无条件
`dirty_items.add(key)`，而它们遍历的 `stored_view()` **含流体**。于是
「往网络里倒一桶水」会让物品视图版本前进、给每个终端发一批空增量。
11.md 第 117 行明写「物品视图版本不因流体单独变化而推进」，**这条当时是被
违反的**。修法是收口到 `_mark_dirty()`（只收物品），`item_totals` 不动。
修完之后 sync 层不需要任何流体特例。**这是 05 的代码，改动也落在 05 的
文件里**，但它只有 sync 接上之后才看得见后果，因此记在这里。

### 2. 列表模型的锚点：**删除时必须当场记下它在第几行**

`end_batch` 里算「锚点原来在第几行」是错的——批次过程中 `remove()` 已经在
一张张地缩表，等批次结束再问，被删掉的锚点和其他已经消失的键一样无从定位，
只能退回顶部（表现为**滚动位置跳回列表开头**）。修法：`remove()` 在摘掉那
一行**之前**把行号记进 `_anchor_offset`，批次结束后 `_reanchor()` 再把锚点
重挂到一个**活着的**行上（否则列表变短时回退位置会持续前移）。
这条是手写用例逼出来的：`test_the_anchor_falls_back_to_its_old_row`
一开始就是红的。

### 3. `server/adapters/messages.py` 的 docstring 里有一条**实测为假**的理由

原文写「`tooldelta/__init__.py` 在模块级 `import mod.server.extraServerApi`」
——不是它。实测的失败链是 `tooldelta/__init__` → `events` →
`events/client/control.py` 上那条模块级的
`from mod.client.extraClientApi import ...`，撞上工具链装在 site-packages
里那份 `mod` 桩自身的循环导入。**结论不变**（事件类必须在函数体里建），
但依据换成了实测到的那条——一条编造的依据留在注释里，下一个人会照着它
去别处找原因。

### 4. 客户端的一次回调抛异常会让后面的回调收不到同一条消息

`receive` 原本是普通循环。包已经解析完、会话状态已更新、也已入队，此时中断
只让「一部分订阅者知道、另一部分不知道」，而那种不一致查起来毫无线索。
改成逐个回调各自接住并计入 `stats["handler_errors"]`（测试先红后绿）。
