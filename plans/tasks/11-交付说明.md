### 游戏内实测（MCDK）：2026-09-29 首轮

**方式**：真机（MCDK 启动的网易客户端），**不经过任何界面**。数据由
`execute_code` 从外部驱动：服务端那一半走**真的命令通道**
（`ServerBootstrap.submit_command` → `DeviceCommand`），客户端那一半在
客户端侧构造 `ClientEventPort` + `NetworkClient`，事件类挂在**真的 MC 总线**
上，消息真的过引擎派发。

**先铺内容**：存储驱动器（`NodeKey(dim=0, 22, 68, -7)`，gen 0）经真实命令
路径挂上介质（`{"action":"mount","slot":0,"model_id":"endernet:singleside_tape"}`
→ `ok`，`medium_id: medium:1`，`slot_version: 1`），再经真实命令路径写入
三种物品（stone / iron_ingot / gold_ingot）。

| # | 验的路径 | 实测到的 |
| --- | --- | --- |
| 1 | 开会话 + 快照 | `session_ready`（`index_version 5`、`item_view_version 1`、`epoch 1#1`、`network_id 1`）→ `snapshot_begin` → `snapshot_chunk`×1 → `snapshot_end`，共 4 条。模型替换后 **3 行**：gold 5 / iron 3 / stone 4，`total_quantity 12`，`model.version() == nc.item_view_version == 1`。**逐会话的资源描述表也量到了**：客户端 `describe_tables 1`、`descriptions 3`（三种资源各占一个序号），且 `bad_packets 0` —— 「首次发送带描述、之后只发序号」这条在真机上真的走通了 |

**一条反直觉但正确的观察**（第 1 条那张表之外的）：
`request_snapshot(from_version=2)` 在客户端**已经就是版本 2** 时**一条回包都
不产生**。这不是丢包——直接调 `subs.history_since()` 量到：
`history_since(2) == []`（空列表 ⇒ 「接得上」分支，零个批次要补）、
`history_since(1)` → 1 个批次、`history_since(0)` → `None`（⇒ 整份快照）。
**但接口上分不出这两者**：`request_snapshot` 没有回包也没有超时，调用方
无从区分「无事可发」与「包丢了」。11-03 接界面时要知道这一点。

**另一条实测到的行为**（属 05/13 的地界，本轮只是碰上）：经命令通道写入时
四次独立提交**每次最多搬 4 个**（请求 12→4、6→4、5→4；请求 3 个则整体成功），

`partial` + `container_partial`（「余量还在来源端」）。**本轮没有去查这个

**会话 TTL 也顺手量到了**：`registry.diagnostics()` 里
`expired: 1` —— 本轮之前那次实测开的会话，在两次工具调用之间被 600 帧的

### 离线验证能证明什么、不能证明什么

**能证明**：协议编解码与字段边界、会话校验的每一条判据（身份/维度/距离/
实例代次/epoch/主控）、快照冻结与版本推进的顺序、增量批的基准与分片、
断档重取的全部触发条件、订阅与历史的回收、长列表模型的排序/锚点/代次/
分页规则、以及接线把两侧真的接上了。

**不能证明**（这些全部要等 11-14）：

- **真实引擎的时序**：一帧内提交与发布的先后在真负载下是否仍然成立、

## 三、接口输入输出

### 协议：11 种消息（`common/protocol.py`，`SYNC_SCHEMA_VERSION = 1`）

方向 | 种类 | 用途
--- | --- | ---
C2S | `session_open` / `session_close` | 开会话 / 关会话
C2S | `snapshot_request` | 带 `from_version` 重取快照
C2S | `ack` | 推进发送窗口（`transfer_id` + 连续序号）
S2C | `session_ready` | **两个版本都在这里，且名字不同**
S2C | `snapshot_begin` / `snapshot_chunk` / `snapshot_end` | 快照冻结 + 分片
S2C | `item_delta` | 一个窗口 = 一次版本推进 = 1..N 个包
S2C | `resync_required` | 客户端必须丢弃缓存重取
S2C | `error` | **唯一**允许空会话字段的 S2C 消息

信封 `SyncEnvelope` 带 `session_id` / `network_id` / `epoch` / `view_kind`，
**路由字段不放消息体**：「每个 S2C 包都带会话与 epoch」因此是结构保证。
`VIEW_ORDER` 保留常量但**整块拒绝**：`SessionRegistry.check()` 按
`VIEW_KINDS_WITH_PRODUCER` 判、给 `Reason.UNSUPPORTED`（「还没做」），
与「发来一个不认识的种类」（协议错误）**理由不同**——两处测试钉着这条分界。

**两个版本绝不合流**：`index_version`（存储提交 / 交易期望）与
`item_view_version`（物品视图 / 界面发布）。线格式上**没有裸 `version` 字段**，
四个相关字段各自具名（`expected_index_version` / `item_view_version` /
`base_version` / `new_version`），有测试扫这一条。

### 服务端：`TerminalSyncHub`（`server/sync/terminal.py`）

```python
attach(port)                       # 组合根注入引擎边界
accepts(source)                    # 交给 MasterController 的 session_check 闭包
context_of(player_id, device_ref)  # 由 bootstrap 实现（查位置/维度/网络/epoch）

resync_network(network_id, code, detail)

```

**`accepts()` 在 `source.session_id` 为空时必须返回 `True`**——这是 05/08
既有命令的非回归要求，有专门用例钉着。

### 客户端：`NetworkClient`（`client/network_client.py`）

```python

close_session()                       # 无会话时返回 None 且不发包
request_snapshot(from_version)        # **没有缺省值**
```

**没有 `send_command`**（见第五节第 1 条）。客户端**自己定义一份**事件类
（`client/` 不允许 import `server/`），防漂移靠协议常量 + 跨边界离线测试。

两处方向上的不对称，都写进了 docstring 与用例：

- **`__id__` 只在 C2S 方向存在**（引擎附的发送者身份）。服务端必须在解析前
  摘掉它（`ENGINE_ADDED_FIELDS`）；S2C 方向引擎没有发送者身份可附，客户端
  **不摘任何字段**。真机上若这一侧也带了附加字段，症状是**每一条都判成坏包**
  （`stats["bad_packets"]`），测试钉的是「拒收并计数」而不是悄悄容忍。
- **收件人**：服务端 `send(player_id, payload)` 要判有没有收件人；客户端
  `send(payload)` **没有收件人参数**（对端恒为服务端）。两侧都只收**已经
  编码好的**字典——编码要逐会话的资源描述表，只有 hub 拿得到。

### 诊断（实机排障的入口）

- `ServerBootstrap.diagnostics()["sync"]`：hub 的 `stats` / `frame` /
  `networks{会话数、发布版本、历史条数、快照数}` / `rotation`；
- `NetworkClient.diagnostics()`：会话身份、**两个版本各自具名**、待处理包数、
  `stats`（`requests / received / bad_packets / dropped / handler_errors /
  sessions_opened / sessions_closed`）；
- `ClientEventPort.diagnostics()`：`stats` + 两个频道名 + **是否在监听**；
  `AdapterSyncPort.diagnostics()`：只有 `stats` + 两个频道名——**没有
  「是否在监听」这一项**。服务端把监听器记在 `ServerEventBinder` 上
  （`listen` 走 `binder.register`），要看有没有挂上/摘干净，那里有
  `unregistered` 与 `unregister_failures` 两个计数器。

**计数器与键名是契约的一部分**：实机上排障要按名字去查，少一个键不会报错，
只会让人以为「没有这件事发生」。两侧各有用例钉住键的集合。

## 四、适用存档版本与持久化

**11 不写任何权威存档数据。** 会话、订阅、订阅者快照缓存、增量历史全在
**内存**里，进程重启后为空——与 05/09/10 的处境一致（09 的等待台账、
10 的索引同样只在内存里）。

对 12 的交接点：要恢复的是「谁在看什么」这一份**易失**状态，而**没有任何
一方需要它**——会话本来就是瞬时的（玩家关了界面、走远了、离线了就没了），
重连之后重新开会话即可，代价只是一次快照重发。因此**不建议**把会话或
订阅写进存档：那会引入「存档里的会话 id 在新进程里指向谁」这种没有答案的
问题。真正要进存档的是库存与版本（05），而本轮的 `index_version` /
`item_view_version` 都是**从 05 的 `publish_version` 推出来的**，不额外记账。

## 七、开发过程中撞到并修好的问题

### 1. 纯流体提交会推进物品视图版本（**05 的行为缺陷**）

`_apply_contribution` / `_set_reserved` / `_reindex_keys` 三处都无条件
`dirty_items.add(key)`，而它们遍历的 `stored_view()` **含流体**。于是
「往网络里倒一桶水」会让物品视图版本前进、给每个终端发一批空增量。
11.md 第 117 行明写「物品视图版本不因流体单独变化而推进」，**这条当时是被
违反的**。修法是收口到 `_mark_dirty()`（只收物品），`item_totals` 不动。
修完之后 sync 层不需要任何流体特例。**这是 05 的代码，改动也落在 05 的
文件里**，但它只有 sync 接上之后才看得见后果，因此记在这里。

### 2. 列表模型的锚点：**删除时必须当场记下它在第几行**

`end_batch` 里算「锚点原来在第几行」是错的——批次过程中 `remove()` 已经在
一张张地缩表，等批次结束再问，被删掉的锚点和其他已经消失的键一样无从定位，
只能退回顶部（表现为**滚动位置跳回列表开头**）。修法：`remove()` 在摘掉那
一行**之前**把行号记进 `_anchor_offset`，批次结束后 `_reanchor()` 再把锚点
重挂到一个**活着的**行上（否则列表变短时回退位置会持续前移）。
这条是手写用例逼出来的：`test_the_anchor_falls_back_to_its_old_row`
一开始就是红的。

### 3. `server/adapters/messages.py` 的 docstring 里有一条**实测为假**的理由

原文写「`tooldelta/__init__.py` 在模块级 `import mod.server.extraServerApi`」
——不是它。实测的失败链是 `tooldelta/__init__` → `events` →
`events/client/control.py` 上那条模块级的
`from mod.client.extraClientApi import ...`，撞上工具链装在 site-packages
里那份 `mod` 桩自身的循环导入。**结论不变**（事件类必须在函数体里建），
但依据换成了实测到的那条——一条编造的依据留在注释里，下一个人会照着它
去别处找原因。

### 4. 客户端的一次回调抛异常会让后面的回调收不到同一条消息

`receive` 原本是普通循环。包已经解析完、会话状态已更新、也已入队，此时中断
只让「一部分订阅者知道、另一部分不知道」，而那种不一致查起来毫无线索。
改成逐个回调各自接住并计入 `stats["handler_errors"]`（测试先红后绿）。

### 5. **每个端口各建一对事件类 → 同一条消息被投递多次**（2026-09-29 实测）

**这是本轮找到的、唯一一个只有在真机上才看得见的缺陷**，也是把「离线全绿」
与「真机可用」分开的那类问题。

**症状**：每 `listen()` 一个新端口，同一条 S2C 消息就多被处理一次——第 2 个
端口收到 2 份、第 3 个 3 份、第 4 个 4 份（真机逐个数出来的）。而且**只有
最后注册的那个端口收得到**，先前仍在监听中的端口一条都收不到。

**机理**（读 `tooldelta/events/event_bus/event_bus.py`，vendored 上游，未改）：

1. `_dyn_listen` 以**事件类对象本身**为字典键判重（`event_listeners[priority][event]`），
   每新建一个类就多走一次 `_add_sys_event_listener`；
2. `_add_sys_event_listener` 用 `tdevent_handler_<模块>.<类名><优先级>` 这个名字
   把处理器 `setattr` 到 system 上——**同类名即同名**，`setattr` 只留得下
   最后一份；
3. `_dyn_unlisten` **从不调 `UnListenForEvent`**，引擎侧的注册只增不减。

于是「每个端口各建一份类」= 多出来的投递只落到**最后**那份被 `setattr` 上去
的处理器上，**先前仍在监听的端口再也收不到**。

**实测到的是投递次数与收件人**（同一个 `session_id` 的每一条都到齐了 N 份，
且 `port.stats["received"] == client.stats["received"]`，说明不是总线重复调用
而是真的多了一次派发）。**「同一批增量被应用两次 → 基准版本比对判成断档 →
白重取一份快照」是据此推出的后果，本轮没有把它单独跑出来**——因为修复在
界面接上之前就落了地，那个下游症状还没有可以发作的地方。

**为什么离线用例看不见**：`test_sync_channels.py` 的 `FakeBus` 用的是普通
`list` 追加，没有「以类对象判重」这一步。因此这个缺陷在离线侧**结构性地
不可见**。补法是让 `FakeBus.ListenEvent` **照抄 `_dyn_listen` 的去重语义**
（同一个类只记一次注册），新用例
`TestEventClassesAreSharedPerProcess` 才咬得住。

**修法**：`shared_event_classes(events_module)` —— 进程内的
`events 模块 → (C2S, S2C)` 缓存，`port.classes()` 一律走它
（`client/network_client.py`；`server/adapters/messages.py` 是同一构造）。
`build_event_classes()` 保持纯函数，离线测试照旧直接调它核对类定义。
两张缓存是分开的：客户端与服务端造出的类方向相反，**不能共用一张**。

**实测结论**（真机）：

- 修复后三个端口的 `classes()` 返回**同一个对象**；
- 两个各自带独立回调的在监听端口，各收到**恰好 4 条**，无重复；
- 回归守卫**确认会咬**：把「每个端口各建一份」的旧写法用 monkeypatch 装回去，
  3 条用例立刻变红（`3 != 1`、`2 != 1`、类对象不相同）。

**边界，别读过头**：

- **客户端侧是实测的，服务端侧不是。** 本轮进程里只有一个服务端装配实例，
  量不到重复，服务端那半边记的是**「按客户端实测结论推广」**——同行注释
  里也是这么写的，不要读成「服务端已实测」。
- 生产客户端目前**根本没有** `NetworkClient`（`client/bootstrap.py` 写明了
  「显示缓存与订阅（任务 11）。当前为空是刻意的」），因此这个缺陷在本轮
  之前是**潜伏的**：它要等 11-03 把界面接上才会真的发作。
- **反过来说**：同一时刻两个端口各注册**自己的**回调是**正常**的、应当各收
  一份（实测过）。缺陷是「拿不到同一份类」，不是「多个订阅者」。

### 1. 命令通道定稿（决策 D1）

`common/protocol.py` 新增两个 kind：

| kind | 方向 | 消息类 |
| --- | --- | --- |
| `command` | C2S | `TerminalCommand` |
| `command_result` | S2C | `CommandResultMessage` |

`TerminalCommand` 的字段是 `request_id` / `expected_index_version` / `action` /
`key` / `count` / `slot` / `slot_version` / `into_slot`。**全部无条件序列化、
缺席写 `None`**：`_require_fields` 既拒缺项也拒多项，因此可选字段必须总是
出现——这同时让「客户端多塞一个字段」变成硬错误而不是被静默吞掉。它带一个
`payload()`，返回**恰好**是 `StorageService.handle` 会读的那个字典；字段名
映射只此一处，服务端 hub 不碰字段名。

**三个刻意不加的字段**（这是与 11.md 第 46 行字面读法的差异）：

- **无 `player`**：身份只有引擎附的 `__id__` 一个起点，服务端从 `session.player_id` 取。
- **无 `device_ref` / `target`**：目标就是 `session.device_ref`，`_check_target`
  每请求已经验过一次。再带一份就是第二个真相源，且给伪造留口子。
- **无 `cursor`**：`_cursor_refusal` 只在 `payload.get("cursor")` 为真时才拒。
  **不发 = 没有这只手**，不等于客户端声称「手上没东西」。这是「缺席」而不是
  「定案」——R12 定稿时才决定要不要有它。

`CommandResultMessage` 只带 `request_id` + `result`（`CommandResult.to_dict()`
原样字典）。协议层只验形状，**不重建领域对象**：`CommandResult` 与
`TransferReceipt` 都没有 `from_dict`，回执是给界面看的展示数据。

### 6. 点击的约定：**这是本轮定的默认，不是已定案的玩法**

计划没有说「点一行发哪个动作」，这是一个必须补的空白。第一版实现取的是
「全部可用数」，**User 在 2026-09-29 改为「取一组」，代码随后照此改定**：

> **一行点击 = 一条 `inv_put`（网络 → 背包），数量取该行的一组：
> `min(可用数, maxStackSize)`，可用数 = `stored - reserved`。**
> 可用数不足一组时**能拿多少拿多少**；可用数为 0 时不发命令，只选中。

理由只有两条，都不是玩法依据：界面上**没有任何输入数量的控件**，所以
「取一个」与「取一组」都需要先有一个约定；而 `inv_put` 的方向正是玩家对
「从终端列表里拿东西」的预期，且可逆。改取「一组」是因为**一次点击把网络里
这一种抽干**与玩家在物品栏里点击一个槽位的手感不符，也更容易被误触。
**可用数为 0 时不发命令，只选中**——`inv_put` 的 `count` 必须为正，发一个 0
只会换来一条「参数越界」回执，而玩家什么也没做错。

`maxStackSize` 取自 `Item(item_id).GetBasicInfo()`，按资源名缓存
（`TerminalListView._basic_info`，与 `id_aux` 同一次调用）。**引擎给不出合法
上限时退成 1，不是退成可用数**：退成可用数正好会让「取一组」变成它要避开的
那件事，退成 1 最多是少拿。这条退化方向有三个离线用例钉着
（`test_an_unusable_stack_size_falls_back_to_one` 等）。

**不做点击抑制**：连点两次就是两条命令。防抖/连击合并属 R12，本轮不发明；
服务端的去重账本管的是「同一条请求被重发」，不是两次独立点击。

R12 定稿后若改成按住取半、右键取一个，改的就是这一条——它仍是**本轮定的
默认**，User 2026-09-29 已选此口径，但不随本轮变成定案玩法。

## 十一、下半屏改为集合绑定驱动（2026-09-30）

**这一节取代第十节第 3 条里关于 `CustomSlotView` 的全部内容**，也改了第十节里
「界面 JSON 一个字没动」那句话的现状。第十节原文一处未删，均已就地加注。

User 的指令（原话）：

> 尽可能使用绑定（`@Binder.binding`）操作表格元素，不要直接通过 UI 路径操作

这是**对第十节那套实现的当场否决**，不是新增需求。第十节交付时下半屏走的是
`grid.GetGridItem(x, y)` 逐格取控件、缓存子控件引用（`CustomSlotView`）、再用
`SetVisible` / `SetUiItem` / `SetText` 主动重画。本轮把这套整体删除。

### 1. 为什么控件路径这条路**根本走不通**

不是「不优雅」，是**错的**：

1. **格子要到渲染时才存在。** grid 的格子由渲染器在渲染阶段生成，
   `GetGridItem` / `GetChildrenName` 在界面渲染之前返回空。第十节交付时在真机上
   观察到的 `ValueError: Can't initialize UBaseCtrl: comp is None` 就是这个——
   `OnCreate` 第一步就抛，**整块界面建不起来**。那不是环境问题，是按路径取格子的
   必然结果。
2. **格子会被回收换出。** grid 与 `scroll_view` 同用时，引擎会把没有渲染必要的格子
   剔除缓存、需要时再放回「子节点列表」，**放回时不一定在原位置**。缓存下来的子控件
   引用因此在换出之后就是过期的：写进去的值不报错、也不显示，落在已经被回收的那个
   对象上。这一条对**滚动容器里**的 grid 成立（上半屏那个物品列表就在滚动容器里）；
   下半屏这两个 grid 是固定 9×3 / 9×1、不进滚动容器，所以真正咬人的是第 1 条。
3. **ModSDK 的网格文档自己就是这么写的**：「grid 控件不建议使用其子控件路径对其
   动态生成的格子控件直接进行 SetVisible 等操作……如果有需要对格子进行操作，可以
   使用数据绑定的方式」。

因此本轮的目标不是「改用绑定」，而是**让脚本侧一格控件都不持有**。

### 2. 脚本侧：`terminal_panel.py`

**删除**：`CustomSlotView` 整个类、`INVENTORY_PATH`、`_views` 字典、`_refresh()`、
`_paint_selection()` / `_painted_selection`（那对「上一帧画了什么」的影子状态是
主动重画路线的必需品，没有重画就没有第二个真相源）。

**新增**（`TerminalPanelBase`）：

```python
SEGMENTS = (
    (BACKPACK_COLLECTION, "backpack", 0, BACKPACK_COUNT),
    (HOTBAR_COLLECTION,   "hotbar",   HOTBAR_START, HOTBAR_COUNT),
)
SLOT_FIELDS = ("visible", "item_id_aux", "selected", "item_count")

def slot_binding(prefix, suffix):
    return BINDING_PREFIX + prefix + "_" + suffix      # #EnderNetTerminal.backpack_selected
```

- `_bind_slots()`：两段各注册**四个** `DynaBindingCollection`，共 8 条。回调是
  `_slot_reader(callback, segment)` 产出的闭包，**用默认参数捕获段信息**——py2 没有
  `nonlocal`，循环里的闭包会一起指向最后一段；这个坑离线用例钉得住
  （`TestBackpackCellBindings`），真机上则表现为**快捷栏那 9 格按背包的下标去读**，
  界面照常渲染、不报任何错。
- `_slot_index(segment, index)`：**唯一**的下标入口，越界／`bool`（`isinstance(True, int)`
  为真）／非整数一律返回 `None`，四个读值回调全部先过它。集合回调的下标是外部输入，
  「不可能越界」只是我们对引擎行为的假设。
- `_slot_visible` **恒返回 True**：模板把根控件的 `#visible` 挂在这个绑定上，而空格子
  仍然要画出槽底（槽底是它的子控件 `bg`）。**空是用 `#item_id_aux == 0` 表达的，
  不是靠隐藏**——空槽若被隐藏，36 格的底图会缺一块。
  ModSDK 的网格文档还有一句：**「在数据绑定的回调函数中需要明确 grid 本身是否可见，
  否则会造成 grid 子节点控件的可见性数据异常」**。本轮**没有**照做——恒真就是恒真。
  依据是当前没有任何代码去隐藏 `/inventory` 这个面板（整块的显隐由界面的开关承担），
  但这一条是**推断、不是实测**，因此在待验清单里与「画不画得出来」一起看。
- `_unbind_slots()`：逐个 `DynaUnbindingCollection(flag, collection)`，销毁时调用。
  框架在 `OnDestroy()` 之前本就会清全部动态绑定，所以这是**幂等**的；显式写出来的
  理由是「销毁了什么」应当在代码里看得见，而不是靠读者知道框架替我们做了。

**`_poll_backpack()` 的语义变了**：它仍然按 `BACKPACK_POLL_FRAMES = 12` 分频重读
引擎，但**重读之后不通知任何人**——没有重画代码了。引擎在下一渲染帧自己来取新值。

## 十二、绑定必须写在类体里（2026-09-30，**游戏内实测通过**）

第十一节的改动上线后，打开终端面板报：

```
[ERROR][Engine] Exception exceptions.AttributeError raised.
Value: 'CommonTerminalPanel_Base' object has no attribute 'reader'
```

本节是它的真因、改法与实测结果。**这一节与前面各节的性质不同：它有游戏内实测。**

### 1. 真因：运行时注册的绑定在这个引擎上**根本不生效**

链路是从引擎源码 + 运行期反汇编读出来的，不是推断：

- `ScreenBase.process_binding(screen_name)` 遍历 `dir(self)`，对带 `collection_name` 的
  属性走 `_process_collection`、带 `binding_flags` 的走 `_process_default`，两者最后都调
  `gui.bind_*_handler(screen_name, [collection_name,] name, self, func)`。
- **C++ 侧存的是回调函数的 `__name__`（一个字符串）**，渲染时按这个名字到**界面实例**上
  `getattr` 取回调。
- tooldelta 的 `_get_tdscreen_bindings()` 把类体里的绑定连名带壳塞进生成的
  `type(cls.__name__ + "_Base", (ScreenNode,), attrs)`，并把包装器的 `__name__` 设成
  `key`（默认绑定）或 `key + "_bindwrapper"`（集合绑定）——`getattr` 因此找得到。
- 运行时那条路（`DynaBinding` / `DynaBindingCollection`）**不经过 `_Base`**：它的包装器
  `__name__` 取自 `getattr(binding_func, "__name__", "dyna_binding")`，而它本意想用的
  `func_name` 兜底（`str(binding_name).strip("#%").replace(".", "_")`）是**死代码**——
  py2 下 `hasattr(func, "func_name")` 恒真。

于是引擎 `getattr(instance, "reader")` → `AttributeError`，**每渲染一帧一条**，格子全空。
第十一节把下半屏从「控件路径」换成了「集合绑定」，但用的仍是**运行时注册**那条路，
所以换完照样炸——只是炸的名字从 `comp is None` 变成了 `reader`。

### 2. 改法：18 条绑定搬进类体

`terminal_panel.py` 的绑定全部改写为类体上的 `@Binder.binding` /
`@Binder.binding_collection`，共 **21 条**（10 条列表 + 8 条格子 + 3 条点击）。
`_bind_slots` / `_unbind_slots` / `_slot_reader` / `_slot_flags` 与
`TerminalListView._bind` / `_bindings` / `_collection_flags` **全部删除**。

两条绕不开的后果：

- **静态绑定在类注册时就生效，不能按会话摘除**，引擎在没有会话时照样来问。所以每条
  列表回调都先看 `self.list_view is None` 并返回**安全值**（`0` / `False` / 空串）；
  命令行上的安全值是「空」而不是「假装有一行」。
- 因此 `list_view` 必须有**类属性**兜底（`TerminalPanelBase.list_view = None`）——
  绑定的解析早于 `OnCreate`，实例属性来不及。
  `TerminalListView.close()` 相应地不再「摘绑定」，只置 `closed` 并注销收包。

八条格子绑定每条只有四行：转手调 `_slot_*(段, 下标)`，段常量写死在各自的方法里

### 11. 修 F2：会话被判死时界面卡住（2026-09-30）

**这是第 9 小节那次接线引出的复核发现**，不是新功能。

**症状**：服务端判死会话（会话不存在／被别人抢／距离、维度或设备复核不过）
时**只回一条 `error`，不回执**。而客户端的 `receive()` **没有任何人处理
`MSG_ERROR`**——错误被安静地解出来、入队，然后没有人看。后果是三重的：

1. 客户端仍以为自己有会话 → 遮罩不出 → 界面看起来完全正常；
2. `_action_request` 永远等不到回执 → 在途动作悬着；
3. 背包选中也悬着 → 点别的背包槽只会**再发一条没有下文的命令**（`_click`
   见有选中就走交换，根本不改选中），点终端行又因为选中还在而发 `inv_take`。
   玩家看到的是「点什么都没反应」。

**根因是缺一条链路，不是某处写错。** 修法分三层：

| 层 | 改动 |
| --- | --- |
| 服务端 `sync/terminal.py` | `_error` 的 `session_id`：**会话已死传空**，会话还活着传真实 id |
| 客户端 `network_client.py` | 新增 `_absorb_error`：空会话字段 ⇒ `drop_session()`；会话还在 ⇒ 给这次请求补一个结局 |
| 面板 `ui/terminal_panel.py` | 新增 `_settle_lost_session()`，每帧按「会话还在不在」收尾在途动作与选中 |

**三个判断值得记下来：**

1. **判据做成结构性的，不让客户端列原因码表。** 最省事的写法是给客户端一份
   「哪些 `Reason` 算会话级」的清单——但那份表一旦与服务端漂移，坏法正是
   这一类「界面看起来正常、点什么都没反应」，最难查。改成由**服务端**用
   `session_id` 空不空表达，客户端只读一个二元信号。与
   `network_client.py` 里拒绝在校验动作名时给的理由是同一条纪律。
2. **不能一律「收到 error 就丢会话」。** `_error` 的调用点里有两处
   （`service` 执行命令抛异常、返回非 `CommandResult`）**会话还活着**，丢它
   等于「服务端一次内部错误 = 玩家界面掉线」，比要修的毛病更糟。所以两条路
   分开：判死那条丢会话，活着那条只给这次请求补结局。
3. **那条「活着的」路也必须收尾。** 它同样不会有回执，同样会把界面卡住。
   `NetworkClient` 因此把 `error` 翻译成回执的形状塞进 `_results`
   （`_CommandOutcome`），界面只写一条收尾路径（`_settle_action`）——
   分两支的代价是迟早有一支忘了清选中，而表现是「选中框赖着不走」。
   **只补在途表里有的 id**，凭空冒出来的不进队列（否则界面会拿别人的拒绝
   去清自己的选中）。

**顺带修掉一处我上一轮写错的注释**：`_action_request` 的说明原先写着「连点
两下『不是缺陷』——两条命令清的是同一份选中」。**那句是错的**：回执比对只认
`request_id`，不认选中身份，而选中可以在在途窗口里被取消再重建。已改写为
如实记录这个已知坏法（见下）。

**顺带堵住一条本次改动引入的可达异常**：会话丢掉之后界面仍开着，遮罩虽然
会出，但**它拦不拦得住输入没有实测过**（`plans/ui/common_terminal_panel.md`
第 3 节列为待验）。真放进来时，点终端行会走到 `send_command` →
`_require_session` **抛 `ValueError`**，而这是 UI 回调，异常会冒到引擎的派发
里、每次点击报一条。已在 `on_select` 开头加「没有会话就什么都不做」。
（`_send_take` 那一支本来就不会炸——`inventory_slots` 随会话一起清空，
拿不到快照就等待同步——但拦在入口比让两条路各靠一个偶然成立的条件安全。）

**验证**：完整门禁 **2489 项通过，80 个文件通过 Python 2.7 语法门禁**。

### 12. 修 C2S 的 `key` 线上形状：背包命令一直发不出去（2026-09-30）

**真机报的错**（引擎日志）：

```
TypeError: can not serialize 'ResourceKey' object
```

**根因**：`TerminalCommand.to_dict()` 把 `key` **原样写进消息**，而客户端一路
传下去的是 `ResourceKey` **实例**：

```
BackpackEntry.key（ResourceKey）
  → TerminalListView._send_take / on_select / on_backpack_exchange
  → NetworkClient.send_command(key=...)
  → TerminalCommand(key=key)          # 原样存
  → to_dict()["key"] = <ResourceKey>  # 原样写 ← 这里
  → 引擎 msgpack 编码 → 炸
```

**这不是「某处手滑」，是契约没写下来。** `TerminalCommand.key` 的线上形状
是**字典**，三处证据都指向这一点：`from_dict` 原样转交（因此服务端持有的
是字典）、`payload()` 原样转给 `StorageService`（后者的 `_key_from` 只认
`dict`）、以及既有测试都拿 `stone.to_dict()` 构造它。但**没有任何一处把
这条契约说出来**，也没有任何检查拦它——于是客户端塞了个领域对象进去，一直
到发包那一刻才炸。

**为什么离线全绿、门禁一条都没红**：协议层的形状检查量的是「键在不在」
「值是不是文本/整数」，而 `key` 这两样都不查。而「传出去的东西编不编得动」
**从来没有人测过**。

**修法（三处）**：

| 位置 | 改动 |
| --- | --- |
| `client/network_client.py::send_command` | `key.to_dict() if key is not None else None`——转换落在领域对象进入线上层的那一个边界上 |
| `common/protocol.py::TerminalCommand.__init__` | `DEBUG` 下拒掉非字典的 `key`：**这类错必须在离线就炸**（`settings.DEBUG` 默认为真，门禁能拦住） |
| `common/protocol.py::TerminalCommand` 文档 | 把契约写下来：`key` 是线上形状的字典，不是 `ResourceKey` |

**回归（两条，都直接盯编码器）**：

- `test_sync_channels::test_the_whole_body_is_msgpack_encodable`：拿 msgpack

  `key` 一个字段是不够的——将来任何一种「塞了个对象进去」都要在这里被拦下。

  走**真实面板路径**（点击 → `send_command` → 线上字典），把「面板传进去的
  到底是什么」一起钉住；只测 `send_command` 的话，上面再包一层又塞个对象就漏了。

### 13. 虚拟背包空间：多轮操作与「真实背包 → 虚拟空间 → UI」（2026-09-30）

User 的口径：**客户端建一个虚拟背包空间，允许在服务端回执前进行多轮操作；
服务端一回执，立刻遍历一遍真实背包做完整更新**；数据流即
**真实背包 → 虚拟背包空间 → UI 显示**。

**它替换掉了第 9 小节那套「一次一个预测 + 预测在途时挡住连点」**——那套是为
「一次只走一格」写的，多轮一进来就不成立了。现在的模型简单得多：

```
引擎读数 ──→ _base（真值）
               │  _replay（按序重放）
_slots ←───────┘  + _pending（还没被真值兑现的本地操作）
  ↑
  └── 界面只读它（entry()）
```

| 概念 | 落点 | 说明 |
| --- | --- | --- |
| 真值 | `_base` | 上一次引擎读数 |
| 待兑现的本地操作 | `_pending` | `_PendingOp`，**按发生顺序**；每条记着它动手前后那两格的样子 |
| 虚拟空间 | `_slots` | UI 唯一读的东西；`_replay()` 是它唯一的写入口 |

**四个判断值得记下来：**

1. **退场看真值，不看回执。** 回执到达只是去**重读一次**真实背包的信号；一条
   本地操作要等 `_base` 里那两格真的变成它的结果才退（`_retire`）。差别在时序上
   看得见：**回执往往比引擎读数先到**，按回执退会让画面先跳回操作前的样子、再
   跳过来。
2. **退场只从队首、按序。** 服务端也是按序执行这些命令的，真值只会沿队列从头
   兑现。中间某一环没兑现，后面就算「看起来对上了」也不退——那多半是巧合。
3. **真值走到别处就丢弃该操作，不硬撑。** 两格既不是操作前、也不是操作后，说明
   有别的途径动过它；硬撑着预测会把那些改动从画面上抹掉，而玩家会据此继续操作。
   **这个取舍比「闪一下」重要得多。**
4. **本地改过的槽发 `slot_version=None`，并且跳过源槽的快照指纹核对。** 这两样
   是同一条道理：那几格相对服务端的真实状态就是虚拟空间里的预测值，而**快照是
   服务端还没走到那一步时的样子**——对不上是应该的。逐条命令按序执行，轮到它时
   服务端那两格正好长成虚拟空间现在这样，所以发虚拟空间里的 key 才是对的。
   `None` 是 `SlotAnchor` 有意留的「不校验版本」（这正是 S-15 之前的那条路，
   这里是**有理由地退回去**：多轮操作下版本客户端确实算不出来）。**没改过的槽
   照旧核对指纹、发真实版本。**

**实现时撞到并修掉的两个坑**（都留下了回归）：

- **快照核对把第二轮挡死了**。第一版照旧拿 `client.inventory_slots` 核对源槽
  指纹——而那一格在第一轮之后就已经和快照不同了，于是第二条命令**静默不发**。
  现象是「点第二下没反应」，离线用例当场抓到（`test_a_second_round_is_allowed_before_the_receipt`）。
- **退场逐格退会得到一个不存在的画面**。第一版按格退场，结果可能出现「一格的
  预测 + 一格的旧真值」——那个组合在世界上从来没有存在过。改成「一格被证伪就
  **整份**撤」。

**顺带改掉的**：在途命令从单值 `_action_request` 改成集合 `_action_requests`
（多轮意味着同时有几条在途）；交换/合并在发送时就清选中（画面已经变完了，留一个
指向源槽的高亮会让玩家以为还能接着点）——**取放那条「发送即清是不行的」原样保留**，
它没有虚拟空间，仍然要等回执区分成败。

**验证**：完整门禁 **2507 项通过，80 个文件通过 Python 2.7 语法门禁**。新增 16 条
（模型 13、面板 3），覆盖：本地交换/合并立刻生效、真值一点没动、多轮按序叠加、
**回执先到时不闪回**、**真值沿队列从头兑现（第一轮退场不抹掉第二轮）**、
被证伪则整份丢弃、失败只撤那一条、别人的 `request_id` 撤不动、会话丢掉清空、
取放不进虚拟空间、`snapshot()` 报画面而 `truth()` 报真值、多轮两条都在途、
本地改过的槽不发版本而没改过的照旧发、回执到达时重读真实背包。

**未验证**：

1. **游戏内零验证**，同本文件其余各节。尤其没验过的是：**真实引擎读数的到达
   节奏**（决定退场快慢），以及多轮操作下服务端是否真的按序执行。
2. 上面第 4 条那条「`slot_version` 回退到 None」**与 S-15 的方向相反**，是有理由的
   例外（多轮下版本不可知），但**没有在真机上确认过它不会引入 D-06 那类问题**。

### 14. 修 F1：迟到的回执抹掉玩家新建立的选中（2026-09-30）

**症状**：`_settle_action` 清的是「**收到回执那一刻**的选中」，而不是「发命令时
的那个选中」。玩家在在途窗口里取消选中、又选中别的格子之后，那条迟到的回执会
把**新选中**一并抹掉。后果不是「高亮没了」这么轻——**下一次点终端行会落到
`inv_put`（网络 → 背包），方向与玩家的意图相反**。

**修法：给选中态记一个修订号。** `BackpackModel` 新增 `_selection_revision`，
**每一次真的改变选中就 +1**（`_set_selected` 是唯一的写入口）；面板在发命令时把
它连同 `request_id` 一起记下（`_action_requests` 因此从集合变成
`{request_id: 修订号}`），回执回来时**修订号没变才清选中**。

**为什么不能拿槽号去比**：玩家「取消选中 → **又选中同一格**」之后，槽号与发
命令时**一模一样**，而那是两次不同的意图。比槽号正好在这最刁的一种上失灵——
两条回归用例都是照着这个情形写的，而把守卫临时失效之后它们**确实会失败**（验过）。

**必须「值没变就不记」**：否则关界面那一下无谓的 `clear_selection()` 会把别人的
回执判成「玩家动过选中」，该清的就不清了。这一条也有用例钉着。

**两条路径都覆盖**：取放（`inv_take`）本来就靠回执清选中，是 F1 的原始现场；
交换/合并没有这个问题（它们在**发送时**就清了），但回执同样不该再清一次玩家
后来的选中——所以修订号也照记。

**验证**：完整门禁 **2511 项通过，80 个文件通过 Python 2.7 语法门禁**。新增 4 条：
修订号只在真变时移动、「取消又选回同一格」算两次变化、迟到的取放回执不抹新选中、
迟到的交换回执不抹新选中。

**未验证**：游戏内零验证，同本文件其余各节。

## 十四、整槽存入的手势与搬运动画（2026-10-01）

### 1. 手势：点背包槽 → 点列表空白处 = 整槽存进网络

**这一条是 User 2026-10-01 定的**，本文只记录，不代它决定任何别的入口。
点上方网络列表里**没有格子**的地方（含空格子），把当前选中的背包槽**整槽**
存进网络。

它与既有的两条是并列的第三条：

| 这一下点的东西 | 发的命令 | 数量 |
| --- | --- | --- |
| 终端行（有格子的地方） | `inv_take` | **一组** = `min(该槽数量, maxStackSize)` |
| 另一个背包槽 | `inv_merge` / `inv_swap` | 合并封在目标剩余空间内 / 交换不带数量 |
| **列表空白处** | **`inv_quick_move`**（`target="network"`） | **整槽** |

「没有选中时什么也不做」是刻意的：空白处这一下**没有目标**，借一个默认值
（挑最近的、挑第一格）等于替玩家选了一格，而他没选过。

### 2. 用 `inv_quick_move`，不自己造一条「整槽的 inv_take」

服务端那侧 `inv_quick_move` 的定义就是「把某个槽整槽搬走，方向由 `target`
决定」。另写一条「数量等于整槽的 `inv_take`」在协议上更省事，但它会让
「整槽」这个语义在两侧各有一份定义，而**两份定义分家的表现是网络里多出或
少掉一槽东西，界面上两种点击看起来都成功了**。

核账与 `inv_take` **完全同一套**，因此没有为「整槽」放松任何一道关：
发之前重读那一格（`BackpackModel.pending_take(whole=True)`，与取一组共用
同一处——那几道核对才是要紧的，分成两份迟早有一份忘了重读）、对服务端快照
核指纹与槽版本、核对不过是**等待同步**而不是换个法子把命令发出去。
回执走**同一条**收尾（`_settle_action` 不按动作分家），成功或被拒都清选中。

「尽可能多」由服务端裁：网络装不下的部分回 `PARTIAL`。客户端**不预先截断**
——截断要读网络余量，而那是客户端看不到的东西。

### 3. 搬运动画：脚本逐帧推，按秒不按帧

`content.flying_item` 是一个 `inventory_item_renderer`（`visible=false`），
脚本在搬运时把它摆到源槽、逐帧推向目标槽、**先快后慢**
（`1 - (1-t)^2`）。**不用引擎的 UI 属性动画**（`RegisterUIAnimations` /
`SetAnimation`）：那套要在数据里写死 `from`/`to`，而这里每一次搬运的起终点
都随玩家点的那一下变。

**时长（`FLY_SECONDS`）是手感值，只由观感决定。** 初值 0.5 秒；
2026-10-01 游戏内试过之后按 User 的要求**调快 4 倍**（0.125 秒）。它不进任何
判定，改它只会让用例里的折算跟着走（用例一律拿 `FLY_SECONDS` 折算，不写死
秒数）。

**按秒不按帧**：界面渲染帧率与脚本 tick、模拟 tick 都不是一回事，按帧数
计时会让同一段时长在低帧率下拖长一截。时钟是**注入**的
（`FlyingItemAnimator(..., now=time.time)`），离线用例给个假时钟就能精确
推进——有一条用例专门钉「分 5 帧走 0.25 秒与一步走到底，末帧位置逐位相同」。

**落点**：

| 搬运 | 源 | 目标 |
| --- | --- | --- |
| 背包内交换／合并 | 源槽（精确到格子） | 目标槽（精确到格子） |
| 背包 → 网络 | 背包槽 | **该物品在网络里的那一行**；它还没有行时落到列表区中心 |
| 网络 → 背包 | 该物品在网络里的那一行 | **背包那一半的整块区域** |

「网络 → 背包」落到整块区域而不是某个格子，是因为服务端把东西放进**第一个
装得下的格子**，客户端看不到是哪一格。挑一个「看起来对」的格子飞过去，
是在画一件客户端并不知道的事。

**只在命令真的发出去之后才画**：那几处「等待同步」的 `return` 画面上不动
（同 `on_backpack_exchange` 里那条纪律）。动画不参与任何判定，也不表示服务端
接受了那条命令。

### 4. 空白处那一下是**隐形按钮**，不是空格子的副作用

`common.scrolling_panel` 的 `background` 覆盖整个列表区，格子画在它上层，
而**空格子的整格不可见**——于是有格子的地方归格子、没格子的地方落到背景。
背景换成了一个专用模板 `common_terminal_panel_ui.terminal_scroll_background`
（继承 `endernet_ui_common.simple_invisible_button`，只覆盖
`$pressed_button_name=#EnderNetTerminal.quick_store`）。

**名字只能写在专用模板里**：原版模板实例化 `background@$scroll_background_image_control`
时**不接受任何外部变量**，共享模板自己那个默认名（`%netease_editor_template_namespace.click`）
改不动，落在它上面就等于点了个查不到绑定的按钮——**引擎安静地什么都不做**。
这一条有 JSON 契约用例钉着。

### 5. 新增两个客户端模块

| 文件 | 职责 |
| --- | --- |
| `client/ui/flying_item.py` | 动画本身：缓动、按秒计时、控件解析与收尾。**不认识本界面**——控件路径由构造参数给 |
| `client/ui/slot_layout.py` | 槽位**全局矩形**：路径集中在这里（`terminal_panel.SCROLL_PATH` 也从这里导出），并负责 `scroll_mouse` / `scroll_touch` 那条分叉与取不到时的回退 |

矩形**每次现算，不缓存**：滚动一下、窗口一缩放、条目数一变，同一个槽位的
坐标就变了；缓存的结果是动画飞到一个已经没人站的位置。

### 6. 游戏内实测：动画跑起来了，暴露出两处偏差（2026-10-01）

2. **飞行偏慢**，按 User 要求调快 4 倍（0.5 → 0.125 秒）。

## 十六、空闲会话不再静默回收（2026-10-01，服务端补通知）

**修的是第十五节第 7 条**：会话因空闲超时被 `evict_expired` 回收时，服务端
只清自己的账、一条包都不发，客户端继续以为会话还在。**会话照样会被回收**
（TTL 是客户端崩溃或断线时的兜底，这条行为一个字没改），改的是它不再
**无声无息**。用户当时的选项就是这一条：**服务端推一条空会话号的 `error`，
客户端零改动**。

### 1. 改了什么（全在服务端，客户端零改动）

| 位置 | 内容 |
| --- | --- |
| `server/sync/terminal.py` 的 `tick()` | `evict_expired` 之后多一句 `if expired: self._notify_abandoned(expired)` |
| `_notify_abandoned(sessions)` | 新增。逐会话决定发不发，返回发出条数 |
| `_send_gone(session)` | 新增。**不走 `_send`**，直接编码一条空会话号的 `error` 交给端口 |
| `stats` | 新增 `expired_notices`（真发出去的）与 `expired_notices_skipped`（因为「这玩家还有别的活会话」而没发的） |
| `common/protocol.py` | `Reason.SESSION_INVALID` 的注释补上「空闲超时回收」；**没有新增原因码** |

客户端那半边**早就是好的**（`_absorb_error` 的空会话号分支），第九轮修
F2 时就写在那儿了；缺的从来只是**没人告诉它**。这一条因此没有任何客户端
改动，也没有协议形状的改动。

### 2. 两条守卫，都不是装饰

- **一个玩家只发一条。** 同一玩家可以并存多个会话（`max_sessions_per_player`
  是 4），一次回收可能同时丢掉其中几条；逐条发等于让同一个客户端连收几条
  同样的通知。
- **只有这个玩家一条活会话都不剩时才发。** 这条是**必需的，不是优化**：
  客户端一次只持有一个会话，而它手里那个一定是**最后开的**那个；旧会话
  之所以还在，正是关界面时那条 `session_close` 没送到（引擎销毁界面不走
  `OnDestroy` 时就是这样）。此时若替旧会话发一条「你的会话没了」，客户端
  会照字面**把它手里那个新会话一起丢掉**——那比不发更糟。判据因此是
  「清完之后这个玩家还有没有活会话」，与 `_drop_stale_devices` 的「必须
  重新查一遍，不要从变化里推」是同一条理由。

**为什么不能用 `_send`**：那条路会把 `session.session_id` 盖在信封上，而
客户端正是靠「信封里没有会话号」认出「这不是某一次请求失败，是这个会话
本身没了」。带着号发出去，客户端只会当成一次普通失败，界面照旧亮着——
**发了等于没发**。同理 `request_id` 留空是如实的：这一条不回答任何请求
（超时回收的时候客户端并没有在等什么，它只是没说话）。

## 十七、搬运动画按 16×16 校正落点（2026-10-01，User 裁定）

| 物品图标 **16×16**，槽位面板 **18×18** | [custom_slot 说明](../technical_notes/custom_slot.md) 第 1 节原文「槽位大小为 18×18，物品渲染区域为 16×16」 |
| 图标在槽位里**居中** | `custom_slot` 的 `item_renderer` 明写 `anchor_from/anchor_to: center`；`item_can_be_selected` 写 `100%+-2px`（= 18 − 2 = 16）且**不写 anchor**，默认即居中 |
| 因此图标左上角比槽位左上角各多 **1** 像素 | `(18 − 16) / 2` |

所以「图标该落在哪儿」不是槽位控件的左上角，而是**槽位里那张图标的位置**。

### 2. 改法：一条规则收住三种落点

`flying_item._corner` 从「取矩形左上角」改成「**把 `ICON_SIZE` 见方的图标
摆到这个矩形的正中**」，`ICON_SIZE = 16.0` 作为唯一的常驻事实（**不从引擎
读**——那个 `custom` 控件的 `GetSize()` 回 0，正是 2026-10-01 那 9 px 偏差
的来源）。三种落点各得其所：

| 落点 | 结果 |
| --- | --- |
| 槽位（18×18） | `+1`，与槽里那张图标重合 |
| 整块区域（背包那一半、列表区） | 落在**中心**——此前落在左上角，与本文档写的「落到列表区中心」是两回事，这里顺带对上 |
| 退化矩形（点击处 `(x, y, 0, 0)`） | **原样用那个点**；比图标还小的矩形一律不动它。拿它去「居中」会把它挪到左上 8 像素，那是个谁也没点过的位置 |

### 4. 游戏内：**用户目测确认**

`flying_item.py` 新加了模块级常量，而**热重载只换 `func_code`、不换
`func_globals`**（CLAUDE.md 记的那条）——半截重载之后 `_corner` 会去旧
globals 里找 `ICON_SIZE` 而炸。因此走的是**整包重载**，随后在**运行实例**
上核对了三个分支：`ICON_SIZE` 为 16.0、槽位 `(19, 19)`（+1）、点击处
`(40, 40)`（就是那一点）、整块区域 `(82, 42)`（居中）。

**用户随后在游戏里看了实际动画，回报「没问题了，很准确」。**

这就是这一条要的证据形式：**1 像素的落点差只能由眼睛定**，采样采的是
「脚本算出来的数」，而算得对不等于画得对。因此这里记的是**用户目测通过**，
不是「数字对上了」。

**没有逐向确认**：本轮没有把三种搬运各驱动一遍，因此验收清单里
「三种搬运各画一次且方向正确」那一条**仍然不勾**——目测覆盖了哪些方向
取决于用户当时操作了什么，本说明不替它推断。
