# 12 交付说明（12-04 ~ 12-08：接口、网络台账与分阶段恢复）

日期：2026-10-04。范围：**任务 12 的 12-04 至 12-08**——把接口状态与网络级
台账接到 12-03 已选定的真实后端上，做出分阶段恢复的闸门，并补上拆除处置、
待核对不重放与一致性检查。

**这是一次增量交付。** 12-03 只覆盖驱动器与介质；本轮把接口、预留、待核对
转移、订单簿接上同一份存档，并把恢复变成一个有阶段、有闸门、可复核的过程。
边界与未验证项见第六节。

## 一、这一步修的是什么

12-03 之后仍有两条只有游戏内才看得见的断裂：

1. **接口的配置与缓冲归属退出世界即丢**。`PortStore` 有 `save_all` /
   `restore` 这对内存结构，但**没有任何生产调用方**——玩家给取货口配的
   过滤、黑白名单、缓存开关、待核对标记，以及样板口那个纯内存的原料缓冲，
   重进世界后一件不剩。
2. **网络级台账根本没地方存**。`StorageService.save_node_data` 的文档写着
   「预留台账是网络级的……任务 12 需要为网络级数据另开一条记录」，
   而那条记录此前不存在。订单与预留因此在重启后化为乌有，且没有任何读数
   能说明它们曾经存在。

本轮补上这两块，并按要求把「恢复」做成一个有阶段、能拒绝业务的闸门。

## 三、接口与语义

| 项 | 形状 |
| --- | --- |
| 接口记录 | `endernet:endernet.port_state/<位置文本>`，一条接口一条 |
| 处置记录 | `endernet:endernet.port_disposal/<位置文本>`，拆除时留痕 |
| 网络台账 | `endernet:endernet.network_state/<主控位置文本>`，一层信封 `{storage, orders}` |
| 接口载荷 | 配置 / 朝向 / **待核对标记** / 投料批次 / 缓冲归属台账；**不含 `stats`** |
| 网络台账载荷 | `storage`: 预留 + 发号水位 + 待核对转移；`orders`: 订单簿 + 等待产物台账 |
| 提交 | 每帧至多一次 `SaveExtraData()`；写盘预算**两家分**（驱动器/接口各半） |
| 网络台账写入时点 | **停机与显式 `write_network_states()`**（它是审计记录，不是可续跑状态） |

**恢复的三阶段**（`RecoveryGate`）：
`loading`（读持久数据）→ `reconciling`（核对已加载设备、重建拓扑、校验主控、
挂载存储、核对预留与执行）→ `ready`（开放业务）。**读存档失败时停在
`loading`**，业务一律被拒——不把读不出的存档当成空存档继续。

## 六、未验证项与已知限制（重要）

- **「退出世界再进」已在 4.6 测过一轮**（真进程重启 + 26 台真设备走区块发现）。
  但**只测了一次、一个存档**；且那次里**设备都是同一个代次 0 起步**，
  「同位置换方块 / 拆了再放」这类跨会话场景仍未覆盖。
- **方块容器内容已确认会落盘**（4.6 的 7 个石头活过了重进），但
  `persistence_backend.md` §4 欠的那条**仍然欠着**：方块实体数据的
  **大小上限 / 保存时点 / 返回值语义没有测**。「内容不丢」≠「大小无上限」。
- **缓冲归属与方块容器的一致性没有在真机上对过**。`TransferBuffer` 有
  `desync` 计数，但本轮没有制造过真实的「玩家手动改槽」场景。
- **接口载荷里的「真实库存」仍不是我们存的**：那 9/5 格归方块容器
  （引擎持久化，4.6 已证实），我们的记录只带归属台账 / 配置 / 批次 /
  待核对。**两者在重进之后对不对得上**，本轮只有「都还在」这一层读数。
- **订单簿只有「写下去」没有「读回来应用」**：重启后订单不续跑（保守口径），
  因此 `orders` 那一节进档之后**没有任何读取方**。它的用途是可复核记录，
  本轮没有做「谁来看这份记录」的入口。
- **拆除处置的处置动作没有实现**：R05 未定，本轮的处置记录只留痕
  （`held` / `lots` / 归属），**不掉落、不保管、不转交**。真机上也没验过
  「缓冲里真有东西时拆除」那条路（只验了空缓冲）。
- **`WriteCoordinator` 没有接进启动层**：本轮用的是「预算两家分 + 一次
  `commit()`」，`WriteCoordinator`（12-01 交付的批量提交器）仍只在测试里被调。
  两者的职责有重叠，合并属后续整理。
- **规模没测**：整个验证只用了 1 台接口、1 张 3 台设备的小网络。
  「上百台接口 / 上百张订单时的单帧写量与停机写盘耗时」没有读数；
  `write_network_states` 是**逐网络**构造整份订单簿的，订单多时它是纯 O(n)
  的一次性开销（只在停机与显式调用时发生）。
- **`persistence_batch` 两家分**是未经测量的取值（每类各 16）。
- **未知新版本对接口与网络台账的处置只做了离线验证**（冻结不写回），
  真机没验。

## 七、顺带发现（真机揪出的两个）

1. **信封传错一层会让预留台账永远恢复不出来。** `write_network_states` 写的是
   `{storage, orders}` 一层信封，而 `_apply_archived_network_states` 一开始把
   **整个信封**交给了 `storage.import_network_state`——它要的是信封里那一份。
   症状是「记录写了、应用了、一条报错都没有，而归档预留永远是空的」。
   修法与回归位见第五节。
2. **`json.loads` 在 py2 里读回来的是 `unicode`，不是 `str`。**
   `_reservation_sequence` 只判了 `str`，于是**静默返回 0**，发号水位永远抬
   不起来，重进世界后的新预留会与旧预留撞号。这一类 py2/py3 文本型分裂
   离线测不出来（py3 里 `u"x"` 就是 `str`），只能靠真机。已改用本仓库既有的
   `_TEXT_TYPES` 口径。

两条都记在这里：它们不是「实现没写」，而是**只在真机上才现形**的那一类，
而离线全绿正是它们的伪装。
