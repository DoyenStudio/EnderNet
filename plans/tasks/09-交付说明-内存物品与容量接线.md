## 二、交付内容

### 1. 八件内存物品

`MemorySpec` / `MEMORIES` / `ITEM_MEMORIES` 三张表进定义表（容量 128 B ～ 256 KB，
逐字取自 items.md），生成物由既有的 `scripts/gen_items.py` 与
`scripts/gen_placeholder_textures.py` 产出——**两个生成器都只是多了「第三类」一支**，
没有为内存另写一条生成链：

- `endernet_bp/netease_items_beh/endernet_memory_*.json` 8 个（行为包，含 `netease:customtips`）
- `endernet_rp/netease_items_res/endernet_memory_*.json` 8 个（资源包，含图标键）
- `endernet_rp/textures/item_texture.json` 8 条 + `textures/items/` 8 张占位贴图（第三套配色）
- `endernet_rp/texts/zh_CN.lang` 8 行中文名

`DefinitionSet.item_specs()` / `item_keys()` 各追加内存一支，因此
`test_assets.py` 的**全部泛化断言**（行为／资源 JSON 齐全、标识与文件名一致、
堆叠上限与定义表一致、有提示文本、资源侧无 category、图标指向已登记图集键、
图集无孤儿、贴图文件存在、无未引用贴图、中文名与 label 一致、无孤儿语言条目）
**自动覆盖到这 8 件**，不需要逐个补断言。

### 2. 新模块 `server/devices/memory_slot.py`

`MemorySlotStore` + `MemorySlotState`：**内存容量的唯一权威**。它读内存槽方块
容器里插着什么，镜像 `crafting/store.py` 的 `PatternStore` 那套纪律
（只标脏、去抖重读、每帧限量、读不到保留上次读数），并照 `StorageDriverStore`
的形状提供 `on_load_changed` 回调。**它是派生索引，不存档**——内存条是容器里的
实物，容器随方块落盘。

放在 `devices/` 而不是 `crafting/`：`crafting/store.py` 已经
`from ..devices.capabilities import`，反向会成环（`test_import_boundaries` 静态强制）。
代价是它自带一份 settle／budget 常量、以及一个 `_slot_count_of` 小函数
（与 `crafting/store.py:container_slot_count` 同规则的两份实现，两侧各自注明理由）。

### 3. 容量真相切换

- `OrderPolicy.bytes_per_memory_slot` **删除**（连同它在 `unresolved_report()`
  里的那一条与 `describe()` 里的那一项）。它曾是「内存槽台数 × 1024 B」的替身。
- `memory_capacity(members, store)` 改签名，返回 `(内存字节, 插着的根数)`；
  **未加载的成员不计入**（旧口径保留），读不到容器的按「上次读到过的值」算，
  从没读到过按 0——宁可少算不可多算。
- `FactoryService` 增 `memory_store` 注入；`memory_slots` 改名
  `memory_sticks`（**「槽」与「根」正是这次最容易读错的一处**，协议字段名仍叫 `slots`）。

### 4. 能源按内存条根数

`bootstrap._note_memory_load_changed`（插拔后立即回填）与
`_energy_inputs_of` 的 `CATEGORY_MEMORY` 分支（初次挂载／迁移时重读），
照 `StorageDriverStore` 的范式；`blocks.md` 的「内存条个数 × 8 EN/t」由此成立。
**不通知负载重算**：内存槽带宽是固定的 2u，不随根数变。

### 5. 拒收

`MemorySlotStore.accepts_put(device_id, item_name)` 答的只是内存槽那一半
（不是内存槽一律放行），`events._veto_or_mark` 逐个 store 问、任一拒收即
`event.cancel()`。计数器与样板槽**分开**（`memory_slot_rejected` /
`pattern_slot_rejected`），合起来就再也答不出「哪条规则在真机上生效了」。

### 6. 协议语义

`OrderMemoryView.memory.slots` 改为**插入的内存条根数**。**线上字段名不变**
（改名字要同时动协议、客户端与测试，而它本来就是「几个格子／几根」那个意义上的
占位词）；客户端只渲染 `available` 的字节数与比例，**这一改动界面上看不出来**。

## 四、接口输入输出

| 接口 | 语义 |
| --- | --- |
| `memory_capacity(members, store)` | 返回 `(内存字节, 插着的根数)`。`store` 只要鸭子类型 `bytes_of` / `sticks_of` |
| `MemorySlotStore.bytes_of / sticks_of(node_key)` | 未知位置返回 **0**（供容量：宁可少算） |
| `MemorySlotStore.unit_count_of(ref)` | 能源的 `unit_count`；**从没读到过返回 `None`**（待确认，不是 0 根） |
| `MemorySlotStore.accepts_put(device_id, item_name)` | 内存槽只收已注册为物品的内存条；别家容器一律放行 |
| `MemorySlotStore.mark_dirty(node_key)` | 容器变了只记一笔，不在这里读容器 |
| `MemorySlotStore.advance(tick)` | 每帧最多重读 4 台（`MEMORY_REFRESH_BUDGET`）；去抖 2 帧、陈旧兜底 40 帧 |
| `diagnostics()["memory_slots"]` | 设备数、根数、字节合计、读不到的与从没读到过的位置清单 |

## 七、已知实现限制

- **未加载的内存槽不计入容量**（沿旧口径）：它的状态没人能确认，而内存是要拿去
  开工的。这是刻意的保守，代价是区块卸载时可用内存会变小、已通过的订单不受影响。
- **读不到容器时沿用上次读数**；**从没读到过**则容量算 0、能源报 `None`。
  两者分得开，靠 `MemorySlotState.has_reading()`。
- **`count > 1` 的槽不放大容量**：只按占用槽数记 1 根，另在诊断里报
  `overstacked_slots`。堆叠上限是 1，出现这个数说明有别的来源改过容器。
- **拒收只覆盖引擎的两条放入事件**：别的模组直接改方块实体数据不经事件，
  那些物品会被读成 `invalid`（不提供内存、也不搬动）。
- **每帧最多重读 4 台**内存槽，与样板那边各自限量（同一帧尾两批）。
- **没有独立的 `debug_query("memory")`**：容量走 `debug_query("order")` 的
  `memory` 一节，逐台明细走 `diagnostics()["memory_slots"]`。要不要单开一条只读
  入口留给 11／14 一起定。
- **`MemorySlotStore` 不注册 `CAP_MEMORY` 能力对象**：该能力今天由网络侧的
  `MemoryLedger` 承担，再挂一个同名设备级对象会造成两个「Memory」。

## 八、未定案残留（不得读成已定）

- **基带耗能未列（R10）**：这是库默认口径下能源仍判 `unavailable` 的**唯一**
  剩余原因（内存条那一项已于本轮接入）。
- **无处理器时的默认槽位数**：R04 的另一半，仍未定。
- **内存条本身的获取路径**（合成／掉落）没有任何说法——与介质那边
  「介质物品获取路径没有」是同一条空白，属内容注册。
- **内存占用在订单存续期间的语义**（通过准入后持有至完成／手动中止）本轮未动，
  仍是既定的那一侧。
