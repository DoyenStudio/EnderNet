## 三、接口输入输出

### `LogicalClock`

`current_tick()` / `advance(count=1)` / `describe()`（只有 `tick` 与 `advances`）。
**它只有帧序计数器**，没有秒、没有 Hz、没有除法——「频率不写死」是靠「结构里
根本没有频率」保证的，而不是靠自觉。`advance()` 只允许向前：倒退会让已排定的
任务全部变成「过去」，一次退回触发一整批。

**它不记引擎脉冲。** 三种脉冲（脚本 tick / 模拟 tick / 方块实体 tick）的计数在
`ServerEventBinder.pulse_counts()`，读法是
`diagnostics()["scheduler"]["pulses"]`。这里一度另存过一份 `pulses`，而适配器只
更新自己那份，于是 `block_entity_tick` 永远是 0——真机量出来的比值会是 0，
看起来像「引擎根本没派发这个事件」。**同一个数字存两处，分叉只是时间问题。**

### 同帧去重：一帧只算一帧

余量轮会让**同一个运行时在一帧里被访问两次**。`NetworkRuntime.tick` 里按
`context["frame"]` 去重：主控时钟（去重账本的保留期按它算）与 `stats["ticks"]`
都只在帧号变化时前进。不定帧号时（例如 `ApplicationService.tick` 那条入口）
由 `RuntimeManager` 补一个自己的帧序号——**去重不能只在 bootstrap 这条路上成立**，
否则换条入口主控时钟照样走两倍，重复请求可能提前被遗忘。

**时钟由 `drive_once()` 推进，每帧恰好一次。** 不选「消费队列里的 `SCRIPT_TICK`」
有三个理由：受 `drain_limit` 约束（一次区块加载的积压就能让时钟停走，而
`tick_count` 照走 → 出现两套「帧」）、队列空时仍会推进别的步骤、以及依赖同帧两个
`OnScriptTickServer` 监听器的注册顺序。放在 `drive_once` 里，谁先谁后都只推进一次。

`tick()` **自己不动时钟**，这就是「假时钟精确重现卡顿与恢复」的入口。

### `SchedulerService`（`service_id = "scheduler"`）

- `schedule(ref, kind, delay, period, handler, owner)`：**重排 = 替换**。同一
  `(ref, kind)` 在活体表里有且只有一条，因此「重排不会重复执行」是结构性质，
  不要求调用方先 `cancel`。`delay`/`period` 的单位是**逻辑帧**。
- `cancel` / `cancel_all` / `wake` / `sleep` / `set_poll_handler` / `next_due` /
  `due_tasks` / `drain_due` / `queue_view` / `lane_view`。
- `tick(context, budget)`：判定顺序写死——取当前帧 → 队列空则 0 → 最早到期未到则 0
  → 循环取任务直到用完预算或撞上 `max_tasks_per_frame`。
- **不覆盖 `power_ok`**：继承基类的 `None`（「待确认」）。能源是 04 的另一半，
  给 `True`/`False` 都是撒谎，而主控不会据此放行。
- **不覆盖 `handle`**：命令路由表里没有调度器这一格，真调到这里就是编程错误，
  不该伪装成一条业务失败。
- `save_node_data()` 返回 `None`：到期时刻是帧序，跨重启没有意义
  （下次启动帧序从 0 重来，存下的 `due` 要么立刻全部到期、要么永远不到期）。

### 任务的失效：三道检查，都不靠调用方自觉

1. `add_node` 发现同位置 `ref` 变了 → `cancel_all(旧 ref)`。这是主路径。
2. `remove_node` → `cancel_all`。**按键找 lane、按 lane 记的 ref 取消**，
   不依赖传入对象的代次；迟到的卸载通知只清它自己那个代次，不会连 lane 一起删。
3. 执行时 `registry.get_by_ref(task.ref) is None`（代次不符返回 `None`）→ 丢弃。

**冻结 vs 失效**：区块卸载（`loaded=False`，代次不变）→ **冻结**，不执行、不失效，
重新加载后按当前帧重新计时、**不补做**（「卸载不是拆除」）；拆除/替换 → 立即失效。
这条边界是策略字段 `SchedulerPolicy.invalidate_on_unload`（默认冻结）——验收原文里
的「卸载」两种读法都能自圆其说，按全局约束 7 不在这里定案。

### 跨网公平轮转

`RuntimeManager.tick` 的分配形状：**保底一轮**（按环序，每个运行时至多
`share = max(保底, 预算 // n)`）+ **余量一轮**（没花完的额度按同一环序再分）。
`remaining` 只按**实际消耗**递减，因此空闲网络不浪费额度。

能兑现的保证（不要读成更强的）：`budget >= n` 时每帧每个网络至少拿到 1 单位额度；
`budget < n` 时不保证人人每帧有份，但环序起点逐帧前移，连续 `n` 帧内人人当过首位。
总消耗永不超过预算。

### 唤醒信号

`ServerBlockEntityTickEvent` → `WakeSet`（**不入 `EventQueue`**）→ `bootstrap.tick()`
在拓扑重建之后、服务推进之前投递 → `RuntimeManager.deliver_wakes`（按 `NodeLocator`
路由）→ `NetworkRuntime.wake_node` → `NetworkService.on_wake`。

不进 `EventQueue` 的理由：引擎按固定顺序遍历方块实体，产生 `A, B, A, B…` 这种跨位置
交替的脉冲，而队列只合并**紧邻**的重复通知，因此一条都合并不掉，会吃掉
`drain_limit` 的大半；队列满时 `push` 丢的是**新来的**事件，也就是放置事件——
设备会凭空消失。而且 `DeviceLifecycle` 里没有 `BLOCK_ENTITY_TICK` 的处理器，
进队只是白占名额；唤醒本身是**集合语义**，与队列「绝不改变生命周期阶段顺序」的
承诺是两种东西。

**`on_wake` 只把退避打回初值，不把轮询提前到本帧。** 这个区分是关键：方块实体 tick
是引擎每帧的心跳（开 `tick: true` 的设备约 20 Hz），不是「发生了变化」。拿它当变化
信号去立刻轮询，开 tick 的设备就退化成每帧一次扫描——正是 04-03 要避免的事。
「真的变了、现在就该看」的入口是 `wake(ref)`。

### 「空」的语义（沿用 01/02/03 的口径）

- `DueQueue.peek_due()` 返回 `None` = 没有活体任务，不是「到期时刻是 0」。
- `ScheduledTask.period is None` = 一次性任务。
- `DeviceLane.poll_handler is None` = **没有消费者注册轮询回调**。轮询本身照跑并
  计入指标，不是「轮询无效」。本增量该值恒为「无」，见第六节。
- `NodeLocator.locate()` 未命中返回 `None`（不抛错）：设备刚放下的那一帧就是这个
  情形，丢一条唤醒不会丢设备。

## 五、未验证项（重要）

> **2026-09-25 首轮真机实测已经兑现了本节原本的大部分条目**，逐条结果见第八节。
> 下面只列**至今仍然没有答案**的。

1. **游戏内已跑过首轮，但仍有空白**：
   - **无玩家在线时两个 tick 会不会停**：单人环境测不了（需要专用服或第二个玩家）。
     这是「帧 → 秒」换算在服务端独立运行时是否成立的最后一个前提。
   - **窗口最小化 / 世界未加载**这两种停摆场景没有单独测。实测到的是「打开暂停
     菜单不冻结服务端时钟」（第八节 #13），但那不等于其他停摆场景也不冻结。
   - **区块卸载时引擎是否仍派发方块实体 tick**：没构造出这个场景（冻结路径只有
     离线用例覆盖）。
   - **方块实体 tick 在各设备之间的浮动幅度**：世界里只有一个 `tick: true`
     设备，量不到引擎「不保证同步」的实际程度（语义见第八节）。
   - `ServerBlockEntityTickEvent` 与 `OnScriptTickServer` 的**同帧顺序**没有单独
     测量。设计对顺序不敏感（唤醒晚一帧生效也无害），但记录里应注明未测。
2. **唤醒路径没有业务消费者。** `poll_handlers` 恒为 0：本增量只提供退避原语与
   定时器，**没有任何设备注册轮询回调**。因此「无事件容器可最终被轮询发现」这条
   验收只有原语与用例，没有真实消费者。哪些设备属于「外部无通知容器」取决于
   方块定义与 05/06/08/09 的容器语义。
   附带的一个后果：没有消费者时轮询会**一路退避到最疏**（这是刻意的——没人能
   回答「它变了没有」，就不该每 `base` 帧白扫一次）。真机上已经量到这个节奏：
   那台开着的网络 6 个成员、7089 帧里轮询执行 228 次 = **每个成员约每 187 帧
   被扫一次**（默认上限 200，与设计相符，约 6.2 秒一次）。这个节奏对「发现变化
   有多及时」的影响尚未评估——它取决于 05/06 注册消费者后的实际语义。
3. **帧预算未被真正用满。** `max_tasks_per_frame` 与 `runtime_budget` 的默认值是
   测试替身，当前没有任何服务注册到期任务，因此这条上限**一次都没有在真机上生效过**。
4. **规模未测。** `reconcile()` 现在每次发布都重建唤醒索引（O(成员数)），
   `scheduler_view()` 每次诊断都遍历全部运行时。当前规模（个位数网络）没有实测到
   问题，大网络上的开销没有测量。
5. **执行时长只在注入计时器时才测**，离线默认完全不测（`duration_ns_total` 恒 0）。
   真机上要不要开、开了会不会自己成为开销，未验证。
6. **`catch_up=True` 这条分支没有任何使用者**，只有一条用例证明它会终止。

- **`catch_up` 不列为未定项**：「卡顿后不集中补做无限历史 tick」是 04 文档明写的
  要求，不是待定玩法。留成字段是为了让测试能构造另一种口径来证明默认值确实生效。
- **装配期守卫看不到调度策略。** `ServiceRegistry.assert_profile_ok(profile, policy)`
  只读准入策略，**不检查调度策略的未定项**。要么 14 额外传，要么把签名扩成
  `policies=(...)`——本增量**没有偷改签名**，写进「待定与交接」。
- **`on_wake` 覆盖了基类默认实现**的训练：`NetworkService.on_wake` 默认返回 `False`
  （不处理），因此不加覆盖的服务不受影响。这是纯增量钩子，与 `note_domain_change`
  同形。
- **`default_builders()` 里有一个函数内 import**（`services.py` → `ticking.py`）。
  `ticking.py` 在模块级 import 契约层，反向的模块级 import 会成环；`default_builders()`
  只在构造期被调用，因此函数内导入不引入环。注释写清了「不要提到模块顶部」。
- **服务构造器必须接受 `None` 运行时**（`attach()` 才绑定）。这条约定此前只被
  `default_stand_ins()` 依赖，现在 `ServiceFactory.stand_in_slots()` 也要靠它回答
  「这个槽位还是替身吗」。已写进该方法的 docstring。
- **`NodeLocator` 的索引只在 `reconcile()` 里重建**。拓扑发布之外新增成员的路径
  不存在，但如果将来有，唤醒会路由失败（表现为 `unrouted` 增长），不会静默错发。

### 考虑过、但没有采用的方案（一并记下来，免得下一个人重新想一遍）

1. **把唤醒并进 `EventQueue`，给它一种新的合并策略。** 反对的理由在 `WakeSet`
   的 docstring 里：脉冲是集合语义，而队列的承诺是「绝不改变生命周期阶段的
   先后顺序」。给队列加「按 kind 选择相邻合并还是集合合并」确实可行，但那要改
   一个被 01/02 真机验证过的组件，而收益只是少一条通道。**保持现状。**
2. **`NodeLocator` 换成 `TopologySnapshot.component_id_of`。** 快照里已经有
   位置 → 分量 的映射，另建一个索引确实是第二份。但那个索引映射的是**图成员**
   （含尚未挂载的），而路由需要的是**运行时实际持有的成员**——两者在重建进行中
   会不一致。差异是刻意的，因此保留独立索引并把理由写进注释。
3. **把 `UNRESOLVED_FIELDS` / `unresolved_report()` / `assert_settled()` 抽成
   与 `BandwidthPolicy` 共享的基类。** 两处确实是同一个三段式协议。不做的理由是
   那要动一个已交付且**已在真机验收过**的文件（`admission.py`）与它的测试，
   而本增量的收益只是少几十行重复。交接给 14：那个签名问题
   （`assert_profile_ok` 只看一个策略）迟早要处理，届时两处一起收。
4. **用留数轮转（deficit round robin）做跨网公平。** 它需要一份跨帧、需要持久化、
   需要解释的欠账状态，而收益（按需求比例长期分配）已被「余量同帧再分配」覆盖，
   任何一条验收都测不出差别。**复杂度不换来可验证的性质就不加。**

## 七、一轮代码评审带出来的问题

本增量在交付前跑了一轮多角度代码评审（逐行扫描、被删行为审计、跨文件追踪、
复用、简化、效率、实现深度、项目约定八个角度，各自独立找问题再逐条核实）。
下面 13 条里**前 9 条是真实缺陷**，其中前两条最严重。它们都不是「离线的用例
会红」的那类——861 项当时一直全绿，问题在用例没覆盖的路径上。

### 缺陷

0. **模组在真机上根本起不来**（`scheduler.py`，**由第一次游戏内实测抓到，离线门禁不可能发现**）。
   顶层 `import timeit` —— 网易 ModSDK 的沙箱里**没有这个模块**，于是
   `scheduler.py` 导入失败 → `network/runtime.py` → `bootstrap.py` → `modMain.OnServerInited`，
   一路炸穿，`get_server()` 返回 `None`、设备一台都不注册。
   `py2check` 只查语法子集，查不出「模块在目标环境里不存在」；861 项离线用例
   跑在 py3.11 上，那个环境里 `timeit` 是有的。**这是纯离线验证的盲区，只能真机发现。**
   修法是把 `timeit` 的导入放进 `default_timer()` 函数体内（失败退回 `time.time()`），
   顶层一个 import 都不留——**依赖必须能失败在调用点，不能失败在导入链上**。
   代价：`default_timer` 从此不是单调时钟（py2 退回墙钟），但它只用于诊断。

1. **handler 抛异常会让轮询定时器永久丢失**（`ticking.py`）。
   `pop_due` 已经把任务从活体表里拿走，而重排写在 `_dispatch` **之后**，
   于是异常一抛就跳过重排。症状是「某次异常之后这台设备再也不被轮询」，
   而异常只在 `drive_once` 里记进 `tick_errors`——没人会把它和轮询停了联系起来。
   周期任务同理。修法是把重排与计数放进 `try/finally`，**先排好下一次再让异常
   冒泡**（领域层不吞异常的纪律不变）。这条正好是计划里写过的意图，但当时没实现。

2. **没有消费者时退避永远不涨**（`ticking.py`）。`_dispatch` 的「无 handler」
   分支在更新退避之前就 `return 0` 了，于是每轮都用初值间隔重排——
   退避形同虚设，而且与紧邻那句注释「这样退避会正常拉长」正好相反。
   本增量 100% 的 lane 都是这种状态，所以这就是「空闲网络不高频扫描设备」在
   真实装配下的表现。修法是无人消费时也 `note_unchanged()`（没人能回答
   「它变了没有」，就不该每 `base` 帧白扫一次），并让
   `set_poll_handler` 注册消费者时把退避打回初值、重排一次
   （否则新消费者要等「没人看」期间攒下的最疏间隔）。

3. **脉冲计数存了两份，`block_entity_tick` 永远是 0**（`scheduler.py` +
   `adapters/events.py`）。`LogicalClock.pulses` 是第二份计数，而适配器只更新
   自己的 `counts`，于是 04-01 要量的那个比值在真机上会读成 0——看起来像
   「引擎根本没派发这个事件」。修法是删掉时钟那份，
   `ServerEventBinder.pulse_counts()` 成为唯一出口，读法
   `diagnostics()["scheduler"]["pulses"]`。**同一个数字存两处，分叉只是时间问题。**

4. **余量轮会让同一个运行时在一帧里被访问两次，主控时钟跟着走两倍**
   （`network/runtime.py`）。`advance_tick()` 是去重账本 `RequestLedger.prune`
   的时基，走两倍等于把 900 tick 的保留窗口压缩成约 450 帧——**重复请求可能
   提前被遗忘而二次执行**。`stats["ticks"]` 也从「帧数」变成「调用次数」。
   修法是按 `context["frame"]` 去重：同一帧只算一帧。

5. **同一条缺陷还有第二个入口**（`network/runtime.py`）。`ApplicationService.tick`
   没有帧号，而它同样会走余量轮。修法是由 `RuntimeManager` 在调用方没给帧号时
   补一个自己的帧序号——**去重不能只在 bootstrap 这条路上成立**。

6. **关闭中的网络仍会收到唤醒**（`network/runtime.py`）。`tick()` 有
   `if not self._open: return 0` 这道门，新增的 `wake_node` 没有。放唤醒进去
   不只是「白改状态」：网络重新开放的一刻，所有设备的退避都被重置过，
   会以最短间隔同时轮询。修法是加同一道门，并把拦下的数量单列成
   `wakes_withheld`（与「送到了但没人处理」区分开）。

7. **冻结分支不更新 `lane.poll_due`**（`ticking.py`）。轮询分支修过同一处，
   冻结分支漏了，于是区块卸载后 `lane_view()` 显示的是冻结前的时刻，
   读起来像轮询卡死（误差可达上百帧）。修法是统一走一个 `_rearm(task, lane, due)`。

8. **`created_tick` 被赋成 `due`**（`scheduler.py`）。字段名与 `to_dict()`
   暴露的语义都是「创建帧」，实际存的是到期帧——`delay=100` 时它会显示成
   「在未来创建」。按 `last_run_tick - created_tick` 估算等待时长会得到负数。

9. **`count_due` 恰好等于上限时虚报「积压更多」**（`scheduler.py`）。
   判据写成 `count >= limit`，于是正好 64 条（默认扫描上限）时也报
   `deferred_capped`。按这个标志判断积压会得出错误结论。

### 设计与文档一致性

10. **`stand_in_slots()` 的判据**（`services.py`）。第一版修法改成「空造一个实例
    问它 `is_stand_in`」，那会给 05/09 的实现加一条没写进契约的隐含义务
    （构造器必须能用 `None` 构造），而这条路径是诊断——一个在 `__init__` 里读
    `runtime.registry` 的实现会让 `debug_query("assembly")` 直接崩。
    最终判据是「构造器还是默认表里那一个」**且**「该槽位的默认实现本就是替身」
    （`default_pending_tasks()` 就是那张表），不构造任何实例。

11. **`scheduler_view()` 把「没报」折成 0**（`network/runtime.py`）。它与自己
    上一行的注释、以及仓库「缺项不等于 0」的口径都矛盾：一份全 0 的报表会
    看起来像「一切正常」。修法是数出 `unreported`（没有可汇总指标的非替身服务数），
    与 0 分列；同时改走契约方法 `diagnostics()` 而不是戳实现字段 `stats`
    （后者换个实现就崩，前者缺项退化为「没报」）。

12. **同一个统计键在三个层级含义不同**（`network/runtime.py`）。管理器的
    `wakes_delivered` 数的是信号数，运行时的同名键数的是「处理了它的服务数」。
    按名字对齐两处数字会得到恒不相等的值。修法是后者改名 `wakes_handled`。

13. **五处冗余/死状态**：`budget_overruns` / `polls` 两个计数从未被写入；
    `DeviceLane.loaded` 是注册表 `record.loaded` 的第二份拷贝且永不同步
    （诊断一直显示 true）；`idle_poll_ticks` 是死旋钮（与退避上限是同一个量，
    两个名字只会让人以为它们可以不同，已删）；`plan_frame` 的 `max_passes` 形参
    不参与任何计算；`note_frame` 的 `firsts` 按「额度非零」统计，而保底一轮
    给每个人都授了额度，因此它恒等于环序首位——与它自己的 docstring 说的
    「第一个真的做了事的」不符，改成按 `spent > 0` 统计。

## 七点五、开发过程中撞到并修好的问题

1. **替身判据在「默认构造器本身就是正式实现」时失效**（`services.py`，
   **04 带出来的一处真实退化**）。`stand_in_slots()` 原判据是「构造器还是默认表里
   那一个」，其 docstring 的理由是「04/05/09 落地时会**替换**构造器」。但本次是
   把 SCHEDULER 的默认构造器直接换成了 `SchedulerService`——它仍然「是默认的那一个」，
   于是被继续当成替身：`pending_tasks()` 报出一个不存在的待办任务，
   `assert_profile_ok(PRODUCTION)` 会误报「调度器尚未实现」。
   修法是按**实例**判断（`builder(None).is_stand_in`）。反向用例
   `test_stand_in_slots_is_judged_by_instance_not_by_identity` 把两侧都钉住。
   **注意**：`test_partial_override_keeps_other_slots` 在修之前是**通过**的——它断言
   的正是那个错结论；这类「测试保护了缺陷」的情况只有改了判据才会暴露。

2. **替换设备时排轮询任务会崩**（`ticking.py`，本增量自己的缺陷）。
   `add_node` 的替换分支先 `lane.poll_due = None`，随后 `_schedule_poll(lane)` 拿它当
   `due` → `int(None)` 抛 `TypeError`。症状是**同位置换方块直接抛异常**，
   由 `drive_once` 记进 `tick_errors`。修法是给出真实时刻
   （`lane.poll_due = self._now()`），顺带修正语义：换了方块等于换了一台设备，
   轮询该从头开始并且本帧就看一次，而不是沿用旧实例可能已经退避到最疏的倒计时。
   由 `test_a_replaced_device_invalidates_the_old_tasks` 抓到。

3. **拿心跳当变化信号会让开 tick 的设备退化成每帧扫描**（设计缺陷，写代码时发现）。
   初版 `on_wake` 把 `poll_due` 设为当前帧，于是开 `tick: true` 的设备（约 20 Hz）
   每次心跳都触发一次轮询——正是 04-03 要消灭的高频扫描。改成只重置退避档位，
   「立刻看一次」交给 `wake(ref)`。

4. **`catch_up` 的钳位会把补做整个取消掉**（本增量自己的缺陷）。初版写成
   「若 `due + period` 仍在过去，就改成 `now + period`」——那恰好等于永不补做，
   而 `catch_up=True` 的全部意义就是补做。改为不钳位：`due` 每轮只前进一个周期，
   仍在过去就同帧再次到期，直到追上当前帧；不会无界，因为预算与
   `max_tasks_per_frame` 两道闸门都在。

5. **轮询重排没有同步 lane 的诊断读数**（本增量自己的缺陷）。`_run` 里 poll 分支
   重新排定任务后没有更新 `lane.poll_due`，于是 `lane_view()` 一直显示
   「上次执行前的时间」，看起来像轮询卡住了。

6. **零成本任务会让单帧循环自旋**（本增量自己的缺陷）。预算按 handler **自报**的
   工作量计，因此一个恒返回 0 又把自己排到过去的任务会让 `while spent < budget`
   永远转下去。加了 `max_tasks_per_frame` 这道**独立于预算的执行条数上限**，
   它不只是配额，是终止性保证。

7. **负消耗量会反向放大后续额度**（**既有缺陷**，`NetworkRuntime.tick` 的
   `int(x or 0)`）。负值会让 `budget - spent` 变大，症状是「某个服务偶尔多做一堆事」，
   几乎不可能从现象倒推回原因。`NetworkRuntime.tick` 与 `RuntimeManager.tick` 两处
   都钳位并计数（`negative_costs` / `budget_overruns`），缺陷留可见痕迹。

8. **`scheduler_view()` 戳实现字段而不是走契约**（本增量自己的缺陷）。
   初版读 `service.stats`，于是任何自定义调度实现（测试双件）都会把诊断打崩。
   改成走 `NetworkService` 契约里的 `diagnostics()`，缺项退化成 0（诚实的「没报」）。

9. **第一笔提交自己的门禁过不了**（提交拆分时发现，不是代码缺陷）。
   `bootstrap.py` 因为同时含 03 的装配代码被挪到第二笔提交，于是第一笔的树里它还带着
   `from __future__ import ...`，而 py2 门禁恰好拦这一条。用 `git commit --amend`
   把「只删那一行」的改动补进第一笔。**教训**：按文件切提交时，跨批次的一致性清扫
   （这里是全仓库统一删 `__future__`）要跟着**文件所在的提交**走，否则中间态过不了
   自己刚提交的门禁。

### 两条必须记住的时钟语义（由维护者指出，实测印证）

1. **`OnSimTickServerEvent` 是全局时钟**：全世界一个事件，同一窗口内所有观察者
   数到的次数一致。
2. **`ServerBlockEntityTickEvent` 不是时钟。** 它是**逐方块实体**派发的，引擎
   **不保证**同一个时间窗口内所有方块实体的 tick 次数一致，**也不保证与全局
   game tick 一一对应**——各设备的计数会有微小浮动、可能漏拍。因此：
   - **不能拿它当时间基准**，也不能假设「设备 A 数到 N 次时设备 B 也数到 N 次」；
   - 能当基准的只有**脚本 tick**（`LogicalClock` 用的就是它）与**模拟 tick**。

   这条限制**不需要改代码——它验证了现有设计**：本模组只把方块实体 tick 当
   「该醒醒了」的提示，到期与退避一律走**逻辑帧**，方块实体 tick 从不参与任何
   计时或判定。已写进 `EventKind.BLOCK_ENTITY_TICK` 与
   `ServerEventBinder._on_block_entity_tick` 的注释。

### 关于 17.3 Hz 与 20.0 Hz

更早一次实测记录的是模拟 tick ≈17.3 Hz，本次三个窗口都是 **20.0 Hz**。最可能的
差异来源是负载：模拟 tick 会随游戏 tick 落后而变慢。这正是「不要在代码里写死
频率」的又一个理由，也说明它本身就会浮动。

### 本次仍然没覆盖的

- **无玩家在线时是否停**：单人环境测不了，需要专用服或第二个玩家。
- **方块实体 tick 在各设备之间的浮动幅度**：本次世界里只有一个 `tick: true`
  设备，量不到「不同步」的实际程度，只能记下引擎不保证。
- **窗口最小化 / 世界未加载**这两种「非暂停」的停摆场景没有单独测。
- 规模与帧预算（第五节第 4 条）仍未压测。

## 九、给下游任务的交接

- **05（存储）/ 06（转移）/ 08（规划）/ 09（订单）**：注册到期任务走
  `SchedulerService.schedule(ref, kind, delay, period, handler, owner=<你的 service_id>)`。
  `owner` 必须是自己人，否则拒绝并计数。`delay`/`period` 的单位是**逻辑帧**；
  handler 返回工作量的**整数**（轮询类返回 `(changed, cost)` 或 `PollOutcome`）；
  **不得在 handler 里直接改库存或推进订单**——调度只决定「什么时候轮到你」，
  提交完成后再发通知的纪律不变。同一 `(ref, kind)` 只有一条活体，**重排不必先 cancel**。
  需要「外部无通知容器」的探测时用 `set_poll_handler` + 退避原语；`kind` 建议带
  自己的服务前缀，避免撞键。
- **11（终端与状态栏）**：`power_ok` 仍是 `None`（能源未实现），因此设备状态里的
  能源判定是「待确认」，**不要把它显示成「没电」**。`device_status` 的字段集未变。
- **12（持久化）**：调度状态**刻意不落盘**，`save_node_data()` 返回 `None`。
  未完成的周期任务要不要恢复、以什么身份恢复（帧序跨重启没有意义）是 12 的决策。
- **13-05（无通知容器的退避轮询）**：`PollBackoff` + `SchedulerService` 的
  `set_poll_handler` / `wake` / `sleep` 就是给你的入口，本增量没有消费者。
  注册消费者时退避会自动回到初值并按初值重排一次。需要真实频率换算时，读
  `diagnostics()["scheduler"]["pulses"]`（三种引擎脉冲的计数），别在代码里写死 Hz。
- **14（发布验收）**：显式调用 `ServiceRegistry.assert_profile_ok(PRODUCTION, policy)`
  与 `BandwidthPolicy.assert_settled()`——它们不会自动运行。**`SchedulerPolicy.
  assert_settled()` 同理**，且要注意 `assert_profile_ok` 目前看不到调度策略的未定项
  （要么额外传，要么扩签名）。调度指标从
  `diagnostics()["scheduler"]` 或 `debug_query("scheduler")` 读；
  真机验收请把第五节列出的六项实测做完再宣布通过。
