## 一、为什么先跑真机

12-02 的措辞是「**在目标环境**验证……选择实际后端并记录限制」。这不是可以靠读文档
或写离线测试绕过的一步：后端选错的代价是**存档结构**，而存档结构的错法里最坏的一种
是「写入时一切正常、存档时炸」——离线测试永远看不到它。

事实证明确实如此，而且比预想的更险：物品 `userData` 超限的表现是**模态断言框挡住
游戏主线程**（见第三节第 1 条），写入与读回都毫无征兆。**如果先按「介质内容塞进
物品 NBT」把 12-03 写完，这颗雷会在第一次有人装满一块 64 类型的大盘、然后存档时
才炸。**

另外，介质物品绝大多数时间待在**玩家背包**里，而 `containers_engine.py` 顶部明确
记着背包路径的三个原语「一次都没在真机上跑过」。归属标记要建在这条路上，所以这一轮
把它一并测了。

## 二、怎么测的

运行版本 `3.9.0.401155`，世界 `MC_DEV_WORLD`，py2.7.13，经 MCDK 的
`execute_code` 在服务端执行。探针脚本是临时的、**没有入库**（与 04 的处置一致：
读数与结论入库，探针本身不留）。

四轮，逐轮收窄：

1. **ExtraData 与 userData 的上限**：写入不同大小的载荷，比对世界目录
   `db/*.log` 的 WAL 增量，并用标记串 `grep` 磁盘做直接证据。
2. **保存时点**：两个标记对照（只 `SetExtraData(autoSave=False)` vs 额外调
   `SaveExtraData()`），相隔约 100 秒、跨一次 WAL 轮转。
3. **介质载荷大小**：用真实的 `Medium.to_dict()` 按型号装满，量 JSON 字节数。
   （离线即可做，跑在 py3.11 上，因为量的是纯领域对象的序列化大小。）
4. **归属标记与背包路径**：把带三种候选标记的真实介质物品
   （`endernet:singleside_tape`）写进玩家背包再读回，做严格字节比较。

落盘探针做过一次善后：探针用的箱子已逐槽清空并整块移除，临时 ExtraData 键已删，
区域扫描确认没有别的残留。

## 三、实测结论（摘要）

完整读数与表格见[持久化后端与引擎落盘实测](../technical_notes/persistence_backend.md)，
这里只留会影响决策的几条。

1. **物品 `userData` 单个字符串硬上限 32767 字节，超限是断言不是报错。**
   引擎 `DataIO::_writeString` 里有 `v.length() <= 0x7fff` 的断言。写入返回
   `True`、读回完整无误，**错误只在保存序列化时现形**。→ 写进去的单个字符串必须
   远小于 32767。这是**逐字符串**限制，总量上限没测，不能当成「拆成小串就安全」。
2. **介质内容装得下但现在也不装**：按型号装满只有 2963 B（12 类型）与
   12144 B（64 类型），离 32767 有余量，但型号 `max_types` 一扩就撞，而撞的表现
   是存档时断言。**权威内容走世界记录，物品只带身份与展示。**
3. **世界 `ExtraData` 会落盘**——标记串在 leveldb WAL 里直接 `grep` 到了，
   是直接证据而不是从返回值倒推。64 KB 单键往返一致，上限没探到。
4. **每次保存约 39.8 KB 固定开销 + 载荷**，与载荷几乎无关。→ 批量合并是必需品
   不是优化（12-08）。
5. **`autoSave=False` 只有 `SaveExtraData()` 能提交，且提交是异步的。**
   返回 `True` **不等于**已落盘。「已提交」与「已持久」之间有一个窗口，
   12-05/12-06 必须以它为前提：**不承诺任意时刻崩溃精确一次。**
6. **`unicode` 值被引擎静默丢弃**（连同它的键），容器路径与背包路径**一致**；
   非 ASCII 的 `str` 字节串字节级原样。→ ID 与标记都用纯 ASCII `str`。
7. **三个候选归属标记在两条路径上都字节级原样往返**——不可见的 `§1§2§3`、
   可见的 ` [ENLORE1]`、零宽空格串。选不可见的那个。
8. **背包三个原语都跑通了**：`GetPlayerItem` / `SpawnItemToPlayerInv` /
   `SetInvItemNum`（`SetInvItemNum(slot, 0)` 返回 `True`，该槽随后读为 `None`）。

## 四、定下来的两件事

### 后端

**物品携带身份与展示；权威内容按介质 ID 存进世界 `ExtraData`，一块介质一个键**
（键 = `Repository` 的 `(kind, record_id)` 映射成 `endernet:<kind>/<record_id>`）。

一块介质一个键而不是一整块大 blob：运行版本的 `SaveLevelData` 有按 key 增量落盘的
分支与 `TrackedDict` 脏键跟踪，一个键才让「只有这几块脏」变成真的省——而第三节第 4 条
说明固定开销是按**调用次数**付的。提交点集中在 12-08 的合并写。

### 介质身份

写在 `medium_lore.md` 第 2 节的「12-02 定案」里，此处只列骨架：

| 项 | 定案 |
| --- | --- |
| ID 载体 | 物品 `userData["endernet:medium"]` = `{"id": <ASCII str>, "v": <int>}` |
| 分配时机 | **只在首次挂载/进网时**由持久化发号器分配；读取路径永不生成 |
| 空介质 | 合法的未初始化介质；同型号空介质同身份、**可堆叠**；初始化后 ID 不同即不可堆叠 |
| 重复 ID | 同网络内第二个同 ID → **拒绝挂载并报重复**，不合并 |
| 记录缺失 | 按**孤儿**处理，不可读不可交易，**不得当作空盘** |
| 容量行标记 | 行尾不可见颜色码串 `§1§2§3`（`\xc2\xa71\xc2\xa72\xc2\xa73`） |
| 格式版本 | **不写进 Lore**，由同一物品载体的 `v` 给出（单一事实来源） |
| 识别方式 | 只按标记串判归属，不按中文前缀、不按行号 |
| 归一化 | 身份投影里剔除管理行后为空则省略该键；**真实物品载荷一律不动** |
| 旧数据 | 按完整旧记录重建，不原地改键；身份不确定的保留待核对、不按剩余量合并 |

## 六、未验证项与已知限制（重要）

- **方块实体数据的大小/时点/返回值没测**。它的适用性结论有（位置绑定，做不了介质
  内容后端），数值没有。任务 12-02 原文把三者并列，**这一项只完成了「适用范围」那一半**。
- **leveldb 的 fsync 耐久性没测**。LevelDB 默认不 sync，所以第三节第 5 条那个窗口
  在**掉电**场景下有多宽没有读数。**拿到读数之前不承诺掉电精确一次。**
- **原生 tooltip 的目视效果没确认**。悬停渲染不能自动驱动，`§1§2§3` 是否真的一像素
  都不显示需要人眼。**若不成立就退到可见的 ` [ENLORE1]`**——它同样实测过字节往返。
  为此在世界 `MC_DEV_WORLD` 的玩家快捷栏**第 1 格**留了一件探针介质（第 2 格的探针纸
  已清掉）。三行 Lore 分别是三个候选，看完即可丢弃。
- **经 tooldelta 物品包装层写 `userData` 的路径没有重测**。本轮读数全是引擎直连路径；
  `resource_identity.md` 记的 2026-09-25 旧读数来自包装层且与直连不一致，
  那条路仍应假定旧读数成立。
- **玩家背包路径上的 `customTips` 未测**。它会被引擎从顶层搬进
  `userData["ItemCustomTips"]`，影响 05/06 的守恒核对，也可能影响介质物品的身份投影
  ——契约里把它归入「其他身份字段」，**但那个归类没有实测支撑**。
- **契约尚未落到代码**。`capacity_lines()` 还没有标记，身份投影还没有排除管理行，
  `id_source` 还是进程内替身。因此**本文件不能作为「介质 Lore 已实现」的依据**。
