## 三、接口输入输出

### `plan(target, amount, inventory_snapshot, pattern_snapshot, policy)` → `PlanJob`

签名与任务文档一致，另有两个可选参数：`pattern_policy`（R09 的口径，默认保守侧）
与 `policy`（`PlanPolicy`）。返回**任务**而不是结果，因为 08-05 要的是可分帧推进。

### `PlanJob`

| 入口 | 语义 |
| --- | --- |
| `step(budget)` | 推进 `budget` 个工作单位，返回当前状态。**预算耗尽不是失败**，停在 `RUNNING`，下一帧接着来；`step(0)` 是合法空操作 |
| `cancel(detail="")` | 取消，结果作废为 `None`。**不改任何真实库存**（本模块没有写入口，这是结构性的） |
| `status()` / `result()` / `progress()` | 状态 / 计划（未算完或已取消时为 `None`）/ 给 11 的纯数据进度 |
| `ledger()` / `edges()` / `refused_edges()` | 账本、依赖边、**被环拒绝的边**（诊断与自证用） |

### `CraftPlan`

- 基本：`version` / `target` / `amount` / `semantics` / `status` / `steps` /
  `materials` / `gaps` / `blocked_keys` / `limits` / `estimates` / `seal`
- **三个数一起给**（08-01 的「同一口径」）：`requested`（玩家要多少）、
  `held`（其中由现有库存抵扣了多少）、`produced`（本次要产多少）。
  `HOLD` 口径下三者满足 `held + produced >= requested`；`PRODUCE` 下 `held` 恒为 0。
- `digest()` —— **内容**指纹（依据不在里面，见第四节）
- `execution_order()` —— 步骤下标，**是合法拓扑序**（依赖在前、消费者在后；
  由依赖边图算出的层级排定，**不是**按 `depth`——`depth` 会被更浅的路径调小，
  不满足拓扑序，见第七节第 13 条）
- `dispatch_triples()` —— `[(设备实例引用, 槽位, 指纹, 模式)]`，逐个交给 07 的
  `check_dispatch`
- `revalidate(check_dispatch, inventory_snapshot, topology_version)` → `RevalidationReport`
- `summary()` / `to_dict()` / `reasons()` —— 纯数据；`to_dict()` 可直接 `json.dumps`

### `PlanPolicy` —— 八个字段，全部进未定清单

| 字段 | 规则 | 替身取值 |
| --- | --- | --- |
| `target_semantics` | R11 | `HOLD`（目标保有量，已有成品抵扣） |
| `candidate_order` | 08-04 | `STABLE`（照 07 给的稳定顺序） |
| `alternative_recipes` | 08-04 | `FIRST_MATCH`（只取第一条可用候选） |
| `max_depth` / `max_steps` / `max_candidates` / `max_batches_per_step` | 08-04 | 16 / 64 / 8 / 1000000 |
| ~~`memory_units_per_step`~~ → `byte_rounding` | R07 | `CEIL`（向上取整，宁多不少） |

> 最后一行是 **2026-09-26 新规则增量**改过的：内存不再按「聚合步骤数 ×
> 每步系数」估，而是 `根原料总单位物 × 1 B`（中间的产物不重复收费），
> 于是 `memory_units_per_step` 被删掉、换成了「根原料不足一个单位物时
> 怎么取整」这个**边界**字段——1 mB 的原料会算出 0.02 字节，而 R07
> 尚未确认取整口径，所以不擅自舍入，做成具名策略让替身取值看得见
> （`ByteRounding.CEIL`／`.FLOOR`，默认 `CEIL`）。字段数仍是八个。
> 见 [订单规则对齐](../technical_notes/order_planning_execution.md)。

后五个是**帧安全阀**，不是玩法数值；但它们仍然是「配置点」，因此照 04 的先例
一并进 `unresolved_report()`。`assert_settled()` 只在正式验收调用。

**未实现的选项在构造期直接抛错**（`LEAST_MISSING`、`SEARCH_MULTIPLE`），
照 `ReturnRule.DERIVE_CONTAINERS` 的处置：一个「看起来更优」的顺序一旦生效
就是一条被替身悄悄定案的玩法规则。

### 快照（纯数据，由调用方 capture）

- `InventorySnapshot.capture(storage)`：走 `keys()` + `query()`，只认
  `available = stored - reserved`（**别人的预留看不到**，05 的口径）。
  `from_payload()` 吃 `StorageService.snapshot()` 的纯字典形状（12/11 会给 JSON）。
- `PatternSnapshot.capture(store, topology_version)`：对每个产物调
  `candidates(key, include_unavailable=True)`，**深拷贝成纯值**
  （位置元组、代次、槽位、指纹、模式、`PatternDefinition`、可用性、阻塞原因）。
  带上不可用的候选是必须的：只拿可用的会让「有样板但都在离线」与「根本没有样板」
  变成同一个答案。

### 新增原因码

| 码 | 什么时候 |
| --- | --- |
| `plan_no_recipe` | 样板索引里根本没有产出这个资源的样板 |
| `plan_no_available_provider` | 有样板，但候选全不可用（离线、读不到、被拆） |
| `plan_missing_materials` | 配方找到了，基础原料不够（**部分计划**） |
| `plan_cycle` | 搜索路径上出现循环依赖 |
| `plan_limit_reached` | 深度/步骤数/候选窗口/批次上限触顶 |
| `plan_budget_exhausted` | 本帧预算用完，任务可继续。**它不是失败** |
| `plan_cancelled` | 调用方取消 |
| `plan_stock_changed` | 提交前复核：计划声明要用的那几个键的库存不够了 |
| `plan_topology_changed` | 提交前复核：拓扑版本变了 |

**刻意不合并成「没有配方」**（08 文档原文要求）：四种情形对玩家意味着完全不同的
下一步动作——「去装一块样板」「去把离线的那台设备接回来」「去补基础原料」
「少要一点」。糊成一个码就等于把「我该做什么」丢掉。

### 只读查询

`debug_query("plan", target=<ResourceKey>, amount=<int>, component_id=<网络>)`：

- 用**该网络的真实库存**（`available = 库存 - 他人预留`）与**真实样板索引**跑一次规划；
- 没给 `component_id` 就按**空库存**规划，并在 `inventory.note` 里写明原因
  （「空库存」不等于「这个网络什么都没有」，读的人要能分辨）；
- 样板索引是**全局**的（07 的索引不按网络分区），库存是**逐网络**的；
- 返回 `summary` + 完整 `plan` + 库存/样板的来源说明 + 一句「估计值不是预留」。

与 `port` / `pattern` 同形：**没有主控、网络不能工作时照样能答**，而且答的正是
最有用的那部分。这条入口存在的理由写在 `DEBUG_OPS` 里：09 未实现之前规划没有别的
调用方，而仓库纪律明写「只有类文件、没有装配与调用路径的实现不算完整交付」。

## 四、适用存档版本与持久化

### 计划格式：`version: 1`

`CraftPlan.content["version"]`，与 `ResourceKey.schema_version`、
`PATTERN_FORMAT_VERSION` 同一条纪律。计划会流到 09 的订单与 11 的预览，
因此它的形状变化必须能被认出来。

### **08 不存档，也不迁移**

计划是**一次计算的产物**，不是权威状态：它的两份输入（库存、样板索引）都有自己的
权威（05 的介质、07 的方块容器），而它自己没有任何别人拿不到的东西。
12 恢复之后不需要「恢复计划」——**重新规划一次即可**，而且更准。

**如果 12 或 11 要缓存一份计划**（比如断线重连后回到订单列表），必须连
`seal` 一起存，并在用之前跑一次 `revalidate()`：计划的依据会过期，而
**一份过期的计划看起来和一份有效的一模一样**。这条写在 `CraftPlan.revalidate`
的 docstring 里。

### 指纹与依据分开

`digest()` 只认**内容**，不含 `inventory_version` / `inventory_digest` /
`topology_version`（那些在 `seal` 里）。因此「同一份计划、不同的库存版本」
是同一份计划——09 的去重与 11 的「预览有没有变」要的正是这个语义。
反过来，复核**不看版本号看量**：版本变了但计划声明过的键没少，计划照样成立。

## 五、未定规则与剩余限制

### R11：替身取 `HOLD`，另一侧具名可选

**替身口径是「目标保有量，已有成品抵扣」**（2026-09-25 选定）。另一侧
`PRODUCE`（要多少产多少）完整可用、有用例覆盖，但**默认不是它**。

两种口径的**唯一**差别落在 `exempt` 一处：`PRODUCE` 下根需求整份不许被库存抵扣
（否则「要 3 个」会被库里的 3 个悄悄吃掉，两种口径退化成同一种行为）。
嵌套需求两侧完全同构。

`HOLD` 下「库里已经够了」会得到**一份零步骤但 `COMPLETE`** 的计划——这不是失败，
`summary` 里 `requested/held/produced` 三个数一起给出，因此读起来是
「已在库中满足」而不是「什么都没做」。

**替身不等于定案**：R11 一天没写进上级玩法文档，08/09/11 就一天不能宣布验收，
`assert_settled()` 会拒绝，`PRODUCTION` 档的准入链会拦。

### 一条留给 14 的注记：规划侧的未定项拦在哪一层

评审顺带查明的一件事，值得写下来免得 14 误判：**主控的准入链读的是
`runtime.policy`（即 `BandwidthPolicy`），因此 R11 / R04 / 08-04 不在那条链上**
——它们由 `assert_assembly_ok()`（显式调用）与诊断报告拦，走的是与 R09 同一条路。
这正是 03 交付说明第六节说的那个形态：**运行期拦截与装配期检查是两件事**，
规划侧这三条落在后者。14 要做发布验收时，得记得显式调
`assert_assembly_ok()`（或把策略并进主控那条链），否则它们不会自己跳出来。

### R04：内存与槽位是**估计值**，不是预留证明

`estimates.slots` 带 `authoritative: False` 与 `basis` 说明。08-06 明写
「估计值不作为真实资源已预留的证明」，因此 09 拿到计划之后要自己按 R04
复核槽位与内存。

> **这里有一条刻意的分工**：`required_bytes` 与 `total_recipe_tasks()` 是
> **顶层**字段，**故意不挂在 `estimates` 里**，也不带 `authoritative: False`
> ——混进去会让 09 顺手把它们当「参考值」用。它们仍是「按快照算的账，不是
> 预留」（规则要求准入时重新核对网络**当时**的可用字节），所以 09 是拿这个数
> 去问网络，不是拿这个数直接扣。

> **2026-09-26 新规则增量后这一节改了口径。** 三处要点：
>
> 1. **内存的数字换了来源。** 原先报的是 `estimates.memory_units`（聚合步骤数 ×
>    `memory_units_per_step`），现在报的是**顶层**的 `required_bytes`＝
>    `根原料总单位物 × 1 B`（`ByteRounding` 取整、默认向上）。**中间产物不重复
>    收费**是这条口径的关键：一份计划里有几层配方、几条链，都不影响字节数。
> 2. **`estimates.slots` 的含义被限定清楚了。** 它算的是**派发位**（每个步骤一个），
>    是给 08-04 的搜索上限看的估计，**不是**并行槽位的计费口径。并行槽位是
>    「每次配方执行占 1 槽」，由顶层的 `total_recipe_tasks` 那个数量级决定，
>    真正领取它的是 09（见 `server/crafting/capacity.py`）。
> 3. **09 还没有消费这两个新数字**，仍在按聚合步骤数估内存，因此本节的
>    「09 要自己复核」目前仍然是必须的，不是走过场。

### 已知实现限制

1. **计划不给「每一步用掉哪份库存」的分摊。** `materials` 是整份计划层面的账；
   同一个键被两条链要时，那份库存归谁是 09 的分配决定（见第六节第 2 条，
   那里给了顺着执行顺序推的方法）。08 不做这个决定，是因为做一次就要在需求
   后来变大时反分配，而漏掉任何一条反分配路径的表现就是「同一份产出许给两家」。
2. **规划不是预留。** `from_stock` 只是「按快照现在的样子算」，
   **两个订单在同一帧各自规划时会都算上同一份库存**——避免这件事是 09 提交时
   `reserve()` 的职责，而 08 为此提供 `claims` 与 `revalidate`。
   这是本轮最重要的一条交接（第六节第 1 条）。
3. **流体配方与物品配方一样算**（它们只是资源键），但**执行侧整条未接入**
   （13-03），因此流体计划目前派发不出去。计划里不区分，交付说明里说清楚。
4. **预设配方未适配（07-03）**：08 只读玩家装的样板，`NoPresetRecipeSource`
   照旧拒绝。因此「系统预设-工作台/熔炉」那两条还走不通。
5. **过旧的样板会看起来像「没有样板」**：07 的 `_ensure_index` 把
   `is_dispatchable()` 为假的样板排除在索引外，因此 08 看不到它们，
   报的是 `no_recipe`。要查过时的样板走 `debug_query("pattern")`（那里报
   `stale_slots`）。这是 07 的设计，本轮沿用并记在这里。
6. **候选只取第一条可用的**（`FIRST_MATCH`），其余候选只记录在步骤里不展开。
7. **自引用配方一律判环**（`A ← A + B`，催化剂/回收类）。这与 08 文档
   「循环生产不作为首版自动支持项」一致，是保守侧：宁可报「做不到」，
   也不假装一条环能跑。
8. **`returns`（返还物）只报不记账**——见第七节第 1 条。
9. **`blocked_keys` 会连带标出上游**：基础原料缺了，整条链都会被标成
   执行不了（原因 `missing_inputs`，不是 `no_recipe`）。这是有意的：一份
   按原样执行不了的计划，`COMPLETE` 之外的每个祖先都不该看起来有货。
10. **规模未测**：只跑过 4 条样板、1~3 层的图。大图的帧预算属任务 14。
11. **复核报告里的键只给规范文本，不给名字。** `stale_stock` / `stale_dispatch`
    的条目里是 `canonical`，显示用的名字要拿它去**计划自己的** `materials`
    里查（这正是复核器取名字的方式，见第七节第 14 条）。之所以不在报告里
    直接塞一份 `ResourceKey`：那要从纯值反解回来，而反解会经过身份归一化，
    报告上可能显示成另一样东西——「哪一条材料不够」只需要名字，
    为此换一份可能对不上的身份不值当。

## 六、与下游任务的接口定调

### 1. 08 → 09：**计划不是预留**，提交时必须复核

`plans/` 里没有一处明写这件事，而它是 08/09 接缝上最危险的一条，因此钉死：

    CraftPlan 的 from_stock 只是「按快照算的账」，不是预留。
    09 在提交时必须：(a) 用当前的库存与样板重新跑一次 revalidate()，
    (b) 复核通过后按 claims 逐个 reserve()，预留成功才派发。

理由：08 刻意**不预留**（它是只读计算，08 文档的边界），而两份计划在同一帧
各自算上同一份库存是完全正常的。**把 `from_stock` 当成「已经有我的份了」
会让两个订单同时开工、原料却只够一个。**

具体的凭据：`seal["claims"]`（逐键声明用了多少库存）、
`seal["dispatch"]`（每一步用的是哪块样板的哪个版本）、
`seal["topology_version"]`。复核失败时的正确动作是**用新快照重规划或拒绝并报告**，
绝不能拿旧计划去扣料（08 验收第 5 条）。

### 2. 08 → 09：**每一步要备多少料，由 09 顺着执行顺序自己推**

`materials[key]` 给的是**整份计划层面**的账：这个键一共要多少、其中多少来自库存、
多少由计划产出。它**没有说「哪一步用掉库存里的那几个」**——同一个键被两条链要时，
那份库存归谁是一个**分配决定**，而 08 刻意不做（做一次就要在需求后来变大时
反分配，而漏掉任何一条反分配路径的表现就是「同一份产出许给两家」，见第三节的账本说明）。

09 的推法是顺着 `execution_order()` 走一遍，维护一个"手头还有多少"的表：

```
running = {键: materials[键].from_stock}        # 起点：库存里划给这份计划的那部分
for step in plan.steps（已是执行顺序）:
    for entry in step["inputs"]:                # entry["total"] = 这一步要的量
        仍需从外面拿 = entry["total"] - running[entry["key"]]
        running[entry["key"]] -= min(running[entry["key"]], entry["total"])
    for entry in step["outputs"]:               # 这一步做完，产出进入手头
        running[entry["key"]] += entry["total"]
```

`execution_order()` 是**合法拓扑序**，因此走过去的每一步，它的输入都已经有着落。

三个坑写在明处：

- `running` 里的库存部分是**已经由 `claims` 声明、但还没有真的预留**的量
  ——09 必须自己去 `reserve()`（第 1 条）。
- **不要**拿 `demand - from_stock` 当「必须生产的量」：那个差是
  `outstanding`（这个键还差多少），而「本次计划安排生产多少」是 `own_output`。
  批次取整多出来的余量会让两者不相等——那正是 08 验收第 2 条要保留的东西。
- 被标成 `blocked` 的步骤不进这个循环：`blocked_keys` 非空就整份计划拒绝（第 1 条）。

### 3. 08 → 11：进度与结果都是纯数据，且**没有引擎对象**

`job.progress()`（状态、待办数、步骤数、缺口数、已花的工作量、
`plan_budget_exhausted` 或 `plan_cancelled`）与 `plan.summary()`
（`requested/held/produced`、步骤数、缺口按原因分类、缺料清单、是否被截断、
估计值）。`plan.to_dict()` 可直接 `json.dumps`。

**`HOLD` 与 `PRODUCE` 的差别只体现在数值上**，界面不需要分两套逻辑：
三个数一起给，显示什么由界面决定。

### 4. 08 → 07：读的是 `candidates(include_unavailable=True)`

只走 07 交付说明第九节点名交给 08 的两个入口（`output_keys()` 与 `candidates()`），
**不 import `store.py`**。`check_dispatch` 以鸭子类型注入（签名
`(ref, slot, digest, expected_mode) -> (entry, blocker)`），因此 08 不依赖 07 的实现。

**环检测为什么在 08 而不在 07**：环是**配方之间的关系**，不是单块样板的属性
（同一块样板在 A 图里成环、在 B 图里不成环）。07 的 `check_dispatch` 只回答
「这块样板还是不是原来那块」，那是版本身份，不是图结构。

### 5. 08 → 12：不需要恢复计划

见第四节。要缓存就必须连 `seal` 一起存并复核。

### 6. 08 → 14：`assert_settled()` 与 `policy_bundle()` 已就位

R11/R04/08-04 定案之后只改策略，不必动算法，也不会让已算出的计划换一套含义
（与「已存档的样板内容与 R09 的含义分开」同一条设计）。

## 七、开发过程中撞到并修好的问题

（第 2、3、4、9、19 条是自查时撞出来的，其余是**交付前的两路代码评审**找出来的
——它们都只在「预算怎么切」「边界输入」「py2 的字符串语义」「夹具恰好绕开的形状」
这类事情上才发作，逐个夹具的用例原本照不到。第 10、12、14 条是其中三条真正严重的：
第一条会给出一份**假成功**的计划，第二条会让**环**伪装成能做完，第三条会让
**复核本身崩掉**。三条都补了回归用例，且都在真机上复验。）

**这一轮评审最值得记下来的一条经验**：第 10 条那个缺陷，三个地方**同时**绕开了
它的形状——离线夹具把「3 个铁锭」写成一条无槽位的输入（只有工厂样板能那么写）、
性质测试的生成器给输入去了重、真机上验的是「铁块 ← 2 铁锭」这一条。
三处各自看都合理，合起来就是对**合成样板的标准写法**视而不见。
「已实现 ≠ 已覆盖」在这条上体现得比哪一条都清楚：夹具是人挑的，
而人挑的形状会不自觉地贴着实现的假设走。

### 1. 计划内容里混进了「预算怎么切」，确定性直接失效

`content["counters"]` 原本带上了 `rounds`（`step()` 被调了几次）。于是**同一份输入**、
只因为分两帧还是三帧跑，就得到两个不同的指纹——而指纹是 09 的去重与 11 的
「预览变了吗」的唯一依据。

修法是把它排除在计划之外（改成只进**与工作量相关**的那四个计数）。
值得记下来的是：**这条是「验收第 4 条」存在的理由本身**，而它不会在任何一个
固定夹具的用例里发作，只有在「同一份输入、不同预算」的对照里才现形。

### 2. 环检测必须建在边图上，不能建在「祖先路径」上

需求按资源键**聚合**（同一个键被两个分支要，只留一条需求），聚合就丢了逐分支的
祖先路径，于是「这个输入键在不在当前路径上」会漏掉真实的环。

反例：目标 `T` 需要 `A` 和 `B`，而 `A ← B`、`B ← A`。按路径判时 `B` 的路径是
`[T, B]`，看不到已经存在的 `A→B` 这条边，两条边于是互相长大，只能等上限截断
——报出来是「超限」而不是「循环」，而这两件事对玩家完全不同。

改成「插入一条边之前，先问子键是不是已经能到达父键」之后，边图**按构造是 DAG**，
终止性因此可证（上限只是安全阀，不是「靠它才停得下来」）。
`test_a_cycle_through_a_sibling_is_still_caught` 就是这个反例的回归用例。

### 3. 一条深链上的死路会让祖先步骤「看起来有货」

一开始只有账本：每个键的需求与产出各自算。于是目标需要 `X`、`X` 需要 `Y`、
`Y` 需要一份**没有配方**的 `Z` 时，`X` 与目标的 `own_output` 照记，**看起来都齐了**
——而 `Z` 只在最底下报一句缺料。玩家会以为这份计划能执行，09 也可能据此去预留。
这正是架构规划点名的那类谎（「说做得到、其实做不了」）。

修法是收尾时按反向依赖迭代到不动点：输入凑不齐的步骤**产不出东西**，
它的产出因此不计入可达量，于是上游跟着不可达，直到稳定。
`blocked_keys` 把这条链整段列出来。

### 4. 「上游缺料」被报成了「没有配方」

接上一条：可达量传播之后，被标成执行不了的 `X` 需要一个原因。第一版照抄了它子树里
最深的那条缺口（`no_recipe`），于是报告写着「铁锭：没有配方」——**而铁锭的样板
明明就装在上面那一格**。玩家会去找一份已经存在的样板。

修法是给传导而来的那一类单独一个原因 `missing_inputs`，说明里点名**上游是谁、
为什么断**。与 `no_recipe` 分开是必须的，正如它与 `no_provider` 必须分开一样。

### 5. 候选窗口「先过滤再截断」会让截断被误报成「没有提供者」（评审）

`max_candidates` 是帧安全阀。第一版先按可用性过滤、再取前 N 个：于是窗口的宽度
随「恰好有几台离线」变化（同一份输入不可复现），更糟的是**截断会被报成
`no_provider`**——玩家去修一台没坏的设备，而真正要做的是放宽窗口。

已修：**先截断、再过滤**，且「窗口内没有可用候选、但后面还有候选」回
`candidate_limit`。与 08 文档「不能统一称为没有配方」是同一条要求在下一层的落点。

### 6. `PlanSeal` 的派发凭据少了一个字段（评审）

`revalidate` 按规范文本回查材料清单，而 `seal["dispatch"]` 里只写了键的**名字**。
于是复核在任何一次「样板改了」的路径上都 `KeyError` ——**复核器自己先炸了**，
而那正是「提交前最后一道闸」。已修并补了断言（复核报告必须能直接 `json.dumps`）。

### 7. 复核把 07 的四个不同原因压成了一个（评审）

样板腿的复核原本无论什么毛病都报 `pattern_stale`。但 07 为这几种情形各自留了码
（`device_gone` / `driver_unloaded` / `pattern_stale` / `pattern_kind_mismatch`，
以及过旧格式的 `pattern_format_unsupported`），而它们对 09 是**四句不同的话**
（「设备没了，放弃这个订单」与「样板被编辑了，重做计划」完全不是一回事）。

已修：07 的原因码**原样透出，并按码分组**（一腿里也可能有多个原因）。

### 8. 非 ASCII 的格式模板缺 `u` 前缀（评审 + 自查）

21 处中文 `%` 模板写成了字节串。py2 上「非 ASCII 模板 + 插值 unicode 值」
会按 ASCII 解码模板并抛 `UnicodeDecodeError`，而 `ResourceKey.name` 在 py2 上
**永远是 unicode**——最典型的是 7 个 `__repr__`（一个中文名的资源被打印就炸）。
`py2check` 明确不覆盖 `str`/`unicode` 语义，因此离线测试对这类问题**完全瞎**。

已修：写了一个基于 `tokenize` 的一次性脚本给这些字面量补 `u`（**含多行隐式拼接的
每一段**——只补第一段的话，py2 的拼接本身就会解码失败）。脚本已删除，
判据与 07 交付说明那条一致。

### 9. `LedgerRow.depth` 用 0 当哨兵（自查）

「还没设过深度」原本是 0，而 **0 是一个真实取值**（根目标就在第 0 层）。
于是根节点的深度会被判成「没设过」，进而在排序与上限判定上给出错误的位置。
已改为 `None` 哨兵。

### 10. **同一种原料写成多条时，需求只记了最后一条（评审，最严重的一条）**

`_expand_next_input` 按**每条**输入算增量：`need = 该条数量 × 批次 - 已记`。
但「已记」是按**键**累加的，于是第二条算出负增量、直接跳过——账本只留下第一条的量。

**这不是边角情形，而是合成样板的标准写法**：`patterns._check_layout` 要求
有序输入每条占一个槽位、且槽位不重复，所以「3 个铁锭」必然是三条输入
（槽 0、1、2）。工厂样板把同一种料写两遍同样是合法样板。

后果是一条**假成功**：

| | 步骤自己报的 | 账本记的 |
| --- | --- | --- |
| 铁镐 1 批 | 需要 3 个铁锭 + 2 根木棍 | 铁锭需求 1、木棍需求 1 |

于是库里只要有 1 个粗铁与 1 块原木，计划就报 `complete`——而那份派发实际要 3 个。
09 按 `claims` 预留会少扣，按 `steps[].inputs` 派发会多要，**同一份计划里的两个数互相矛盾**。

离线用例没有照到它，是因为夹具把「3 个铁锭」写成**一条**无槽位的输入
（那只有工厂样板能表达），而性质测试的随机生成器又**给输入去了重**。
真机上验的「铁块 ← 2 铁锭」同样是一条。**三处都恰好绕开了这个形状。**

已修：输入在记账前先**按键合并**（`CraftStep.input_pairs`），合并后的列表同时用于
展开、可达量判定与派发清单，两个数不可能再分叉。回归用例
`TestDuplicateInputs` 用**真实的有序写法**写铁镐，并断言「原料不足时不得报 complete」。

### 11. 被环拒绝的边每重走一遍就再记一次需求（评审）

`_refused` 里的毛量在下一次重走时又从 0 算起（只有 `_edges` 被减掉），
于是同一个键的需求会随重选次数膨胀——膨胀出来的需求谁也满足不了，
报告里就成了一个查不出原因的缺口。已修：两条账（接受与被拒）都参与增量计算。

顺带把**被拒绝的边不再记需求**：它既不会被任何步骤产出、也不会由库存来补，
记进去等于凭空造一笔永远满足不了的需求（`PRODUCE` 口径下还会让它误以为
用上了库存）。「这条输入要不到」由三处独立表达——该键自己的 `CYCLE` 缺口、
父步骤的 `blocked`/`blocked_by`、以及收尾的可达量传播——一样都不会丢。

### 12. 可达量算的是**最大**不动点，互相依赖的两步会互相作保（评审）

`_achievable` 原本从「全都能跑」往下减：判 A 时拿 B 的产出当供给，
判 B 时又拿 A 的产出当供给，于是 `A ← B`、`B ← A` 双双「凑得齐」。
环因此会伪装成一份**能做完**的计划（`complete`），而它一步都执行不了。

已修：改成从「一步都跑不了」**往上加**——每一步都必须由已经证明拿得到的东西
（库存 + 已确认可执行的步骤）支撑，结论只少不多。这与 `_verdict` 把真实原因
排在截断之前是同一条取向：**宁可说做不到，也不说做得到**。

### 13. 步骤顺序号称是拓扑序，实际上不是（评审）

顺序原本按 `step.depth` 排，而 `depth` 是「被见到的最浅深度」，它会在依赖边
建立之后被更浅的路径**调小**——于是「每条边都从 depth 指向 depth+1」不再成立。
一个键既被目标直接需要、又是另一条链上的子需求时（**共享子需求，08-03 的核心形状**），
依赖会被排到消费者之后，09 照着派发就会先派发一条原料还没到位的步骤。

已修：`execution_ranks()` 由边图算层级（叶子为 0，父键为子键最大值 +1），
按层级**升序**排列必然是合法拓扑序。把顺序写成「升序」也算一次自查——
第一版改成了降序，那会得到一份**反**拓扑序：看着每条边都跨层，实际上正好反过来。
回归用例不再钉死一份具体顺序，而是**按边验证**「依赖必须排在消费者之前」。

### 14. 复核在「声明过的键整个消失」时抛异常（评审 + 真机）

`_find_key` 找不到时返回了**规范文本字符串**，而报告层对它调用 `_name()`。
05 的索引在存量归零时会把整行删掉（`_set_stored`），因此「被拿光了」与
「从来没见过」在新快照里是同一个样子——**而那正是最该拦下来的一种变化**。
复核因此不是拒绝、而是崩掉：09 失去唯一那道闸，异常还会冒到帧里。

已修：报告只依赖**计划自己记着**的材料清单取名字（`CraftPlan._label`），
不在场地上现找；找不到的键按「现有 0」处理并报 `plan_stock_changed`。

### 15. `gaps` 与 `blocked_keys` 对同一个键给出两个数（评审）

两个字段原本用两把尺子：`gaps[].shortfall` 取账本池子的 `outstanding`，
`blocked_keys[].shortfall` 取可达量。池子把「一个执行不了的步骤的产出」也算进去了，
于是可能出现「账面上够了、实际拿不到」——那时缺口若被丢掉，`blocked_keys` 里
却还有它，两个字段对同一件事给出相反的说法。

已修：缺口的去留与数量**都改用可达量**，「有缺口」与「执行不了」从此是同一件事；
`_inherited_gap` 也改为**同时走被拒绝的边**，否则「输入全在环上」的键找不到
任何上游缺口，报告里只剩一句「缺口记录已不在」——而玩家该去看的是那个成环的键。

### 16. 规划在改快照（评审）

候选选中时被标了一个 `selected`，而候选属于**快照**：一份快照被两个任务共用时，
第二个任务会看到第一个留下的标记；更糟的是 `PatternSnapshot.digest()`
把候选算进去了，于是**「规划一次」会改掉快照的指纹**。

已修：删掉那个字段。「这一批用了哪个候选」记在**步骤**上
（`CraftStep.chosen` 与计划里的 `provider`），那才是它该在的地方。
回归用例断言「规划前后快照的指纹与内容一字不变」。

### 17. 性质测试的生成器把输入去重了，于是那个形状一次都没生成（评审）

见第 10 条：`random_recipes` 原本把同一键的输入合并成一条，

### 改了什么

规划器改成**先筛后建**：候选在**建步骤之前**逐个过 `_screen_inputs()`
（问「这条候选自己的输入在当前边图上能不能绕回本键」），会绕回的被排除、
继续试下一条；只有可用候选**全部**被排除时才记一条 `RECURSIVE_CANDIDATES`
缺料。**不是「试算—回滚」**：被排除的候选根本不碰账本（不改批次、不记产出、
不建边、不记需求），因此不存在残留污染，比回滚更强。

「材料库存优先」不用改代码——它在选择候选之前就返回，本来就成立。

### 顺带修掉的一个既有缺陷（本次最重要的发现）

**库存播种的环会返回 `COMPLETE`**：`T ← A + B`、`A ← B`、`B ← A`，
库存 1 个 B 时，B 的步骤被建出来自己产自己，收尾时可达量以库存为 B 播种，
于是 A 的步骤看着能跑、又反哺 B，最后那条缺口被「需求减可达量」删掉
——判决 `COMPLETE`。而那份计划**物理上做不到**：1 个 B 变不出「1 个 A + 1 个 B」，
并且 `steps[B].inputs` 声称消耗 1 个 A、`materials[A].demand` 只有 1，
同一份计划里躺着两个互相矛盾的数字。

**这条不是推理出来的**：先在未改动的代码上把
`test_a_stock_seeded_cycle_is_not_reported_complete` 跑红（报 `complete`
而不是 `missing_materials`），确认缺陷真实存在，再动代码。改后 B 的步骤
根本不建，库存池保持诚实。

### 可见的契约变化（09 与 12 都会看到）

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 成环时的总判决 | `CYCLE` | `MISSING_MATERIALS`（原因码 `plan_missing_materials`） |
| 缺口的 `reason` | `plan_cycle`（在 `CYCLE` 缺口上） | `plan_cycle`（在 `RECURSIVE_CANDIDATES` 缺口上） |
| `GapCause` | 有 `CYCLE` | 删 `CYCLE`，增 `RECURSIVE_CANDIDATES`（归 `ABSENCE_CAUSES`） |

| `PlanStatus.CYCLE` | 会产出 | 保留但**不再产出**（给 12 读旧存档） |

`steps[].blocked` 之所以恒为假：全仓库只有「展开时发现成环就拒绝那条边」
那一个写入点，而候选现在在建步骤之前就被排除，那个分支**不可达**了。

`blocked_keys` **不受影响**：它由「需求减可达量」算出，照旧列出真正拿不到的键。

新增三个诊断计数 `candidate_trials` / `recursive_candidates` / `cycles_refused`，
**不进 `content["counters"]`**，因此**不改变计划指纹**——它们是「实现怎么走的」，
不是「计划是什么」。

**一处环境坑（记下来避免重踩）**：`.mcdev.json` 开了 `auto_hot_reload_mods`，
改 `planner.py` 期间的**中间态**被热重载加载过并停在那里——运行中的模块
**词表是旧的**（`GapCause` 还有 `CYCLE`、`_GAP_REASONS` 没有
`recursive_candidates`）而**行为已经是新的**，于是缺口 `reason` 落进

`plan_limit_reached`，看起来像代码写错了。**改完代码必须显式 `reload_game`

**一处观察到但未定位的问题（不属 08，交回 07）**：实测中 `PatternStore.install()`
抛过一次 `TypeError: an integer is required`，栈是 `install` → `refresh(force=True)`
→ `content_fingerprint()`（`store.py:572` → `:275`）。**写入本身是成功的**，
只有紧随其后的重读比较炸了；同一容器几秒后重算指纹正常，**没有再复现**。
但有一处**结构问题是真的**：`refresh()` 的 docstring 写着「保证不抛」，
而 `before = state.content_fingerprint()`（`store.py:572`）落在内层 `try`
**之外**，它抛出的任何异常都会穿出 `refresh`。修法很小，但那是 07 的边界。

### 已知限制（记录，不在本轮修）

- **同深度兄弟由 `(depth, 身份)` 贪心定序**：成环那一侧先被选中时，
  好路线就没了，计划报缺料——**是次优，不是谎话**（环路径与缺口都诚实）。
  修它等于放开多候选搜索（`SEARCH_MULTIPLE`，仍待定）。
- **`_achievable` 按输入逐条比较、不做守恒**，同一份库存可能被两个消费者
  各算一次，于是 `steps[].runnable` 偏乐观。它不影响总判决（`blocked_keys`
  与 `gaps[].shortfall` 都走守恒正确的账本），属既有问题。
- **候选排序仍未定**：`LEAST_MISSING` / `SEARCH_MULTIPLE` 仍在构造期抛错。
  本次交付的是**过滤器**（一条候选自己会不会绕回本键），不是**搜索**
  （在多条候选之间挑最优），两者别混。
