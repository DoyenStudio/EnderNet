## 三、接口与语义

| 项 | 形状 |
| --- | --- |
| 记录键 | `endernet:<kind>/<record_id>`（`kind` 沿用既有的 `endernet.storage_medium` / `endernet.storage_driver`） |
| 索引键 | `endernet:index/<kind>`——**引擎的 ExtraData 没有键枚举接口**，`list_ids` 只能靠它 |
| 载荷 | JSON 字符串，`ensure_ascii=True`（理由与实测见 `persistence_backend.md` §3.4） |
| 提交 | `write` 只改引擎内存区（`auto_save=False`），`commit()` 是**唯一**的 `SaveExtraData()` 调用点，且**没有待提交改动时一次都不发** |
| 驱动器记录 ID | `node_key` 文本 `"维度,x,y,z"`——**位置才是稳定身份**，设备代次不是 |
| 介质 ID | `medium:<n>`；`use_durable_ids()` 把水位抬到存档里已有的最大序号之上 |

**存档版本**：`CURRENT_SCHEMA_VERSION = 1`（与 12-01 一致）。介质载荷自带
`MEDIUM_SCHEMA_VERSION = 1`（`medium.py`，12-03 未改其值）。

## 四、已实测确认（游戏内，`MC_DEV_WORLD`，运行版本 3.9.0.401155）

探针走 MCDK 的 `execute_code`（服务端）。**探针与它放下的两台驱动器方块
已逐项清理**：临时 ExtraData 键全部 `CleanExtraData`、两台方块改回空气、
登记表回到 26 台、`tick_errors` 为 0。

1. **ExtraData 的两种载荷形状都活过「保存 + 重载」**（新增读数，见
   `persistence_backend.md` §3.4）：嵌套 dict（含 `None`/`True`/`int`/`float`/
   列表/子 dict/中文）与纯 ASCII 的 JSON 串，`SaveExtraData()` 后重载读回
   **`==` 原值为真**。非 ASCII 的 py2 `str` 字节级原样。
2. **写盘路径通**：脚本放一台驱动器 → `force_backfill` 发现设备 →
   `create_medium` + 装槽 + 存入 3 个石头 → `flush_persistence()`。
   ExtraData 里出现
   `endernet:endernet.storage_medium/medium:1`（内容 3 个石头）、
   `endernet:index/endernet.storage_medium` = `["medium:1"]`、
   `endernet:endernet.storage_driver/0,23,70,-7`（槽 0 → `medium:1`，`slot_version` 1）。
   **`save_calls` 恰为 1**——整批一次提交。
3. **重载后内容跟着身份回来**：`restored_mediums: 1`、`restored_drivers: 1`、
   `restore_error` 为空；`medium:1` 仍是 `medium:1`（**未重新发号**），
   内容 3 个石头、`assert_consistent()` 通过、未标孤儿；`tick_errors` 为 0。
4. **槽位按位置重挂**：设备被重新发现后，槽 0 挂回 `medium:1`
   （`slot_version` 1 原样），`disk_count` 投影回到 `DeviceConfig.config["disk_count"] = 1`，
   并成功从该介质读出 1 个石头（`moved=1, complete`）。
   ——这条验的正是「**代次重启后从 0 重来也不丢盘**」：槽位存的是 `node_key`，
   不是 `DeviceRef`。
5. **跨驱动器重复挂载被拒**：放第二台驱动器、拿同一块盘装它的 0 号槽 →
   `duplicate_medium_mount`，消息指明它现在装在 `0,23,70,-7 的 0 号槽`。
6. **未知新版本被保留且永不写回**：手工往 ExtraData 注入一条
   `schema_version: 99` 的介质记录（内含 1234 个钻石）并重载 →
   它进 `frozen_mediums`，`recovery = unknown_schema`、`is_tradeable() = False`、
   `raw_payload` 完整保留（1234 个钻石一件不少），
   **`pending_archive_writes` 为 0**（跑了 12 帧一次都没试图写回）；
   同一份存档里的 `medium:1` 照常恢复。`unknown_version_skips: 1`。
7. **评审修复后重跑一遍**（见第七节）：写盘 → 重载 → `medium:100` 按原 ID 恢复、
   槽位回到 2 号槽、从中读出 1 个钻石成功、`tick_errors` 为 0。
   持久 ID 发号器在此顺带被验证：此前探针写到过 `medium:99`，
   重载后新发的号是 **`medium:100`**，确实是从存档推导的水位。
8. **「载荷读不懂」的盘在拆除驱动器后原封不动**（评审第 2 条的真机验证）：
   注入一条**信封版本仍是 1、载荷版本是 2** 的介质记录 → 重载后
   `recovery = unknown_schema`、进 `frozen_mediums`、不可交易、
   `raw_payload` 保留；接着**拆掉持有它的驱动器**（这条路径会调
   `note_medium_changed`，修复前正是在这里把空盘写回去的）→
   存档里的那个键**字节级没变**（`stored_unchanged: True`，
   里面仍是 `"schema_version": 2`），`tick_errors` 为 0。

## 七、交付前的代码评审（揪出 5 条，全部已修）

写完之后对整份 diff 跑了一轮对抗式评审，逐条都在真实代码上复现过。
**其中两条是「会毁玩家数据」级别**，而且都出在同一个思路上：
**用「记录的版本」代替「内容的版本」做判断**。

1. **（高）信封版本过新的驱动器记录被使用并覆盖。** 只对介质查了
   `record.read_only`，驱动器那半没查：恢复时照常应用槽位，随后一次
   `note_slots_changed` 就把这条记录按当前版本重写，**新版本独有的字段被抹掉**。
   修法：恢复期给这类记录加进 `_frozen_drivers`，`note_slots_changed` 与
   `save_to_repository` 两处都不写；连 `drop()` 的删除也跳过——
   那份存档不是本构建写的，凭什么断定它该从档案里消失。
2. **（高）「载荷读不懂」的盘会被写成空盘。** 冻结只判了 `record.read_only`，
   而它看的是**信封**版本（`CURRENT_SCHEMA_VERSION`）；载荷自己的版本是
   `MEDIUM_SCHEMA_VERSION`，两者可以不同步。更要命的是 `Medium.to_dict()`
   **没有 `raw_payload` 回退**，所以一块型号缺失/损坏/载荷版本过新的盘，
   只要被 `drop()` 标脏一次，写回去的就是 `entries: []` 的**空盘**——
   内容永久消失。修法：冻结判据加上 `medium.recovery != OK`，
   并在 `save_to_repository` 里再挡一道。
3. **（中）恢复循环会被「读不懂的载荷」整个打断。** `Medium._unreadable` 给
   每份读不懂的载荷一个**同一个占位 ID**（`"unreadable"`），第二条记录就撞上
   「已被接管」，异常从恢复循环里逃出去——**后面连槽位都恢复不了**，
   而且 `use_durable_ids()` 被跳过。修法：接管时用**记录的键**覆盖载荷里的
   `medium_id`（键才是权威，与 `ExtraDataRepository.load` 同一条纪律）。
4. **（中低）放不下的槽位被静默丢弃。** 槽数被改小（R10 未定案）或槽数未配置
   时，装不下的槽位从 `_pending_slots` 里被 pop 掉、不计数、也不写回，
   档案与内存从此各说各话，每进一次世界重演一次。修法：**保留不截断**，
   逐条计进新的 `unplaced_slots` 诊断（12 验收对样板槽的同一条纪律）。
5. **（低）`archive_stats` 计数张冠李戴**：`medium_writes` 把驱动器写与删除
   一起算了进去，`driver_writes` / `driver_deletes` 恒为 0。修法：各记各的。

**回归位**：`test_storage.TestRepositoryArchive` 新增**五条**用例，
对应上面五条各一（载荷读不懂 → 冻结、拆驱动器不覆盖原载荷、
信封过新的驱动器记录不写回、两条读不懂的记录不打断恢复、
放不下的槽位保留不截断）。
**逐条验过「不给修复就红」**：把第 1、2 两处的修复退回去重跑，
四条用例当场变红（`failures=4`），确认它们不是恒真的空用例。

> 这一步本身揪出了**第五条**——不是产品代码的，是用例的：
> 「拆驱动器不覆盖」那条一开始拿**夹具原来那个 `ref`** 去拆，
> 而重开后的 store 里一台设备都没有，`get_by_ref` 查不到、
> `drop()` 是个空操作，于是它**永远通过**、测的东西一次都没跑过。
> 修好之后它才在退回修复时变红。留下这条记录是因为「去掉修复就红」
> 这道工序本身也不够——**得先确认用例真的走到了那条路**。

评审同时确认**干净**的部分：`resource_key` 的投影不破坏 `to_dict`/`from_dict`
往返与 `raw_identity`；`medium_item` 的 py2/py3 类型分裂正确；
`ExtraDataRepository` 的索引维护与 `_pending`/`commit` 语义一致；
