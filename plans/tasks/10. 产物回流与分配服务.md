# 10. 产物回流与分配服务

状态：**离线全量交付 + 游戏内整链实测通过**（详见 [10-交付说明](10-交付说明.md)）。
负责人：待分配。前置：05、06 的实际回执；与 09 联合确定执行台账（已冻结在
[2026-09-26 订单与回流的执行台账契约](../technical_notes/order_returns_contract.md)），
07 的装配产出使用相同入口（该入口已备好，**仍无调用方**——07-06 未实现）。

## 目标与边界

将输入网络的实际产物独占分配给正在等待的执行实例。保持既定玩法：不要求输入来自指定机器，手动输入也能满足；同一份物品只能使一个订单的结果计数增加。

代码归属：`ROOT/server/crafting/returns.py`。参考 AE2：`me/service/helpers/CraftingServiceStorage.java`、`CraftingService.insertIntoCpus` 和 `CraftingCpuLogic.insert`。

## 接口与交付

按 [2026-09-26 订单规则](../technical_notes/order_planning_execution.md)，同一配方执行 10 次是 10 个任务，回流归属必须保留逐次执行语义；一次任务全部产物满足时，仅完成该任务、释放其 1 个并行槽并更新订单进度。不得把聚合整批作为一个槽位或一个完成任务。订单内存不在单任务完成时释放。

维护“资源键→等待执行实例”的索引，以及每实例每产物的剩余需求。入口接收主控允许的已提交回执和操作 ID；输出分配明细、实际持有/预留更新和步骤完成事件。

## 分步任务

- [x] 10-01 仅登记已经确认派发的执行实例；按实例跟踪全部预期输出，而不是只登记玩家最终目标物品。
      （登记由 09 在**派发确认之后**发起；`expectations` 是完整的 `StepOutput`
      序列，产物与返还物同构，都进同一份剩余需求。）
- [x] 10-02 从真实接受数量进行分配，应用 R06 的稳定顺序；每分配一部分都扣减本次剩余可分配量。
      （入口是 `TransferCoordinator.sink`，在 `commit()` 成功之后触发，
      因此 `count` 就是真进网的数量；**R06 本身仍是替身口径**——
      FIFO + 不提权，进 `unresolved_report()` / `policy_bundle()`，
      正式档由 `assert_assembly_ok()` 拦下。验收 A 离线通过。）
- [x] 10-03 与 05 协作把分配资源保留给相应订单，禁止只有历史计数而没有材料归属；分配和资源归属更新在同一受控提交阶段完成。
      （`storage.reserve(order_id, ...)` **以订单 ID 为拥有者**，于是 09 的
      `reservations_of(order_id)` / `release_owned_by(order_id)` 天然认得它，
      取消时 09 自动释放，10 不需要另写取消钩子。`reserve` 失败时不调用
      `receive_output`——不会出现「只有计数没有归属」。）
- [x] 10-04 校验回执来源：外部新输入、本地装配产出可以进入；模拟、拒收、缓存重建、内部移动、补偿和恢复不产生新计数。
      （`ORIGIN_INTERNAL` 走 `stats["rejected_origin"]` 且不加数。本地装配
      产出的具名接缝 `ReturnsPort.accept_assembled` 存在并跳过来源闸，
      **但没有调用方**——07-06 未实现，与 `port_stage` 当初的处境相同。）
- [x] 10-05 按操作 ID 去重，覆盖同一回执重试、同步回调和恢复；物理物品另一次真实输入使用新操作 ID，是否来自指定机器不影响接受。
      （键是 `(component_id, op_id)`；空 `op_id` 仍收下并进
      `stats["no_op_id"]`——丢掉一条真实入库会让订单永远等差。
      游戏内已核对：同额输入换 `op_id` 后照常计数。）
- [x] 10-06 多产物全部满足才通知步骤完成；剩余不被订单接受的资源保留为普通库存或原缓冲，不丢弃。
- [~] 10-07 处理取消、失效等待者、网络迁移与迟到产物；由 09 注销等待记录，避免回调命中已取消实例。
      **取消 / 失效等待者 / 迟到产物都做了**（迟到或未知 `execution_id` →
      `stats["orphan"]` 加一、**不报错**、资源留在网络里当普通库存）；
      **网络迁移没有专门实现**，也没有游戏内验证——10 的索引只按
      `component_id` 过滤，一台设备的归属真的跨了分量时行为未测。
- [~] 10-08 保存必要台账并提供诊断：预期、已分配、剩余、最后回执和归属信息。
      **诊断做了**：`describe()` 与 `debug_query("returns")` 给出逐条
      `key / execution_id / order_id / expected / allocated / remaining`、
      聚合 `stats`、`last_receipt`、`policy`（含 `unresolved`）；
      入口**只读**，一条命令都不发、一份库存都不改。
      **「保存」没做**：10 的索引是**纯内存**的，没有进存档，
      接 12 后端是另一件事。

## 验收

- [x] A、B 各需 8 个铁锭，输入 10 个，分配总和恰好 10，任何顺序均不得让两者都获得 8。
      **离线通过**（`TestAllocationOrder`）；游戏内未构造这个场景。
- [x] 原机器未运行时，手动输入符合身份的资源仍能满足已派发步骤。
      **游戏内实测通过**：机器（样板口面对的箱子）全程没动过，
      手工把 2 个金锭放进存货口容器 → 作为 `ORIGIN_EXTERNAL` 真的进网 →
      sink 触发 → 分配 → 订单 `completed`、`progress.ratio == 1.0`。
- [x] 一次输入 64 件按实际数量累计；流体按整数 mB 需求处理，不能按事件次数加 1。
      **离线通过**（`TestRealQuantity`：一次 64 按 64 累计、流体键按整数 mB）；
      游戏内只跑过 `count = 2` 的小额，**64 件与流体的真机路径未验证**。
- [x] 8 鱼和 1 空桶的配方只回鱼时不完成；重复回执与内部转存不再次加数。
      **离线通过**（`TestMultiProduct` / `TestDedupe`）；游戏内未构造多产物场景。
- [x] 已分配中间产物不被其他订单或普通取货抢走；取消后未分配产物有清晰去向。
      **离线通过**（`TestOwnership`）；游戏内只核对到「分配后
      `reservations_of(order_id)` 里有那份料、`available` 已扣」这一半。
- [ ] 计数更新、持有者更新和存档恢复之间不形成可重复消费的两份资源。
      **存档恢复那一半不存在**：10 的索引不进存档（见 10-08），
      因此这条**只做了「计数与持有者在同一次受控提交里更新」的部分**，
      离线通过；整条验收要等 12 的存档后端接上才能做。

## 待定与交接

R06 只决定先满足谁，独占计数本身已经确定。R05 决定资源落在磁盘还是有限订单缓冲；最终完成以 09 的落盘条件为准，不照搬参考源码中提前完成的边界行为。

**本轮交付的 R06 口径**：取 `BandwidthPolicy` 那一侧——库默认是**可用的、
有文档的替身**（登记先后 = FIFO，不防饥饿），做成具名策略字段
（`return.priority` / `return.starvation`）进 `unresolved_report()` /
`policy_bundle()`，PRODUCTION 档由 `assert_assembly_ok()` 拦下。
理由：分配顺序不授予任何权限、不破坏守恒，只是「谁先拿」；保守默认会让
整条链在 DEV 档下也走不完，而安全性一分没多。另一侧（`PER_ORDER` /
`AGING`）的取值在构造期直接 `ValueError`。

**给下游的交接**：11 的终端若要做「产物去向」视图，读
`debug_query("returns")`；14 的发布验收要在这里按 `assert_settled()`
把 R06 定下来，并补上 10-07 的网络迁移与 10-08 的存档两半。
