# 05 交付说明（05-04：真实介质交接）

日期：2026-10-04。范围：**任务 05 的 05-04**——让玩家能把介质物品放进存储驱动器、
从里面拿出来，并且网络真的认得出它。同时把「哪个介质在哪个槽」的权威从
12-03 的**存档槽位表**换成驱动器那 10 格**方块容器的读数**。

**这是一次增量交付，而且换了权威。** 12-03 交付的 `endernet.storage_driver/<位置>`
记录**退役**；介质记录（内容）一字未动。

## 一、这一步修的是什么

在这之前，模组**的核心闭环上不了手**：

- 驱动器方块有 10 格 `netease:block_container`，但**全仓没有任何代码读它**
  （`EngineContainerProvider` 只被样板槽与内存槽用）。
- `common/medium_item.py` 的载体编解码写好了却**零调用方**。
- 唯一的挂载入口是 `mount` 命令的 `model_id` 分支：**凭空发号造一块盘**，
  世界里没有对应物品。

于是「玩家把磁带放进驱动器」这件事在网络里**看不见**，而 05-04 与 05 的
验收 `:81`（「拔插介质、重进存档和网络拆分后资源总数不变」）要求的正是它。

## 三、权威与语义

| 项 | 语义 |
| --- | --- |
| 槽位占用 | **驱动器那 10 格方块容器的读数**。读不到时沿用上一次读数并标 `unreadable` |
| 介质身份 | 物品 `userData["endernet:medium"] = {"id", "v"}`（12-03 的载体，**现在真的有调用方了**）|
| 介质内容 | 仍按介质 ID 存世界 ExtraData（12-03，不动） |
| 发号时机 | **只在读到一块没有载体的空白介质时**；读取路径永不生成 ID |
| 写回载体 | 写完**只认读回核对**（`SpawnItemToContainer` 会写成功却返回 `False`）|
| 重复发号防护 | `_pending_carriers` 以 `(位置, 槽)` 为键、**在发号之前落账** |
| 重复挂载 | 本机：槽号小者胜；跨驱动器：`(位置文本, 槽号)` 字典序小者胜；网络侧仍是最后一道 |
| 孤儿（载体有 ID、记录缺失）| **占着槽**、计入 `disk_count`、交易以 `MEDIUM_UNRECOVERED` 拒绝；**不发号、不当空盘** |
| 展示写回 | 内容变了 / 首次读到 → 标脏 → 去抖 + 每帧 2 件预算 + **只比管理行、显示不变跳过** |
| `mount` 命令 | 确保该槽里放着该介质的物品（`model_id` = 造一块新的空白介质）|
| `unmount` 命令 | 把物品取出来，**必须有去向**（本命令只支持 `into="player"`）|
| 拆除 | **不再把介质标孤儿**——归属是那件物品本身 |
| 旧驱动器记录 | 读回来**只报进诊断并退役**，不据此在世界里造物品 |

## 四、离线验证

`python -B endernet_tests/run_tests.py`：**3786 项全部通过**，
**116 个文件**通过 Python 2.7 语法门禁（本轮新增 `test_medium_bay.py` 30 项 +
`test_bootstrap.py` 4 项，其余为驱动器那一路的改写）。

值得点名的几条（都在 `test_medium_bay.py`）：

- **同一 (位置, 槽) 反复重读只发一个号**：写回失败时保留待办、下一帧复用同号，
  超过 `DRIVER_PENDING_MAX_ATTEMPTS` 才放弃；放弃之后也**不再发新号**。
- **写回撒谎仍算挂上**（`LyingContainer`：写成功却返回 `False`）——
  判据是读回，不是返回值。
- **坏载体绝不当空白盘**：有载体键却读不动 → `malformed_carrier`，
  **不发号**（不然会把一块有内容的盘重识别成新盘）。
- **孤儿占槽不占空盘**：`slot_of` 有它、`medium()` 没有它、`read` 报
  `MEDIUM_UNRECOVERED`、`mediums_created` 为 0。
- **读不到 ≠ 被拔了**：无容器提供者时旧读数原样保留；中途一格读失败**整次作废**。
- **跨驱动器同 ID 的确定性裁决**：`(位置文本, 槽号)` 字典序小者胜。
- **一格里叠了多块**（空白介质可堆叠）报 `stacked_media` 并**原样不动**。
- **展示写回**：写进去的管理行只有一份标记、身份不变（`canonical()` 相等）、
  玩家自己的 Lore 行保留、显示不变时跳过写回。

## 五、真机实测（2026-10-04，`MC_DEV_WORLD`，运行版本 3.9.0.401155）

探针走 MCDK 的 `execute_code`（服务端），用的是世界里**真实的驱动器方块与真实物品**。
**这一轮是真正的退出世界再进**（设备代次归零、走区块发现）。改动已逐项还原。

### 5.1 一个空白介质进网（核心那条）

在一台真驱动器（`0,22,68,-7`）的格子里放一件**空白** `endernet:singleside_tape`，
重进之后：

| 核对项 | 读数 |
| --- | --- |
| 发号 | `mediums_created: 1`，记录 `medium:1` 落进 ExtraData（`archive_medium_writes: 1`）|
| 载体写进物品 | `carriers_written: 1`；读回 `('medium:1', 1)`，**`id` 是 py2 `str`、`v` 是 `int`** |
| 挂载 | 该驱动器 0 号槽 → `medium:1`，`disk_count = 1` |
| 展示写回 | `display_writes: 1`；物品上的两行是「剩余种类数：12 / 剩余总数量：1728 单位物」，**每行标记只有一个** |
| **tooltip 目视**（人眼）| 原生提示正常显示那两行，**`§1§2§3` 一个像素都不显示**（见 5.4）|
| 驱动器记录 | **`driver_records: []`**——权威换掉之后一条槽位记录都没写 |
| 空转代价 | 2032 tick 里 `refreshes: 2`（两台驱动器各一次），没有每帧重读、没有重复发号 |
| `tick_errors` | 0 |

**「载体写回的保真度」这条从 12-03 就一直欠着的读数，到此有了**：引擎把我们的载体
原样留住了（py2 `str` 就是它留得住的那一种，`resource_key.md` §2.2 那条也正是为此）。

### 5.2 展示写回会自己跟上

往盘里写 3 个石头 → 标脏 → **在真实帧边界上自己刷成「剩余种类数：11 / 剩余总数量：1725 单位物」**，
`pending_display: 0`、`display_skipped: 0`、**每行标记仍然只有一个**。这同时是
`materialize_item_user_data` 那处「标记加两遍」修复在**真实数据**上的确认。

### 5.3 跨驱动器移动与同 ID 重复

取出 → 放入另一台真驱动器：

- 取出的那件物品**仍带 `('medium:1', 1)`**，而且 Lore 是**最新**的（`11` / `1725`）；
- 取出期间 `unclaimed_mediums` 正好报出这一块；
- 放进第二台之后 **B 挂上它、`B_disk_count: 1`、内容仍是那 3 个石头**——内容跟着身份走了；
- 反过来，A 持有它时把一件**同 ID** 的载体物品写进 B 的槽：**B 不挂载**，
  如实报 `duplicate_across_drivers`（详情「介质 medium:1 已在 0,22…」），A 保持持有。

**顺带量到一条引擎行为**：`SpawnItemToContainer` 往**空格**里写返回 `True`；
对**已经放着同一件物品**的格子重写返回 `False`。返回值的判据仍然只能是读回。

### 5.4 仍没验的

- **破坏驱动器方块时容器里的介质物品会怎样**（掉落 / 删除 / 留存）——**没测**。
  那是一次破坏性动作，没有在真世界里做。它决定 `drop()` 与「无主介质」的处置，归 12-06 / R05。
- **`§1§2§3` 的 tooltip 目视已经确认**（2026-10-04，人眼悬停驱动器界面里那块磁带）：
  原生提示显示「小型单面磁带 / 容量:12 类型 1728 单位物 / 读 4 单位物/s,写 4 单位物/s /
  **剩余种类数:12** / **剩余总数量:1728 单位物**」——两行管理行正常渲染，
  **看不到任何 `§1§2§3` 残留**。这条从 12-02 起就挂着的待人工项到此结清。
- `unmount` 命令交给玩家背包那条路、规模（上百台驱动器）、旧存档迁移，
  都只有离线证据。

### 5.5 探针里撞到、模组路径上没有发作的一次异常（如实记）

探针里有一段序列**确定性地**抛 `TypeError: an integer is required`：
**在同一个脚本里先往引擎容器 `write_slot`、紧接着调 `refresh`**。
挖到底之后它是**探针环境**的现象，不是模组的：

- 抛点在 `refresh` 一开始的 `state.content_fingerprint()`；同一个对象上
  `occupied()` / 列表推导 / `sorted()` 单独调都正常，**只有那个要新建生成器帧的调用中招**；
- 现场把 `sys.exc_info()` 打出来是
  `SyntaxError('invalid syntax', ('<string>', 1, …))`——**MCDK 的 `execute_code`
  先按表达式 `eval` 一次、失败再退回 `exec`，留下一个没清干净的编译期异常**；
  同时那次 `SpawnItemToContainer` 本身也返回了 `False`（C 层的错误位也可能带脏）。
  两者叠加之后，下一个需要新建帧的调用会拿到一条**错位的**错误文本。
- **模组自己的路径上一次都没发作**：两台驱动器 `stats["errors"]` 都是 0、
  `unreadable` 都是空；而发号 / 写载体 / 展示写回 / 跨驱动器移动全都在同一段
  时间里真的做成了（读数见 5.1~5.3）。

**但它顺带暴露了我一个真缺陷**：`refresh` 最开始那次 `content_fingerprint()` 与
最后那几步（去重 / 投影 / 首次读到）原先都在 `try` **外面**——一次偶发失败就会
真的抛出 `refresh`，与它自己声明的「保证不抛」相矛盾。已把整段收进 `try`，
并补了 4 条用例（`TestRefreshNeverRaises`）钉住这个契约。
**注意**：这条修复是在真机读数**之后**做的，是纯粹的「把语句挪进已有的 `try`」；
真机读数对应的是挪之前的构建。

## 六、顺带修掉的一个真缺陷（`common/medium_item.py`）

`materialize_item_user_data` 把标记**加了两遍**：它把 `medium_lore_lines(medium)`

写进物品」）。本轮接上展示写回、第一次真的调用它，`test_medium_bay` 立刻红了。
改成传 `medium.capacity_lines()`。

## 七、未验证项与已知限制（重要）

- **下面这些已经真机验过**（读数见第五节）：空白介质进网发号 + 载体写进真实物品
  （`id` 是 py2 `str`、`v` 是 `int`）、记录落盘、**驱动器记录一条都没写**、
  展示写回自己跟上且标记只有一个、拔出后内容跟随身份、跨驱动器移动、
  同 ID 重复挂载被拒且报得清楚、几千 tick 里没有每帧重读或重复发号、
  `tick_errors` 为 0。
- **`§1§2§3` 在原生 tooltip 上的目视效果**——**仍然待人工**（要人悬停看）。
- **容器事件真的到、`mark_dirty` 计数增长**——没单独量过。这一轮介质是**重进时**
  由 `ensure` 读到的（`marks: 0`），事件路径没有被触发过。
- **破坏驱动器方块时容器里的介质物品会怎样**（掉落 / 删除 / 留存）**完全未知**。
  它决定 `drop()` 要不要改、以及「无主介质」怎么处置（现在只报在
  `diagnostics()["unclaimed_mediums"]`）。处置归 12-06 / R05。
- **跨驱动器同 ID 的裁决规则是新引入的**：改版前这件事靠「物理上不可能同时插在
  两台里」保证。`(位置文本, 槽号)` 字典序是否合意，需要确认。
- **一盘叠多块不做处置**：`stacked_media` 只报不动。要把其中一块拆出来挂载，
  还得定「剩下那些放哪」——那是一道未定规则（R05/R10）。
- **`DriverPolicy.recover_slots_on_reload` 已结构性作废**（槽位不再从存档恢复）。
  按 S-09 的先例**保留字段并加注**，不静默删除、不作为 R10 的定案。
- **展示写回是 best-effort**：玩家把物品从容器里拿走的那一刻，我们已经没有地方
  写它了，因此物品上的摘要有可能有界地过期（受 `DRIVER_DISPLAY_BUDGET` 与静默帧
  影响）。「交接到玩家背包前确保最新」这半条**没有做到**。
- **节拍常量是未测量值**（`DRIVER_REFRESH_BUDGET=4`、`DRIVER_DISPLAY_BUDGET=2`，
  照内存槽量级取）。规模（上百台驱动器）没有读数。
- **旧驱动器记录不物化**：那些「幽灵盘」（旧 `mount` 造的、没有对应物品的介质）
  恢复后变成无人认领的记录，内容仍在 ExtraData 但玩家取不回。
- **`unmount` 命令只支持交给玩家背包**，没有「掉在原地」那条去向；
  也**没有任何生产调用方**（玩家自己用手拿是另一条路）。
- **`SpawnItemToContainer` 返回值的一条新读数**（真机）：往**空格**里写返回 `True`；
  对**已经放着同一件物品**的格子重写返回 `False`。判据仍然只能是读回。
- **`place_medium` 传的是 `medium.model_id`，而它从存档读回来可能是 `unicode`**——
  真机上这条路走通了（`place_into_A_ok: True`），但**没有单独验过**
  「同一个 `userData` 用 unicode 名字写进去、读回来载体是否完好」。

## 八、给下游任务的交接

- **12**：`endernet.storage_driver` 记录退役；介质记录与发号水位不变。
  旧存档里的驱动器记录由 `restore_from_repository` 报进
  `diagnostics()["legacy_driver_records"]` 后删掉（信封读不懂的连删都不删）。
- **06 / 11**：`mount` / `unmount` 已经是**容器操作**，「凭空发号造盘」那条路
  没有了。**跨驱动器移动应当走真实转移**（从 A 槽取出来、放进 B 槽），
  不要用 `mount(medium_id)` 去「造」第二件物品。
- **14**：故障注入入口仍是 `MemoryRepository.inject_fault`；
  驱动器的可观测点新增 `never_read` / `unreadable` / `invalid_slots` /
  `pending_carriers` / `pending_display_writes` / `unclaimed_mediums` /
  `legacy_driver_records`。
