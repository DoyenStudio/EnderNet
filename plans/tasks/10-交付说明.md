### 游戏内实测（MCDK，2026-09-26）

**做了，整链跑通。** 测试世界是自己搭的（09 交付说明第八节记的那张
`(-26,72,…)` 网络在这个世界里全是空气——世界被重建过），因此先补了
09 那轮缺的三样东西：一张真样板、一块已挂载的存储介质、一台处理器与一个
内存槽（**没有它们订单会被 `order_no_capacity` 挡住**）。

**跑通的那一轮（第一轮）**：

1. `diagnostics()` 确认接线：`order["returns_sink"]["adapter_id"] == "returns"`、
   `available: True`、`wired: True`；协调器 `sink_wired: True`；
2. 存货口（`endernet:bus_item_io` @ `(24,68,-8)`）里手工写入 2 个铁锭 →
   端口轮询把它当 `ORIGIN_EXTERNAL` 搬进网络，`st.query(iron)` 读到
   `stored: 2`；
3. 提交订单：`{"action": "submit", "target": <gold>, "amount": 2}` →
   `ok`，`order_id = order@1/((0, 19, 69, -7), 0)#0/1`；
4. 推进 → 步骤进入 `waiting_outputs`，`inputs` 的
   `delivered: 2 / required: 2 / staged: 2`——**2 个铁锭真的进了机器**；
5. **机器全程没启动**（样板口面对的箱子只是普通箱子）。手工把 2 个金锭
   放进存货口容器 → `waiting_entries` 从 1 变 0 → 订单
   `status: completed`、`progress.ratio: 1.0`；
6. 回执对得上：`last_receipt = {op_id: "port:(0, 24, 68, -8):36",
   origin: "external", count: 2, accepted: 2, outcome: "allocated"}`。

**第二轮（换 `op_id` 复现）**：再存 2 个铁锭、下一张 4 个金锭的单（库存里
已有 2 个，`target_semantics = hold` 的替身口径让它只补差 2 个）→
步骤 `waiting_outputs` 时读到 **`reservations_of(order_id)` 里有那份料**
（`reservation_id: order@1/...#0/3:3`、`owner_id` 就是这张订单、`count: 2`、
落在 `medium:4`），且 `available: 0 / stored: 2 / reserved: 2`；
再投 2 个金锭 → 结单，`last_receipt.op_id = "port:(0, 24, 68, -8):48"`
（**与第一轮的 `:36`、孤儿那次的 `:17` 都不同**），`accepted: 2`。

**累计核对**：`returns` 侧 `receipts: 4`、`allocated: 4`、`orphan: 2`、
`registered: 2`、`unregistered: 2`、`duplicate: 0`、`rejected_origin: 0`、
`reserve_failed: 0`；协调器侧 `external_inputs: 4`、`sink_missing: 0`、
`uncertain: 0`、`compensations: 0`。**四个数互相对得上**（4 次手工投料 =
4 次外部输入 = 4 条回执；其中 2 条命中等待者被分配、2 条在没有等待者时到达
被记成孤儿）。

**孤儿是设计内行为，不是缺陷**：第一次投铁时订单还没下，索引里没有等待者，
`outcome: "orphan"`、资源照常留在网络里当普通库存（10-06「不丢弃」）。
这条恰好是契约 §6.3 想要的形态。

### 仍然没在真机上验的

- **验收 F（存档恢复不产生两份资源）**：10 的索引根本不进存档，**整条做不了**。
- **10-07 的网络迁移**：没有实现，也没有验证。

### 离线验证能证明什么、不能证明什么

**能证明**：分配顺序与逐一扣减、来源闸、`op_id` 去重、按实际量累计、

## 三、接口输入输出

### 06 → 10：`reflow_sink(request, count, now)`

由 `TransferCoordinator._deliver_external_input` 在 **`commit()` 成功之后**
调用，因此 `count` 是真的进了网络存储的量（`TransferReceipt.moved`）。
`StorageService(reflow_sink=...)` 注入，装配点在 `_storage_builder`。

### 09 → 10：`ReturnsSink` 的四个方法（鸭子类型，10 不继承它）

```python
register(execution_id, expectations, order_id)  # 替换语义
unregister(execution_id)                        # 返回还没等到的件数
describe()                                      # available: True
blocker()                                       # 接上了就没有阻塞 → None
```

`ReturnsPort` 同时是这两个接口的实现，因此
`describe()["available"] is True` 会让 09 的 `service_sink_available()` 变真、
`_sink_blocker()` 返回 `None`、`status()["returns_wired"]` 变真、
`runtime.order_view()["returns_absent"]` 归零——09 缺陷 17/18 的修复链**自动生效**。

### 10 → 09：`OrderExecutor.receive_output(execution_id, key, count, op_id, source)`

返回本次**实际被接受**的量。10 先 `storage.reserve(order_id, ...)`（**以订单 ID
为拥有者**，全有或全无），成功了才调它；`accepted < take` 时把差额
`release` 掉，并**按 `accepted` 而不是 `take`** 累加索引。

### 只读查询：`debug_query("returns", component_id=..., key=..., execution_id=...)`

只读白名单里的一条，**一条命令都不发、一份库存都不改**。返回
`{entries, summary, wired}`：`entries` 是逐条等待记录
（`key / name / execution_id / order_id / expected / allocated / remaining /
counts_for_completion / component_id / seq`），`summary` 是聚合
（`adapter_id / available / wired / components / waiting_instances /
waiting_entries / waiting_by_key / allocated / orphan / duplicate /
rejected_origin / no_op_id / reserve_failed / last_receipt / policy`）。

## 四、适用存档版本与持久化

**10 不写任何权威存档数据。** `ReturnsService` 的索引是**纯内存**的，
进程重启后为空——这与 05/09 的处境一致（09 的等待台账同样只在内存里），
接 12 的存档后端是另一件事，也是 10-08「保存必要台账」那半没有做的原因。

对 12 的交接点：恢复时要重建的是「谁在等什么」，而那份数据的**权威在 09**
（`WaitingLedger`）。10 的索引是它的**派生视图**（多了分配顺序所需的 `seq`
与全局索引），因此正确做法是**恢复 09 的台账之后再让 10 重新登记**，
而不是把 10 的索引单独存一份——两份账正是契约开头要避免的。

## 五、未定规则与剩余限制

### R06：回流分配的优先级与防饥饿是**替身口径**

**本轮已与用户确认取 `BandwidthPolicy` 那一侧**：库默认是**可用的、有文档的
替身**（登记先后 = FIFO，不防饥饿），而不是 `EnergyPolicy` 那种保守拒绝侧。
理由：分配顺序不授予任何权限、不破坏守恒，只是「谁先拿」；保守默认会让整条链
在 DEV 档下也走不完，而安全性一分没多。

因此**不设 `dev_stand_in()`**——默认值本身就是那个替身（与 `BandwidthPolicy`
同例；`EnergyPolicy.dev_stand_in()` 存在是因为它的默认是拒绝侧）。
另一侧的取值在构造期直接 `ValueError`，不会被悄悄用上。

`assert_settled()` 按 `pending` 判，**只在正式验收时调用**；本轮开发与离线测试
**没有调用它**。PRODUCTION 档对 R06 的拦截走 `assert_assembly_ok()`，
与 R04/R09/R11 现状一致。

### 已知实现限制

1. **`accept_assembled` 有实现、有用例、没有调用方**（07-06 未实现）。
   与 `port_stage` 当初的处境相同，如实记在这里。
2. **没有排队层**。契约 §8 要求「同步到达的回执在本次提交完成后再分配」，
   09 侧也没有排队层，因此本轮的选择是**不做**，改用约束：10 不得从 09 的
   命令处理内部同步回调它。这句话写在 `accept` 的 docstring 里，
   **没有运行时守卫**——计划里提过的 `stats["reentrant"]` 计数没有落地，
   不留一个永远为 0 的字段。
3. **索引纯内存**（见第四节），**网络迁移没有专门处理**。
4. **全局索引、按分量分配**：`self._index` 是全局的（为了诊断与将来的跨网络），
   但分配时按 `component_id` 过滤——资源到达网络 N 只满足 N 上的订单。
   跨网络的转移通道不存在，因此这不是「暂时」的限制。
5. **`receipt_limit = 4096`** 是替身取值（回执账本上限），未定案。

### 1. 10 ↔ 11：产物去向走只读查询

见第四节。**不要**把 10 的索引单独存一份。

`ReturnPolicy` 的两个字段与 `UNRESOLVED_FIELDS` 是唯一需要动的地方；
分配算法本身（有序贪心 + 逐一扣减）不随 R06 的取值变化。

### 4. 10 ↔ 07：`accept_assembled` 是留给 07-06 的入口

2026-09-27 规格补充：装配仓使用网易容器，9 槽为输出槽；该槽物品直接送回网络。接入时以 06 从输出槽实际回网的数量生成回执，不能仅凭合成进度结束就增加网络库存或分配产物。07-06 与 09-05 尚未补齐，本条不改变“没有调用方”的交付状态。

## 七、开发过程中撞到并修好的问题

### 1. `_sync_reservation` 只在本地已有行时对齐 → 多步订单报**假的** `ORDER_STOCK_TAKEN`

**症状**：10 会在**计划没认领的键**上为订单预留（中间产物走的就是这条路，
计划只为 `from_stock > 0` 的键建行）。09 的 `_sync_reservation` 只在
`order.reservations` 里已有那一行时才把 `reserved` 对齐到 05 的活预约。
于是下一步备料时：

- 本地无行 → `mine = 0`；
- `_stock_blocker_for_staging` 算 `usable = available + mine`，而 `available`
  **已经把我们自己锁住的那一份扣掉了** → `usable` 少算一份；
- 报一条假的 `ORDER_STOCK_TAKEN` → **多步订单永远停在第二步备料上**。

**修法**：`live` 非空而 `row is None` 时按 05 的活预留**补一行镜像**
（`claimed: 0`，与 `Order.to_dict()` 的 `.get("claimed", 0)` 相容）。
镜像的职责本来就是「05 的活预约占在这里长什么样」，而不是「计划当时认领了
多少」。回归用例是 `TestMultiLevelRegression`。

**这条是 09 的代码，改动也落在 09 的文件里**——但它只有 10 接上之后才会发作，
因此记在这里。

### 2. 引擎物品字典的字段名是 `newItemName` / `newAuxValue`

游戏内联调时第一次写容器失败（`SpawnItemToContainer` 返回 `False`、
读回是空），原因是我按 `{"name": ..., "count": ..., "aux": ...}` 传的。
引擎要的是 `{"newItemName", "newAuxValue", "count", "showInHand"}` 加六个身份
字段——也就是 `common/item_codec.item_dict_from_key()` 生成的那一份。

**没有改代码**：`containers_engine.set_container_item()` 一直是对的
（它把调用方的字典原样交给引擎），是联调脚本自己拼错了。记在这里是因为
它值得成为一条教训：**构造引擎物品字典只有 `item_dict_from_key` 一条路**，
手拼就等着踩这个坑。

### 3. 容器组件的工厂方法不是 `CreateContainer`

`GetEngineCompFactoryServer` 上**没有** `CreateContainer`。要拿容器组件得走
`GetEngineCompFactory().CreateItem(GetLevelId())`。
`containers_engine.py` 里本来就这么写的，联调脚本猜错了名字。

### 4. `force_backfill` 不会重扫已加载的区块

脚本用 `SetBlockNew` 放下的方块**不会**触发区块加载事件（区块本来就加载着），
因此新设备不会进注册表。要 `reset_backfill()` 之后 `force_backfill(None)`
（返回 2691 个区块）才扫得到。

**这不是缺陷，是设计**：`plan_startup_backfill` 本来就只是兜底与**手动重扫**
入口，跑完即停。但联调时要知道这条，否则会以为方块没放上。

## 八、游戏内联调的过程记录

### 测试世界的现状与 09 交付说明的差异

09 交付说明第八节记的那张网络在 `(-26, 72, -59..-61)`，**在这个世界里全是空气**
——世界被重建过。当前世界的分量 1 是另一组方块
（主控 `endernet:tiny_network_endpoint` @ `(19,69,-7)`、6 段基带、
存储驱动器 @ `(22,68,-7)`、被动接口 @ `(24,68,-8)`、取货口 @ `(24,68,-7)`
对着一个箱子 @ `(24,68,-6)`），分量 2/3 是 `no_controller`。

### 为跑通这一轮补的三样东西

| 缺什么 | 症状 | 补了什么 |
| --- | --- | --- |
| 样板提供者 | 计划生不出步骤（`steps_total: 0`） | `endernet:bus_template_io` @ `(20,68,-6)` 对着箱子 @ `(20,68,-5)`，并在槽 0 装一张「2 铁锭 → 2 金锭」的工厂样板 |
| 存储介质 | 存储服务 `is_ready()` 为假 | `create_medium("endernet:harddisk_4k")` → `provider.mount(0, ...)` |
| **处理器与内存槽** | 订单被 `order_no_capacity` 挡住（`slots.capacity: 0`、`memory.capacity: 0`） | `endernet:parallel_processor_connector` @ `(21,68,-6)` + `endernet:parallel_processor` @ `(21,68,-5)`（**必须经连接器**，处理器不能直连基带）+ `endernet:memory_slot` @ `(23,68,-10)` |

补完之后 `capacity_slots: 1`、`capacity_mem: 1`，订单才开始推进。

### 踩到的两个配置坑

- **接口的过滤名单必须非空。** `PortConfig.is_ready_for` 对 `PASSIVE` 与
  `OUTPUT` 在名单为空时一律返回 `False`（`blocks.md` 的「设定 N 种」），
  于是计划报 `port_unconfigured`。**样板口与存货口都要显式给白名单**，
  而且存货口的白名单要**同时含铁与金**——只给铁的话手工投的金锭根本
  进不了网。
- **`PortStore.ensure` 是幂等的，不会重读已有的 `facing`。** 想让一个接口
  改朝向，只能把它挪走再放到新位置（本轮就是这么做的），
  改方块状态不会生效。

### 这一轮验到的联动链

`ReturnsPort.describe()["available"] is True`
→ 09 的 `service_sink_available()` 为真
→ `_sink_blocker()` 返回 `None`
→ `status()["returns_wired"]` 为真
→ `runtime.order_view()["returns_absent"]` 归零
→ 订单从「推到等待产物就阻塞」变成「真的能结单」。

这五步在游戏内逐条核对过（`order_diagnostics()["returns_sink"]["adapter_id"]`
就是 `"returns"`），因此 09 缺陷 17/18 的修复链**不只是离线成立**。
