# 02. 网络拓扑与负载服务

状态：未开始。负责人：待分配。前置：01 的节点、设备定义与事件契约。

## 目标与边界

根据已加载设备和明确连接规则建立图，处理连接、拆分、合并、控制器计数和负载准入。图服务只给出拓扑和资格，不读写库存或执行订单。

代码归属：`ROOT/server/network/{node,topology,admission}.py`。参考 AE2：`me/GridNode.java`、`me/service/PathingService.java`。

## 接口与交付

`TopologySnapshot` 包含分量成员、拓扑版本、控制器实例列表、连接状态和处理器群归属；`AdmissionResult` 包含设备是否获准、原因及路径负载。对外提供标脏、有限步重建、版本查询和稳定快照接口。

业务网络与基带负载域分开建模：按 blocks.md，相连基带共享负载，同一控制器连接的互不相连基带分别计算。对设备输出 `bandwidth_domain_id`、需求量、分配量、域容量/占用及判定版本，供界面显示本设备的 `bandwidth_ok`；与能源状态分别计算。

## 分步任务

- [ ] 02-01 把允许连接的类型、方向和端口做成显式规则；校验双方端口，不根据相邻即默认连通。
- [ ] 02-02 合并同帧变更，使用迭代遍历重建受影响分量，维护跨帧游标；大任务期间对受影响部分标记重建中。
- [ ] 02-03 统计“网络控制器”分组所有实例：零个不可运行，一个候选主控，多个无效；未知/未恢复拓扑不视作确认无控制器。
- [ ] 02-04 实现处理器—处理器—连接器—基带的专用关系；无连接器不贡献槽位，禁止处理器直接连接控制器/基带。
- [ ] 02-05 先按已确定的共享/独立分支规则建立负载域，再按 R02 确定混合容量、环路、多接入和负载取整策略；不将同控制器各域的预算直接合池。
- [ ] 02-06 统一图版本的发布阶段：撤销旧资格、完成归属、发布新快照。通知 03 挂载迁移，通知 09 更新槽位来源。
- [ ] 02-07 给拆线、合网、控制器数量异常和超载提供可定位的原因，不把业务错误仅显示为“离线”。
- [ ] 02-08 提供本设备带宽判定及只读状态变化通知，接入 11-13。区分未获额度、已获额度、结果待确认，按 R13 处理恰好满载，断电不抹除仍有效的负载判定。

## 验收

- [ ] 链、分支、环和跨区块图均正确连通；删掉桥接基带后分量正确拆开。
- [ ] 两个单控网络连通后不继续形成两个可写主控；断开后各自重新校验并恢复。
- [ ] 一个处理器通过多条路径可达时槽位不重复；未接入连接器的群提供零槽位。
- [ ] 拓扑重建跨帧期间不能使用旧版本进行新转移；无变化时不逐块重搜网络。
- [ ] 按选定负载策略验证 8/16/32u 边界、插拔介质引发的动态负载变化、不同设备优先级。
- [ ] 一个基带域满载时，不误报同控制器另一独立域的设备；已获准设备与新请求设备的带宽显示符合选定满载规则。
