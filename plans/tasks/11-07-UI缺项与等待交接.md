## 二、A 组：打开入口与注册

- **A1 —— 2026-09-29 定案：走「引擎自动打开」，脚本侧以 `is_proxy=True` 挂代理。**
  本设备属容器类，因此**不建自有屏、不拦右键**：引擎按方块组件打开那张原生屏，
  逻辑由 `NSManagerIns.RegisterScreenProxy` 挂上去（见
  [打开机制](../technical_notes/netease_container_screens.md) §零「落地形态」与 §四 乙-A）。
  下面三条候选保留作决策记录；结论与依据见同文 §零。
  本屏幕是容器屏幕，屏幕根是 `main@common.inventory_screen_common`
  （[bus_item_output_io.json:487-488](../../endernet_rp/ui/bus_item_output_io.json)），
  网格用引擎集合 `netease_container`（硬编码在
  [endernet_container_common.json:128](../../endernet_rp/ui/endernet_container_common.json)）。
  三条路线：

  | 路线 | 机制 | 现状与代价 |
  | --- | --- | --- |
  | 引擎自动打开 | 方块组件 `netease:block_container`（`screen_name` + `container_size`）+ `description.base_block: "netease_container"` | **最终选中这条。** 当日已有 4 台设备走它，声明处 [gen_blocks.py:140](../../scripts/gen_blocks.py)；当时的声明注释（`:119-121`）明确写了端口为什么不在内：「存货口/取货口不在内：blocks.md 说它们『自动从/向朝向的容器』搬运，动的是**邻居**，不是自身缓冲」。**该理由已被 §十 的裁决取代**，取货口补上了组件，本仓走这条的设备由 4 台增至 **9 台** |
  | 脚本拦截 | `ClientBlockUseEvent`（[block.py:5-6](../../endernet_bp/endernet_scripts/tooldelta/events/client/block.py)，经 `AddExtraBlocks` 加入白名单）可 `cancel()` 拦截引擎的打开行为，再 `PushUI` | 与 11 文档设想的 `RegistToolDeltaScreen` 形态不同，需同步改文档；白名单机制要实测 |
  | 服务端打开 | `comp.OpenNeteaseContainer(screenName, ...)`（引擎侧注释原文：「打开自定义容器界面，**不依赖于方块**」） | 引擎要求 `collection_name` 为 `netease_ui_container`，与本仓硬编码的 `netease_container` **不是同一个集合**；且它不经过方块，与本设备「玩家右键方块」的交互模型不一致 |

  **这三条不能靠猜。** 选哪条决定 5 格的身份（真实方块容器 / 脚本维护的集合 / 服务端 UI 容器），
  也就是决定整个 11-07 的实现形态。核实步骤见
  [网易容器屏幕的打开机制](../technical_notes/netease_container_screens.md)。
- **A2 全仓没有任何设备界面的注册或打开调用。** `client/ui/__init__.py:5-9` 的 `register_screens()`
  只导入并返回 `CommonTerminalPanel`；全仓唯一一处 `@RegistToolDeltaScreen` 是
  `client/ui/terminal_panel.py:127`（通用终端，`is_proxy=False`）。取货口、存货口及其余
  设备界面**均无 Screen 类**——按 §零 的形态，容器类设备各需要一次 `is_proxy=True` 的注册。
- **A3 交互校验（玩家／维度／距离／设备实例代次）需要服务端通道，该通道不存在**（见 C3）。
  11 文档第 85 行要求「只读诊断校验玩家、维度、距离和设备实例」；没有通道时这项无从实现。

## 九、真机核实中修掉的两处缺陷（属 11 的物品／流体选择链路）

本节记录 2026-09-29 上机核实（§八）时暴露、并已修掉的两处**真机致命**缺陷，
外加一处**未修**的不一致。三项都在 11 的物品／流体选择链路上，**不属 11-07**，
所以另立一节而不并入 [11-交付说明](11-交付说明.md)。

1. **模组在 `OnServerInited` 直接崩 —— 绑定方法挂不住 `_td_static`。**
   症状：`AttributeError: 'instancemethod' object has no attribute '_td_static'`，
   `OnServerInited` / `OnClientInited` 里的 `start_catalog()` 断掉，**目录服务整条起不来**。
   根因在 vendored 上游 `tooldelta/events/event_bus/event_bus.py:37-41`：`static=True` 时
   它会执行 `listener._td_static = True`，而 Python 2 的**绑定方法不能挂属性**
   （`modMain.py:52-53`／`:59-60` 的启动链正是把绑定方法传进去的）。
   改法：三处调用点去掉 `static=True`——
   `server/adapters/item_catalog.py`（`self.receive`）、
   `client/item_catalog.py`（`self.receive` / `self.on_ready`）、
   `client/network_client.py`（`dispatch`，那本是每次新建的闭包，该标记从来命中不了）。
   `server/adapters/events.py:167` **有意不动**：它装饰的是方法内部定义的普通函数
   （`:287` 起十余处），与上游 `ServerEvent.Listen` 同形，本来就能跑。
2. **目录永远发不出包 —— `minecraft:air` 让整张目录为空。**
   修掉第 1 条后立刻露出第二个：`GetLoadItems(True)` 会把 `minecraft:air` 这类
   **没有物品定义**的条目也报上来，`Item.GetBasicInfo()` 对它抛 `ValueError`
   （`tooldelta/define/item.py:127-128`），异常穿出 `filter_item_ids`
   （`server/adapters/item_catalog.py:22-37`）→ `ItemCatalogService.receive()` 在**发包之前**就断了。
   症状不是「少一条」而是**客户端永远拿到空目录**。改法：该处捕获 `ValueError` 跳过。
3. **未修：终端屏的脚本路径与 JSON 对不上**（此条即 §七 Q4 所指）。
   `client/ui/terminal_panel.py:59` 的 `INVENTORY_PATH = "/terminal/inventory"`，
   而 `common_terminal_panel.json` 里那个控件实际在 `content/inventory`
   （`main/terminal` 是另一片空 panel，其下没有 `inventory`）。屏能渲染，
   但 Python 侧 `GetBaseUIControl` 取不到控件。**它属 11 的终端，不属 11-07**，
   本轮只登记、不改。

**离线门禁为什么没拦住**（这是第 1 条最值得记的一点）：`test_sync_channels.py` 与
`test_select_item_window.py` 里的替身 `ListenEvent` **只把 `static` 收下就不作声**，
从不做 `_td_static` 赋值——于是「`static=True` + 绑定方法」这个组合在离线一路绿灯。
两条替身现已照真总线复现该赋值，断言也改成 `assertFalse(static)`；
`ItemStub.GetBasicInfo` 现在对 `minecraft:air` 抛 `ValueError`，
并新增 `test_items_without_basic_info_are_dropped_not_fatal`。
第 1 条**实测过会失败**（临时改回 `static=True`，替身立刻在
`callback._td_static = True` 处抛 `AttributeError`，随后还原）。
