- **库默认口径下，真实网络的判定是 `energy_unavailable`**（「待确认」而不是

这是诚实的「还没算准」，不是故障；`diagnostics()` 的 `scope_note` 与 `energy`
节都会这么写，`debug_query("energy")` 能查到替身口径到底忽略了哪几台设备。

## 全局约束

1. 同一网络图最多 1 个 master controller，工作时必须恰好 1 个。控制器按 `blocks.md`“网络控制器”分组的所有类型合计计数。
2. 输入、输出、终端和订单请求均由所属主控制器准入，再由网络服务执行；不在各设备中复制一套网络业务。
3. 物品、流体和能源守恒；每次转移按实际数量提交。一次产物回流只能分配一次。
4. 每个介质的容量、类型数和读写额度统一管理；主控制器和订单不得提供无上限隐藏库存。
5. 区块卸载、方块拆除、同位置替换分别处理；恢复不重复派发、扣库存或累计产物。
6. 世界 API 和状态提交在服务端主线程；耗时计算可分帧。客户端只提交意图、显示确认后的状态。
7. 未定玩法不得用临时实现悄悄定案。开发测试可注入明确标注的配置，正式验收须完成受影响规则决策。
8. 终端参考 AE2 面板，自行实现动态长列表的网络槽和界面内玩家背包槽的渲染与交互；网络槽可显示超过 maxStackSize 的汇总量，真实背包堆叠仍遵守游戏限制。
9. 接网设备除控制器本身外，界面通过 `stat_bar` 显示绿色“在线”或红色“离线”；点击 `interact_btn` 弹出 `device_status_window_basic` 显示详细原因。状态由服务端汇总，设备离线时仍可查看诊断；编写前核实实际控件与绑定。

## 任务交接与完成定义

**UI 创建与脚本对接分工（User 确认）：** 所有界面的创建工作由 User 全权完成，包括物品槽位、按钮、开关及其他控件、布局与视觉资源。User 完成相应界面并交接后，脚本实现方（Codex）才能对接该界面的脚本层，并按绑定与显示需要微调 UI；不得自行补建缺失界面或控件。缺少 UI 时，一旦工作涉及该 UI 的逻辑，必须暂停这部分工作并记录“等待 User 创建 UI”；不得假设任何 UI 逻辑，也不得以占位或模拟逻辑提前实现。仅可继续完全不依赖该 UI、无需假设其行为的独立工作；服务端、协议或数据模型若依赖该 UI 的交互约定，同样必须暂停。此约定适用于全部设备与终端，具体交接要求见 [11 的 UI 分工与实施前置](<./11. 终端与客户端同步.md#ui-分工与实施前置>)。

每项以 `编号-步骤` 标识，如 `05-03`。负责人填写“未开始 / 进行中 / 待联调 / 已验收 / 阻塞”，并记录阻塞的规则或接口，未实际完成的复选框保持空白。

完成交接至少包括：修改文件、接口输入输出与错误结果、适用存档版本、验证方式与结果、剩余限制。跨服务只通过约定接口、命令和已提交事件协作。每篇的“验收”是待执行清单，不是本次规划已经运行的测试。
