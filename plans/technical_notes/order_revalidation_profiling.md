# 订单重验性能验证（2026-10-04）

## 改动

1. `PatternStore.dispatch_revision()` 与显示侧产物索引版本分离，覆盖内容、标脏、加载变化与读取异常。`OrderExecutor` 按计划对象、样板库对象、拓扑版本、派发有效性版本缓存已通过的样板腿。
2. 库存版本变化仍走剩余需求与实际预留核对，不再因为无关库存进出重复扫描整份样板计划。没有版本接口的旧替身保持完整重验。
3. 以单调信号序号记录标脏与读回的先后关系，避免 `dirty_tick == refresh_tick` 时多条引用反复读取同一个提供者。新的同帧信号以及读取期间产生的信号都使旧读结果失效。提供者删除／替换时清除相关记录，规模受提供者数量限制。
4. 缓存只保存检查依据，不能替代权威订单、预留与租约；取消、完成、拒绝与恢复时清除。恢复后重新验证，不序列化缓存。既有订单重验触发时机、拓扑阻塞恢复处置和资源归属语义保持不变。

## 实测

初始基线 `1a106fc7bf0-3-196cc6ba`（目标 60 秒）中 handler 最大 485.04 ms，订单重验最大 343.97 ms。

仅加入订单层复用后的 `1a1070bc712-5-a068ad32` 中，handler 仍有 267.90 ms，重验最大 226.41 ms。进一步定位到同帧重复提供者刷新。

最终版本对同一张运行中订单 `order@1/((0, -9, 86, -10), 1)#1/38` 的同一份计划做受控对比：14 条派发引用，5 个提供者。两条路径分别先对这些提供者标脏，再调用相同的 `CraftPlan.revalidate`；旧路径使用 HEAD 中原 `check_dispatch` 函数，新路径使用当前函数。没有提交／取消订单或调整物料，两边均返回相同的 `plan_topology_changed` 原因（该订单的拓扑已变化）。仅进行了一个对比对，不代表统计分布。

| 路径 | 提供者读取次数 | 重验耗时 |
| --- | ---: | ---: |
| 原同帧时间戳判断 | 14 | 259.78 ms |
| 信号序号去重 | 5 | 60.83 ms |

单次减少 198.95 ms，约 76.6%；读次数减少 9 次，约 64.3%。计时采用 Windows Python 2 的 `time.clock()` 墙钟。旧函数只用于这次对比，完成后删除临时定义。

最终版本自然观察 trace `1a10711a1e2-6-32082478`（20 秒）：handler 最大 12.56 ms，`_recheck_if_stale` 601 次、最大 0.357 ms、累计 10.43 ms，未出现完整 `revalidate`。这验证了当前稳定版本下的复用路径，不能当作重新下单全过程与 60 秒基线的等场景收益。

场景中主控代次与订单树都发生过变化（旧主控订单因此保持阻塞），所以整段 trace 的峰值差不用于宣称端到端优化百分比。热加载时方法源位置变化，原生 `/compare` 会把部分函数列为 added/removed，也不能把 removed 当作耗时归零。
