## 1. 网络条目与数量标签

显示集合为真实库存物品与网络样板物品产物的并集；按完整 ResourceKey 合并，暂不扩展网络列表的流体显示。样板产物只是显示来源，不计入介质库存、容量、可用数量或可交易数量。

“有样板”来自所属网络注册的、定义有效且未过时的样板提供者，不能通过扫描仓储中存放的样板物品推断。标记表示存在制作该物品的样板，不承诺材料、提供者、能源、内存等当前均满足；实际可执行性由服务端规划和正式准入判断。离线提供者的候选可用性与注册存续分开，不把 `has_pattern` 当作准入凭据。

| 真实库存 stored | has_pattern | 数量标签 |
| --- | --- | --- |
| 大于 0 | true | `stored` 的十进制文本后加 `+`，如 `256+`；1 个也显示 `1+` |
| 等于 0 | true | `+`，不显示 `0+` |
| 大于 0 | false | 沿用现有无样板条目的数量显示（可用数 stored − reserved，0/1 留空） |
| 等于 0 | false | 不保留显示条目 |

User 本次指定的是带样板条目的“库存数量”；因此带 `+` 的数字使用 stored，不使用 available。已有 D4 可用数显示只继续适用于无样板条目。预留不会改变 `256+` 的数字，但实际取物始终只能使用 available，不能用标签反推可取量。数量排序继续按 stored，`+` 单独存在的条目按 0 排序；搜索与稳定资源身份规则沿用现有实现。

库存取空且样板仍在时保留条目并变为 `+`；最后一份相关样板移除且库存为零时才删除显示条目。多个样板产出同一资源只显示一行，移除一个不能误清除仍存在的样板标记。产物集合不自动把显式 returns 当作可制作产物。

## 2. 手势与数量窗口

短按继续使用共享列表的选中、取消选中、背包存取及样板虚格协作逻辑。无库存条目可选中，但不可从网络取出真实物品。

长按带 `+` 的网络条目打开已有 `show_number_set_window`，用于选择订单目标数量；不带 `+` 的条目不触发此下单入口。长按命中后吞掉本次释放产生的短按，不能同时存取、取消选中或清空样板配置。事件捕获时记住完整资源键，后续不能按排序前的 collection_index 重新找目标。数量窗口取消不发预览或订单请求。

数量确认后显示 `order_preview_window`，并向服务端请求该资源及数量的规划预览。数量为正整数，服务端校验；默认值、最大值和长按阈值本次没有指定，沿用已确认通用策略，若没有既有策略须明确记录，不能宣称 User 已确认具体数值。最终成品是否抵扣目标数量仍遵守既有 R11／TargetSemantics，不能由这个入口擅自改定。

## 3. 预览状态与分帧计算

打开预览立即保持 `/order_preview_window/loading_panel` 可见，下单按钮禁用。服务端分帧计算订单配方树中每一步配方所需的原料及汇总结果，沿用每规划请求每 tick 最多 1 个逻辑配方节点、子树最早下一 tick 展开的限制；重复配方执行仍保留逐次语义。候选搜索、汇总和缺料传播都要有界，不在完成帧隐藏一次性无界遍历。

预览计算使用权威库存、预留及样板快照，走已有库存优先、循环候选排除和材料账本规则，不自行在客户端递归推导配方。失败路线不得污染其他候选或重复承诺库存。预览不创建执行订单，不占执行内存、并行槽、材料预留或活跃执行订单名额。

计算成功完成（含已完成的缺料结果）并收到完整匹配的结果后，将 `/order_preview_window/loading_panel` 的 visible 改为 False，展示总所需原料；不能因收到第一条进度或部分行而提前结束 loading。计算错误、超预算与失效不得假装“无缺料”，终止 loading 并禁用提交，显示原因。退出、关闭数量／预览窗口、会话失效或改目标时撤销对应交互，迟到结果按会话、预览 ID 和查询代次丢弃。

## 4. 原料行与缺料传播

预览覆盖整棵实际规划树中各配方的直接输入需求，保留中间品的需求与计划制作信息，不仅展示最终不可展开的叶子缺口。重复执行按实际次数乘算，同种完整资源键在不同分支的需求汇总，同时保留配方实例／依赖归属；库存分配必须复用整单账本，同一份库存不能同时满足两个分支。展示汇总与内存计费是两件事，中间品显示不意味着重复计入根原料字节。

每步配方的缺料判据为：其直接消耗原料存在未满足需求，或其依赖子树的任一叶子配方存在缺料。等价地，自底向上计算 `step_missing = direct_missing OR any(child.step_missing)`，沿实际采用的依赖传播到所有受影响祖先；未采用的失败候选不把成功路线染红，库存已经满足且无需展开的分支不因全网另一张配方缺料而染红。

网格的 `order_preview_src_item` 表示一个原料需求行：原料本身有未满足缺口，或负责制作该原料的所选配方子树缺料时，该行 `/order_preview_src_item/bg` 显示 RGB `(255, 200, 200)`。
**2026-10-03 实现备注（不改规则）**：`#color` 绑在 **image** 上在这台引擎里实测**不生效**
（同一个 `BF_BindColor` 绑在 label 上有效，11-13 的绿字在线是验过的）。因此实际渲染走的是
**同一行模板里的一层遮罩** `missing_mask`（静态色 RGB(255,200,200)，用 `#visible` 控显隐）——
`#visible` 是本仓库有先例的那条路。`bg` 上那条颜色绑定按本节原文保留：不生效也不碍事，
引擎哪天认了它就自动生效。证据见 [11 交付说明 §32](../tasks/11-交付说明.md)。同键汇总行任一实际需求分支缺料，该行即标红；无缺料行恢复模板正常颜色，不能保留上一预览的红色。UI 使用归一化颜色时转换为 `(1.0, 200.0 / 255.0, 200.0 / 255.0)`。

服务端输出每行需求、分配库存、计划制作数量和缺料标记，以及整单的缺料／阻塞结论。客户端不凭原料图标是否存在、样板标记、各行库存独立相减或显示文本推断缺料。现有“库存 0 计划制作 0”文字须换成权威计算值；库存栏指本计划分配的可用库存份额，不把全网同一份库存在多行重复显示为可用供给。

只要实际树中有一步配方缺料，就禁用整个下单按钮；不能仅检查根配方直接原料，也不能仅检查当前可见网格行。没有缺料且预览有效、无其他规划阻塞时才允许点击“下单”。颜色只是表现，服务端必须独立拒绝不满足条件的提交。

## 5. 确认提交与正式准入

“下单”才向系统发送正式订单提交；预览请求、数量确认和显示完成都不能自动提交。提交携带服务端可验证的预览身份和目标，不把客户端返回的配方树当权威计划。防止重复点击／重发创建重复订单；提交在途时禁用按钮。

预览不是资源锁定。正式提交重新校验网络身份、权限、库存／预留、样板／提供者、拓扑及内存等原有准入条件；过期结果不能绕过校验。若需重新规划，继续执行分帧与预算规则，不能一次性同步重算整树。是否复用有效预览计划、失效重算或返回刷新要求由实现策略明确，但都不得接受失效计划。

取消预览按钮只关闭／取消预览，不能调用执行订单取消；取消预览不影响已存在订单。真实订单取消仍属于工厂终端和既有 09 服务。提交后订单状态、拒绝记录、固定内存租约、执行及取消继续按 [订单规则](order_planning_execution.md) 执行。

## 6. 同步与验收边界

网络显示投影需要独立覆盖库存及样板变更的版本／脏键，支持快照与增量、分批完整性、重同步、旧会话过滤与订阅清理。显示版本不能冒充实际交易的库存 index_version。纯样板变更必须能新增／删除／刷新行；存储索引仍只记录真实库存。

预览结果须包含稳定的预览身份、目标、数量、状态、版本依据、原料行、缺料和阻塞结论。字段名、消息名、绑定名由后续实现交接核对后落地；本文的 has_pattern 等为语义名，不声称协议已存在。大结果应分批传输，客户端完整接收后原子切换显示。

离线回归与游戏验证必须分别登记；需求确认不代表 JSON 已接线、长按已可用或预览规划已实现。
