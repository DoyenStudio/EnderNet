## 参考与计数单位

默认参考 AE2 源模组：`CraftingService` 的规划与执行分工、`CraftingCpuLogic` 的派发与等待产物机制。这里不是已逐行核验 AE2 源码的等价声明；显式玩法以 User 确认的规则为准，其他参考行为需要核对来源，不能自行补成定案。

配方执行一次是一个逻辑任务／配方节点。同配方执行 10 次计 10 个任务，每次占 1 槽、完成一次进度加 1。内部允许压缩保存重复节点，但分帧计算、槽位计费、回流归属及进度必须保留逐次语义，不能按不同配方种类数或聚合步骤数代替。

## 分帧规划与准入

**成环规则（User 确认，按 AE2 修订）：** 材料需求先尝试使用可用库存，库存满足则无需展开该材料的配方；不足时，在当前祖先依赖链上检查候选配方，排除会导致递归的候选，继续尝试其他非循环候选。不能因一个候选成环而拒绝整单，也不能因全网配方图存在环而禁用所有相关配方。库存或其他路线满足需求时允许继续形成可执行计划；所有可用路线仍无法满足时，才将剩余需求判为原料不足并在执行准入前拒绝下单。

排除分支不修改实际样板、不删除需求，不把环内预计产出当作已有原料。失败候选的模拟消耗与产出不能污染其他候选或重复承诺库存；切换候选仍受逐 tick 规划及搜索安全预算约束，预算超限与已确认缺料分别报告。环路信息可以保留为缺料诊断，拒绝时不取得订单内存、并行槽或执行材料预留，也不进入执行订单 `FAILED`。拒绝记录保留方式、其他失败路径终态，以及 R11 已有最终成品抵扣不由本规则决定。

源码依据固定为 AE2 官方提交 `b7cf5822d9c128a61d9291cb2c1f92319253e4f0`：[CraftingTreeNode](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/b7cf5822d9c128a61d9291cb2c1f92319253e4f0/src/main/java/appeng/crafting/CraftingTreeNode.java#L111) 的 `buildChildPatterns`／`notRecursive` 排除递归候选，`request` 先取模拟库存，再尝试配方分支，最后报告剩余缺料；[CraftingCalculation](https://github.com/AppliedEnergistics/Applied-Energistics-2/blob/b7cf5822d9c128a61d9291cb2c1f92319253e4f0/src/main/java/appeng/crafting/CraftingCalculation.java#L103) 在求解失败后进行缺料模拟。本次采纳该循环处理原则，不自动采纳 AE2 其他内存、调度或目标量规则。

下单请求先进入规划中；此时不是已获执行准入的订单。每订单每 tick 只计算 1 个配方节点，子树最早下一 tick 开始；同 tick 的重复调度不能额外计算节点。不能简单把通用工作量预算设成 1 就宣称符合，工作单位必须与配方节点对应。内部遍历、候选搜索仍需有界，不能在一个节点内隐藏无界递归。多订单共享的全网计算预算另行调度，不能放宽单订单限制。

规划完成后按整棵实际订单树的叶子根原料需求量计算内存：`required_bytes = 根原料总单位物 × 1 B/单位物`。同种原料在不同分支的实际需求相加，不能只数种类；按完整执行次数计需求，不能只算一次配方或当前库存缺口；中间产物不重复收费。**叶子的界定（2026-09-26 User 确认）：** 叶子＝`demand - own_output - byproduct_output > 0` 的那些键。逐项：

- **根原料**（没有任何步骤产出它）：`own_output = 0`，整份需求都计入——不管它是从库存来的还是从外部输入来的，它都是这个订单要占住的那一份。
- **库存已抵扣、因而不再展开的中间品**：那份抵扣量就是这里的差额，**计入**。这正是「把抵扣物折算成内存」。
- **由本计划产出的中间品**：`demand == own_output`，差额 0，不计入——它的原料在下一层已经计过了。
- **副产物**：从别的步骤顺带出来的，那份产出同样有自己的原料在账上，再计一次就是重复收费。

结果是**每一单位物正好被计一次**：要么作为要生产的根原料，要么作为从库存／外部拿的叶子。这也是验收「中间产物不重复收费」的判据。

仍未明确、须明确后验收的两项：**返还物循环复用**的计费方式，以及**非整单位流体的取整口径**（已做成具名字段 `ByteRounding`，替身取向上取整，见 R07 那一行）。不凭实现猜测。

准入时重新核对网络当前可用字节并实际取得订单内存租约，避免并发请求超卖。大于可用值则拒绝下达，不作为已接受的缺内存订单自动等待；等于可用值通过内存这一项检查，其他准入仍照常校验。未接受的规划请求可以保留诊断，但不得持有执行资源或自动转成执行订单。

开始订单时一次性确定并占用固定大小的内存，直到订单完成或玩家手动中止前，占用字节数始终不变。原料消耗、剩余任务数、部分配方完成、同时运行的配方数量、暂停、断电、阻塞或异常都不使这份内存增减；不得按剩余原料或当前活跃配方重新计费。比如开始时占用 40 B，执行进度 0%、50%、99% 时都占用 40 B，结束时一次性释放。旧实现的失败自动释放路径需要按此重审。存档重启、主控破坏等异常生命周期与 R05/12 联合确定，不把它们暗中等同于手动取消。

## 执行、槽位与进度

槽位租约归属于每次配方执行实例：开始前取得 1 槽，配方完成释放。一个订单应持续派发依赖已满足的任务，直到网络无可用槽位或没有可执行任务；并非保证所有树节点都能立刻并行。实际派发仍受材料、提供者、能源及每帧预算约束，预算耗尽后继续推进，不以一次只推进一个未完成步骤作为订单的并行上限。多订单派发优先级与公平性尚需明确。

每次执行单独跟踪预期输出和实际回流，10 只把一份真实产物分配给一个等待实例；全部要求的输出满足才完成该任务并释放其槽。取消时在途任务、槽位注销及迟到产物必须与 10/R05 对齐，不能伪造外部机器回滚。

执行进度为 `completed_recipe_tasks / total_recipe_tasks`，总数包含重复执行次数；例如 10 次相同配方完成 3 次就是 3/10。服务端在任务完成时更新权威计数，重复回执不能重复累计；规划中的总数未确定时不能冒充执行完成比例。客户端实时展示归 11-06，等待 User 创建并交接 UI 后再对接，不能据此推测控件、交互或 UI 同步协议。

## 2026-09-26 追加决定

以下五点由 User 同日追加确认，与上文同等效力。

### 1. 执行期异常一律「阻塞／需人工处理」，不再有不可取消的失败

订单**通过准入之后**遇到的任何问题（提供者离线、写盘阻塞、断电、主控不可用、
批次推不动、样板被改）都**不进入 `FAILED`**，而是停在**阻塞**：停止新派发，
**已确定的固定内存继续占用**。玩家可以随时**手动中止**，由 09 统一释放内存。

- 这样**不需要「失败后清理」这种额外的玩家操作**：任何已开始的订单都留得出路。
- `FAILED` 收窄为「**尚未通过准入的请求**」的兜底终态，**不持有任何执行资源**
  （内存、并行槽、预留都不占）。正常玩法输入到不了它。
- **释放内存不等于删除物料。** 手动中止时在途物料仍需**保留归属**，
  已经投进外部机器的东西也拿不回来（R05 未定，替身口径仍是「留在原地、
  逐条报出来」）。

### 2. 拒绝下达保留一条独立的拒绝记录

被拒绝的请求**不是订单**，另存一条记录：目标、数量、拒绝原因、时间、请求 ID。

- **不占内存、不占并行槽、不占活跃订单名额**；**不自动重试**；
- 有数量上限的近期记录，避免无限增长；
- 存在的理由：**分帧规划让「拒绝」变成异步的**——玩家点下按钮时命令先返回
  「规划中」，可能过很多帧才给出拒绝，那时人多半已经离开界面。
  **只剩一个统计数字等于没有结果。**
- **本决定只覆盖服务端记录**；如何展示等 User 创建并交接 UI 后再对接，
  不据此推测控件与交互。

### 3. 派发按订单轮转，不加「每单每帧最多 M 个」的替身

- 每一轮，每个**有就绪任务**的订单派发 1 个任务，然后开始下一轮；
  直到槽位用尽、没有就绪任务或帧预算耗尽。
- **只有一个订单时，它照样可以吃满全部空闲槽**（与「每个订单固定占 1 槽」相反）。
- 多订单**共享新空出的槽位**，**不抢占已经运行的任务**。
- **轮转位置跨 tick 保留**，避免总让第一单先拿。
- 这条是 **09 的派发公平性**，与 R06 的**产物回流分配**是两件事，不互相替代。

### 4. 执行实例 ID = `订单ID/步骤下标/执行序号`

- 同一配方执行 10 次就有 **10 个不同的执行实例**；**同一次执行重试必须沿用原
  ID**，不能重新编号。
- **订单 ID 必须避免重启或重建后重复。** 现有的
  `order@<分量>/<主控实例>/<序号>` 在**进程重启后会重复**：分量编号会重新分配、
  序号从 0 重新开始（真机实测过同一个网络的分量从 2 变成 3）。因此订单 ID 里要加
  一个**启动期生成的一次性进程标识**。它是 12 落地持久计数器之前的过渡身份，
  不是持久身份。
- **两个 ID 各管一件事，都要保留**：
  - **执行实例 ID** —— 标识「**产物归谁**」；
  - **回流操作 ID** —— 标识「**这份回执是否重复**」。

  **不能只按执行实例 ID 去重**，否则同一次执行分多次回流时，后几次会被误当成
  重复丢掉。09 的等待台账现在用的去重键是
  `(执行实例, 操作 ID, 资源键)` 三元组，正是为了这件事——本节只改 ID 的形状，
  键的结构不变。

### 5. 规划名额与活跃订单名额分开

- 拆成 `max_planning_requests`（规划中的请求上限）与 `max_active_orders`
  （已接受订单上限）两个。
- 规划完成、**正式准入时重新检查**活跃订单数与可用内存，并**一起取得资格**。
- 已接受但正在排队、阻塞或取消处理的订单**仍占活跃名额**；
  **已拒绝的记录不占**。
- 这样大量规划请求不会挤占执行订单名额，也不会无限消耗计算资源。
- 两个上限的**具体数值仍未定**（属 R04 的剩余数值）。

### 候选预筛：08 侧边界与 09 侧的期望（2026-09-26 落地）

**08 侧做完了什么。** 规划器改成**先筛后建**：候选在**建步骤之前**逐个过
`_screen_inputs()`（问「这条候选自己的输入在当前边图上能不能绕回本键」），
会绕回的被排除、继续试下一条；只有可用候选**全部**被排除时才记一条
`RECURSIVE_CANDIDATES` 缺料（环路路径进 `detail` 作诊断）。
**它不是「试算—回滚」**：被排除的候选根本不碰账本（不改批次、不记产出、
不建边、不记需求），因此不存在「残留污染」，比回滚更强。
既有的「展开时发现成环就拒绝那条边」分支保留为防御网，
但它在新结构下**不可达**（`counters["cycles_refused"]` 是它的唯一观测点）。

**连带的可见契约变化**（08 侧，09 与 12 都会看到）：

- 总判决**不再出现** `CYCLE`：目标自己配方自引用时落 `MISSING_MATERIALS`，
  原因码是 `PLAN_MISSING_MATERIALS`（**不再是 `PLAN_CYCLE`**），
  环路仍然写在 `status_detail` 与缺口的 `detail` 里。
  `PlanStatus.CYCLE` 与 `_STATUS_REASONS` 里那一条**保留**，
  好让 12 恢复一份旧存档的计划时仍拿得到原因码，只是规划器不再产出它。
- `GapCause.CYCLE` **已删除**，取代它的是 `RECURSIVE_CANDIDATES`
  （归 `ABSENCE_CAUSES`：这是「看完候选之后的结论」，不是「没看完」）。
- `steps[].blocked` 与 `steps[].blocked_by` 从此**恒为 `False` / `[]`**
  ——全仓库只有那个防御网会写它们，而它不可达。`blocked_keys`
  **不受影响**（它由「需求减可达量」算出，照旧列出真正拿不到的键）。
- 新增三个诊断计数 `candidate_trials`／`recursive_candidates`／`cycles_refused`，
  **不进 `plan_counters()`**：那个元组会进 `content["counters"]` → 进指纹，
  而这三个是「实现怎么走的」、不是「计划是什么」的事实。

**09 侧（本轮未动）的期望。** 原因码从 `PLAN_CYCLE` 变成
`PLAN_MISSING_MATERIALS` 之后，09 的处置逻辑**不需要按原因码分支**就该是对
——它本来就是「规划失败 ⇒ 走 `_reject_request`，不建订单、不占名额、
不持有任何执行资源」。要改的只有**断言与文案**：若有用例或诊断在
`PLAN_CYCLE` 上做判断，要跟着换码；detail 里的环路路径仍然拿得到。

**已知限制（本轮只记录，不修）。** 同一深度上的兄弟键由 `(depth, 身份)`
贪心定序：若成环的那一侧先被选中，好路线就没了，计划报缺料——
**是次优，不是谎话**（环路径与缺口都诚实）。修它等于放开多候选搜索
（`SEARCH_MULTIPLE`，仍待定）。另外 `_achievable` 按输入逐条比较、
不做守恒，同一份库存可能被两个消费者各算一次，于是 `steps[].runnable`
偏乐观——它不影响总判决，属既有问题。

### 复核中发现的、表上没有记的问题

1. **`OrderPolicy.submit_plan_budget` 与 `plan_budget_per_tick` 是死开关。**
   它们只在 `capacity.py` 里被声明、校验并报进 `unresolved_report()`，
   全仓库没有任何消费者——分帧改造之后「提交预算」这个口径本身已经不存在。
   要么在 09-02/03 的改造里删掉，要么交给取代它的每帧节点上限。
2. **`submit_order()` 里 `status in (FAILED, CANCELLED)` 那条分支已不可达**
   （`_start_planning()` 只建 `PlanJob`，不再同步判失败）。它是 09 交付说明
   第 19 条的修复，现在只剩注释价值。
3. **复核拒绝那条腿不带「被别人锁着」的补注。** `_taken_stock_reasons()`
   只挂在计划失败那条路上（读 `plan.gaps`），而复核失败时计划本身是完整的、
   `gaps` 为空。于是并发下单时玩家看到的是「声明 2，现有 0」，分不开
   「网络里确实没有」与「有，但被别的订单锁着」。新规则把这条路变成了
   并发下单的常见路径，补注该跟着搬过来。测试里留了带说明的断言
   （`test_two_orders_never_get_the_same_stock`）。
4. **`QUEUED` 从外部观察不到。** 调度器会在同一帧里访问同一个运行时两次
   （`_step_plan()` 的 docstring 已记着这件事），因此落地那一帧订单就已经
   进了 `RUNNING` 并开始推进步骤。想看「有没有过准入」要看 `adopted`，
   不要看状态字符串。
5. **`test_a_second_order_does_not_clobber_the_first_ones_batch` 原本是空转的。**
   它手工调 `slots.refresh(capacity + 1)` 放开容量，而 `refresh_capacity()`
   每帧重算会把这份手工值推翻——第二个订单从来没拿到过槽位，那条用例看着绿，
   其实什么也没证到。现在夹具补了第二组处理器与内存槽，它才真的在验
   「不抢批次槽」。
6. ~~**代码声称的一条「User 确认」在本规则里仍是未明确项，两边必须对齐。**~~
   **已于盘点当日查明并修正**：`planner.py` 的 `leaf_units()` 声称的
   「库存已抵扣而不再展开的中间品也要折算（2026-09-26 User 确认）」**确有其事**
   ——是本文原先漏记，不是代码替未定规则定案。已按 User 裁决把叶子界定
   写进「分帧规划与准入」那一节（四种键各自的算法与理由、以及「每一单位物
   正好被计一次」这个判据），代码注释里的引用随之成立。同一句话里剩下的
   「返还物循环复用」与「非整单位流体的取整口径」仍按未定处理，前者未安置，
   后者已具名进 R07。**留这一条是为了记住这类两边不一致的形态**：
   文档缺记会被读成「实现偷偷定案」，两种表现一样、成因相反。

### 本轮随之迁移的测试口径

新规则改掉的是**观察点**，不是结论。`endernet_tests/test_executor.py` 里
32 条用例按新口径迁移（离线全绿）：

- 「提交完立刻看状态」不再成立：新增 `settle()`（推进到离开「规划中」）与
  `assert_admitted()`（过准入看 `adopted`），多订单用例必须传 `order_id`。
- 「拒绝」的判据从命令的返回挪到**拒绝记录**上（`last_rejection()`），
  这正是追加决定 2 说的那件事：命令那一帧只答得了「规划中」。
- 备料会在落地那一帧把预留花掉，因此断言「还锁着多少」的用例改用
  关掉样板口或小一号缓冲来构造那个时刻。

## 新规则验收（均待执行）

**「均待执行」说的是游戏内验收，不是「都没写」。** 到 2026-09-26 为止，其中
一部分已经有实现与**离线**证据（分帧规划的节点语义、根原料字节计费、
拒绝记录），但离线用例证明不了这一节要的东西——它们大半要在一张真网络上
跨帧跑出来（并发下单不超卖、4 个槽同时在途、断电与阻塞期间内存不增不减、
重进后租约不重复）。逐条的实现状态见上面的「当前差异及任务落点」，
**没有一条能勾掉**。

其中第 1–4 条（成环那四条）在 2026-09-26 又拿到了一层**离线**证据：
`planner.py` 的候选预筛与 `test_planner.py` 的四条对应用例都跑绿了，
证据钩在差异表第 1 行与「复核证据」那一节。**离线用例证明不了这一节要的东西**
——成环与回退要在一张真网络上跨帧跑才说得上验过，所以这四条照旧**保持空白**。

- [ ] 仅有循环路线且库存无法满足时，排除递归候选后报告剩余缺料，拒绝下单，不取得执行资源、不修改样板。
- [ ] 制作 A 需要 B、制作 B 需要 A，但库存 B 足够时，直接使用 B 完成规划，不因配方图存在环拒绝。

**2026-09-26 追加决定的验收**

- [ ] 已开始的订单在提供者离线、写盘阻塞、断电、主控不可用、批次推不动、
      样板被改这六种情况下**都不进入 `FAILED`**，而是阻塞；玩家手动中止后

R04 已确定字节单位、根原料计费、内存持有周期和逐次配方槽位周期；仍未确定各内存条容量、无处理器时的默认槽位等数值。R11 的已有最终产物抵扣、配方选择策略等未被“默认参考 AE2”自动定案。

按字节计费之后**新露出来一条**边界：流体不足 50 mB 时的精确计费与字节取整
口径。1 mB 恰好 1 微单位，于是 1 mB 的原料会算出 `0.02 B`——规则要求
「不擅自舍入」，所以它被做成具名字段 `ByteRounding`（默认 `CEIL` 向上取整），
并已补进 R07 那一行。这也是「已实现 ≠ 已定案」的又一例：替身口径能跑，
但它不是定案值。
