# 订单正常退出恢复（2026-10-04）

玩家退出整个存档后重进，订单列表此前变空：`write_network_states()` 保存了
订单摘要，但 `_apply_archived_network_states()` 只应用存储台账，没有订单读取方。
本次补齐新订单的完整快照与恢复路径。当前存档为测试存档，按 User 要求不迁移
旧版仅含审计摘要的订单，没有删除游戏存档。

## 保存边界

网络仍按主控位置文本保存一条 `network_state`，包含存储预留、待核对转移和
订单簿。`stop()` 在标记设备未加载之前调用 `flush_persistence()`；显式
`write_network_states()` 也可保存快照，不逐帧序列化整张订单簿。

订单簿新增 `resume_version = 1` 与 `resume_orders`，保存目标的完整资源键、
完整计划、步骤配方与依赖、批次创建/完成计数、逐次执行 ID、输入的
`staged / delivered / delivered_base`、产物已接收数量、原料接口批次 ID、
装配消费/产出游标、不确定标记、暂停状态、固定内存字节数与在途名单。
资源键按 `ResourceKey.to_dict()` 保存，恢复不用规范文本反解物品身份；
元组与节点也经过显式编解码，JSON 往返不会破坏位置键。

保存预留数量以存储服务的活账为准，包含任务 10 新分配给订单的产物预留；
不假定订单镜像已经同步。订单回执去重表与回流服务本网络的去重表同时保存。

## 恢复顺序与续跑

1. 读取网络记录，等待设备发现、拓扑与唯一主控形成。
2. 按主控位置恢复订单，保留原订单/执行 ID，并抬高发号水位。重启生成的新
   分量号与主控运行实例只用于当前绑定；存档中本就属于另一主控的订单保持阻塞。
3. 恢复既有内存与在途槽位占用。即使内存条或处理器尚未加载、容量暂时缩水，
   也保留原占用，不把已接受订单重新当成内存准入请求。
4. 主控先于原预留介质出现时，订单先恢复可见，网络暂时关闭业务，等待原介质
   挂载；期间不覆盖完整网络存档。存储服务只恢复有对应活订单的原预留
   （包含原介质分摊与预留 ID）；无主或
   终态订单的预留仍归档。待核对转移保持待核对，绝不重放。
5. 重建等待产物索引与去重表，**早于首帧接口回流及业务推进**，防止首帧产物
   被当成无人认领的普通库存。回流等待者的登记序号也保存，恢复不改变 FIFO 顺序。
6. 订单首次推进时等待原提供者加载，核对设备类型与预留数量，重绑本次设备
   代次，随后沿用既有样板复核。缺失提供者时订单可见且阻塞，不释放固定内存。
   装配仓恢复独占归属；重复归属或预留不一致停止该订单并报告待核对。
7. 规划中的请求重新抓取快照规划，沿用原订单 ID；已落地订单沿用原计划与
   逐次执行账。已经备料或投进机器的部分不再次搬运，已消费的装配输入不再次
   消费，已生成的产物不重复生成。暂停保持暂停；完成和手动取消释放恢复的租约。

恢复快照无法解码或版本不支持时，关闭业务闸门、公开 `persistence_restore_error`，
保留原网络记录并禁止用空簿覆盖。重复应用同一订单簿不会复制订单或租约。
