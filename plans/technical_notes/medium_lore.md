# 存储介质容量 Lore：身份与刷新实施契约

日期：2026-09-25。对应 `items.md`、任务 05/06/11/12/14。本文是新增待实现契约，不代表代码已交付或性能已测量。

## 1. 三层数据与职责

| 数据 | 用途 | 更新边界 |
| --- | --- | --- |
| 介质稳定 ID 与权威内容 | 标识具体介质，保存内容及归属 | 由 12-02 明确物品携带方式和持久后端，不能由 Lore 推导 |
| 盘内资源的 ResourceKey 与数量 | 区分石头、附魔物品等实际库存 | 仅实际库存交易改变对应数量；介质 Lore 刷新不改盘内资源键 |
| 介质物品容量 Lore | 展示该盘剩余类型/数量 | 由权威摘要生成，可合并、延迟写回和重建 |

介质物品本身被当作库存资源时，还需要它自身的 ResourceKey。这与盘内资源键不同：容量 Lore 更新不得被解释为盘内全部资源更换身份。现有 ResourceKey 构造时复制元数据，修改真实物品不会自动修改旧键；禁止原地修改已作字典键使用的身份字段。

`customTips` 中由型号规格生成的容量、类型数、读写速度是静态型号参数；本功能的两行 Lore 是实例剩余量。二者分别保留，不互相覆盖或作为彼此的缓存。

## 2. 身份比较与物品还原

采用以下边界，具体编码和迁移由 12-02 完成后才接入正式身份路径：

1. 例外只适用于已识别的 EnderNet 存储介质，且只排除本模组管理的两行动态容量 Lore 及其纯展示管理信息。禁止全局忽略 `userData`、整个 `display` 或整个 `Lore`。
2. 自定义名称、其他 Lore、附魔、附加值及其他有效身份字段仍按原契约参与比较。稳定介质 ID 用于区分实例，并进入介质物品的身份表达；同型号、同剩余量的两块不同介质不能因此被合并。未初始化空介质的堆叠与 ID 分配时机由 12-02 明确，不能擅自为每次读取生成新 ID。
3. 身份投影只用于比较/哈希；实际物品载荷保留完整展示与元数据。不得通过删除真实物品的 Lore 来取得稳定键，也不得用旧 ResourceKey 的 `_raw` 或旧图标样本覆盖最新容量行。
4. 真实物品还原/输出路径按介质 ID 获取权威摘要，保留其他物品字段，再物化最新容量行。完整载荷、身份投影和展示版本分别管理；仅展示变化不产生库存 remove/add、预留重建或产物回流事件。
5. 缓存键只在身份字段改变时失效；容量展示改变仅使展示缓存失效。不能缓存对可变原始字典的引用，也不能让新旧身份算法在同一索引中混用。

### 12-02 必须交付的决定

- 稳定 ID 的字段、初始化/持久化方式、重复 ID 检测、未知记录处理，以及空介质堆叠规则。
- 容量行的可靠归属标记与格式版本。不能仅按中文前缀或固定行号删行：玩家或其他模组可能拥有相同文本、插入或重排其他 Lore。标记方案须实测原生详情和物品往返；无法确认归属时保留原数据并报告待迁移，不能误删。
- 明确格式缺失、空 `display`/`Lore` 与排除管理行后的空结构怎样归一化，保证添加/删除受管理展示信息不改变身份，而其他字段仍遵守既有空值区分契约。
- 对旧 ResourceKey 描述/指纹、存档、索引及同步描述表制定版本迁移。根据完整旧记录重建，不能在现有字典中原地改键；无法确定介质身份的旧数据保留待核对，不按剩余量合并。重建前暂停受影响交易，完成后重建派生索引并使旧描述会话失效。

稳定 ID 与受管理 Lore 排除相互配合，不能仅添加 ID 就宣称已解决问题：若动态 Lore 仍参与比较，同一 ID 的键仍会随展示变化。

## 3. 摘要计算与更新代价

建议摘要字段为 `medium_id`、`content_version`、`remaining_types`、`remaining_capacity_micro`，最后一项使用现有 1/50 单位物整数尺度。显示用整数除法与余数生成精确文本，例如 25 微单位显示 0.5 单位物，不使用浮点往返或 K/M 缩写。

实际内容提交维护已用类型数与容量计数；若现有实现查询时遍历内容，先测量，再在提交/恢复边界维护可核验计数，不宣称现有查询已经 O(1)。新类型首次加入和最后一份取空分别增加/释放类型占用，部分成功按实际量计算；预留/释放、模拟、失败、去重命中不增加容量展示工作。

热路径只更新必要计数/版本并对介质去重标脏，不构造介质物品 ResourceKey、不格式化 Lore、不调用引擎物品写回。盘内实际交易仍按原 ResourceKey 契约执行。

## 4. 有界合并刷新

| 触发条件 | 处理 |
| --- | --- |
| 首次初始化/权威恢复完成 | 摘要可用，标脏；首次展示或交接前生成容量行 |
| 实际存取提交 | 对受影响介质更新摘要版本，合并为一项待刷新状态 |
| 无查看者、无交接 | 不周期性重写真实物品；保留每介质的最新脏版本，不积累每笔交易队列 |
| 玩家打开驱动器或读取介质详情 | 注册所需介质的展示需求，首次读取最新摘要；持续查看期间按预算合并刷新 |
| 拔出/转移/既定掉落 | 在交接边界强制生成与所交接内容版本一致的物品载荷 |
| 关闭界面、离开或设备失效 | 清理查看订阅，取消旧位置的展示写回，不删除权威介质数据 |

合并窗口与每帧最大写回数量是待测配置，不在文档中承诺固定延迟或帧率收益。始终以介质 ID 去重，每次刷新只取最新摘要；用公平有界队列避免大驱动器独占写回。实际生成的两行与当前一致时跳过写回，成功核对后推进展示版本；不能只比较 `content_version`，因为存取抵消后显示可能不变。

原生背包悬停未必有可用的服务端事件。11 须核实引擎能力：可用设备会话/可见槽订阅驱动查看更新，背包中的介质依靠交接前写入保证详情；不得假设原生 tooltip 可即时回调服务端。查看开始时允许拉取最新展示，但不依赖悬停事件保证物品正确性。

## 5. 写回与交接顺序

1. 定位真实持有者及槽位，捕获介质 ID、设备代次、槽位版本和内容版本。
2. 读取当前物品完整载荷，从权威摘要生成两行，按已确认的管理格式替换，保留其他字段。
3. 写入前重新核对身份/槽位/内容版本。发生替换或内容继续变化时丢弃旧候选，重新生成；普通展示可合并到下一轮。
4. 经适配层提交并按其能力确认结果。仅确认成功才更新展示已应用版本；失败保留脏状态，有限退避。结果不确定先读回核对，不盲目重放物品转移。
5. 拔出等交接冻结该介质的并发内容修改或取得一致交接版本，将最新 Lore 合入将交出的物品载荷；只有已确认的交接才切换归属。不先交出旧物品再凭旧槽号补写；不能确认写入或交接结果时沿用 06/12 的待核对流程。

普通展示写回失败不回滚已成功库存交易，不产生第二份介质或新增产物。仅刷新缓存不绕过既有离线装卸权限，也不改变存档提交规则。无内容变化的重复刷新应幂等，不重复追加容量行。
