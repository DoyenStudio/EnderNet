# 订单与回流的执行台账契约（09 ↔ 10）

更新日期：2026-09-26。状态：**两侧都已实现**——09 侧离线验证并在游戏内实测过；
10 侧（`crafting/returns.py`）离线全绿，且已在本机测试世界里跑通「下单 → 派发到
机器 → 手动投料 → 分配 → 结单」整条链（见 `10-交付说明.md`）。
用途：把「09 的等待台账」与「10 的产物分配索引」之间的接缝一次定死，
免得两边各写一份而中间的账对不上。任务 09 文档原文要求「与 10 先联合确定
等待台账契约」，这份文件就是那个契约。

**这份文件不是玩法文档**。产物的分配顺序归 R06（10 定），执行实例的
生命周期归 09。这里只写两边**怎么把数据交过来交过去**。

## 1. 一句话分工

    **09 记住「谁在等什么、还差多少」；10 记住「东西来了该给谁」。**

- **09 拥有**：执行实例 ID、每实例每产物的**剩余需求**、`op_id` 去重、
  登记与注销的时机。
- **10 拥有**：全局的「资源键 → 等待执行实例」索引、分配顺序（R06）、
  从真实回执里取得的**实际接受量**。

分开的理由很简单：索引要**跨网络**看全部等待者才排得出顺序，而剩余需求
是某一个执行实例自己的账，只有它自己知道。合成一份的代价是两边都要
维护另一边的数据结构。

## 2. 执行实例 ID

    执行实例 ID = "<订单 ID>/<步骤下标>"

例：`order@1/((0, 1, 65, 0), 0)#0/1/0`。

- **订单 ID 里带着主控实例**（`order@<分量>/<主控实例>/<序号>`），因此
  「这张订单属于哪台主控」在字符串上就看得出来，不需要另存对应关系。
- **一个执行实例 = 一个步骤**，不是「一次投料」。同一步可能分几批备料、
  分几批投料，那些批次共用同一个执行实例 ID。
- 步骤完成或订单取消时**必须注销**（见 §5）。10 的索引里留着一条已经
  不存在的实例，会让一份迟到的产物命中一个死掉的等待者。

## 3. 09 → 10：登记（`ReturnsSink.register`）

```
register(execution_id, expectations, order_id) -> bool
```

- **时机：派发确认之后**（10-01 原文：「仅登记已经确认派发的执行实例」）。
  09 在**全部输入都真的进了外部机器**（`PortState.batch.delivered` 到齐）
  那一刻登记。太早登记会让 10 把产物分给一个还没投料的步骤；
  太晚则会让第一批产物命中不到等待者、被记成孤儿。
- `expectations` 是 `StepOutput` 序列，每项含
  `key`（活的 `ResourceKey`）、`canonical`、`expected`（**这一实例要等多少**）、
  `counts_for_completion`。产物与**返还物**都在里面。
- **登记是替换语义**（同一 `execution_id` 再登记一次覆盖旧的）。累加会让
  剩余需求凭空翻倍，然后永远等不到。
- 返回值表示「接收侧接上了没有」。09 的默认（库）口径注入的是
  `AbsentReturns`，它返回 `False` 并明确报「任务 10 未接线」——
  订单因此停在等待产物并报 `order_returns_absent`。**这不是假成功**。

## 4. 10 → 09：分配（`OrderExecutor.receive_output`）

```
receive_output(execution_id, key, count, op_id="", source=None) -> int
```

返回**本次实际被接受的量**。三条语义写死：

1. **`count` 必须是已经真的进了网络管理的存储的量。** 10 应当先执行
   `StorageService.commit_insert(...)`（或等价路径）拿到真实回执，再把
   `receipt.moved` 交给 09——**不是**把「机器应该产出了多少」报上来。
   这正是 10-02「从真实接受数量进行分配」的落点。
2. **`op_id` 必填且必须稳定。** 同一条回执重试时用同一个 `op_id`，
   09 会**返回 0 且不再加数**（10-05）。没有 `op_id` 的回执仍会被收下
   （丢掉一条真实入库会让订单永远等差），但会进 `stats["no_op_id"]`，
   诊断里看得见「谁没用 op_id」。
3. **多出来的部分不接受。** 09 按剩余需求截断，超出部分留在网络里
   当普通库存（10-06 原文：「不丢弃」）。不吞、不丢，只是不计数。

**09 不接受任何其他形式的完成通知。** 没有「直接告诉订单做完了」的入口：
那会绕过等待台账，让「谁在等什么」与「到货了什么」变成两份可以对不上的账。

## 5. 注销（`ReturnsSink.unregister` / `WaitingLedger.unregister`）

| 时机 | 谁发起 | 为什么 |
| --- | --- | --- |
| 步骤完成 | 09 | 不再等它了 |
| 订单取消 | 09 | 10-07 原文：「由 09 注销等待记录，避免回调命中已取消实例」 |
| 订单失败/结单 | 09 | 同上 |

`unregister` 返回**还没等到的件数**。取消时它通常是正数——那说明有产物
还在外面，调用方要把它记进 `residue` 报出来，而不是让订单看起来干净地
结束了。

## 6. 三个必须两边都守住的口径

### 6.1 「没到」不等于「不会到」

订单停在 `WAITING_OUTPUTS` 是**正常工作状态**，不是故障。10 的分配可以
隔很久才发生（外部机器慢、外面的人还没把东西放进去）。09 的
`_track_outputs` 每帧只读内存里的台账，不产生任何副作用。

### 6.2 返还物算完成条件

`OrderPolicy.returns_block_completion` 的**替身取 `True`**：09 验收原文
「所需鱼已回流但空桶未到时步骤仍工作中」说的正是「返还物没到齐就不算做完」。
R09 定案之前这一条挂在 `unresolved_report()` 里，正式档会被拦下。
10 那边**不需要区分**产物与返还物——两者都进 `expectations`，
按同一个剩余需求记账。

### 6.3 迟到产物仍要有接收路径

取消之后又到的产物：10 的索引里那条等待记录已经被注销，于是它命中
不到任何实例。**它不是「被丢弃」，而是回到普通库存**——10 应当把它
按普通入库处理（10-06 末句）。09 侧的表现是 `WaitingLedger` 的
`stats["orphan"]` 加一，而**不报错**：报错会让 10 的重试逻辑把同一条
回执反复送进来。

## 7. 离线验证用的假回流

`endernet_tests/test_executor.py` 里的 `FakeReturns` 是**具名的假实现**，
它把两段都做了（先 `commit_insert` 真入库、再 `receive_output` 分配），
因此状态机走的是真的那条路，而不是一条只有测试才知道的捷径。

**它只是为了让状态机可测**（09 文档原文：「初期可用假回流验证状态机，
不代表可玩验收」）。10 已经落地（`crafting/returns.py` 的 `ReturnsService` /
`ReturnsPort`），走的是同一个 `receive_output`；`FakeReturns` 因此退回成
「不经过真实存储回执的替身」，只在 09 自己的用例里用。
**`AbsentReturns` 仍然是库的默认口径**，订单在默认装配下会如实停在等待产物。

## 8. 给 10 的实现清单

- [x] 维护 `资源键 -> [(执行实例, 剩余需求)]` 的全局索引，登记/注销由
      `ReturnsSink` 的三个方法驱动。（索引在 `ReturnsService._index`，
      全局一份；**分配时按 `component_id` 过滤**——资源到达网络 N 只满足
      N 上的订单，跨网络没有转移通道。全局的那一份只用于诊断。）
- [x] 产物**先真入库**（拿 `TransferReceipt.moved`），再按 `moved` 分配。
      （入口是 `TransferCoordinator.sink`，由 `_deliver_external_input`
      在 `commit()` **成功之后**调用，因此 `count` 就是真进网的数量。）
- [x] 按 R06 的稳定顺序分配；每次分配都要扣减本次剩余可分配量，
      保证「A、B 各需 8 个、输入 10 个时分配总和恰好 10」。
      （R06 本身仍是替身口径：FIFO + 不提权，进 `unresolved_report()`。）
- [x] `op_id` 去重：同一回执重试、同步回调、恢复重放都走同一条路径。
      （键是 `(component_id, op_id)`；空 `op_id` 仍收下并进
      `stats["no_op_id"]`。）
- [x] 冻结/排队：09 在 `handle` 与备料命令进行期间是「忙」的，
      同步到达的回执应当在本次提交完成后再分配（09-05 原文：
      「同步回调排队到本次提交完成后分配」）。
      **本次实现选择不做排队层**（09 侧也没有），而是在 `accept` 上写明
      这条约束：10 **不得**从 09 的命令处理内部同步回调它。留出的暴露点是
      `stats` 的记账——真有人那样调，诊断里看得见。计划里提到的
      `stats["reentrant"]` 计数**没有落地**（不留一个永远为 0 的字段）。
- [x] `returns.py` 的 `describe()` 要给出 `available: True`，
      09 靠它区分「接上了」与「还是替身」。
      （`ReturnsPort.describe()["available"] is True` → 09 的
      `service_sink_available()` 为真、`_sink_blocker()` 返回 `None`、
      `status()["returns_wired"]` 为真、`runtime.order_view()["returns_absent"]`
      归零。游戏内已核对 `adapter_id: "returns"`、`available: True`。）
