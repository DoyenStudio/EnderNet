# 通用终端物品列表：增量索引与同步实施说明

更新日期：2026-09-24。状态：实现规划，尚未实现或进行性能验收。

本文细化 [05. 存储服务](<../tasks/05. 存储服务.md>) 的 05-04/05-05/05-07/05-09 和 [11. 终端与客户端同步](<../tasks/11. 终端与客户端同步.md>) 的 11-01/11-02/11-03/11-09/11-10/11-14；测试归入 [14. 集成测试与发布验收](<../tasks/14. 集成测试与发布验收.md>)。不改变主控准入、介质限速、资源归属和持久化契约。

## 1. 范围与实施顺序

通用终端列出所属网络已有效挂载的所有存储介质中的物品，同一 ResourceKey 合并为一个条目，暂不显示流体。混合介质中的物品仍纳入；外部箱子、订单缓冲、玩家背包和可合成但无库存的配方不自动算作介质库存。不可用设备的挂卸遵守网络生命周期；整网暂停时缓存可以保留，但不得将旧缓存当作当前可交易状态。

实施顺序为：确定数据契约 → 介质与网络增量记账 → 挂卸和恢复 → 合并发布 → 快照与增量协议 → 客户端列表 → 虚拟槽位 → 联调测量。前四步先使用纯逻辑后端验证，实际交易接入 03/04/06/12 的准入、预算、转移和存档。

首版采用每网络共享服务端索引、客户端完整物品摘要缓存、分批传输与虚拟滚动。服务端筛选分页只在测量证明完整摘要过重后引入；不能把分批传输误实现为每页重新扫描硬盘。

## 2. 步骤一：数据结构与不变量（05-05、05-09）

建议代码位置：`ROOT/server/storage/medium.py`、`service.py`；`ROOT` 为 `endernet_bp/endernet_scripts/endernet/`。下列名称为实施契约，不代表已存在 API。

| 结构 | 内容与职责 |
| --- | --- |
| `medium.items[key] = count` | 介质权威库存，整数数量，仅保留正数条目 |
| `item_totals[key] = (stored, reserved)` | 每网络唯一的物品汇总派生索引；available 由两者相减 |
| `item_sources[key] = set(medium_id)` | 持有该物品的介质候选集合，不再扫描全网找货 |
| `mounted[medium_id]` | 介质引用、挂载位置与挂载代次，阻止重复计入及旧回调 |
| `dirty_items = set(key)` | 待发布物品集合，同一发布窗口内去重 |
| `item_catalog[key]` | 稳定显示身份与图标描述；按需缓存，不随数量变化重复构造 |

要求：

1. 复用 `common/resource_key.py` 的 ResourceKey，数量不属于身份；附魔、耐久、自定义数据不同的物品不能误合并。进入库存后不修改键及其身份数据。
2. 仅物品进入上述物品索引；流体仍按存储服务原契约记账，不能因终端不显示就丢弃流体数据。
3. 对有效挂载集合，`stored[key] = sum(medium.items[key])`；预留由有效预留台账汇总，满足 `0 <= reserved <= stored`。
4. `stored > 0` 时保留条目，即使 available 为零。最后一份实际库存取空才移除条目；预留撤销必须与介质失效协调。
5. 索引不作为第二份权威物品存档，恢复时由介质与有效预留台账重建。
6. 候选集合只负责定位；实际选盘按明确的优先级与稳定介质 ID 顺序，不依赖 set 遍历顺序。空盘/可接收新类型的写入候选另由存储服务维护，不能只从 item_sources 选择。

首版直接使用 ResourceKey 字典。不要在每次加减数量时重新规范化物品数据或生成完整文本指纹；如后续身份哈希成为热点，再评估不可变键的哈希缓存或内部资源 ID。

## 3. 步骤二：把索引更新接入提交路径（05-06、05-07）

在服务端主线程由统一存储服务完成以下顺序：

1. 主控准入后检查介质代次、实际库存/预留、容量及共享读写预算。
2. 确定实际可提交量；纯模拟、拒绝和已经处理过的请求不进入记账阶段。
3. 在不向订阅者暴露中间状态的提交段内更新介质、预留台账、网络汇总和来源索引。失败时不得留下单边更新；具体回滚/预校验策略与转移契约一起实现。
4. 只有某介质对该键从 0 变正数或从正数变 0 时，才增加/移除 item_sources 中的成员。
5. 把受影响物品键加入 dirty_items，并记录存档脏介质。完成记账后才发布业务提交回执。

预留/释放虽然不搬动物品，也须标记数量视图变化。取出预留物品时同时结算 stored 和 reserved。跨多个介质的一次实际转移汇总后再对外通知。同网内部移动若最终 stored/reserved 不变，可省略终端更新，但仍须更新介质归属、来源和存档。

区分“业务提交回执”和“UI 批量更新”：前者保留实际操作身份和产物来源，不能为了 UI 合并而丢掉订单回流信息；挂载和缓存重建不是新产物回流。

完成检查：连续存取、部分成功、失败、模拟、重复请求及预留变化后，用测试中的全量求和作为独立校验；生产运行不逐 tick 执行此全量校验。

## 4. 步骤三：挂卸、拓扑与恢复（05-04、03-06、12-05）

| 事件 | 实施动作 |
| --- | --- |
| 新介质挂载 | 校验稳定 ID 未挂载；遍历该介质条目，将物品加入 totals/sources，批量标脏 |
| 介质卸载 | 拒绝该挂载代次的新提交；撤销有效预留并通知订单重验；扣除该介质贡献，清理来源，批量标脏 |
| 驱动器拆除/卸载 | 对其有效挂载介质执行上述卸载流程，不遍历无关驱动器 |
| 拓扑变化但归属未变 | 对最终挂载集合求差，复用未变部分的索引 |
| 网络拆分/迁移 | 冻结受影响交易，基于最终归属迁移挂载；切换完成后再开放业务并使旧会话失效 |
| 控制器冲突或整网断电 | 暂停交易，终端按会话规则失效；可保留派生缓存，避免电力波动触发全量重建 |
| 存档恢复/索引修复 | 从介质和有效预留重建，完成前不开放交易和完整库存查询 |

重复挂载、重复卸载应幂等；跨网迁移先解除旧归属再挂载新归属，同一介质不得同时贡献两份库存。网络重建期间如需分帧，构建暂存索引，完成后统一切换；不要逐帧把半张索引当作完整快照。

当前已列介质最多 64 种资源，单介质挂卸成本按条目数计算，与该介质存了多少件物品无关；不能把 64 写死为未来介质的通用上限。

## 5. 步骤四：脏项合并发布（05-07、11-02）

库存提交立即更新索引；UI 发布由调度器合并，首轮可使用 100～200ms 的可配置窗口进行测试，该范围不是已验收指标。

1. 仅在有物品订阅者且存在脏项时安排发布任务，避免每个终端自己轮询。
2. 发布时取出脏集合，读取各键最新 stored/reserved，构造绝对值 upsert；已不存在的键构造 remove。
3. 同一个键在窗口内多次变化只出现一次。允许发送冗余但正确的最终值，不必为了省一条消息额外保存全网上一版副本。
4. 相同网络/代次/视图且基准版本一致的订阅者共享不可变批次与编码结果；会话头和发送仍分别处理，网络字节数不会因共享编码而消失。
5. 无订阅者时继续准确记账，但不生成 UI 包或保留无限日志。首次订阅从新快照开始；快照传输中的会话也计入订阅者。
6. 设置每批字节/条目上限、每会话积压上限、历史字节与时长上限。慢客户端超过上限则终止旧传输并重取快照，不无限排队；持续失败采用退避，避免快照重试风暴。

关闭界面、离线、距离失效、设备替换、网络实例改变时注销会话；最后一个订阅者离开后回收 UI 历史与发布任务。已有业务订阅者不因 UI 关闭而被注销。

## 6. 步骤五：版本化快照与增量（11-01、11-02）

建议在 `ROOT/common/protocol.py` 定义物品同步协议，由 `ROOT/server/sync/` 管理会话。现有 StorageChanged 只有单项结果版本，不能直接充当完整的批量协议。

区分存储提交版本与物品视图发布版本：前者服务于交易验证；后者在每次非空物品批次发布时推进一次。流体单独变化不推进物品视图版本。若窗口内物品最终抵消，可以发送最终值并推进版本，不强求检测抵消。二者不能互相替代；交易版本过期后的拒绝/重验遵守主控命令契约。

消息至少包含以下信息：

| 消息 | 字段与语义 |
| --- | --- |
| 公共身份 | session_id、网络实例/epoch、view_kind=item；客户端拒绝旧会话或旧 epoch |
| snapshot_begin | snapshot_id、view_version、条目总数与分批信息 |
| snapshot_chunk | snapshot_id、chunk_index、物品描述和整数数量条目 |
| snapshot_end | snapshot_id、view_version；仅完整收到全部批次才可完成 |
| item_delta | base_version、new_version、upserts、removes；upsert 数量为绝对值 |
| resync_required | 原因及新会话/快照恢复指引 |

资源描述应足以显示名称、图标与特殊元数据；只有 canonical 文本指纹不足以直接还原图标。可先发送完整描述，后续数量更新只带稳定键；未来使用短 ID 时必须有 epoch 内描述映射，不能把 Python hash 当协议身份。整数按目标传输环境验证精确范围，必要时采用明确的十进制字符串编码。

首版快照衔接算法：

1. 在同一主线程边界，先发布现有待合并变化，使视图版本 V 与当前索引一致，再固定快照内容并登记从 V 开始的订阅游标。中间不允许插入其他提交。
2. 从网络物品索引复制不可变的键/数量记录，图标描述引用不可变缓存；分批编码、发送此固定快照，禁止分批遍历不断变化的实时字典。
3. 快照生成后继续正常交易并保存后续物品批次。客户端使用临时缓存接收快照，并有界缓存 V 之后的增量。
4. 全部快照批次完整后，客户端按版本依次应用增量，再切换显示缓存；对齐期间不把不完整列表当作完整结果允许交互。
5. `base_version == local_version` 才应用整个增量批次；已应用版本的重包丢弃。缺包/乱序可请求补发或重取；不能跳过缺失版本直接套用后续包。
6. 超大增量需要拆包时，各片携带同一批次 ID 和分片序号，收齐后才推进版本。心跳或确认游标用于发现最后一个更新包丢失，即使之后没有新库存变化也能恢复。

首版固定快照的复制成本为 O(K)，K 为全网物品种类数，随后传输分帧；分批传输并不消除复制时的主线程耗时。记录其耗时和内存；若超过预算，再使用不可变条目与写时复制/版本化快照，不能为了分帧直接读出混合版本。相同版本的固定快照可在有效生命周期内复用，避免同时开多个终端重复复制。

## 7. 步骤六：客户端缓存、搜索与排序（11-03、11-09）

归属 `ROOT/client/network_client.py`、`ROOT/client/ui/item_list_model.py`，按 [设备脚本架构](script_architecture.md) 与当前 `client/ui/` 合并，不另建 view_models。

1. 建立 `entries[key]` 物品摘要表、`ordered_keys` 显示顺序和缓存的名称/搜索文本；数据与 UI 控件独立。
2. upsert 更新数据；remove 删除条目与相关选择状态。纯数量变化只标记对应显示条目，不重建整张列表。
3. 首次快照完成后统一筛选排序。默认名称排序加稳定资源身份作为相同名称的次序依据。
4. 按名称排序时，数量变化不重排；新增/删除合并到本批次再修改顺序。按数量排序时每个同步批次最多统一重排一次，必要时进一步节流并保留滚动锚点。
5. 搜索输入合并处理并维护查询代次；若筛选分帧，旧计算结果不能覆盖新查询。首版搜索在客户端完整摘要上执行，无需服务端逐键请求。
6. 选中项与滚动锚点使用稳定资源键；锚点被删时按固定规则选择邻近条目。点击时捕获键和意图，禁止排队后重新读取控件当前绑定项。

Python 普通列表插入会移动元素；二分查找位置不意味着插入整体是 O(log K)。首版允许按结构变化批次重建/排序，测量后再决定是否引入更复杂的数据结构。不得宣称任何排序模式下单次 UI 更新都为 O(1)。

## 8. 步骤七：虚拟槽位与局部刷新（11-10）

沿用 [custom_slot](./custom_slot.md)，在 `ROOT/client/ui/widgets/` 中实现槽位显示与控件池，列表模型位于 `client/ui/item_list_model.py`：

1. 根据可见行列数建立控件池，加少量上下缓冲行；控件数不随全网 K 增长。
2. 初始化时缓存控件引用。滚动跨行时重绑池中槽位，重置旧图标、标签、耐久、锁定、选中和事件目标。
3. 分离 `bind_item` 与 `update_counts`：资源身份变化才设置图标，纯数量变化只刷新标签/提示；格式化后的标签相同可省去 SetText，但精确提示仍更新。
4. 图标使用合法样本物品，网络数量单独显示，不把汇总量当作真实背包堆叠。交互提交精确整数，不能解析 1.2K 等格式化文本。
5. 离屏更新仅修改数据缓存；槽位再次可见时读取最新值。关闭界面释放控件引用、会话、查询任务和回调。

## 9. 步骤八：验收与测量（11-14、14-07）

所有检查均待实施，不因写入本说明而勾选任务完成。

| 用例 | 必须验证 |
| --- | --- |
| 同种物品跨多介质、不同元数据 | 汇总准确；身份不同不误合并 |
| 模拟/失败/部分提交/重复请求 | 只有实际成功量改变介质和汇总 |
| 全部预留、释放、取空、卸载预留盘 | 条目存续正确，reserved 不超过 stored，订单收到失效通知 |
| 同窗多次修改、归零后重新加入、内部搬运 | 最终状态正确，来源索引正确，无虚假回流 |
| 重复挂卸、跨驱动器移动、拆网/重进 | 不重复计数，无旧代次写入，恢复后独立求和一致 |
| 快照期间新增/删除/改数量、缺片、乱序、重包、末包丢失 | 收敛到服务端当前状态，版本不会误推进 |
| 流体单独变化、混合介质 | 物品列表不出现流体，物品同步流无错误版本断档 |
| 慢客户端、关闭重开、旧 epoch 包 | 内存有界，订阅正确清理，旧数据不能污染新会话 |
| 空列表、快速滚动、搜索、重排后点击 | 控件复用无残留，操作始终指向原资源 |

分别测量静止网络、繁忙单一物品、繁忙多种物品、集中挂卸和多终端同时打开。记录：介质数 M、介质资源条目总数 E、全网不同物品数 K、本批变化键数 D、订阅者数 P、可见槽位数 V。

性能记录至少包括：库存提交与索引耗时、全量介质枚举次数、快照复制/编码耗时与峰值内存、每批同步字节、队列/历史高水位、客户端筛选排序耗时、实际图标/标签更新次数、存取往返延迟。

预期结构特征：正常单键记账不遍历 M/E；单盘挂卸只枚举该盘条目；首次快照 O(K)；增量构造 O(D)，发送量随实际接收者增长；控件数 O(V)。无终端订阅时 UI 包为零，静止已同步视图不反复全量传输。后端选择、键哈希、排序和实际引擎调用另外计量，不将这些结构特征冒充目标设备上的帧率保证。
